# Changelog

## Unreleased

- New app, `apps/viewer`: a static player for runs recorded as `agentrun.recording/1` (its `RECORDING.md`). It draws the process lane from the supervisor's lines with each kill labelled, the calls and model turns, and the counters strip (paid calls made, repeated, asked twice, unknown, judge asks, model turns, re-asked turns as observed or not recorded, processes, kills, cost as unknown when any part is), all folded from durable lines; repeated and asked twice are per call: a workflow effect's outside calls the host reported as applied, folded line by line over its append-only list, in more than one process or twice in one (an effect whose host reports no calls shows repeated as not measured, never 0), and an agent's tool call only when it is paid (the run holds a receipt for its tool and arguments, keyed as the DSL keys it); documents reduce per `(doc, key, conv, task)`, and the validator checks the manifest's cost against the lines' fold; a scrub stops only between commits and equals a fresh reduce to that point. A restore after a box died (the run reopens a checkpoint, and the commits after it become a lost branch) is accepted only with its `transport.moves` restore record, and every move record's `head` is checked: the lost branch's calls count as paid, a redo counts as repeated, and the viewer marks the restore on the timeline. A manifest's `chapters` and `baseline` (another real recording, whose counters show beside this one's) are drawn when present. Panels follow a pure `accepts`, `reduce`, `view` contract (`PANELS.md`); a click on anything with a workflow path focuses that branch in every panel, as a view input: the shell drops no line for it. `?at=` (a commit, or `<gen>:<commit>`), `?cite=` and `?focus=` links, a gallery of recorded runs (none yet), and Cloudflare and Vercel deploy configs. One classic script with no dependency, so it opens from `file://`. `npm run test:viewer` (in `npm run check` and CI) typechecks it, checks a fixture cut from a real killed run against the format and that run's own counts, and opens the build from `file://` in a local Chrome when there is one.
- `@parcha/agentrun-pi/durable` reads and writes tool results the same way on pi-durable 1.0.4 to 1.2.x, in one build; pi-durable 1.2 names a tool result's blocks `output` instead of `content` and reads a result that has only `content` as empty, with no error. The peer ranges do not move yet.
  - Every tool result the package writes carries its blocks under both keys: the record tool's answers and its fatal return, and `reuseReceipts`' refusal and its answer from a receipt. `toolResult(blocks, fields)` builds such a result for a host's own tools.
  - **Behaviour change:** a call through `reuseReceipts(...).wrap` whose result has its blocks only under the key the loaded pi-durable does not read now throws `ToolResultKeyError` (code `TOOL_RESULT_KEY`, with the tool's name), and no receipt is written. Before, on 1.2, the model received an empty result and the receipt stored an empty text. Results are read under the loaded version's key, so a failure envelope in a 1.2 result is no longer recorded as paid.
  - A Session that fails at a storage error (pi-durable 1.2 then rejects later calls with `SessionFailed`) reaches the recovery driver as the storage's own message and code, with the `SessionFailed` as its cause, and a run's `wait()` rejects with the storage's error, as on 1.1.

Under the driver, `runEffect` receives `effect: { id, argsHash }` (typed on `RecoveryEffectParams`, beside `call`): the effect's journal id and the hash of its arguments, as `journal.admit` stored them and the same in every process of the run. A host that keeps what an outside call answered under them settles an effect whose call was cut with `journal.complete`, without recomputing the driver's hash. Additive; the journal's stored format is unchanged.

- `@parcha/agentrun-pi/durable` stores a run's decision rows in pi-durable: the session document `agentrun.decisions` (document version 1, row version 1), `appendDecision`, `readDecisions`, and `createDecisionWriter({ open })`, which commits rows in the order they are recorded, opens the run's Session on the first row, reports the first failed commit from `settled()` and `flush()`, and releases the Session in `flush()` even after a failure. The entry point now imports pi-durable and chord at runtime; both stay optional peers of the package, needed only by a host that imports `./durable`.
- `@parcha/agentrun-pi/durable` runs a workflow's LLM nodes on pi-durable. `nodeRunner(host)` returns one extension to install before the Harness opens, and `on(scope)` gives the `runNode` that `withRecovery(driver, { runNode }, { durableNodes: true })` calls once per attempt and the `closeStepSession` that `openRecovery` takes. A host passes `agent()` and, as it needs them, `stance`, `record`, `verify`, `onNodeOpen`, `init`, `submit`, `digest` and `maxAttempts`. One attempt is one conversation, found again after a crash: an attempt that already delivered makes no request, a turn that committed is never requested again, and nothing of a resumed node reaches a model before the host's `onNodeOpen` ran. `legacy(entry)` gives a conversation an older build opened its extension back under that build's name.
  - The record core the node's `submit` tool is built from is exported with it. `deliver(contract, store, args)` decides one call over a small store interface: transport repair, the file envelope under a host-named key, the delivery attempts, one feedback round of a second reading, and the model-facing texts. `lintRecordSchema` reports what an author should fix in a record schema, for a host or a validator: a root that admits no object, and a schema that declares its fields and requires one outside them. `recordTool`, `recordNudge` and `workspaceRecordFile` put it on a pi-durable conversation, and `runNodeAttempt(scope, attempt)` is the kernel under the runner (`taskScope`, `hostScope`).
  - Four document kinds. `agentrun.record` (`{ record, attempts }`) and `agentrun.gate` (`{ bounced, disagreements }`) are conversation documents, and `agentrun.nodes` is a session document family keyed by the attempt's session id (`conversation`, `digest`, `startedMs`, `closed`). `agentrun.node` is new: a conversation document with the node's system text, label, schema and file key. It is additive, and a conversation an older build opened gets one when the runner first reaches it.
  - A node that delivers no record throws `NodeFailure` (`code: "NODE_NOT_DELIVERED"`). `final: true` says a second attempt would spend the same again: the delivery attempts are spent, the model did not answer past pi's retries (pi's reason and detail are on `unanswered`), or the schema is one no `submit` call can satisfy (`lintRecordRoot`: it is no JSON Schema object, or its root type admits no object), which is refused before any conversation exists. A schema that requires a field outside its `properties` is not refused: the tool's parameters are open and the node's task carries the schema, so a model can deliver on it. `final: false` says the node's run ended with no record and attempts left, so a driver may admit a second attempt, a new conversation. An attempt found under another binding digest is refused with `NodeBindingMismatch` (`code: "NODE_BINDING_MISMATCH"`). A pause rethrows the run's stop and leaves the conversation for the attempt's next entry; any other stop aborts the conversation's work. A host whose `onNodeOpen` throws fails the node's call with that error and releases nothing: what pi resumed of the node waits for the attempt's next entry, or ends with the Harness's close.
  - Two limits of the attempt count, each pinned by a test. The nudge that spends the last attempt still continues the run, so a run can take one request more than its attempts and the stored count can read one past the limit. A rejection cut by a crash after its commit is decided and counted again when the call replays, so a crash there costs the node one attempt.
  - `spec/lean/AgentRunEnvelope/Gate.lean` models the gate's delivery (attempts, the one feedback round, termination), with an audit that fails when its list of theorems changes; `lake build` builds it by default.
- `@parcha/agentrun-pi/durable` runs a workflow as one pi-durable task. `createWorkflowExtension(host)` returns the extension to install before the Harness opens and the host's three operations on a run: `start(harness, { key, workflow, input, bind? }, context)`, `read(harness, key, context)` and `stop(harness, key, "pause" | "cancel", context, source?)`. The task is `agentrun.workflow`, version 1, with one phase: it opens the recovery driver over `documentStore` as the journal's one owner, runs the interpreter to its end inside one invocation and makes one terminal commit. A process that dies leaves the task pending, and the next process's `harness.resume()` runs the phase again over the same journal, which answers what committed and refuses an effect left unknown. The host gives the driver's options (`options`), then either its adapters, which the task wraps with `withRecovery`, or the dependencies it built over the open driver, with its own `interpret` when it runs its documents under its own policy (`run`).
  - A run's key names one task. The session document family `agentrun.task` (version 1, keyed by the run's key, `{ task, stop }`) is new and additive, and the journal's documents are unchanged. The entry and its task are created in one commit, so two starts of one key make one task. `start` reports `created`, `attached` (the task was live) or `settled`: a task that ended complete, escalated or cancelled is returned as it is, and one that ended refused or failed is replaced by a new task over the same journal, which refuses again until the host reconciles it. A journal an older build started, with no entry, gets its task at the next start.
  - A start that reaches a task asks for the run that task holds. Its workflow, what the host binds and its input are compared with the task's stored request by canonical digest, so key order does not matter. A request for another run is refused with the driver's `RUN_STORE_BINDING_MISMATCH`, whose `moved` names the workflow's parts, what the host binds, or the input's fields (`input.<field>`), and the start commits nothing: no task, no stop, no cancel. Before, a changed request reused its key silently: a live task ran its original request, a finished one returned its old outcome, and a replaced one ran the changed input over the earlier run's journal when that run had failed before its first step. The driver's binding is unchanged; it does not cover the input.
  - `wait` gives a `WorkflowOutcome`: `complete`, `escalated`, `refused` or `stopped`. A typed failure is a committed outcome, never a faulted task: `refused` carries its code and message, and `detail` the failure's own plain fields. A run whose terminal commit the Session refuses fails its waiters in that process with the run's own failure instead of leaving them waiting.
  - A pause reaches a run where it is live, in this process. `stop(..., "pause")` resolves `paused` once the run's work has stopped with the pause in its journal (an effect in flight completes and commits first, see the next entry), `ended` when the run ended otherwise, and `not-live` when it is not running here. The task stays pending; the host closes the Harness, and the next open continues the run with no second dispatch. A cancel is pi's `abortTask` and resolves once the task is marked: pi ends the run's invocation and the conversations the task owns, then the task's abort handler commits `cancelled` in the journal and an `aborted` outcome. The effect a cancel cut stays unknown, and a cancelled run never resumes. The first cancel names the run's source, and a later one does not change it. A stop given with the start (`options.stop`) is recorded in the commit that creates or reaches the task and is taken before any step; a cancel that a process recorded and died before pi marked the task is taken by the run's next invocation, before any step and before the host's ladder. A pause given with a start that attaches to a run already running in this process is recorded and taken when the run's next invocation opens; `stop` pauses a run that is running here.
  - A host's ladder runs inside the task. With `escalated(ending, invocation)`, a run that did not complete and was not refused continues there in the same invocation, so the continuation the host opens is owned by the task and a cancel aborts it before the task. The host commits the escalation row through `invocation.driver.escalate` before anything acts on it; a run reopened after that commit goes back to the ladder with the row, and the interpreter does not run again. A refusal, a stop or an abort never ladders.
- `@parcha/agentrun-pi/durable`: three seams for a durable host.
  - Breaking: `readJournal(file, key)` and `durableDoc(file, kind, key?)` take the run's store file instead of a directory. They no longer look for `<directory>/durable/run.sqlite`, so a store is read where its host keeps it (pi-durable-disk keeps it at `store/run.sqlite` under the claim); a directory passed as the file throws. `committedRoutes(state)` is unchanged.
  - `decisionRecovery(invocation)` returns `{ recordDecision, decision }` for a workflow task, from the invocation the host's `run` is handed: `recordDecision` commits each decision receipt as a row through the task's own commit, in the order receipts are recorded, and `decision(id)` answers `recovery.decision` from the last answered row that run recorded under that id, so a resumed run does not ask the judge again. `DecisionRow` gains four optional fields, `decision_id`, `request`, `state_sha256` and `run_key`, which make the row the whole receipt again for the run that asked it; another run in the same Session is never answered from it. The row version stays 1; a row without them is read as before and never answers.

- `@parcha/agentrun-dsl/recovery`: a pause lets an effect in flight complete. Breaking for a host that relied on a pause cutting an effect. `driver.stop({ action: "pause" })` refuses new work at once and is taken when no effect is in flight: an effect already admitted dispatches, completes and commits its receipt first, so a paused run resumes without a reconciliation. Before, a pause aborted the effect through the driver's signal and left it unknown. New work (a node's resume, an effect, a wait, a step's attempt) waits at the new `driver.seam()` until the pause is taken and is then refused with `FROZEN_PAUSED`; finished work still commits. A cancel is unchanged: it is immediate, and the effect it cuts stays unknown. The recovery models do not move: neither has a stop, a pause adds no state between an admission and its completion, and the state a cancel leaves is the one a crash leaves.

- `@parcha/agentrun-dsl` records typed-question decisions. A host that supplies `recordDecision(receipt, exchange)` gets one `DecisionReceipt` per request (`judge`, `pick`, `sift`, `route`, an `ask` predicate, a `verify` review), awaited before the answers reach state, an event or a branch; a rejection fails the node with `WorkflowDecisionRecordError`. A receipt holds the questions, the answers, the rule with its thresholds and the action, and `rederiveDecision(receipt)` recomputes the action without a model call. See "Decision receipts" in `docs/host-integration.md`.
  - The decision events carry the receipt's id: `decision_id` on `judge.answered`, `route.chosen`, `ask.evaluated` and `verify.answered`, and `decision_ids` (one per request) on a sift's `judge.answered`. `runJudge` receives it as `decisionId`. The id is the request's identity, so the same request asked again has the same id.
  - A sift split over the host's limits records one receipt per request. When one request fails, the requests in flight are recorded as `cancelled`, and a split sift now refuses a request's answers as soon as they arrive instead of after every request has returned.
  - `recovery.decision(id)` answers a request from the receipt an earlier run recorded. Before, a resumed run asked again: a loop's `until: ask` could end the loop on an earlier pass's state after later passes had run, and a route could take another branch than the one already started. With the hook, both follow the recorded decision.
  - No change for a host that supplies neither hook, except the new event fields.
- The Lean model's `sift` no longer fails when its items exceed the question limit: like the interpreter, it refuses only a question set that cannot fit one request. The conformance corpus gains its first sift cases, a sift is scripted per item, and a case may set `limits.maxQuestionsPerRequest`.
- Formal models of recovery. `spec/receipts/Receipts.tla` (TLA+) and `spec/lean/AgentRunRecovery/Frozen.lean` (Lean) state what a recovery driver does with effects over a `RecoveryJournal` across crashes and failed commits: admitted before dispatch, one dispatch per effect, a completed effect answered and an unknown one refused on resume, nothing admitted after a failed commit. TLC checks seven properties on two configs, nine guard mutants must each be caught by its named property, and Lean proves the driver's properties for every number of steps and crashes. A new `receipts-spec` CI job runs the TLA+ checks when a change touches the spec, and a nightly workflow runs them on `main`. AGENTS.md and CONTRIBUTING.md add the rule: a change to modeled behavior changes the model in the same pull request.

- `@parcha/agentrun-dsl` admits a tool effect with the external call it makes. `RecoveryEffect` gains an optional `intent: { tool, argsHash }` and `RecoveryJournal.admit` an optional last `intent` argument; the driver admits a `via: "tool"` node with `gatewayIntentOf(node.tool, input)` (for a node that calls the gateway through the `fetch` wrapper, the tool the wrapper names and the hash of its inner arguments), and the intent is kept from admission, through completion, at every later open. Shell and executor effects get none, and an effect admitted without one has no `intent` key. Additive: a journal written before this change reads as before, and its unknown effects stay matched by name and hash alone. Before, a continuation could match a completed effect by its receipt but never an unknown one, so a tail dispatched an identical paid call again; `inheritableUnknowns` now carries the intent and `reuseReceipts` refuses a call whose key matches it. A store built for the store contract must keep the intent: the conformance suite gains a case for it, and a mutant store that drops it.
- `@parcha/agentrun-dsl/recovery` builds a handoff from an escalation the driver committed: `buildHandoff(journal, options)` returns the bounded, redacted block and digest a continuation reads first, the attempt written as files under `evidence/frozen/`, and the receipts and unknown effects the journal hands over (`inheritableReceipts`, `inheritableUnknowns`, `gatewayIntentOf`). An input field named like a credential is never copied, and a failed file write is reported on the handoff, not hidden.
- `@parcha/agentrun-pi/durable` keeps a run's paid receipts as a document: `ReceiptIndex` (the session document `agentrun.receipts`, document version 1, one entry per paid call keyed by tool and argument hash, with the paid result and the session that paid), `reuseReceipts({ tools, sessionId, answer, unknown })` and `seedReceipts(host, receipts, from)`. `reuseReceipts(...).wrap(tool)` records a paid call's result, answers a repeat of another session's call from the receipt and says so (when `answer` is set), and refuses a call equal to an effect whose outcome is unknown; a tool result that is an error, or whose text is a failure envelope, is not a paid result and is not recorded. `seedReceipts` puts a handoff's receipts in the document before a continuation's first request and keeps a receipt already held. A receipt holds the result's text (the text blocks, joined by a newline): another kind of block, an image for one, is not kept, and a repeat is answered with the text alone; a call that returned nothing is a receipt whose result reads `null`, and its repeat is answered, not dispatched. The document's kind, version and key are a stored format.

## 0.1.0-beta.9, 2026-10-04

- `runEffect` receives `deadlineAt`: the attempt's deadline instant on this process's `performance.now()` clock, exactly as the interpreter armed its deadline timer, so a host can measure its own kill and an effect's duration against the instant the timer fires instead of a start time it stamps a moment later. Each attempt carries its own instant, and a host's composed and mapped calls receive it unchanged. It is absent only for a call with no deadline. Nothing else changes.
- `validateAnswers` accepts a Score whose `score` could be the two-place rounding of its distribution's weighted level, by the same rule as the probability mass: a value on the two-place grid may be off by up to 0.005, and any other value is taken as exact. The unrounded probabilities lie within their rounding intervals and still sum to 1, which bounds the weighted level, and the score must meet those bounds. jev-1.13 rounds both the probabilities and the score, so valid Score answers were refused as `score_consistency`. A full-precision score with full-precision probabilities is still held to 1e-5, and a score no rounding explains is still refused. A score that isn't a number still fails as `score_range`. Answers are accepted as reported, never recomputed. (GRE-3057)
- A Jev HTTP failure that Jev classifies as `max_tokens_exceeded` now says so in the error message: `Jev returned HTTP 400: the request exceeds the model's token budget (max_tokens_exceeded). Send fewer or shorter items per request.` Before, the message was only `Jev returned HTTP 400.` and the reason sat in `responseDiagnostic`, which a host that logs only the message never showed. The Pi extension's run report says the same in its message. Only the structured reason is named. The provider's response body still never reaches the message, the report or the trace, because it can echo the request's input. An unclassified failure keeps its plain message. (GRE-3058)
- A `sift` whose items × questions exceed `maxQuestionsPerRequest`, or whose judge state would exceed the new host-owned `WorkflowDeps.maxStateBytesPerRequest`, is split in item order into requests that each fit. Up to four requests run at a time, the same default as `map.maxConcurrency`, and their answers join back onto the original items. The first failed request stops dispatch, cancels the requests in flight, and fails the sift once they settle. Before, the interpreter refused the sift over the question limit, and an oversized state surfaced only as the provider's refusal. `maxStateBytesPerRequest` counts UTF-8 bytes of the JSON state, the measure the Jev adapter uses for `maxStateBytes`. It has no default, so without it only the question limit splits.
  - Each request carries the sift's `state` and only its own items, as `items[j]` with the original `item_<i>` id.
  - A sift that fits one request sends exactly the request it did before.
  - An item that cannot fit a request on its own is refused before any request. So is a sift `state` too large before any item, and that error names the state.
  - `judge.answered` sums `cost_usd` across the requests and reports `requests` when there was more than one.
  - The Pi extension passes `maxStateBytesPerRequest` through, and its `jev_state_too_large` hint names it. It now forwards any set `maxQuestionsPerRequest` or `maxStateBytesPerRequest`, including an invalid `0` or `NaN`, so the interpreter refuses an invalid setting instead of silently running without it. (GRE-3059)
- `onEvent` observers receive a detached snapshot of each event, not the objects the interpreter goes on to use. Before, a callback that modified an event could change a code step's patch, a judge's answers, a route's branch, or the source records a `pick` or `sift` selected, just by observing them. The snapshot never calls getters or proxy traps. Functions, proxies and non-plain objects arrive as inert markers, so a host that validates its trace as JSON still rejects them. Observer errors are still ignored. This is a visible change for a host that changed execution by modifying an event, compared event objects by identity, or expected a `Date`, `Map` or class instance in an event: it now gets a copy, and those values arrive as markers. A host with required trace validation can pass a synchronous `prepareEvent(event)` to bound or reject an event before it is copied, and the Pi extension uses it for its existing trace limits.
- New example, `examples/rank-candidates.mjs` (`npm run demo:rank`): a reusable workflow that ranks a list with Jev. A `sift` scores each candidate against a brief, a `code` step sorts and applies a minimum score, a second `sift` over pairs finds near-duplicates, and a last `code` step applies per-bucket quotas and the top k, with a reason for every candidate cut. It runs offline with a scripted judge, on your own list with `--live`, and from another workflow through a `workflow` node.
