kind: breaking

The container image's default command now starts the server and its runner as two processes, so a busy runner's journal writes no longer hold up the API's reads. The command is `server-and-runner --data /data --listen 0.0.0.0 --port 7340 --drain-timeout 6s`: the server with `--no-runner`, and one runner on the same data once the server answers `GET /v2/health`. A `docker stop` reaches both, and if either exits, the other stops and the container exits non-zero.
Who breaks: an operator who gives the image server options of their own (`docker run IMAGE --data /data --port 7340`) still gets one process with the runner inside it. Put `server-and-runner` before those options to get the two processes. `runner ...` and the other commands run as before.
A paired computer needs the runner in the server's process: an operator who uses one gives the image the server's options alone, without `server-and-runner`. On a server started with `--no-runner` (the image's default included), the pairing code, the pair answer and each paired computer in `GET /v2/computers` carry `runs_refused`, which says no run there can use it and gives that fix; the console shows it with the code and on the computer's row. A run that names such a computer is refused in the same words.

- `GET /v2/runs` (and an agent's runs) reads each run's listing from its row: the status filter, the order, the limit and the cursor are one query, so a list costs the same at 10 runs and at thousands, however long their journals. Each item is what `GET /v2/runs/{id}` gives for the run, as before. The SQLite store goes from version 11 to 12 and Postgres takes migration 0017. The server brings the store up at its first start; a runner refuses a version 11 store until the server has. After the upgrade the server builds each run's listing in the background, runs no runner holds first; a list that reaches a run not built yet builds it then.
