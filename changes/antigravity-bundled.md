Google Antigravity's recipe ships with the ACP adapter, and every command takes its name where it takes a recipe file: `agentrun harness install antigravity`, `agentrun harness-check --recipe antigravity`, `agentrun harness sign-in --recipe antigravity` and `agentrun-serve --harness-recipe antigravity` (or `AGENTRUN_SERVE_HARNESS_RECIPES=antigravity`). It is still a recipe, with the same pins, check, keys page and sign-in. Each command says which recipe it resolved. A file of that name in the directory is never passed over: the command is refused, saying both, and `./antigravity` names the file. The hints a recipe prints (install, check, sign-in) name a shipped recipe by its name, not by where the package is installed. The recipe file moved from `examples/harness-recipe/antigravity.json` to the package's `recipes/bundled/antigravity.json`. An AgentRun release that changes it asks for a new check and the keys to be saved again, as an edit of your own recipe file would.

agy joins server and tool with a single `_`, so another MCP server's tool could spell one of AgentRun's (a server `agentrun_look` with a tool `up` reads as `mcp_agentrun_look_up`), be taken as AgentRun's by the recipe's `announces.prefix`, and have its permission request allowed once on the title tie without the host's gate. Under a recipe whose `announces.prefix` joins `agentrun` to the tool's name with one `_` or `-`, as the Antigravity recipe's `mcp_agentrun_` does, the agent is now given AgentRun's MCP server under a name of each start's own, `ar` and 6 random hex digits (as long as `agentrun`), and the prefix and the title tie read that name alone: any other server's call goes to the host's gate. Goose's and Cursor's recipes keep `agentrun`. agy caps a tool's name at 64 characters, so under that name a tool of AgentRun's may be named at most 51, as under `agentrun`: a longer one is left out of the tools agy is given at that start, and the run gets a notice naming it while the run goes on with the rest. An agent that announces a call with a field the tool's schema declares but the model left out has that announcement matched to its MCP call with the field or without it, so two such calls in flight keep their own ids. An `announces.extras` field that a tool's own input schema declares (a `toolSummary` argument of the tool's, at its top, in `allOf`, `anyOf` or `oneOf`, or behind a local `$ref`) is kept as that call's argument, never left out as agy's. Two calls in flight whose arguments differ only in that field, one sending it and one leaving it out, keep their own ids whichever reaches MCP first: a call matching more than one announcement only without the field waits while another call may still need one of them. The fake ACP agent (`./testing`) gains a `{ sayTools }` step that answers with the names its MCP server lists.
