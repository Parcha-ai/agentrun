Render: a sandbox's labels file is read only where it agrees with the sandbox's name, and a create's wait for its new sandbox to be listed asks Render for that sandbox's whole name. The name carries the run's hash and the epoch, set at create; the file is the guest's root's to rewrite. A file that says another run or epoch than the name is treated as unread: a listing that must read it fails closed, naming the sandbox and what differs, and `get` answers the two labels the name carries, so release still terminates it. A create whose labels have both a run and an epoch looks for the sandbox it made by that whole name (`computer-<12 hex>-r<run hash>-e<epoch>`) with Render's exact name filter, while it waits for the sandbox to be listed and in its sweep after a failed create: one page each poll, no labels file read. Its first check and its convergence still read every page by the request's name, so a request asked again with another run or epoch finds its sandbox and is refused as `exists`. In a workspace of more than 10,000 live sandboxes (100 pages), those reads fail, and the create is refused before any sandbox is made. Rolling back to beta.62, or a beta.62 replica still serving during a rolling deploy, treats the suffixed names as not computers: those sandboxes keep billing until Render ends them at their timeout, at most a day after their create.
