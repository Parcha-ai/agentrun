A self-hosted Daytona target with an Archil egress relay takes Archil mounts again; Daytona's hosted cloud still refuses them. `DAYTONA_ARCHIL_EGRESS` is a Daytona key again (optional), filling `DaytonaProvider`'s `archilEgress` option, `<IPv4 gateway>:<mount lane>:<data lane>`, checked at construction as the shared adapter checks it. A provider made with it declares `capabilities().mount` `["archil"]`, `check()` and `create()` take an Archil mount, and the helper's mount and revoke go through the relay. A provider made without it is unchanged: `check()` and `create()` refuse an Archil mount up front, before any request, in the descriptor's `unmounted.archil` words, now "Archil mounts don't work on Daytona's hosted cloud, where Archil's client hangs on its sandboxes; a self-hosted Daytona target takes one once its operator sets DAYTONA_ARCHIL_EGRESS". Set the key only for a self-hosted target: on the hosted cloud the mount waits out its bound. A Daytona GPU computer still takes no mount.
A descriptor may declare `mountsWith: { <kind>: "<KEY>" }`, a mount kind its computers take only where the operator sets that optional key (the kind is in `unmounted` too), and `mountsOf(descriptor, set)` gives the mounts for the keys set; `defineProvider` refuses a `mountsWith` that names no optional key or a kind `unmounted` lacks. The conformance module reads `COMPUTER_DAYTONA_ARCHIL_EGRESS`, and its `mountFor("archil")` makes a run folder only with it set.
In serve, a Mode 2 Daytona sandbox is ready, at its save and its run's start, where `DAYTONA_ARCHIL_EGRESS` is saved or set and `AGENTRUN_DAYTONA_SNAPSHOT` names a snapshot of `box/Dockerfile`. With the relay but no snapshot named, it is refused, saying to name one there; without the relay, it is refused as before. Settings → Computers now refuses a key saved as whitespace alone (422, `wrong_type`), as the Archil routes already do and as the environment reads one as unset: such a relay would have shown a Daytona sandbox ready that its run's start refused.
