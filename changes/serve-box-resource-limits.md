A run's Docker box has CPU, memory and process limits by default: 2 CPUs' time, 4 GiB of memory with swap included, and 1,024 processes and threads (`--cpu-period 100000 --cpu-quota 200000 --memory 4g --memory-swap 4g --pids-limit 1024`). Before, `docker run` set none, so one run's fork bomb or runaway build could starve the host. `AGENTRUN_BOX_CPUS` (at least `0.01`), `AGENTRUN_BOX_MEMORY` (a size with its unit, such as `8g`, at least `6m`) and `AGENTRUN_BOX_PIDS` (at most 4,194,304) change them. Any other value refuses the start and names the setting. The CPU limit is a CFS quota, the cap `--cpus` sets, so it holds whatever CPU count Docker's VM has, and Docker ignores it with a warning where the kernel gives it no CPU controller. `--cpus` fails in both cases.
- `dockerBoxes` takes `cpus`, `memory` (bytes, or Docker's size such as `4g`) and `pidsLimit`. They become `--cpu-period 100000 --cpu-quota <cpus × 100000>`, `--memory` with `--memory-swap` the same, and `--pids-limit`. A spec's own `cpus` or `memoryMb` takes the place of the option's, and a spec's `cpus` is now a quota too, where it was `--cpus`. A spec's `memoryMb` now bounds swap too, and `facts()` reports the limits a box got. A value under 0.01 CPUs, a memory that is not positive or not a size, or a `pidsLimit` outside 1 to 4194304 throws when the provider is made.
