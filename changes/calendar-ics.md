A calendar for agents: an owner saves the server's one calendar by its secret iCal address (Google Calendar's "Secret address in iCal format", Outlook's ICS link, iCloud's public link), and the new host tool `calendar_events {from?, to?}` reads its events.
- The calendar's routes (the console's page for it comes next): `GET`, `PUT` and `DELETE /v2/settings/calendar` and `POST /v2/settings/calendar/test`, the owner's signed-in session alone (a secret write; the token is 403). `PUT {url}` takes https, and reads `webcal://` as https. The address is sealed in the store's sealed keys. It is in no answer, event, log line, error or run input, a failed fetch's words and the calendar's own name included. Each text is scrubbed before it is cut short, and the address's secret token (a path segment or query value that reads as one) is scrubbed on its own too, so no part of it gets through. `GET` answers `{configured, host, name, time_zone}`. The test answers in words, "Work: 214 events, time zone America/New_York, next: Standup, Mon Nov 17 09:30", for the saved address or the body's, saving nothing.
- `calendar_events`: the window defaults to now through 7 days on, and is at most 62 days (a longer one is refused in words). It answers `{calendar, time_zone, from, to, count, truncated, events}` sorted by start, at most 200 events. Each event: `{title, start, end, all_day, location, description (cut at 500), status, recurring, organizer, attendees: [{name, email}]}`. Repeating events are expanded in the window (RRULE, RDATE, EXDATE). An RDATE period keeps its own end or duration. A moved instance (RECURRENCE-ID) is in its new place, and a cancelled one is left out; with RANGE=THISANDFUTURE, the move or cancellation applies to every later instance too. One read has a work budget across all its series: 15,000 rule steps, and at most 0.5 s. A calendar that needs more, such as hundreds of old every-minute series, is answered in words (it has too many repeating events to read), never as a partial list. A rule that ended before the window is not walked, and a plain rule starts just before the window instead of at its first instance years back. Each event keeps its own time zone, so a 09:30 meeting stays at 09:30 across a DST change, and floating times read in the calendar's X-WR-TIMEZONE, else the server's. An all-day event's start and end are dates. It runs on every harness, beside `web_fetch` and the email tools. An event's words are untrusted, as a page's are. It is allowed by default and not metered. The timeline reads "Calendar: 8 events, Nov 17-23", or "Calendar: couldn't read the calendar".
- The fetch is held to the server's one address rule, the one an MCP server's is: https only, a private address refused unless its host is allowed in Settings → MCP servers (private hosts), link-local and this machine never, loopback only on a local install, each redirect checked again and every hop dialled at the address checked. 10 MB, 20 s, 5 redirects. A read is reused for 5 minutes, then revalidated with its ETag and Last-Modified (a 304 keeps the parsed copy).
- Templates: a package's `tools` may name `calendar_events`. With no calendar saved, it applies as the email tools do, and the tool answers that no calendar is saved. A template eval case may say `calendar: <file>.ics`: a fake calendar server on loopback serves it as the eval server's calendar, and the case's `now` is the window's clock.
- New dependency: `ical.js` 2.2.1, pinned exact (MPL-2.0, no dependencies of its own; 268 KB `dist/ical.js`, 1.2 MB unpacked). It loads at a calendar read only, never with the server.
