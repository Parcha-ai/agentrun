Slack triggers: mention the server's Slack app in a channel to start a run, and reply in the thread to steer it. `PUT /v2/settings/sources/slack`, from the owner's session, sets the app (its signing secret and bot token, checked with Slack's `auth.test` and kept sealed in the store's trigger settings; each shown as a secret's set-or-not, never its value), the one route for every source whose settings are the server's (GitHub's is shown there, and written only by Connect GitHub: `409 settings_managed`), and a trigger with `source: {kind: "slack", channels, post_answer?}` owns its channels (`409 scope_taken` for one another trigger lists). Slack is a source in the trigger registry, served by the one push handler at `/v2/hooks/slack`: each request is checked by Slack's v0 signature before anything else, and `url_verification` is answered only after that check. One line is posted in the thread when the run needs its person and when it ends, tried again until Slack takes it.

A pushed source now declares who may start a run and who may steer one (`trust`), and the trigger kernel holds every event to it: a Slack thread opens only by a workspace member's mention, and a reply steers its run only from a member; it answers nothing the run waits on yet (a question, a stop, an approval, a pause at the cap: skipped, for the console). A bot's message starts and steers nothing. A thread and its run are kept in the store (trigger_conversations), so a reply after a restart reaches the same run. GitHub declares that whoever its signed delivery is from may start a run, and nothing steers one.

A `start_run` target may set `include_last_answer: true`: each run's input then carries the trigger's last run's final answer, untrusted, in `<last-run-answer>`, cut at 16 KiB, or one line saying that run did not complete.

A trigger's Timeline row names its source and its trigger as it is now: "Schedule utc-check: Tell me the time in UTC." where it read "Trigger trg_…: …", and the trigger's id once it is deleted. The name a trigger had when it fired is not kept yet: it comes when the message that fires a run carries it. The sources a trigger origin may name, and the word a row begins with, are a registry (pi-durable-agent `registerTriggerSource`, `triggerSources`, `triggerLabel`), which serve fills from its trigger registry; `TriggerSource` is a registered source's id, a string.

Schema change: a trigger's conversations are indexed by their last write (`trigger_conversations_by_last_at` on `trigger_id, last_at`), read by the trigger's one-statement prune. SQLite's store schema is version 7 (a version-6 store is refused, as every earlier version is); Postgres gets it in migration `0004_trigger_conversations_by_last_at.sql`.
