A Composio trigger's config field named like a credential is now sealed when the trigger is saved. This covers names like `developer_api_key`, `api_key`, `client_secret`, `access_token` and `password`: any field where a word of the name is secret, password, passwd, passphrase, token, credential, apikey, authorization, bearer or cookie, or where the last word is key, and the value is a string. The value is kept in the composio source's sealed settings, next to the subscription's secret. Composio still receives it when the server creates the trigger instance. Every trigger answer (create, GET, list, PATCH, template apply) shows `"[sealed]"` in place of the value and names the field in the source's new read-only `sealed_config`.
- A create whose config holds such a value below its top level (inside an object or a list) is refused with a 422 that names the field. Composio's trigger configs are flat.
- A PATCH that leaves a sealed field out, or sends `"[sealed]"`, keeps the value. Sending a different value is a config change and is refused, as any config change to a composio trigger already is. To change a key, delete the trigger and make a new one; the refusal says so.
- Deleting the trigger removes its sealed values. A trigger saved before this release with such a value in plain text is answered masked at once, at any depth, and sealed at the next start; its Composio instance is not changed. On SQLite the old row's bytes are cleared from the store's files at that rewrite. The log names the trigger and the field, never the value.
- The events list (`GET /v2/settings/mcp-servers/{name}/composio/events`) names each event's sealed fields under `sealed`, and the console's form takes those as password inputs. A trigger's page shows them as sealed.
- Composio's error text for a failed create no longer repeats a sealed value.
- An Idempotency-Key's record in the data directory now keeps an HMAC of the request body under a key derived from the server's seal key, not the body itself, and keeps its answer masked. Records an older server wrote (kept for up to a day) are rewritten at start, and the log says how many.
