`PATCH /runs/{run_id}` with `{max_cost_usd}` raises a run's spend cap, and only raises it. The new cap must be above the run's current cap, its last raise included, by more than 1e-9, and the same raise sent again (a retry, within 1e-9) changes nothing. A raise serve.json could not keep is not taken. It is `422` otherwise, and for a run with no cap or a workflow run; an ended run is `409 not_continuable`.
- **Where the cap is kept:** the run's serve.json keeps the new cap, with each raise in `cap_raised`. The run's next process opens under it, and so does a server started again.
- **A run paused at its cap goes on.** The answer is `{resumed: true, message_id}` at once. The pause gets one follow-up turn, "The cap was raised to $X; continue the task.", under that `message_id`, sent once the process being let go is gone; the turn runs under the new cap. A second raise before it goes answers the same id and raises what it says.
- **Sent once, or the run fails saying why:** a server started again sends a follow-up that had not gone, to the process a launch started too. One that cannot be sent is tried again twice, then the run ends `failed` in plain words. A raised run's paused process that exits without releasing the run does not fail it. The follow-up shows in the timeline as the server's, "AgentRun: The cap was raised…", never as the person's.
- **What a paused run has spent:** its figures are shown to a millionth of a dollar, as `cost.usd` is. Once its process is gone, `pending.spent_usd` is the store's spend when that is lower than the refusal's figure, which counted requests still answering at what it held for them. `suggested_cap_usd` follows it.
- **The raise to offer:** a paused run's `pending` (`kind: "budget"`) adds `suggested_cap_usd`. It is `spent_usd` + 10 × `needs_usd`, rounded up to a whole dollar, and always above the run's cap, so a `PATCH` with it resumes the run. This is part of the `cappause/1` widening.
- **Within a float's tail:** a request whose least, with what the run has spent, makes its cap to within a float's own tail (1e-12) fits it, but a spend past the cap by any more, however little, does not. The same holds for a paid call's check and for a cost read after a response. A request past the cap names a raise a cent above it, never the cap itself. Two caps within 1e-9 are the same cap.
- **A working run's live process** keeps the cap it was opened with until its next process, and the answer's `note` says so.
