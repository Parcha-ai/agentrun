A Composio trigger's config seals addresses that carry a credential, and stops sealing counts.
- A credential word right next to a count word names a count, so `max_tokens`, `token_count`, `token_limit`, `tokens_used` and `maxTokens` stay as they are, a number in one too. `access_token`, `token`, `api_tokens`, `refresh_token`, `token_secret` and `bot_token` are still sealed. A field the event's schema marks as a password is sealed whatever its name.
- An address in any scheme (`https`, `postgres`, `redis`, `amqp`, `mongodb+srv`...) with a user part (`user:pass@`, `:pass@`, or a token alone as in `https://TOKEN@host`), or with a query or fragment parameter named like a credential (`token`, `api_key`, `access_token`, `sig`), is sealed whole, whatever its field's name. A create with one below the config's top level is refused `422`; one an earlier server kept is masked on reads and sealed at the next start. An address with none stays as it is.
- After a start, the server reads the schema of each event an older trigger uses, once, and seals the fields it marks, logging `composio_config_sealed`. A create answer kept under an Idempotency-Key for that trigger is masked too. If that file can't be written, the log says `idempotency_not_saved` with a code and the trigger stays sealed; the next save writes the record masked. It writes a trigger only while it is as it read it; one changed or deleted meanwhile is left for the next start, with nothing sealed left behind for it. It runs no `VACUUM` while serving: the log says `store_scrub_not_done` with `reason=deferred`, and the next start's scrub finishes before it serves. When Composio can't be reached, it logs `composio_config_schemas_unread` once with a code and tries again at the next start. The start doesn't wait for this.
- A field named `sig` is now sealed.
