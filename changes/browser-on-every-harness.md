An agent on any CLI harness (claude-agent, codex, opencode, and Goose or Cursor where their owner installed them) now gets the browser, the same way it gets web_fetch. Before, granting `browser` to such an agent came back with "browser runs on pi here; on <harness> it is not bound yet", and a run of an agent whose computer is a browser was refused at its claim with "This agent's computer is a browser, which only the pi harness drives here". Now neither is refused on any of them. The harness is handed the browser's tools (`snapshot`, `run`, `screenshot` and the rest) as host tools. They drive the same session pi's would: the agent's browser computer, or else the vendor its tool plane picks. They use the same live view, the same spend held under the run's cap, and the same release when the run is let go.
- The person can take part as on pi: the agent's `browser_request_handoff` asks them and its call waits, with the run working, its row saying it waits for them in the browser, and its session held, until they hand the browser back; and the person can take the browser over in its live view unasked, while the agent's next browser call waits for them and is then told they had it. Either way the agent's later browser calls drive the same session, and none is made again.
- A browser call in flight when its runner dies is answered as interrupted ("may or may not have taken effect") when the run resumes on another runner, and is never sent to the browser again; the model goes on from that answer. The next claim takes back the session the run opened, and it is released once when the run ends. Each browser call's memo is its own, so nothing it kept carries into another call.
- Every browser answer the harness is handed (a page's snapshot text, the hand-over and take-over words) passes through the run's redactor first, as every other host tool's answer does: a secret the run holds that a page shows back reaches the CLI only as `[redacted]`.
- `subagent` still runs on pi only, and is refused in words on every other harness; `pdf_pages` and `llm` stay a workflow's node tools.
- `capabilities.tools` lists every harness under the browser's `harnesses`, not `pi` alone.
