Everything the agents make is now on the disk, apart from the data directory's own files. Each agent has one folder, `<data>/disk/agents/<agent>/` (its id in lower case, a dash, and 16 hex digits of its SHA-256). That folder holds the agent's learning folder (`learning/`) and its runs (`runs/<run>/`, each with `store/run.sqlite` and `work/`). store.sqlite and the server's files stay at the top of the data directory, as the control plane, and only the server opens them. A run's row in store.sqlite now holds its claim: `claim_epoch` and `claim_holder`. Each launch of the run's process bumps the epoch, with that process as the holder, and hands the process its epoch. Once the process is gone, the server takes the run back: it bumps the epoch, names itself the holder, and checkpoints the run's database. A run's database (pi-durable-disk's exclusive profile) is WAL, under an exclusive lock, with `wal_autocheckpoint = 0` and synchronous FULL. The run's process ends with its WAL in place: its store's close keeps the connection open (`keepWal`), and the process ends by process.exit, which never checkpoints. A test pins this node:sqlite behaviour, and its inverse: a close does checkpoint. The server reads a run's database with a fresh read-only, lock-free open (`vfs=unix-none`, EXCLUSIVE) per read. It opens the WAL only once the WAL holds a commit that SQLite's recovery would take: a frame with the header's salts, a valid chained checksum and a nonzero commit size. Until then it reads the database file alone, as an immutable file. A lock-free reader of a WAL whose first transaction is still being written recovers no frame, and its close removes that WAL, which loses the writer's rows. agentrun-pi exports that check as `walHasCommit`, and both readers use it. It never shows a read whose last entry is behind one it read before. It never opens the database for writing while a process holds the run. A data directory an earlier version wrote (runs under `<data>/runs/`, or a store of store version 1) is refused at start, in words, and nothing is migrated. pi-durable-agent's store is now store version 2. It names a run's folder by its row's agent (`runDir`, `runStorePath`), and adds `claimRun` and `runClaim`. A store of version 1 is refused. serve gains the local disk adapter: `mount`, `sync`, `unmount` and `revoke` for one machine, where a runner works in the folder itself and a revoke is the server's take-back of the claim. agentrun-pi's durable readers take `unlocked` (a fresh `vfs=unix-none` read, as the server's), which serve's reads of a run's decisions use. A run's folder is never made through a symbolic link: a link on the way to it refuses the run's start, and refuses an import that finishes a run its last import left without a transcript (pi-durable-agent `runFolders`).
