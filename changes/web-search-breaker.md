web_search stops asking a provider that has said no, for as long as the provider asked. If a run's search provider says the run is out of quota (Parallel's or a model provider's 402, Anthropic's billing_error, OpenAI's insufficient_quota), every later web_search call in that run answers "search is unavailable for the rest of this run; answer from what you have", and the provider isn't called again. If it says the run is rate-limited (keyless Exa's free limit, a 429, rate_limit_error, rate_limit_exceeded, or the hosted search's own too_many_requests, even after another search in the same request found results), each call answers "search is busy; try again in N s, or answer from what you have" without calling the provider, until the wait the provider named has passed. That wait comes from Retry-After, in seconds or as a date, is 60 s when the provider names none, and is capped at 15 minutes. When two calls in flight are both rate-limited, the longer wait holds: a shorter one never shrinks it. After it, the next call goes to the provider again. A quota answer holds even after a wait passes. The timeline shows each held call as a failed search in those words. One run had kept searching 520 times against Exa's limit. The breaker belongs to the run, so another run on the same server searches as before. Other failures leave it closed: a 5xx, a timeout, or Exa refusing the connection.
