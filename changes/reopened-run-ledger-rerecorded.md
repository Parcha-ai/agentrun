A learning run that a follow-up opened again and that ended before this release has its ledger row recorded again under the new split at the server's first start on this release. Its `cost.usd`, `learning_usd` and `followup_usd`, the agent's cost page and its bill read the follow-up as the job's, as `tools_usd` and the usage lines do. Before, such a run kept its job at its first round's figure, so its read could show `tools_usd` above `usd` and count the follow-up both in `learning_usd` and in its usage lines. The pass reads only the runs whose learning kept a second round, a page of 64 a transaction. A stop partway keeps the pages it committed, and the next start walks every such run again from the first: recording one again writes the same row. Those runs' earlier figures change once, as intended: `cost.usd` moves up by the follow-up's spend and `learning_usd` down by the same amount. A backend that reconciles `cost.usd` against what it billed before sees each such run move.
`GET /v2/runs/{run_id}` of a run a learned workflow served reads the agent's ledger, for its share of its revision's compile and check, outside the store snapshot that reads its `usd` and `tools_usd`. Before, that read held the snapshot over every run of the agent: on SQLite every runner's journal commit waited behind it, and on a large agent the read failed past the store's 10 s deadline.

`GET /v2/runs/{run_id}/usage`'s `reason` no longer has `reopened` (`runusage/6`): since the last release a learning run a follow-up opened again has lines, so no read answered it.

Upgrading: the store moves to Postgres migration `0034` and SQLite version 18, and both break runners of earlier builds, whose end still writes such a row the old way: the runner floor rises to 34. The server marks that pass done only after one that started with no runner of an earlier build there and no run held by a claim taken before the server's open and 30 s, which covers an earlier runner whose name a rolling restart's runner took; until then it records those runs again every 30 s, so a reopened run such a runner ends meanwhile is recorded under the new split too. `reason`'s `reopened` goes from the TypeScript client (`RunUsage["reason"]`) and the Python client `parcha-agentrun` alike: a TypeScript program keyed on the whole enum (a `Record` of every reason, a `switch` that names each) stops compiling until it drops `reopened`. A client tells a server with this change by `runusage/6`.
