A process that dies inside a browser run on a local Chrome is reattached at once. Before, Stagehand's extension kept the dead client's callback batch running until its own timeout (60 s by default) and held the new process's `Stagehand.create` behind it, so the reattach took about as long as Stagehand's 60 s init deadline and failed when the batch timeout was longer. The copy of the extension the cdp provider gives a local Chrome now aborts a gone client's running batches when the extension releases it. The copy carries Stagehand's LICENSE and a NOTICE saying what changed. A Stagehand release whose worker has moved the code the change rewrites is refused by name at launch. The change isn't applied to a browser that brings its own copy of the extension (Browserbase), which still waits until Stagehand fixes this upstream. A local launch with no private TMPDIR (Windows, or a host temp path too long for one) already runs Stagehand's own extension directory unconfined, so it doesn't get the change either and still waits, like Browserbase. pi-browser now pins Stagehand 4.4.0 exactly, the version the change was written against.
