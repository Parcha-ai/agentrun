An agent that learns can learn from rows: `POST /v2/agents/{id}/learning/batches` takes rows, the columns to give the agent and the one that holds the reference answer, and a cap on its runs (`max_cost_usd`, required: each row's run, its look-back and its review's turn are capped at what is left, strict, so no request passes it on a cache miss; the grades of what they learn are counted in the batch's cost but not capped, as on every run), and the server runs the agent on each row in order with learning on. When a run has answered and its learning has settled, the server sends it the review the learning bench sends, `Review: the reference answer is "X"; you answered "Y".`, the same words right or wrong, so it looks back again. One batch runs at a time per agent, a row starts only when what is left of the cap covers the mean of the rows done, and the batch stops `cap` there (or `cost_unknown` when a row's cost is not known, `learning_off` when the agent stops learning: learning is checked before every row). Its progress is the server's: `GET .../learning/batches/{batch_id}` answers rows done, right or wrong per row, the path each run took, the lessons kept (notes, skills, workflow revisions) and the cost so far, after a reload or a restart (a running batch takes up at its first unfinished row, and a row is counted done only once its review's turn completed); `POST .../cancel` ends it, its row's run stopped first. Its reads show what it saved cut of the server's secrets and the agent's sign-in pointers as they are now, as the agent's learning reads are, and withhold it (403) the same way when one of the agent's sign-ins can't be read here. The Learning tab's "Learn from a CSV" uploads a CSV, takes the input and answer columns and the cap, and shows that progress.
