A workflow step can carry a guard: `"guard": {"signal": "self" | "jev" | "both", "threshold": 0.7, "question"?: "...", "fit"?: {"w": [...], "b": 0, "n": 0, "fitted_at": "..."}}` on an agent, decide, extract, code, call, workflow, judge, pick or sift node. After the step runs, the host puts p, the chance the step is right, against the threshold. Below it, the run escalates at that step with kind `guard`. `self` reads the step's own confidence: an agent or decide node submits a `confidence` between 0 and 1 beside its record, kept at `<as>$confidence` and never in its value, and a judge, pick or sift node uses its weakest answer's. `jev` asks Jev once about the step's input and output. `both` puts the two through the guard's fitted logistic, or takes the lower of the two when it has no fit. `validateWorkflow` refuses a bad signal, threshold, question or fit, and refuses `self` on a node that reports no confidence, with a message that says what to write. A host that runs guarded workflows passes `WorkflowDeps.guardStep`; a run without it refuses a guarded workflow before any node runs.
In a learned workflow's call, a guard below its threshold hands the job back to the agent in the same run. The agent's input carries the trace and one line per guard: its signal, what it read, p and the threshold. Jev runs on the pinned model `jev-1.14.0`, with the run's Jev key: a workflow whose guard reads Jev is given that key as a decision node is. Each Jev request is a paid request of the call, at TypeSafe's published input price, and counts toward the run's cost and cap. A guard with no signal to read (no Jev key, or a failed Jev call) hands back and never passes. A learning run's `metrics.guards` lists each check as `{node, signal, self?, jev?, p, threshold, escalated}`.
