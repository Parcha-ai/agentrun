A runner can run on a disk of its own, and `runner --check` checks its environment by name. A runner with `AGENTRUN_STORE_URL`, `AGENTRUN_SEAL_KEY` and a local `--data` never reads the server's data directory: in Mode 2 (Archil settings saved) it runs every run; while the server is in Mode 1 it claims nothing and says why, on its log and to the server, which refuses a new run in those words (`503 runner_refused`) while no runner on its own data directory is there. The mode is the server's (its saved settings, or the Archil settings in its own environment), never the runner's. The runner never fails the run itself. The server tells the disks apart by an id it keeps in `/data/data-root.id` and says in the store at each start, beside the names (never the values) of its run-facing environment.
What breaks: `runner --check --data D --name N` now also checks the runner's environment (the store opens, the seal key is the store's, the runner holds every run-facing name the server holds, an upstream on loopback answers) and fails on any gap. A health check run with an empty environment (compose's `env -i`) now fails: run it with the container's environment (the check prints names, never values), or use `runner --check --heartbeat --data D --name N` for the heartbeat alone. `runner --check --env [--data D]` checks the environment alone, before a runner starts. Not yet on a disk of its own: a run's uploads (`file_ids`), which fail at the claim, and screen recordings. See deploy/README.md, "A runner on a disk of its own".
