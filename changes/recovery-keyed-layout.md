The recovery driver can keep a run in a keyed layout (`agentrun.frozen_run.v4`), so a map's commits stay linear in its items. Opt in with `RecoveryOptions.layout: "v4"` (for a pi task host, return it from `WorkflowTaskHost.options`); the default in this release is `"v3"`, which keeps the driver's whole state in one record rewritten at every commit. On the reference job, a map of 400 one-call items wrote 2.007 GB in 643 s in `"v3"`, and 10.6 MB in 20 s in `"v4"`.
- What lies in each map item is kept in that item's record beside the state, each committed state inside an item as a delta against its map's base, checked against its digest when it is rebuilt (a state that does not rebuild refuses the open with `FROZEN_CHECKPOINT_INVALID`), and each state the driver references once by its digest. In the pi document store these are two new document families, `agentrun.items` (one per map item, keyed by the journal key and the item's path) and `agentrun.states` (one per state, keyed by the journal key and its digest); `agentrun.driver` keeps its record shape and its `generation`.
- Only a store that keeps parts can hold the keyed layout: its opened journal has `items(paths)` and `stateOf(sha256)`, and every write takes the parts that go with its state (`RecoveryJournal`'s `save`, `admit` and `complete` gain an optional `parts`, `admit` an optional `owner`). The memory, file and pi document stores keep them. On a store without them the driver keeps `"v3"`, says why once per open in a new note kind, `layout`, and reports it as `driver.layout`. The store conformance suite (`@parcha/agentrun-dsl/recovery/testing`) gains three cases for parts.
- A run in the keyed layout stays in it whatever a later process asks for. A run stored whole moves to it at its first write that knows the base of every map still running (a map names its base when it resumes, a moment after the open).
- A driver that knows only `"v3"`, from an earlier release, refuses a run in the keyed layout (`FROZEN_CHECKPOINT_INVALID`) rather than run it with its items missing. 0.1.0-beta.13 and earlier fail their own task on a v4 run and report it refused; a host that treats refused as final will tell its user the run failed; a later start on this release resumes it with no call repeated. So opt in only when every process that can open the run is on this release or later. The default moves to `"v4"` in a later release.
- From this release, a run stored in a schema newer than the build knows is refused with its own code, `RECOVERY_SCHEMA_NEWER` (the error names the schema it `found` and the ones it knows, `known`), and the pi workflow task leaves that run pending, never terminal: the process's waiters get the refusal, and a build that knows the schema continues the run. A checkpoint the driver cannot read (`FROZEN_CHECKPOINT_INVALID`) still ends the task.
- `validateWorkflow` results carry an optional `warnings` list that never refuses a workflow. Its first warning is a map with no `resultPath` whose body writes no `as`: each item's result is its whole state, the mapped list included, so the map's result grows with the square of its items. The author skill says the same.
