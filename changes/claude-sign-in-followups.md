Settings → Model keys' login on this machine: fixes to the claude CLI's sign-in and to its status check.
- The line shown for "this machine's" login on the CLI's default folder starts a CLI whose path holds `=` (a data folder such as `/data/a=b`): it still clears the CLI's folder variables with 0.1.0-beta.56's `env -u CLAUDE_CONFIG_DIR -u CLAUDE_SECURESTORAGE_CONFIG_DIR ...`, and such a path goes to `sh -c 'exec "$0" auth login'` as its `$0`. Before, env read that path as one more variable, and the CLI never started. The line runs alike pasted into sh, bash, zsh, fish or tcsh; env skips a `claude` alias or function of the person's shell.
- `PUT /v2/settings/claude-login` that moves the login to the other `place` ends a sign-in the server started that still waits, and answers once its CLI is gone; before, that CLI kept waiting to sign in at the old place. A `PUT` at the same place leaves it waiting.
- "This machine's" login honours `CLAUDE_SECURESTORAGE_CONFIG_DIR` in the server's environment, as the person's own claude CLI with that variable does: the status check, the sign-in, the shown line and a run keep the tokens in that folder (on macOS the Keychain item named from it). Set and empty, it means `~/.claude` and, on macOS, the Keychain item with no suffix, which the CLI gets as an empty value there. A relative value is not taken. The view says it as `machine.credentials`, and the console names it under the folder. Before, the server ignored it and read the tokens from the config folder, so a person whose CLI sets it read signed out. The harness's login takes `secure` and `unsuffixed` for it, and `claudeSignInEnv` and `claudeLoginCommand` take the platform, as `claudeLoginEnv` does. A run with the CLI's own sandbox on denies its commands reading that folder too, as it does the login's own folders; on macOS an empty value names a Keychain item, and adds nothing.
- The sign-in's CLI dies with the server that started it: `startClaudeLogin` starts it under the kernel's parent watch (`parentWatched`: the parent-death signal through `setpriv` on Linux, else the watching shim), as a session's CLI is. Before, a server killed outright (SIGKILL, the OOM killer) left `auth login` running with no limit, holding the browser's callback port. A CLI path that is no program still reads as never started, in the spawn's words. `startClaudeLogin` takes `watch` to choose the watch. A sign-in stopped or ended at its limit under the shim ends only once its CLI is gone, though the CLI ignores SIGTERM: the shim kills it 2 s after passing the TERM on, before the server's own kill 5 s after it, which reaches the shim alone.
- The login's setting names the machine it was turned on for by an id the server makes once in its data folder (`machine-id`, 0600) and reads back on every later start, in place of the hostname. Before, a laptop's hostname changed with its network, so a login turned on at home read "turned on for another machine" elsewhere, and its runs asked for a key. Two data folders are two machines.
- Settings → Model keys: Turn on says why it is grey while "Only I run agents on this server" is not ticked, beside it and as its description for a screen reader.
- The Playground's "No model yet" bar is gone for an agent on Claude Agent (`claude-agent`) while the login is on and reads signed in, since Claude Agent runs on it. Before, it offered ChatGPT or a key as if no model were there. An agent on another harness keeps the bar. The bar reads the revision picked in the Playground, which the run will use, and the agent's current one when none is picked; a picked revision whose definition the console does not hold keeps it. The console reads the login once, again on leaving Settings (where a sign-in finishes) and after a run starts, never on each move between pages, since each read runs `claude auth status` on the server.
- The status check copies the account file only when it is a regular file of at most 32 MiB, read without holding up the server: it opens the file without waiting (`O_NONBLOCK`) and checks what it opened before reading. Before, a FIFO in its place stopped the whole server until something wrote to it, and a device such as `/dev/zero` or a huge file was read whole into memory. A FIFO, a device, a folder or a bigger file is copied as nothing, as a file that doesn't parse is. A link is still followed, since dotfile managers often link `~/.claude.json`.
- Every status check runs the CLI on a copy of the account file in a folder of its own, AgentRun's own login folder included, never on the file itself, so a check never has the CLI rewrite the login's `.claude.json`. In 0.1.0-beta.56 the check on AgentRun's own folder, and on any harness login not marked `shared`, read the login's folder as its config dir, as that release's entry says; none does now. The harness login's `shared` flag is gone (see its breaking entry).
- A server sweeps the status checks' folders (`agentrun-claude-status-*` in the temporary folder) as it starts, when the Claude login is allowed on it: the ones this user owns whose check has ended: each check writes in its folder when it ends at the latest (its limit, whatever the caller gave, and 2 s), and the sweep takes the folder more than 15 s after that; a folder with no such end, or one that lies before its file was written (empty, a partial write, a negative), is taken once changed more than twice the status check's limit ago. `claudeLoginStatus` throws a `RangeError` for a `timeoutMs` that is no whole number of ms from 1 to 2^31 - 1, before it starts the CLI. A check that was killed mid-way (SIGKILL runs no clean-up) left its folder, with a copy of the account file in it, until the machine cleared its temporary folder. The harness exports `sweepClaudeStatusFolders`.
- The status check ends at its limit whatever the CLI does: it asks the CLI to go (SIGTERM), kills it (SIGKILL) 1 s later, and waits at most 1 s more for the CLI's output, then reads as timed out. Before, it sent one SIGTERM and waited for the output's pipe to close, so a CLI that ignored the TERM, or a process it started that held its output open, kept the check, and the run's claim behind it, waiting for ever.
- The person's home is read once, where the server makes the login (the server's `HOME` when it is an absolute path, else the OS's home), and the status check, the sign-in and a run on macOS all take it from the login's new `userHome`. Before, the sign-in took the server's `HOME` while the status check and a run took the OS's home, so a server started with another `HOME` signed in at one home and checked another. `claudeLoginStatus` and `startClaudeLogin` no longer take the `home` option 0.1.0-beta.56 gave them (see their breaking entries).
- A Claude-plan run no longer fails because the login's status check was slow. On a loaded machine the claude CLI could take longer than the check's 15 s, and the run was refused as "could not say whether its login is signed in" though the login was fine. Now a check that gives no answer (the CLI outlasts it, or answers nothing that reads as a status) is asked once more; if that one gives no answer either, the run goes on when the same login read signed in within the last 10 minutes on this server (at a run's check or in Settings), and is refused as before otherwise, in words that say why (a check that timed out says so, and after how long). Any other failure of the check, such as no CLI at its path, refuses the run at once in its own words, as before. A signed-out answer still refuses the run at once, and is never asked again. The harness's `claudeLoginStatus` throws `ClaudeLoginTimedOut` (`code: "timed_out"`) when the CLI outlasts its limit, and `ClaudeLoginNoStatus` (`code: "no_status"`) when it answers in time with no status.
- On macOS, a run on the login runs in the person's home, so the claude CLI writes its cache and logs under their `~/Library/Caches/claude-cli-nodejs`, where they stay after the run. Removing that folder is safe.
