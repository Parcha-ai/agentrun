Settings → Model keys' login on this machine: four fixes to the claude CLI's sign-in.
- The line shown for "this machine's" login on the CLI's default folder clears the CLI's folder variables in a subshell of the person's own shell, `(unset CLAUDE_CONFIG_DIR CLAUDE_SECURESTORAGE_CONFIG_DIR; ANTHROPIC_CONFIG_DIR=... claude auth login)`, in place of `env -u ...`. Under `env`, a CLI path holding `=` (a data folder such as `/data/a=b`) was read as a variable and the CLI never started, and a `claude` alias (often the CLI's local install) was skipped.
- `PUT /v2/settings/claude-login` that moves the login to the other `place` ends a sign-in the server started that still waits, and answers once its CLI is gone; before, that CLI kept waiting to sign in at the old place. A `PUT` at the same place leaves it waiting.
- "This machine's" login honours `CLAUDE_SECURESTORAGE_CONFIG_DIR` in the server's environment, as the person's own claude CLI with that variable does: the status check, the sign-in, the shown line and a run keep the tokens in that folder (on macOS the Keychain item named from it). Set and empty, it means `~/.claude` and, on macOS, the Keychain item with no suffix, which the CLI gets as an empty value there. A relative value is not taken. The view says it as `machine.credentials`, and the console names it under the folder. Before, the server ignored it and read the tokens from the config folder, so a person whose CLI sets it read signed out. The harness's login takes `secure` and `unsuffixed` for it, and `claudeSignInEnv` and `claudeLoginCommand` take the platform, as `claudeLoginEnv` does. A run with the CLI's own sandbox on denies its commands reading that folder too, as it does the login's own folders; on macOS an empty value names a Keychain item, and adds nothing.
- The sign-in's CLI dies with the server that started it: `startClaudeLogin` starts it under the kernel's parent watch (`parentWatched`: the parent-death signal through `setpriv` on Linux, else the watching shim), as a session's CLI is. Before, a server killed outright (SIGKILL, the OOM killer) left `auth login` running with no limit, holding the browser's callback port. A CLI path that is no program still reads as never started, in the spawn's words. `startClaudeLogin` takes `watch` to choose the watch.
- The login's setting names the machine it was turned on for by an id the server makes once in its data folder (`machine-id`, 0600) and reads back on every later start, in place of the hostname. Before, a laptop's hostname changed with its network, so a login turned on at home read "turned on for another machine" elsewhere, and its runs asked for a key. Two data folders are two machines. Breaking: a login turned on before this release reads as turned on for another machine (`other_machine`) once; turn it on again under Settings → Model keys.
