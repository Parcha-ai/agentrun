Settings → Model keys' login on this machine: fixes to the claude CLI's sign-in and to its status check.
- Breaking: after this upgrade, a Claude login turned on before it reads "turned on for another machine" (`other_machine`) once. Turn it on again under Settings → Model keys.
- The line shown for "this machine's" login on the CLI's default folder clears the CLI's folder variables in a subshell of the person's own shell, `(unset CLAUDE_CONFIG_DIR CLAUDE_SECURESTORAGE_CONFIG_DIR; ANTHROPIC_CONFIG_DIR=... claude auth login)`, in place of `env -u ...`. Under `env`, a CLI path holding `=` (a data folder such as `/data/a=b`) was read as a variable and the CLI never started, and a `claude` alias (often the CLI's local install) was skipped.
- `PUT /v2/settings/claude-login` that moves the login to the other `place` ends a sign-in the server started that still waits, and answers once its CLI is gone; before, that CLI kept waiting to sign in at the old place. A `PUT` at the same place leaves it waiting.
- "This machine's" login honours `CLAUDE_SECURESTORAGE_CONFIG_DIR` in the server's environment, as the person's own claude CLI with that variable does: the status check, the sign-in, the shown line and a run keep the tokens in that folder (on macOS the Keychain item named from it). Set and empty, it means `~/.claude` and, on macOS, the Keychain item with no suffix, which the CLI gets as an empty value there. A relative value is not taken. The view says it as `machine.credentials`, and the console names it under the folder. Before, the server ignored it and read the tokens from the config folder, so a person whose CLI sets it read signed out. The harness's login takes `secure` and `unsuffixed` for it, and `claudeSignInEnv` and `claudeLoginCommand` take the platform, as `claudeLoginEnv` does. A run with the CLI's own sandbox on denies its commands reading that folder too, as it does the login's own folders; on macOS an empty value names a Keychain item, and adds nothing.
- The sign-in's CLI dies with the server that started it: `startClaudeLogin` starts it under the kernel's parent watch (`parentWatched`: the parent-death signal through `setpriv` on Linux, else the watching shim), as a session's CLI is. Before, a server killed outright (SIGKILL, the OOM killer) left `auth login` running with no limit, holding the browser's callback port. A CLI path that is no program still reads as never started, in the spawn's words. `startClaudeLogin` takes `watch` to choose the watch.
- The login's setting names the machine it was turned on for by an id the server makes once in its data folder (`machine-id`, 0600) and reads back on every later start, in place of the hostname. Before, a laptop's hostname changed with its network, so a login turned on at home read "turned on for another machine" elsewhere, and its runs asked for a key. Two data folders are two machines.
- Settings → Model keys: Turn on says why it is grey while "Only I run agents on this server" is not ticked, beside it and as its description for a screen reader.
- The Playground's "No model yet" bar is gone while the login is on and reads signed in, since Claude Agent runs on it. Before, it offered ChatGPT or a key as if no model were there.
- The status check copies the account file only when it is a regular file of at most 32 MiB, read without holding up the server: it opens the file without waiting (`O_NONBLOCK`) and checks what it opened before reading. Before, a FIFO in its place stopped the whole server until something wrote to it, and a device such as `/dev/zero` or a huge file was read whole into memory. A FIFO, a device, a folder or a bigger file is copied as nothing, as a file that doesn't parse is. A link is still followed, since dotfile managers often link `~/.claude.json`.
- Every status check runs the CLI on a copy of the account file, AgentRun's own login folder included, never on the file itself. Before, a login not marked as one the person's own CLI shares had its `.claude.json` rewritten by the CLI on every check. The harness's login no longer takes `shared`; a caller that still sets it is ignored.
- A server sweeps the status checks' folders (`agentrun-claude-status-*` in the temporary folder) as it starts, when the Claude login is allowed on it: the ones this user owns and that are older than twice the status check's limit. A check that was killed mid-way (SIGKILL runs no clean-up) left its folder, with a copy of the account file in it, until the machine cleared its temporary folder. The harness exports `sweepClaudeStatusFolders`.
- The person's home is read once, where the server makes the login (the server's `HOME` when it is an absolute path, else the OS's home), and the status check, the sign-in and a run on macOS all take it from the login's new `userHome`. Before, the sign-in took the server's `HOME` while the status check and a run took the OS's home, so a server started with another `HOME` signed in at one home and checked another. `claudeLoginStatus` and `startClaudeLogin` no longer take `home`.
- A Claude-plan run no longer fails because the login's status check was slow. On a loaded machine the claude CLI could take longer than the check's 15 s, and the run was refused as "could not say whether its login is signed in" though the login was fine. Now a check the CLI outlasts is asked once more; if that one gives no answer either, the run goes on when the same login read signed in within the last 10 minutes on this server (at a run's check or in Settings), and is refused as before otherwise, in words that say the check timed out and after how long. A signed-out answer still refuses the run at once, and is never asked again. The harness's `claudeLoginStatus` throws `ClaudeLoginTimedOut` (`code: "timed_out"`) when the CLI outlasts its limit.
- The harness's login API as this release has it (no earlier release had the `shared` flag or the `home` options): a login carries `userHome`, the person's home, which serve sets once where it makes the login; every status check copies the account file, so a login has no `shared`; and `claudeLoginStatus` and `startClaudeLogin` take no `home` option.
- On macOS, a run on the login runs in the person's home, so the claude CLI writes its cache and logs under their `~/Library/Caches/claude-cli-nodejs`, where they stay after the run. Removing that folder is safe.
