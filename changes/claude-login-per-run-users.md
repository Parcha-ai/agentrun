Where each run is a user of its own (the image, `run_isolation: "uid"`), a claude-agent run now runs on Claude Code's login in AgentRun's own login folder instead of failing at its claim. The runner, as the server's user, reads the login's access token from that folder and hands the run's CLI that token alone, in `CLAUDE_CODE_OAUTH_TOKEN`: never the folder and never the refresh token, so the run's CLI never renews the login, and AgentRun does not renew it either yet. The runner reads the folder again when the run starts and whenever Anthropic refuses the token mid-run, so a renewal your own Claude Code wrote there is picked up. A token with less than five minutes left fails the run at its start, and a token refused mid-run with no newer one there ends the turn. The first says to open Claude Code once to renew the login, the second to run the claude CLI once on this login to renew it. A command the run's CLI starts can read the token, as the run's own user can. Under per-run users, a run on this machine's own Claude Code login (`~/.claude`) still fails at its claim. So does a login run while another runner on the same data folder runs its login runs under the server's user, and the error names that runner. A login kept in a form the runner does not read fails in words too. For each of these, set `AGENTRUN_RUN_USER=same` or give the run a `model_key`. `claudeAgentAdapter({ login })` in `@parcha/agentrun-harness-claude` also takes `{ token() }`, a host's reader of the login's access token, and answers the CLI's request for a newer token from it.
