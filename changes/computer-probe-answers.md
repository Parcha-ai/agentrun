Network none, read from inside a computer, now holds when nothing answers: `computerd probe` counts a target reached only when bytes come back from it, not when a TCP connection is accepted. Each target gets a request by its port (443 a TLS ClientHello, with no server name for an IP address; 80 an HTTP `HEAD`; 53 a DNS query over TCP; any other port an HTTP `HEAD`), 3 s to connect and 3 s to answer, and at most 4 KiB is read. Any byte back is an answer: a ServerHello, a TLS alert, an HTTP status line, a DNS response, a banner, or bytes of no expected protocol. The probe's JSON line keeps `reached` (now the targets that answered) and adds `accepted` (a connection accepted, then nothing back) and `results` (each target's protocol, outcome, bytes and detail).
A provider refuses network none only on an answer. A connection accepted with nothing back is recorded, never refused and never hidden: `create` now returns `CreatedComputer`, a `ComputerRef` with optional `notes`, and `attach`'s `AttachedComputer` gains `notes`, such as `network: none; accepted with no answer (no bytes came back): 1.1.1.1:443`. This is for vendors whose firewall accepts every outbound connection and then closes a denied one (E2B documents this). From inside, an accept with nothing back cannot show that the outbound bytes went nowhere. The answered check catches a path that carries traffic both ways, not a one-way leak. The Modal provider is the one that probes today. Docker and Daytona read their network back from the vendor, and a probe there is refused outright, so their results do not change.
