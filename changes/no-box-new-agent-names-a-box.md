On a server with no Docker box whose runner has no shell (Mode 1), a new agent with no place is refused, never sent to the runner or to another box, and `capabilities.places.default_place` is `null` there. Two things break. A create that used to succeed now fails: an agentic definition that names no place and would get the Docker box (it names no tools, or names a shell tool such as `bash` or a background tool) is `422 input_invalid` with `{field: "definition.place", reason: "missing"}`, and the message `name a box: this server has no Docker box for a new agent. Set place to {mode: sandbox, box: <one of: …>}, or to {mode: runner} to run without a shell.` The message lists the boxes this server has, or `<none is set up>`, and ends with why the Docker box is not here, in its own words with their fix (`docker: <why>.`, such as joining the docker group, then a restart); the `fix` names the place to set alone. Before, such an agent was saved with no place and ran on the runner with no shell. An edit that would save such a revision is refused the same way, and so is a template apply, or an `agentrun deploy`, of a package that names no `tools` and no `computer` list, whatever MCP tools the apply ticks: with Docker such an apply gets the Docker box and its shell tools, as a create does. Its `dry_run` is refused alike, in the same field, reason and words, with no plan, so `agentrun deploy` stops at the preview: no plan printed, no confirmation asked, no apply sent. And `capabilities.places.default_place`, still always sent, can be `null`: no default, so a new agent names its place. `default_reason` is there exactly when it is `null`, with the refusal's words. A client tells the cases apart by `default_place === null`, never by reading `default_reason`.

Upgrading: by mode, where a new agent with no place goes now. Agents saved before the upgrade with no place and no tools keep running on the runner, in every mode: the store holds their tools as `[]`, the same as an agent that named none, so they are not refused.
- Refused (`name a box`; `default_place` is `null`): no Docker box, and the runner has no shell (Mode 1).
- Not refused: where Docker's box is available, a new agent gets it (`default_place` is `{"mode": "sandbox", "box": "docker"}`, no `default_reason`). In Mode 2, the runner's shell is Archil's serverless exec: a new agent with no place saves for the runner as before, and `default_place` is `{"mode": "runner"}`, no `default_reason`.

What to do on a Mode 1 server with no Docker: name the place, `"place": {"mode": "sandbox", "box": "<a box this server has>"}`, or `"place": {"mode": "runner"}` with no shell tool. To keep the runner without naming it, name the tools, with no shell tool among them (`"tools": []`, or `["read", "write"]`). A client that catches the refusal keys on `field` `definition.place` and `reason` `missing` (no new error code). A client that read `places.default_place.mode` checks for `null` first; the OpenAPI document marks the field `x-agentrun-serve: "place/5"`.
- The default box is the one whose provider descriptor sets `defaultBox` (Docker's). Another box that answers is never picked for a new agent.
- On Mode 1, a run of an agent saved earlier with no place and a shell tool, once Docker is gone, is `409 agent_not_runnable` in the same words. That run was already refused; only the words change.
- A package for an apply or a deploy on Mode 1 with no Docker names its tools (`tools: []` keeps the runner) or its computer list (`computer: [shell, none]`). One that already names either applies as before.
- A definition with no place that names a shell tool and the browser, on Mode 1 with no Docker, is refused at the shell tool (`not_an_option`): no place runs both, since a box refuses the browser, so the words say to remove one, never to name a box.
- Unchanged: a workflow, a definition that names its place (the runner included), and one whose tools need no shell.
- On Mode 1 with no Docker, the start's `Boxes:` line reads `Boxes: none, so a new agent must name its place: a box, or the runner.`, followed by Docker's reason. In Mode 2 it still reads `Boxes: none, so new agents run on the runner.` `agentrun doctor` reads `places.default_place`: with `null` it says a new agent must name its place, a box (listing the ready ones) or the runner, never that it runs in another box instead; otherwise it says what it said before.
- The console reads a `null` `default_place`: its new-agent form starts on neither the server nor a box (in the Computer step, no kind is picked), and Create waits until one is chosen, None included; on a server with no box, its place picker says to set one up for the agent, or choose On the server to run it without a shell.
