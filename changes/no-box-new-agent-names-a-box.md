On a server with no Docker box whose runner has no shell (Mode 1), a new agent with no place is refused, never sent to the runner or to another box, and `capabilities.places.default_place` is `null` there. Two things break. A create that used to succeed now fails: an agentic definition that names no place and would get the Docker box (it names no tools, or names a shell tool such as `bash` or a background tool) is `422 input_invalid` with `{field: "definition.place", reason: "missing"}`, and the message `name a box: this server has no Docker box for a new agent. Set place to {mode: sandbox, box: <one of: …>}, or to {mode: runner} to run without a shell.` The message lists the boxes this server has, or `<none is set up>`, and the `fix` says the same. Before, such an agent was saved with no place and ran on the runner with no shell. An edit that would save such a revision is refused the same way. And `capabilities.places.default_place`, still always sent, can be `null`: no default, so a new agent names its place. `default_reason` is there exactly when it is `null`, with the refusal's words. A client tells the cases apart by `default_place === null`, never by reading `default_reason`.

Upgrading: by mode, where a new agent with no place goes now.
- Refused (`name a box`; `default_place` is `null`): no Docker box, and the runner has no shell (Mode 1).
- Not refused: where Docker's box is available, a new agent gets it (`default_place` is `{"mode": "sandbox", "box": "docker"}`, no `default_reason`). In Mode 2, the runner's shell is Archil's serverless exec: a new agent with no place saves for the runner as before, and `default_place` is `{"mode": "runner"}`, no `default_reason`.

What to do on a Mode 1 server with no Docker: name the place, `"place": {"mode": "sandbox", "box": "<a box this server has>"}`, or `"place": {"mode": "runner"}` with no shell tool. To keep the runner without naming it, name the tools, with no shell tool among them (`"tools": []`, or `["read", "write"]`). A client that catches the refusal keys on `field` `definition.place` and `reason` `missing` (no new error code). A client that read `places.default_place.mode` checks for `null` first; the OpenAPI document marks the field `x-agentrun-serve: "place/5"`.
- The default box is the one whose provider descriptor sets `defaultBox` (Docker's). Another box that answers is never picked for a new agent.
- On Mode 1, a run of an agent saved earlier with no place and a shell tool, once Docker is gone, is `409 agent_not_runnable` in the same words. That run was already refused; only the words change.
- Unchanged: a workflow, a definition that names its place (the runner included), one whose tools need no shell, and a template apply. An apply compiles its tools where it runs (a box's shell tools only where Docker's box is here), and its `grants` are the package's MCP tools alone; a package whose own `tools` name `bash` was already refused on Mode 1 with no Docker, now in the `name a box` words.
- On Mode 1 with no Docker, the start's `Boxes:` line reads `Boxes: none, so a new agent must name its place: a box, or the runner.`, followed by Docker's reason. In Mode 2 it still reads `Boxes: none, so new agents run on the runner.` `agentrun doctor` reads `places.default_place`: with `null` it says a new agent must name its place, with the server's `default_reason`; otherwise that new agents run on the runner, as before.
- The console reads a `null` `default_place`: its new-agent form starts on neither the server nor a box (in the Computer step, no kind is picked), and Create waits until one is chosen, None included; on a server with no box, its place picker says to set one up for the agent, or choose On the server to run it without a shell.
