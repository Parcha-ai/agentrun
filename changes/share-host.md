`agentrun-serve --share-host` (or `AGENTRUN_SHARE_HOST=1`) starts a share host: a server that answers under `/r/` alone and stores shares in `DIR/shares/`. A share's page is `/r/<id>` (the console's `share.html`, with its asset URLs under `/r/_assets/` and a CSP that loads nothing from any other origin), its stored bytes are `/r/<id>/bundle.json` (`nosniff`, `X-Robots-Tag: noindex`), and its API is `POST /r/v2/shares`, `GET /r/v2/shares` (the caller's own), `DELETE /r/v2/shares/<id>` and a public `GET /r/v2/health`. Every other address is a 404, the console, `/v2`, MCP and every run, agent, key, computer and trigger route among them. A share host starts no runner and has no owner or console session: its API takes one of its tokens (`AGENTRUN_TOKENS`), whose id owns each share it uploads.
An upload is a run's `agentrun.share/1` bundle exactly as `GET /v2/runs/<id>/export` wrote it: canonical JSON at most 8 MiB, the export's closed fields and caps, each file's size and digest and the document's sha256 checked (a mismatch is `400`). The host then scrubs the whole body, and each of its strings alone, in cut mode with the values it holds (its keys and tokens). A value it finds refuses the upload unless a `restored` record names it exactly (pointer, rule, start, end) and its kind is one of the kinds the host's own scrub says may be restored (label, personal, jev); the other cuts can't be put back. A restored record naming no value the host finds refuses it too (save a restore of Jev's rule, which the host never runs: taken unchecked, its value still scrubbed, and counted in `restored_unchecked`), and so does a scrub that fails. An upload that needs more than 50,000 string reads is `413` before any scrub. Each distinct string is one read for each context it is read under (a file's path, a workflow call's command), and a call's command is read once for all of its output. Each refusal is `422 input_invalid` with `details.reason` and counts by rule, never a value, and nothing is stored; the host never repairs a bundle. A stored share answers `201 {id, url, sha256}`, its id 128 random bits in base32 and its URL on `AGENTRUN_PUBLIC_URL` (never a Host header; a share host on an address other than loopback needs it to start). A token keeps at most 100 shares (`403 forbidden`, `details.reason: share_quota`, past it); shares never expire. Only the token that made a share deletes it (`204`); its bytes go, and its page and bundle then answer `410`. Run one replica with `DIR` on a persistent volume: the quota and the share index are the one process's.
A share page draws no image at all: not a run's file and not a provider's URL, in a workflow's graph or in a report.
The host re-reads a file's content with its path and a workflow call's output with that call's command. A Timeline row's output it re-reads without its call's context, since a bundle carries no calls, so the host's check of a row is the context-free rules' alone. The export still cuts the row with its call's context.
The share page has not yet been drawn in a real browser: its HTML, CSP and assets were fetched from a real console build on a loopback share host.
