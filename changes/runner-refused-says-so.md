A server whose runners all refuse to claim (their run isolation refused, for one an `AGENTRUN_RUN_USER` the runner does not know, or the image's helper unable to switch users on the platform) now says so instead of queueing runs forever. Before, on Render with `AGENTRUN_RUN_USER` removed, a person started a run, got 202, and watched it sit `queued` for good while `/v2/health` said `ok`; the reason was only in the service's log. Now the start is 503 `runner_refused` with the runner's words and their fix (`set AGENTRUN_RUN_USER=same`), a run already queued ends `failed` with error code `runner_refused`, `GET /v2/capabilities` has the words in `runner_refused`, and `GET /v2/health` answers 200 `degraded` with its `runner` check `refused` (200, so Render's health check does not restart the service in a loop over a setting). A message to a run and a backend SDK run's start are refused the same way. Once a runner that can claim starts, it all clears. Both shapes count: the runner beside the server, and runners in processes of their own, on this host or another over one Postgres store (each runner now keeps a row in the store saying it is there). A runner in a process of its own says on that same row, under the same incarnation, where its relay takes the dials the server relays to it, so the relay's table `runner_relays` becomes `runners`, and whether a relay is there is judged on the store's clock (the database's on Postgres): a runner on another host whose clock drifts from the server's is no longer refused as not running. Postgres migration `0020_runners.sql` renames the table in place and keeps its rows. On SQLite the server's start drops `runner_relays` and makes `runners`, with no store version change: its rows are heartbeats each runner writes again within 10 s, so none is copied. Start this build's server before its runners: a runner waits until the server has done it, and a runner of an earlier build with a relay does not start against a store this build's server opened. A server with `--no-runner` and no runner started yet still queues runs for its runner to come. The failed run's error code `computer_unavailable`, served since the computer-loss end, is now in the OpenAPI document's `RunErrorCode` too.
