A server whose runners all refuse to claim (their run isolation refused, for one an `AGENTRUN_RUN_USER` the runner does not know, or the image's helper unable to switch users on the platform) now says so instead of queueing runs forever. Before, on Render with `AGENTRUN_RUN_USER` removed, a person started a run, got 202, and watched it sit `queued` for good while `/v2/health` said `ok`; the reason was only in the service's log. Now the start is 503 `runner_refused` with the runner's words and their fix (`set AGENTRUN_RUN_USER=same`), a run already queued ends `failed` with error code `runner_refused`, `GET /v2/capabilities` has the words in `runner_refused`, and `GET /v2/health` answers 200 `degraded` with its `runner` check `refused` (200, so Render's health check does not restart the service in a loop over a setting). A message to a run and a backend SDK run's start are refused the same way. Once a runner that can claim starts, it all clears. Both shapes count: the runner beside the server, and runners in processes of their own, on this host or another over one Postgres store (each runner now keeps a row in the store saying it is there; Postgres migration `0020_runners.sql`). A server with `--no-runner` and no runner started yet still queues runs for its runner to come. The failed run's error code `computer_unavailable`, served since the computer-loss end, is now in the OpenAPI document's `RunErrorCode` too.
