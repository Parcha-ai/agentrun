`DELETE /v2/agents/{id}` deletes an agent another system owns (one an inline run made with `external`), whole, and answers 204.
- The order is fixed. First the agent refuses new runs, and that refusal is stored, so a run POST, a message that would start a run, a trigger firing, a schedule and an SDK run are all refused (409 `agent_not_runnable`, "being deleted"); then its learning batches still running are cancelled, and its runs and learning runs are cancelled and waited on until each is final. Then its learning is deleted: every file of its learning folder, then its promotions, grades, evals and learning batches. While learning work is in flight that delete refuses, and the DELETE answers 409 `learning_busy`, naming the work in `details.runs`, with the agent left refusing runs. Last, its triggers, sign-ins, own computer, disk, folders, kept idempotent answers, runs (journal, launch records, channel posts, changes) and revisions are deleted, then the agent.
- Nothing the agent owns elsewhere is left behind: a trigger's registration upstream, a saved sign-in at its vendor, its own computer and its Archil disk are each deleted there before the record here that names them. While one is not (the vendor or Archil failing, or Archil turned off on this server with a disk still stored on the agent), the DELETE answers 503 `unavailable` (retryable) with the agent kept and refusing runs.
- A run whose launch named an Archil disk (`archil_disk`, the caller's) kept its folder there: that folder is deleted on the disk before the run's launch record, and the disk and everything else on it are kept; a disk Archil says is gone has nothing left to delete. While Archil refuses (a computer still holds the folder, Archil is not reached or is off), the DELETE answers 503 the same way.
- From the first step the agent also takes no new trigger, not even one made off (Composio registers those too), no trigger moved to it or turned on, and no write to its home or its learning (a home file's write or delete, a note, an eval, a run's grade, a learning batch's create or cancel, a replay): each is 409 `agent_not_runnable`. Such a write sent while a DELETE runs waits for it, then finds the agent gone (404), so none lands after the learning went. A trigger that reached it anyway keeps the agent (503 `unavailable`) until the next DELETE removes that trigger upstream and here. A kept idempotent answer whose removal failed to save is removed by the next DELETE, and a request still at work under its key when the DELETE removed its run keeps no answer, so a key never replays a deleted run, a restart included.
- A trigger's adapter settings (a webhook's secret, a poll's cursor) are removed before its row, on this delete and on `DELETE /v2/triggers/{id}`, so a failure between the two leaves the trigger for the next DELETE to find.
- Sending the DELETE again finishes the job after a crash at any step; once it has finished, the agent is 404.
- An API-only server (`AGENTRUN_API_ONLY=1`) serves it too, for the backend that made the agent.
- An agent made here is never deleted: 409 `agent_not_external`, pointing at `POST /v2/agents/{id}/archive`. A run that cannot be ended from here answers 409 `runs_in_flight` (retryable).
- Shared things stay: MCP servers, sealed keys, paired computers, tokens and uploaded files.
- The clients gain `deleteAgent` (TypeScript and Python) and `agentrun agents delete-agent`.
