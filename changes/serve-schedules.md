Schedules start an agent's capped runs on their own: `POST /v2/triggers` with a source of `{kind: "schedule", cron, timezone}` (five fields, an IANA zone), `{kind: "schedule", at}` (once; the trigger turns itself off after) or `{kind: "schedule", every_s, start_at?}` (60 to 31622400, a year and a day, on the grid from `start_at`), and a target of `{kind: "start_run", agent_id, input, max_cost_usd, effort?}`. `max_cost_usd` is required, and a workflow agent is refused, since a workflow run's spend is not capped here.
Each firing starts its run once, across retries and restarts: its key comes from the trigger and its nominal time, and its run is started under that key. A firing while the trigger's last run is still active (working, or waiting on a person) is recorded as skipped, with why. Times missed while the server was down are one `missed` firing with their count; the schedule goes on from now. `PATCH /v2/triggers/{id}` with `enabled: false` pauses it, and the time it was off is skipped, not caught up. `POST /v2/triggers/{id}/fire` runs it now, once per `Idempotency-Key`. `GET /v2/triggers/{id}/firings` lists its last 200 firings, and a run it started names it in `trigger`. Triggers live in `triggers.json` in the data directory; capabilities list them under `features.triggers`.
