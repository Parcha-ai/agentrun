Computer time is priced the way providers bill it: by the resources a computer holds, never by a size. An operator copies its provider's per-resource rates from the provider's price sheet into `AGENTRUN_COMPUTE_USD_PER_VCPU_SECOND_<PROVIDER>`, `AGENTRUN_COMPUTE_USD_PER_GIB_SECOND_<PROVIDER>`, `AGENTRUN_COMPUTE_USD_PER_GPU_SECOND_<PROVIDER>_<GPU_TYPE>` and `AGENTRUN_COMPUTE_USD_PER_DISK_GB_MONTH_<PROVIDER>` (a month of 730 hours). A priced computer's time is held on the run's ledger under its `max_cost_usd`, one 5-minute stretch ahead, as browser time is: a claim's computer, made while the run is set up, has its first stretch held as soon as the run's cap can judge, so the run's first request is judged beside it (a cap with no room parks the run there); a computer made later in the run (a lost sandbox's new one) has its first stretch held before its create, and a cap with no room makes nothing and fails the run in the cap's words; a cap with no room for a later stretch pauses the run for a raise; and the time it ran is booked before the run's end is written, so the end's `cost.usd` holds it all. The run's ledger tells a caller whether its cap can judge yet (`RunLedger.judges`), and a paid step asked while the run's spec is built waits for it instead of failing. With no price set nothing changes: the computer runs outside the cap, as a tool call with no price does, and is never refused. A resource set to `0` is booked at $0 and reads $0, never `unpriced`. `GET /v2/runs/{run_id}/usage` gives `compute_time` lines (`runusage/4`), one per provider and resource, with the raw quantity, its unit, its basis and the dollars the run's ledger booked, so `total` stays the run's `cost.usd`; the time no claim held (a computer kept for a follow-up, one deleted after its run, one whose delete failed) is said apart as `unheld_quantity` and is in no cost. Each computer interval gives `disk_gb` and `booked_seconds` (Postgres migration `0023_computer_interval_resources.sql`; a SQLite store gets both columns at the server's open). A computer's figures are its provider's own where its answer gives them: `CreatedComputer.resources` in `@parcha/agentrun-computer`, filled from Daytona's sandbox (vCPUs, memory, disk and GPUs), E2B's `getInfo` and Fly's machine guest (vCPUs and memory), and `Machine.resources` for a hosted provider's read of its machine.
