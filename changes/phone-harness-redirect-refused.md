The phone harness provider's API calls go through the shared REST client, so a redirect from the API fails in that client's words, "POST /sessions: the API answered with a redirect, which is never followed: it would carry the key", where it said the phone harness could not be reached. A create that meets a redirect still asks the service for the phone by the request's key, and the ledger keeps the key if that ask meets one too: the redirect's answer is never read, and the service may have made the phone. A request cut off by its bound now reads "GET /sessions/<id> did not answer within 30 s", one that gets no answer keeps the code `unreachable` in the client's words, and a `phones_busy` refusal's wait comes from the answer's `retry_after_seconds`. An error answer whose words break off keeps its status's code (a 401 is still `denied`), here and in every provider on the shared client, and the phone harness names the status of one with no words, "Bad Gateway (502)".
