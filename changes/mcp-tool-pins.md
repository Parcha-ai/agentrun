An MCP tool's setting may pin arguments: `pin: {<argument>: <JSON scalar>}` on `mcp:<server>/<tool>` (never the wildcard), in `PUT /v2/settings/tools` and in an agent's `definition.tool_settings`, 1 to 8 top-level arguments, each a JSON scalar (`null`: left out) or a list of 1 to 16 of them, the argument one of the list. The tool gate refuses a call whose arguments are not as pinned before it is sent or asked about, whatever the permission, and the model reads "mcp:slack/slack_send_message may only be called with channel_id = C0123: its destination is fixed by the agent's settings". A call approved under ask is checked again before it runs. A pin in `tool-settings.json` that does not read refuses every call of its tool, is served as `pin_broken: true`, and stays broken through any save that keeps its key without a valid pin. The agent's pin and the server's both hold (an argument both pin takes what holds both); where nothing holds both, every call is refused. A template's `mcp` entry takes `pin: {<tool>: {<argument>: "<value or ${parameters.x}>"}}`: apply writes it, filled, into the agent's tool settings, and a pin whose parameter was not given sets the tool to deny with a `pins.<tool>` warning. `GET /v2/templates` shows each tool's `pin`. `market-monitor` pins its Slack and Gmail sends to its `channel`, and `inbound-lead` its Slack send to `slack_channel`, so a granted send can only go to the destination the owner set at apply; `code-review` pins `pull_request_review_write` to `method` one of `create`, `submit_pending`, `delete_pending` and `event` absent or `COMMENT`, so it can never approve, request changes or resolve a thread.

Until the agent store's cutover an agent's own pin is refused at `POST /v2/agents` (`422 not_set_up_here`, pointing at `/v2/settings/tools`), and a template apply writes no pin and warns `pins.<tool>` with the pin to set on the server; the server's pin holds every run today.
