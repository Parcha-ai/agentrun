A server runs a harness recipe it is started with: `agentrun-serve --harness-recipe FILE` (repeatable, or `AGENTRUN_SERVE_HARNESS_RECIPES`), and `agentrun-serve runner` takes the same flag. The harness is listed, and a run starts, only once a `harness-check` passed on the data directory for that recipe file, binary and tree (`<id>.checked`; else `HARNESS_NOT_CHECKED`); each start digests the binary and tree again. A proxy-billed agent runs on the server's model proxy. A plan-billed one runs on keys saved for its harness, which no server saves yet (`HARNESS_KEYS_NOT_SAVED`), or, on a server its owner starts with `--harness-sign-in` on their own machine (loopback, its own SQLite store, its runs as its own user, one owner; else `HARNESS_SIGN_IN_NOT_LOCAL`), on the owner's own sign-in for a run a person starts; a scheduled or triggered run on it is refused at its claim. `harness-check` runs on a recipe's keys alone, never the sign-in, and a plan-billed recipe must name a key. `agentrun harness sign-in` prints one warning line that the vendor's terms (the recipe's new `signIn.terms`) may not cover use through AgentRun. A run's agent reaches beyond loopback only through the server's egress proxy, to the recipe's `model.hosts`. The loader now refuses a key whose name is not shaped as a key (`FOO_CRED`: `RECIPE_KEY_NOT_OWN`).
