A secret is saved only from the owner's session, and the server never starts without a seal key. Saving, replacing or removing a tool key or a model key (`PUT` and `DELETE /v2/settings/tool-keys/{key_id}`) takes the owner's password session (accounts on), or, on a server bound to loopback alone with accounts off, the console the launch link opened; the API token is refused (403) in one sentence on every server, loopback included, and a server bound off loopback with accounts off takes no secret at all. One check in the dispatch decides it, from a registry each kind of secret adds its write routes to; the API document marks every secret field `x-agentrun-secret: true`, and a test fails for a marked route that skips the check. `GET /v2/auth/session` now answers with accounts off too: `accounts`, `secrets_writable`, and `secrets_reason` (`sign_in`, `no_accounts` or `token`) when it is false. Every secret's view answers one shape, `SecretMeta` (name, set, source: env, console or sign-in, changed_at), never a value: an object holding one secret carries it as `secret`, one holding several as `secrets`, each named `<plane>:<id>`. Each row of `GET /v2/settings/tool-keys` now has `secrets`, one per field, named `tool:<FIELD>` or `model:<FIELD>`, with the time that field's own value was saved. With no `AGENTRUN_SEAL_KEY`, the server makes one at its first start in `agentrun/seal.key` under `$XDG_CONFIG_HOME` (`~/.config`), 0600 in a 0700 directory, printing only its path, by the launcher's rules; a key or directory another user can read, a linked directory, or nowhere to keep one stops the start, in words. The runner reads the same key: it no longer falls back to an all-zero key. Upgrading: a script that saved keys with the token now gets a 403; save them in the console, or set them where the server starts (the environment always wins).
