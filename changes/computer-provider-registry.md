The provider registry: a new computer is one provider file and one registry line. `src/providers.ts` maps each id to a lazy import of its provider file (`docker`, `modal`, `daytona`), so loading it loads no provider and no vendor SDK; `providerFromEnv(id, env?)`, `providerModule(id)`, `providerIds` and the `ProviderModule` and `ConformanceModule` types are exported from the package, and an unknown id is refused naming the ones the registry holds.
- Each provider file exports `ENV`, the variables it reads, every one `COMPUTER_<ID>_*`, and `fromEnv(env, options?)`, the provider built from them alone. The env reading moved out of the conformance modules into the provider files with its rules unchanged: Modal takes its key from `COMPUTER_MODAL_TOKEN_ID` and `COMPUTER_MODAL_TOKEN_SECRET` only, pins the server it goes to, and refuses while `MODAL_SERVER_URL` is set; Daytona never reads `DAYTONA_API_KEY`; Docker reads `COMPUTER_DOCKER_DAEMON` (default this package's daemon for the architecture `docker version` reports, bounded at 30 s) and `COMPUTER_DOCKER_USER`. Modal's live switch, the 30-minute run cap, Daytona's run bounds, snapshot and notes, and the drifted providers stay in the conformance modules, which build through `fromEnv`; the three copies of the drifted daemon's Go build are one.
- The conformance CLI resolves `--provider <id>` through the registry for every id, Docker included, and its usage lists the registry's ids. A module path still works, and may be a provider file that exports `fromEnv()`, run with no drifted provider. `dockerConformance()` and its `close()` are gone: `dist/conformance/docker.js` exports `createProvider()` and `createDriftedProvider()` like the others, and the CLI's `dockerTimeoutMs` option is now `providerOptions`, given to the module's functions.
