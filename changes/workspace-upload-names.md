An uploaded template package's name is now its workspace's own. On an API-only server, two workspaces (the `AgentRun-Workspace` header) can each upload a package of the same name, and each gets `201` and its own package under the same id, `upload:<name>`. Before, the second upload was `409 name_taken`, which also told that workspace another one held the name. Each workspace's read, list, apply, reimport and delete reaches its own package alone, so a workspace's delete never removes another's. A workspace's reimport sent while its own delete of that name runs now lands (`201`); before, it could be refused `409 name_taken` as held outside the workspace, though the name was free right after. An agent's purge removes the upload it was applied from in the agent's workspace alone. A request with no workspace keeps the packages of none: on a server with no workspaces nothing changes, and on an API-only server a request with no header no longer sees, replaces or is refused by a workspace's package.
Upgrading: Postgres migration `0036` keys `imported_templates` by workspace and id, and on SQLite the server's open does the same in place, with the schema version staying 18. Each row keeps the workspace it already had, and a row with none stays in none, still one package a name there. No runner reads or writes the table, so the runner floor stays where it was: runners of the earlier build keep running, with no drain. A server of an earlier build refuses a Postgres schema at `0036`, as it does any later schema. On SQLite, a server of an earlier build started again on a store this build's server has opened (a rollback) opens it, but every upload it takes fails until this build's server is back.
