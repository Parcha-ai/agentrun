Each run is a process of its own under its runner, and in the image a user of its own; `GET /v2/capabilities` says which as `run_isolation` (`"uid"` or `"process"`).
  - The run's process is handed its own keys on a pipe and a channel to its runner. Over the channel it reads and writes its journal, under the runner's fence, and the store's rows of its own run and agent, each call checked against its claim. What the seal key opens for the run, the runner opens and hands over; the seal key, the API token and the store's URL stay in the runner. A run's own model key (`model_key`) is opened by its runner, at its claim and for each message that hands one; a run that holds one is handed none of the server's model keys. A frame past 32 MiB, or one that is no message of the channel, fails the run.
  - In the image, slot `s` of a runner runs as uid and gid `1001 + s`, through `agentrun-runas` (root:node `0750`, file capabilities `cap_setuid`, `cap_setgid`, `cap_setpcap`): its slot's group alone, no capability, `no_new_privs`. The data directory is `0711` (the Railway template's start command sets its volume so too) and the store's files `0600`. At a run's end every process of its uid is killed and its files in `/tmp`, `/var/tmp`, `/dev/shm`, `/run/lock` (`/var/lock`) and `/dev/mqueue` are removed (SysV IPC objects are not), and its runner sweeps the run's scratch folder, its temporary folder with it.
  - A platform that strips file capabilities or sets `no-new-privileges` makes the runner refuse to claim, in words naming the setting; `AGENTRUN_RUN_USER=same` runs every run as the runner's own user instead, said on its log. Runners in containers of their own on one `/data` volume take slots from an `AGENTRUN_RUN_SLOT_FIRST` of their own (`deploy/compose.yaml`: 0 and 128); a runner told to hold more runs than the slots from its first to 255 refuses to start, and each run's slot is locked on the volume (`run-slots`) until its reap, so runners whose ranges overlap never run two runs as one user.
  - What a run's process is handed is bound to its claim: a GitHub token only for its own pull request's repository, contents read; decision and tier model keys only for the learned workflows its runner chose for it; of the settings, the server's shared configuration and its own run's and agent's rows; its runner's live address with a proof key of its own run alone. Its uploads and opening message are placed by its runner before it starts, and the learning its end takes (a check's replays, a promotion) is its runner's. A slot is reaped before its first run too, and a reap that does not hold retires the slot. The server started with its runner beside it in one process (the image's default) runs each run as a process of its own. A run that runs no agent's code on the runner stays in the runner's process: a learning run, an SDK backend run (its agent runs in the caller's application) and a native run (its agent is the source machine's own sign-in). A computer made for a run is let go by its runner at the run's end even when the run's process never let it go.
  - A local install has no helper: each run is a process of its own as the user who started the server (`run_isolation: "process"`).
