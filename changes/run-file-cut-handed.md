A cut read of a run's file (`GET /v2/runs/{run_id}/files/{path}?cut=run`, which a template eval's grader reads) now cuts what the run's caller handed it: its own model key (`model_key`), its tool keys and its MCP servers' credentials. Before, the cut held only this server's values and the run's sign-in refs, so a file that held the run's own key read with the key in it. While the run holds them, the read cuts them by value. The run's end erases them, as before, and now first counts where they sit in each of the run's text files: each file's MAC (HMAC-SHA256 under a key derived from the seal key) and the byte ranges to cut, never the values or a hash of one. Each file is named by a MAC of its path too, never the path, so a file the run named by a key (`cache/<key>.json`) leaves the key nowhere in the stored count. After the end, a file still byte for byte as counted is cut at those ranges. Any other file is `403 forbidden` ("not counted at that end as it is now"): one written or changed after the end, one past the count's limits (2,000 files, 64 MiB read in all, 256 KiB per file, the most a cut read answers, 512 KiB of count in all), and every file of a run whose end made no count. A file the count cut in more than 256 places reads `[redacted]` whole after the end. A run never handed a secret reads as before.
- Fail closed: a run whose handed values don't open under this server's seal key is withheld whole, its view, list row and files (cut or raw), as a run whose sign-in can't be read back. A later turn that hands new secrets keeps the earlier count for the files it left unchanged; a file that turn writes or changes is withheld after its end, since it may hold what the earlier turn was handed. Once a run handed secrets has ended a turn, a file a later turn writes or changes stays withheld from cut reads for good, whether or not that turn hands secrets (read it raw).
- Store: a run's launch keeps the count (`run_launch.census`, Postgres migration 0027 `run_launch_census`; SQLite adds the column when the server opens, and a runner waits for that server). A launch is marked "pending" when it first holds sealed secrets, including each one live at the upgrade, so an end by a runner from before this release (during a rolling deploy) leaves its files withheld, never read uncut. On Postgres a trigger keeps that rule for a server from before this release still writing during the deploy. The runner makes the count just before the end's commit, bounded at 60 s; past that, or when it fails, the end writes "unscanned" and the run's files are withheld after it, and the runner says so in one line (`Runner <name>: census <run id>: ...`, with the error's code or name, never its message). Migration 0027 takes an ACCESS EXCLUSIVE lock on `run_launch` and scans it to check the new column's constraint, its wait bounded by the store's busy timeout: on a large `run_launch`, apply it in a quiet window.
- A start's input (which the run's title is read from) and a message's text are cut of the keys handed with them when the server writes them, and a message's text of the keys the run holds too. Before, a key typed into the input was cut only while the run held it, and the run's title showed it raw after the end.
- A message that hands a new key mid-turn keeps the one it replaced sealed, only to be cut, until the turn's end erases both. Before, the replaced key was dropped from the cut at once, so the run's files and timeline showed it live, and the end's count missed it. A message that seals over secrets that don't open here (or past 256 replaced values in one turn) leaves the run withheld until its end.
- A cut read keeps a file's byte order mark as the character it is, as a raw read serves its bytes. Before, it dropped a leading one, and a run's end counted the file's byte ranges without it, so after the end the last bytes of a key in such a file were served.
- A handed MCP header in a known scheme (`Basic`, `Token`, `Digest`, `ApiKey`, `Key`, as `Bearer` was, in any case) has its credential cut alone, and a Basic credential's `user:password` and password too, and its user when the password is empty or short (a key sent as the user). A header in another scheme (`SSWS`, `Bot`, `OAuth`, `Splunk`, `Klaviyo-API-Key` and the like) has its credential cut alone when that word is shaped like one: it has a digit, is 20 characters or more, or is base64 or hex of 8 or more. Before, a header with a space in it was never cut. A two-word header value whose second word is none of these (a client's name, `Acme Integration`) is not split.
- A run's end waits for its count (up to 60 s) before it writes, and its runner keeps renewing the claim while it waits, so a count slower than the lease (30 s by default) still lands the end. Renewal stops once the end has landed. A claim that only ends a run (one stopped before it started) is renewed the same way.
- A run's file listing read with `?cut=run` names no file once the run's end erased what its caller handed it: the count says where a value sits in a file's text, never in its name, so a name can't be cut by it. A template eval's grader then shows each text file by no name and counts the rest, as from a server that doesn't know `cut`.
- Ended runs from before this release have no count, and their files read cut of the server's values alone, as before.
