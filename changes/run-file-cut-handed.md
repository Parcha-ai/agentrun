A cut read of a run's file (`GET /v2/runs/{run_id}/files/{path}?cut=run`, which a template eval's grader reads) now cuts what the run's caller handed it: its own model key (`model_key`), its tool keys and its MCP servers' credentials. Before, the cut held only this server's values and the run's sign-in refs, so a file that held the run's own key read with the key in it. While the run holds them, the read cuts them by value. The run's end erases them, as before, and now first counts where they sit in each of the run's text files: each file's SHA-256 and the byte ranges to cut, never the values or a hash of one. After the end, a file still byte for byte as counted is cut at those ranges. Any other file is `403 forbidden` ("not counted at that end as it is now"): one written or changed after the end, one past the count's limits (2,000 files, 64 MiB read in all, 256 KiB per file, the most a cut read answers), and every file of a run whose end made no count. A run never handed a secret reads as before.
- Fail closed: a run whose handed values don't open under this server's seal key is withheld whole, its view, list row and files (cut or raw), as a run whose sign-in can't be read back. A later turn that hands new secrets keeps the earlier count for the files it left unchanged; a file that turn writes or changes is withheld after its end, since it may hold what the earlier turn was handed.
- Store: a run's launch keeps the count (`run_launch.census`, Postgres migration 0027 `run_launch_census`; SQLite adds the column when the server opens, and a runner waits for that server). A launch is marked "pending" when it first holds sealed secrets, including each one live at the upgrade, so an end by a runner from before this release (during a rolling deploy) leaves its files withheld, never read uncut. The runner makes the count just before the end's commit, bounded at 60 s; past that, or when it fails, the end writes "unscanned" and the run's files are withheld after it.
- A start's input (which the run's title is read from) and a message's text are cut of the keys handed with them when the server writes them, and a message's text of the keys the run holds too. Before, a key typed into the input was cut only while the run held it, and the run's title showed it raw after the end.
- A message that hands a new key mid-turn keeps the one it replaced sealed, only to be cut, until the turn's end erases both. Before, the replaced key was dropped from the cut at once, so the run's files and timeline showed it live, and the end's count missed it. A message that seals over secrets that don't open here (or past 256 replaced values in one turn) leaves the run withheld until its end.
