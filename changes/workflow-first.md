A learning agent now starts a run on its learned workflow before its own model takes a turn, when exactly one active learned workflow fits the run's input. A workflow fits when its input schema has a required field and the run's input passes that schema. If the workflow answers, its answer is the run's answer and the agent's model is never asked. For an agent with an output schema, the answer is shaped to it first: an object output as it is, a one-field output (a bare code or a line of text) as the schema's object with that field, fenced as the answer's json block so `result.output` meets the schema; an output that cannot meet the schema goes back to the agent with the schema's complaint. If it hands back (an `escalate` node holds, a node fails, or its output fails its schema), the same run goes on to the agent, whose first input says which step handed back and why, what the workflow had, and then the job. The run's `metrics` say which path it took: `path` is `workflow`, `handed_back` or `agent`, with `learned_revision`, `workflow` and `workflow_digest`. Its cost includes the workflow's model nodes. A handed-back run's end-of-run turn asks for the workflow's next revision by its name. The reflect prompt asks that a workflow take the run's input as the run is given it, and that its model nodes name tier `fast` unless a step needs the agent's own judgment.
A handback is an escalation, not a failure, and never stops a workflow from serving. One money rule does: a workflow runs first while its mean all-in cost over its last 10 runs served at its current version (its `workflow_digest`) stays under the agent's cost by hand, the mean all-in cost of the agent's `agent`-path runs (with none, of its runs before the workflow first ran). All-in is the run's `total_usd` on the cost page: its own cost plus every learning round booked for it (look-backs and grades). A run whose all-in cost is unknown is left out of the mean and counted (`unknown_cost_runs` on each workflow), never read as 0. Fewer than 10 such runs, or no by-hand cost at all (said in the log), and it serves. At or over the line it no longer runs first: the agent takes the run, the run's journal keeps why with the two numbers, its end-of-run turn asks for a new version of the workflow, and `GET /agents/{id}/learning/cost` lists it under `workflows` with `state: "needs_revision"` and both means (the console's Cost per run says so). A new version serves again from zero. The rule does not catch a workflow that answers wrong with confidence. The run's `metrics.path` is the one path the agent's cost per run (`GET /agents/{id}/learning/cost`) shows, including for a run whose agent called the learned workflow itself. `learned_workflow` set to ask still parks the run before any node runs. Set `workflow_first: false` on a run to send it to the agent from its first turn.
A follow-up to a run its workflow answered goes to the agent with the job, the workflow's answer and then the message, and the run's `path` becomes `handed_back`. A follow-up to a served or handed-back run looks back as a learning round of its own, as on any run that learns.
On pi, the learned workflow's first call counts toward the agent's `max_tool_calls` like any tool call the model makes, so a handed-back run never goes past its tool-call budget. A learned workflow with a name only a workflow may have (such as `sort_invoice`) gets its revision ask like any other.
