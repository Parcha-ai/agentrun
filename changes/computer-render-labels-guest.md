Render: releasing a computer no longer depends on its sandbox answering. When a server doesn't already know a sandbox's labels (after a restart, or in another process), it reads them from a file inside the sandbox, and that read is now held to the call's own time limit. For a read of one sandbox, a read that fails or gets no answer gives the two labels the sandbox's name carries, so release still finds and terminates a wedged sandbox instead of leaving it to bill until its timeout. A listing by a label beyond the name's reads at most 4 files at once, all within the listing's time limit. If any file can't be read by then, the listing fails with an error naming each such sandbox and why, because it can't tell whether that sandbox carries the labels asked. Before, every file was read at once, and the first failure failed the listing without waiting for the rest. A listing by name alone reads no file. A sandbox that Render still reads as running just after its terminate is no longer read through its guest, so release settles and a listing doesn't fail on it. The server forgets a sandbox's labels once Render reads it terminated or not found, or once a whole listing no longer shows it. Sandbox ids are sent encoded in paths instead of being held to the `sbx-…` form, so a sandbox whose id has a new form is still terminated. `prepareImage()` calls in one process that run at the same time for the same workspace share one import, even when they go through different providers (a server makes one per claim), and a build of the box image that is still pending or running is waited for instead of being imported again.
