An API-only server's token (`AGENTRUN_API_ONLY=1`) also saves a `per_run` MCP server (`PUT /settings/mcp-servers/{name}`; in 0.1.0-beta.55 the token had no generic save), which keeps no credential (each run hands its own), at an origin the operator lists in the new `AGENTRUN_MCP_TOKEN_ORIGINS`: comma-separated exact origins, each `https://host[:port]`, or one loopback origin (http on `127.0.0.1` or `[::1]`, with its port) that counts only with `AGENTRUN_MCP_ALLOW_LOOPBACK=1`. An entry with a path, query, fragment, user or wildcard stops the server's or runner's start, in words that name the entry by its place in the list and never echo it; unset, no origin is listed. An address at any other origin (a lookalike host, another port, a path that names a listed one) is `422 not_an_option` under `url`, naming no listed origin; any `auth.type` but `per_run`, or none, is `403`. The save's `toolkit` is recorded, so a template's need for that toolkit maps onto the server at an apply, and the token may delete the server. Each run's start (of an agentic agent or a workflow) checks the server's origin against the server's list again, and each run's claim against the runner's own: one no longer listed is refused by the server's name (`409 agent_not_runnable` at the start, before any run is made), and nothing is sent. `GET /capabilities` lists the variable under `switches`: the owner's session reads the origins as the server counts them, and any other caller, the token included, reads only whether it is set. Only a server the token saved on the API-only server is checked: one it saved while the server served the full API, or saved there again over one it had saved at a listed origin, is not: review or delete those before switching to API-only.

An owner's OAuth sign-in on a server the token saved makes it the owner's, as an owner's save does, so the token's save over it and its delete are `403`. A token's Composio save never uses an auth config a server the owner saved uses: naming one (`auth_config_id`) is `403`, and so is a save whose toolkit's own auth config, as Composio answers it, is that one, before anything is made at Composio; an `auth_config_id` Composio answers under another id (another letter case, say) is `422` under it. The token's Composio user has a namespace of its own: a save that is not `per_run` reaches Composio, and its server calls, as `agentrun.token.<user_id>` (no `user_id`: `agentrun.token.agentrun`), a user only the token's own connect link connects; its `user_id` is at most 113 characters. No save names a `user_id` starting `agentrun.token.`, the owner's included: `422` under `user_id`, before anything is sent. Nor does the token's save stand on an ACTIVE connected account it did not connect: each one Composio already has for that user under its auth config is `403` before anything is made, unless a server the token saved holds it as one it made (connected through the token's own link). A token server saved in 0.1.0-beta.56 keeps calling as its bare `user_id` until it is saved again: that save moves it to the namespaced user and returns a connect link to connect the account again, deletes at Composio the account its own link made under the bare user unless another saved server stands on it (which then owns it), and keeps an account it found there. Or delete it. A `per_run` server's runs still call as whatever user each run names. A token's save that names an auth config another server the token saved made uses it without taking over its removal: only that other server's delete removes it at Composio, or, while the token's new server still uses it, hands it to that server, whose own delete then removes it. Over a server the token saved, whose address reads show by its origin alone, the owner's sign-in, save and preview take its full URL: sending the shown address back is `422` under `url`, nothing is sent, and the owner's credential goes only to an address the owner named; the token's own save and preview still take the shown address. A refresh of a server's tools (`POST /settings/mcp-servers/{name}/refresh`) never writes back over a save that moved the server or changed its auth type while the refresh listed: it writes nothing and is `503`, to be read again and tried again. A save that kept the address and auth type (new prices, say) stands too, even one in the same millisecond as the refresh's read: the refresh keeps its listing on top of that save, with the save's prices, never the ones it read.
