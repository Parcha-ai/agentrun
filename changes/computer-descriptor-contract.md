---
packages: @parcha/agentrun-computer, @parcha/agentrun-serve, @parcha/pi-durable-agent
kind: breaking
---
Each computer provider is now declared once, in a descriptor (`defineProvider`: its id, label, keys and the option each fills, settings, mounts, configurations, default images, whether it prepares its image, runs on this host or takes a ledger, and a lazy `load()`), and the registry and the kind registry's `PROVIDERS` are derived from the descriptors. `ProviderId` is any string; the built-in ids are `BuiltinProviderId`. The server reads every provider from its descriptor and names none, and an agent's computer can name an image a provider's configurations offer.

Who breaks, and what to do:

- The package root no longer exports the provider classes or their option types. Import `DockerProvider`, `DaytonaProvider`, `ModalProvider`, `BrowserbaseProvider`, `KernelProvider` and their helpers from the provider's subpath (`@parcha/agentrun-computer/docker`, `/daytona`, `/modal`, `/e2b`, `/orgo`, `/orgo-desktop`, `/phone-harness`, `/browserbase`, `/kernel`), or build a provider by id with `providerFor(id, options)`. Their option types (`DockerProviderOptions`, `ModalSdk` and the like) come from the same subpaths. Each provider's default image (`DAYTONA_DEFAULT_SNAPSHOT`, `MODAL_DEFAULT_IMAGE`, `E2B_BASE_TEMPLATE`, `ORGO_BASE_IMAGE`, `PHONE_IMAGE`, `BROWSER_IMAGE` and so on) is its descriptor's, exported from the root and no longer from its provider module. `ProviderKey` is gone: use `DescriptorKey`.
- A vendor's own failure is now code `vendor`, with the provider's id in the error's `vendor` field, where it was code `docker`, `daytona`, `modal`, `e2b`, `orgo` or `phone`. Match on `code === "vendor"` and read `vendor`. Settings → Computers' test reads it as "<provider> answered with an error"; an old code has no words of its own.
- `ComputerSpec.lifetimeMs` is optional in the type: a run's computer still needs it (`checkTenure`, which replaces `checkLifetime` in a provider's `check()`, refuses a spec without it), and an agent's computer has none.
- A provider whose descriptor declares `prepareImage` has `prepareImage()`, the image a computer starts from, built or pulled (Docker's is its `image()`). The server calls it before the first create and refuses the computer in words when it is missing; nothing looks for an `image()` method instead.
- Orgo offers Linux desktops only: its Windows and macOS desktops are parked (the descriptor's new `parked` list). An agent whose computer names Orgo's `windows` or `macos` image is refused at its run's start in words saying the desktop is parked and naming the image Orgo offers, `linux`; Settings → Computers lists no Windows image. `create({ os: "windows" })` and `create({ os: "macos" })` still build their providers, for the conformance suite.
- Local Chrome, the keyless local browser that 0.1.0-beta.34 shipped as the provider `local`, is the provider `local-chrome` (its descriptor `descriptors/local-chrome.ts`; `LocalBrowserProvider` from `@parcha/agentrun-computer/local-chrome`, its provider id's subpath; `./local` is gone): an agent's computer names `{ kind: "browser", provider: "local-chrome" }`, and one saved as `provider: "local"` is refused at its run's start as a provider this server does not know: set it to `local-chrome`.
- A provider module no longer exports `NETWORK`: the networks a provider makes are its descriptor's `network` (`ORGO.network`, for one), which the kind registry's entry carries and of which each built provider's `capabilities().network` is its own configuration's. Its conformance names are `AGENTRUN_COMPUTER_LIVE_LOCAL_CHROME`, `COMPUTER_LOCAL_CHROME_PATH` and `COMPUTER_LOCAL_CHROME_HEADED`. A descriptor's `hostEnv` names the server's own environment variables its provider reads on this machine (Local Chrome's Chrome lookup), which the server passes as `options.env`.
- Orgo computers made by a release before this one are swept at the next janitor pass; release them before upgrading. An Orgo computer's deadline is the one in its name alone, never Orgo's own end (`ends_at`) or its labels file, so one whose name carries none is a run's computer with no deadline, which the janitor ends.

Persistent computers are in the provider contract: `capabilities().persistence`, `spec.owner` (`{ agent, idleTtlMs? }`, labelled `agentrun.owner=agent:<id>`), `release(ref, "detach")`, `attach(ref, { claim })` under a new claim epoch, and on `ComputerInfo` `owned`, `owner` and `detachedAt`. Every built-in provider refuses `spec.owner` and `detach` in words; none declares persistence yet. `sweep` never deletes an agent's computer by a deadline, only when `ownerGone(agent)` says so or after its owner's idle TTL; `releaseOlder` detaches an agent's computer instead of deleting it (`ReleasedOlder.detached`). Only a provider that declares persistence has agents' computers: of one that does not, an owner label a caller put on a run's spec keeps nothing from the janitor. The conformance suite adds `provider.owner` and `provider.detach` (Core) and `provider.persistence` (Full, where persistence is declared). Docker's inspect read-back moves to `src/docker/inspect.ts`, with the same exports.

A configuration (`KindCapabilities`) may name the `image` an agent's setting selects it by and the create() `options` that build it (`imagesOf`, `configurationOf`). An agent's computer may name one: `computer: { kind, provider, image }`, such as `{ kind: "desktop", provider: "orgo", image: "linux" }`. It selects the provider's configuration of that name, built by its options beside the keys' (Orgo's `os`); absent, the kind's default. GET /computers lists each provider's `images` for the kind, the default first. An image the provider does not offer saves with a warning naming the ones it does, and its runs are refused at their start in the same words.

The server reads what each provider takes from its descriptor: its saved keys fill the options the descriptor names, a setting it declares (Modal's `modalApp`) fills its option from the server's settings or its default, the store's session ledger goes to a provider that declares one, and the image and host options go to one that declares `prepareImage` or `local`. A provider added to the computer package needs no server edit; an id no descriptor declares is refused.

Orgo's Windows desktop (parked: built, not offered to an agent): `create({ os: "windows", apiKey, workspaceId })` (`@parcha/agentrun-computer/orgo-desktop`) gives a desktop with daemon `none` that answers the protocol over Orgo's REST API. The screen is Orgo's screenshot; the pointer and keys are its click, drag, scroll, type and key calls; exec is its bash call, PowerShell, and the files methods go through PowerShell too. A cwd or variable that cannot be set runs nothing, and a move with overwrite replaces what is at its target as rename(2) does. Settings → Computers asks for Orgo's workspace beside its key: `ORGO_WORKSPACE_ID` fills `workspaceId`, which every Orgo provider is built with. The network is `open`, since Orgo has no egress control. Orgo's descriptor offers one configuration, `linux` (the default), and parks `windows` and `macos`. Nothing runs in a computer Orgo does not read running. What Orgo's API cannot do (a triple click, a held key) is refused in words. A `down` and its `up` become one click or drag, and a cancelled batch lets go of its press. Each Orgo provider's list keeps to its own system's desktops (Orgo's listing names each one's os), so no janitor sweeps another's. The conformance suite skips, in words, a case written for another system (`Case.os`, `caseOs`): the Linux exec and process cases, and the files cases on Windows. Such a skip (`CaseResult.os`) is not this computer's to pass or fail, so it leaves Core's verdict as an undeclared group's does. With `COMPUTER_ORGO_OS=windows`, `--kind desktop` runs the desktop's cases against a Windows fixture this package carries, a PowerShell script.
