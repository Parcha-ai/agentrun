The local server reads and sends email through one account of the owner's (IMAP and SMTP with an app password), saved in Settings → Email and sealed like every other secret. The account is kept whole in one sealed row, written once, so a save that fails leaves the previous account, and nothing reads one account's servers with another's password.
- `GET`, `PUT` and `DELETE /v2/settings/email` keep the account (presets for Gmail, Fastmail and iCloud, or servers of your own; Outlook is refused in words: it needs a Microsoft sign-in this server does not do yet), and `POST /v2/settings/email/test` signs in to both servers without saving or sending anything. All four are the owner's session's alone.
- An email trigger, `{kind: "email", mailbox?: "INBOX", every_s?: 60, accept?}`, reads the mailbox on a clock and starts a run for each new message its `accept` takes, keyed by its Message-ID. It watches from the moment it is made, its mailbox or account is changed, or it is turned on again: mail from before then starts no run, and that is said; any other edit keeps its place. A mailbox it can't reach then still makes the trigger, which starts watching at the first check that signs in. Another account saved in place of the one it read, or a mailbox the server rebuilt, starts it over from then, and that is said. A message this server sent is left. A run an email started is handed no earlier run's answer, as each message is a different sender's (a schedule's runs still are). A run's input is the message's payload as whole JSON within 16 KiB: a longer text is cut, said to be cut and marked `text_truncated: true`. The trigger shows its last check, and turns itself off (`sign_in_refused`) after the mail server refuses the sign-in three times in a row.
- Five tools: `email_search`, `email_read`, `email_draft`, `email_send` and `email_file`. `email_send` asks a person by default, and its approval shows who it goes to and what it says; it answers `{sent, message_id, rejected?, note?}`, `rejected` listing the addresses the mail server refused (the rest got it, and nobody is sent to again). `email_read` with `thread: true` reads the thread's newest 20 messages at most, chosen by their headers before any body is fetched, and answers `truncated`, `more` and the earlier ones' ids (`omitted`) to read one at a time. `email_file` files a message under a Gmail label, where it stays in the inbox (`archive: true` takes it out), or, elsewhere, moves it out of the inbox to a folder in one call (an explicit `archive: false` is refused, as a move takes the message out of the inbox), making the label or folder if missing; its description says in one line which the saved account's server does; it answers `{filed, message_id, to, archived, subject, note?}`, the note on a move saying "moved out of the inbox to <folder>", and never deletes mail, so the trash and junk folders are refused. A run an email started reads and files only that email's thread unless the agent's `scope: "mailbox"` setting widens it, and of that thread only the messages its sender took part in (their address in From, To or Cc, as on the account's own mail to them): a Message-ID a sender writes in References, or reuses as their own, grants nothing alone: the thread is read from the message where the trigger found it, or, once it has moved, its copy from the same sender. On Gmail a thread is found by its messages' Message-ID and References; elsewhere by In-Reply-To too, with up to 5 minutes for the search, past which the tool says the server took too long. Every answer stays under the host's result bound.
- Each email call reads as one line on a run's timeline: `Searched mail for "quarterly report" from:ana@example.com unread`, `Read <subject>`, `Drafted a reply to <to>: <subject>`, `Sent an email to <to> and 2 more: <subject>` (with ` (refused: 1)` when the server refused one), `Filed <subject> under Receipts, out of the inbox`. No message body is in any of them.
- New dependencies of `@parcha/agentrun-serve`: `imapflow` (IMAP), `mailparser` (parsing a message) and `nodemailer` (composing one and sending it over SMTP). They load only when the account is tested, a trigger checks the mailbox or a run is given an email tool, never when the server starts.
