A learned workflow whose answer quotes the pages it fetched re-picks once on a quote miss before it hands back. The learning checks refuse a draft whose step writing the answer hands back on its first miss: that step must be the body of a `loop` with `maxIters` 2 whose `until` is `not` of the answer's `quote_missing` check (the same `path`, `field` and `pages`), followed by the `quote_missing` escalate. The check is a step of the top-level chain after the loop, never inside it: a draft with a `quote_missing` escalate in the loop's body is refused, since that escalate would hand back on the first miss. The step in the loop has no `state` map, so it reads the whole run state; a `state` map passes only the keys it names, so its second pass would never see the failed draft, and a draft with one there is refused. A first miss writes the answer once more with the failed draft in its state; a second miss hands back. A loop's `until` is one predicate, so the answer's quotes must have one check: a draft whose quotes need two different `quote_missing` checks (`quotes: string | [{quote}]`, or quotes in two places) is refused, the detail asking for one place one check reads. The compile prompt asks for the same loop and the same single place. On the H5d test, re-picking kept 26 of 31 misses at about half the cost of handing every miss to the agent.
  - A run's metrics carry `loops`: one row per loop exit of its learned workflows, `{node, iterations, met, workflow}`, so a re-pick (`iterations` 2) and whether its quotes were found (`met`) can be counted. Its model request is booked as any node's.
  - Upgrading: a learned workflow already merged keeps serving as it is; its next compiled revision must carry the re-pick loop to pass the checks.
