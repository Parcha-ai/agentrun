The Jev runner never sends a request over Jev's context (32k tokens for the state plus any one question, 64k for all of them; `JEV_CONTEXT_TOKENS`), which Jev refused whole with HTTP 400 `max_tokens_exceeded` and failed the workflow step. Measured by its UTF-8 bytes, which bound its text's tokens, plus a bound for every use of every image (`jevImageTokens`: a token per 14x14-pixel patch, since TypeSafe publishes no per-image figure), a request that may not fit goes whole with TypeSafe's `TypeSafe-Danger-Zone-Long-Context` header (262k tokens, same price; `longContext`, on by default on TypeSafe's route); one that may not fit that either, or the default on OpenRouter, has its longest state values cut, each ending ` [cut]` (`JEV_CUT_MARK`). Questions and images too long even then are refused before sending (`over_context`).
A decision receipt now holds the state its provider sent, not the one asked: a provider that cuts values returns `state_sent` (the state as sent, and each value cut with its JSON Pointer `path`, `bytes` and `sent_bytes`) on its `DecisionOutcome`, or `stateSent` on its `DecisionProviderError`, and the receipt's `state` is that state with `state_cut` naming the cuts. `state_sha256` stays the digest of the state asked, the request's identity.
Behaviour change: a judge request over the default context now runs in Jev's slower long-context mode instead of failing; pass `longContext: false` to cut to the default context instead.
