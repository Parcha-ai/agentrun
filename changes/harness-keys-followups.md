A saved harness key with no binding to any recipe file now says so: `reenter.why` is `not_bound`, not `recipe_changed`. That covers a key saved before keys were bound and one whose binding write was cut off. Upgrading from 0.1.0-beta.56 or earlier: every harness key saved then has read as not saved since 0.1.0-beta.57, the first release that binds keys (there as `recipe_changed`, now `not_bound`), and its runs have been refused since; paste each such key again on the Harness keys page. The Harness keys page says "Not tied to a recipe file" beside it. Such a key reads as not saved and no run gets it, so a scheduled or triggered run of that recipe is refused until each of its keys is pasted again on the Harness keys page; the old value stays sealed and cut until then. `GET /capabilities` with a bearer the server does not take still answers, with no kept ids, and now also writes an `auth_failed` line (`reason=wrong_token`) like every other route. A `DELETE` of a key the harness doesn't hold is refused with the keys it does hold ("acme's keys are ACME_API_KEY."), never "acme runs on …" for an id no recipe runs.
