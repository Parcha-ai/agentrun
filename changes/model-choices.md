A template package can offer up to three named model choices (`model.choices`), each a model on one of its harnesses with an optional warning and setup note, and the owner picks one at install. `POST /v2/templates/{id}/apply` takes `overrides.choice: <id>` and runs the agent on exactly that model and harness, or refuses: an unknown id, or a choice sent with `overrides.model`, is `422 overrides.choice`; a choice's missing key is `409 agent_not_runnable`, as a package's is; a model this server can't run on that harness is `409` naming the model, never the tier's model in its place. `GET /v2/templates` lists the choices under `model.choices`.
- A package's `model.prefer` follows the same rule: where this server can't run it on the chosen harness (no key for its provider, no catalog here lists it, or the harness does not run it), apply is `409 agent_not_runnable` under `model`, naming the model and the fix (save the provider's key in Settings → Model keys, or apply with `overrides.model` or a model choice), and makes nothing. It used to take the tier's model in its place without saying so (or, for an unlisted model, with only a warning). The bundled code-review package no longer has a `prefer`, which would have refused its install on a server with the ChatGPT sign-in and no OpenRouter key. It runs on the server's fast model, and `openrouter/particle-ai/particle-1` is now its model choice `particle`, "Particle 1 (OpenRouter)", whose note says it is the model the package was tuned and measured on, at about 18 cents a review. A server behind a gateway still skips `prefer` with a warning, as before.
- The console's install form shows one Model group when a package offers choices: its default first, then each choice by label, each warning and note shown word for word under it, and sends the pick as `overrides.choice`. A package with no choices shows no group.
