A map can collect its items' failures: `onItemFailure: "collect"` with `failedAs: "<key>"`. An item that ends on an item failure becomes a row `{ item_index, label, code, message }` of `failedAs`, in item order, the other items finish, and `as` stays aligned with the items: `as[i]` is item i's result, or `null` when item i failed. The default, `onItemFailure: "stop"`, is the behaviour before: the first failing item stops the map and the run. The map never escalates by itself; gate on `failedAs` with `escalate` or a code node.

- An item failure is one of the interpreter's own typed node failures (an `EffectFailure` after its retries, `WorkflowOutputInvalidError`, `WorkflowStateError`, `WorkflowCodeError`, `WorkflowVerificationError`) or a host error that declares itself one, with a string `code` and `itemFailure: true`. `isItemFailure(error)` is the rule, exported from `@parcha/agentrun-dsl`. Never collected: an effect whose outcome is unknown, any `RecoveryError`, an `escalate` inside the item, a stop or cancel, several failures at once, and anything else. Each collected row emits `map.item_failed` `{ item_index, label, code }`. When several branches of a parallel (or items of a map that stops) fail at once, the failure reported is the first one, unless that is an item failure and another is not: then it is the other, so an item failure never hides a failure a collecting map must stop on. A row's `label` is the node that failed: the innermost step, or a structural node (a nested map whose list is not one) when the failure is its own.
- The validator: `onItemFailure` is `stop` or `collect`; `failedAs` is required with `collect`, refused without it, may not begin with `$` and differs from `as`; parallel branches may not both write it. Each refusal is an issue at the map's pointer: a bad `onItemFailure`, a missing `failedAs` or one equal to `as` `NODE_FIELD_INVALID`, a `$` `failedAs` `STATE_KEY_RESERVED`, `failedAs` without `collect` `NODE_KEY_UNKNOWN` (a key of the other form), two branches writing it `PARALLEL_WRITE_CONFLICT`. The schema, the author contract and the guide say so.
- Recovery: `WorkflowDeps.recovery` gains `failItem` and `itemFailure`. A collected failure commits with its item before the map goes on, and every later process ends the item on it without running its body. A store without both hooks cannot hold a collecting map: it is refused before any step runs. The recovery driver keeps the row in its frame's `failures` (the whole layout) or the item's `agentrun.items` record (`status: "failed"`, `outcome`, in the keyed layout), and a step that failed on an item failure keeps it (`failure`), so a process that resumes between the step's commit and the item's ends the item the same way. An item whose call it left with an unknown outcome is refused as `FROZEN_EFFECT_UNKNOWN`, never collected.
- `@parcha/agentrun-pi`: `NodeFailure.itemFailure` is true when the node's delivery attempts are spent or its model will not answer (`model_error`, as a provider's content filter), never for an abort, a stale or faulted run, a missing model or a schema no record can satisfy.
- Deploy rule: run a collecting workflow only once every process that can open the run is on this release or later. A process on an earlier release refuses the workflow at validation, so its open fails its task, and that ends every agent node of the run then in flight. With the node runner's new attempt for a replaced task (which this release needs under it) those nodes start again from their beginning in new conversations, so the run still completes, but each such open costs those agent turns again: in the reference kill storm (30 kills a seed), 4.17 to 4.57 model requests per committed turn with old processes against 3.10 and 3.46 without (medians of two 50-seed storms), about 32% more.
