A Browserbase saved sign-in now waits one settle window after the session that saved to it ends, 10 seconds, everywhere: the next session of the same run that saves to it, the next run's save, and whether Settings shows it as held. Before, a second saving session in the same run could open on it after 5 seconds while the server still held it for 10, so it could open on a profile Browserbase was still writing back. The window is the Browserbase provider's own (`capabilities().browser.profiles.settleMs`), and the server reads it from the provider's descriptor rather than keeping a number of its own.

The server now creates and removes saved sign-ins through the browser provider itself, so those calls need the provider's own keys (Browserbase's project id too), and a missing key or a non-https base URL fails in the provider's words instead of a vendor 401 or "unreachable". A Browserbase connection behind `BROWSERBASE_CONNECT_BASE_URL` now goes through that gateway wherever it is opened, not only on the browser tool's attach. A provider descriptor gains an optional `profiles: { settleMs }` for a browser that keeps saved sign-ins; the sweep's usage text lists the providers the shared machine-host adapter takes from the registry. An attach conformance run against a driver on another protocol now reads "its driver speaks protocol X, and this server Y".
