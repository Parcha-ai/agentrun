A command a run's loop refuses after the runner's dispatch took it for now is now written refused, in the runner's process and in a run's own process alike. This covers a row that arrives before the run's harness loop is chosen, as the row that wakes or reopens a run does. Before, the refusal was dropped and the row stayed untaken, so the run was claimed again on every poll, for good. A raise the cap's rule refuses (a retry, or the second of two raises at once) did this to a run parked at its cap. A trigger's message refused in a session on its owner's sign-in did it to a run that ended or was stopped before its first input: each pass started the run's process, opened its secrets and its computer, and wrote a new end, so a `run.ended` webhook and a Slack notice went out on every poll. A refusal that cannot be written now leaves the row for the run's next claim, and is never handed to the loop again. A message that reopens a run in the moment after its end was written, before the runner had finished with that end, is no longer claimed, given back and claimed again: the runner holds the reopen's first claim, starts the run's next turn only once the claim before it has let go, and the end before it still says released. Where runs have users of their own, that turn's process no longer starts while the last one's slot is still reaped, which took back the run's folders and removed its TMPDIR under it.
