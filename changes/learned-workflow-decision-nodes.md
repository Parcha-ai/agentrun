A learned workflow can hold decision nodes (judge, pick, sift, a route by question, an ask predicate, a verify), under the run's spend cap. Each decision is admitted on the run's cap before it is sent, priced the way a workflow agent's decision is, and booked at what it charged. If the cap has no room, the decision is never sent: the run pauses at the cap, and the `learned_workflow` call says why. A decision node's provider (the one it names, else the default, `jev`) is checked against the run's tool settings: each provider is a settings key of its own (`jev`, `parallel`, `openrouter`), allow by default, allow or deny. Set to deny for the agent or on the server, the workflow is refused before any node runs, in the gate's words. A workflow agent's own decisions read no such setting. A decision's spend is in the run's cost (its row, its view, `/v2/usage`), beside its model requests and paid tool calls, and a decision of unknown cost leaves the run's unknown. The runner hands the run the keys of the providers its learned workflows name, so a decision node is answered by the run's decision provider under its cap. A denied provider refuses the workflow in the gate's words, and one the server has no key for refuses it as a provider this host does not have; either way nothing is sent. A decision node that sends images reads them from the run's work folder, as a workflow agent's does. A run's new workflow draft with a decision node is checked against the server's decision providers, so it is proposed and graded like any draft, and a retired one is restored the same way.
Upgrading: nothing to do. To keep an agent's learned workflows from asking a provider, set that provider's id (`jev`, `parallel`, `openrouter`) to deny in the agent's tool settings.
