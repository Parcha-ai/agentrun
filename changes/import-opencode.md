`@parcha/agentrun-import` reads OpenCode, its fourth source (`opencode`, run by serve's `opencode` harness). It reads every session in `$XDG_DATA_HOME/opencode` (`~/.local/share/opencode`): the `opencode*.db` databases (1.x and 2.x schemas), the one `OPENCODE_DB` names, and the JSON storage OpenCode kept before SQLite. SQLite goes through `node:sqlite` on Node and `bun:sqlite` under Bun.
- One locator per session: `{ file: <db>, id }`, or a storage session's JSON file. A session in several databases is listed once, from the one that wrote it last (its rows' latest `time_updated`; a tie, the first). A 2.x session wins over the 1.x copy beside it, and a 2.x fork's rows copied from its source count nothing.
- A 1.x fork's copies count once. OpenCode 1.x's `fork()` copies each message under a new id with its time, tokens and cost, and marks nothing, so the reader keys each request by a fingerprint (time, step, model, tokens and cost as written) and each prompt by its time and text, and passes over one the import has read. A 2.x row without a fork mark is keyed the same way. OpenCode's reader orders a home's sessions oldest first (`LocatorSize.created`, a reader's `order` takes an `OrderKey`), so a source is read before its forks. The cursor keeps its read's fingerprints (`owned`), so a session read again is no copy of itself. A prompt's fingerprint is its turn's `uuids` (serve's `record_uuids`). serve seeds the request and prompt fingerprints of the OpenCode runs in its store, so a fork imported after its source counts its own requests and prompts alone. The known-answer key of a database session is the sha256 of `<db path relative to the home>#<session id>`.
- The cursor holds the database's device and inode and a stamp of the session's rows. An unchanged session is not read again, a changed one is read again whole, and a replaced database is read from its start. A turns: false cursor (parseHome's state) holds no prompt, title or working directory, as a line source's does, so a read resumed from it gives none.
- Each step of an OpenCode message is one request, at its `step-finish` usage. `normalizeUsage("opencode", …)` adds the reasoning to `output` and keeps it as `reasoning`. OpenCode wrote the reasoning into `output` until 1.3.16 (anomalyco/opencode#21047), so `normalizeUsage(format, raw, { version })` keeps the output as written for a session whose `version` is older; the options are optional, and no version reads as today's. Where a step records `total`, the total says it whatever the version.
- A request OpenCode ran on its claude-agent provider names the Claude Code session that also holds it (`mirrors`, per request and per session). When `parseHome` reads that Claude Code session in the same call, the request counts there and not again in OpenCode's totals (tokens, calls, cost). Otherwise it counts in OpenCode's.
- `parseHome` adds a subagent's own written cost to its parent's for every source except Claude Code, whose `cost-state` already holds it. OpenCode's subagents are sessions of their own.
- A reader may give `stat(locator)`: the session's own size and last write. OpenCode's is the session's rows' (their `data` bytes, their latest `time_updated`), not its database's. `locatorSize` exports it, falling back to the file's, and `inOrder` returns it with each locator.
- The mirror rule is one export, `mirroredIn` with `sessionKey` and `ownRequests`, which `parseHome` and serve both use.
- serve's import goes by each session's own size and last write: the 10-minute "still being written" check, the per-session cap and the run's 256 MiB budget. One live OpenCode session leaves the rest of its database importable, and a database over the budget imports every session that fits.
- serve's import holds back an OpenCode run whose request ran through a Claude Code session that is on disk and not imported now (still written, held back with a live subagent, in a project not chosen, or of a source this import does not read: with `--from opencode` alone it lists Claude Code's sessions to know), said under a new left-out kind, `mirror`. It comes in with that session, so the request counts once in either order. A session no import brings in as it is (over the cap, unreadable, a temp or gone folder, none of the person's messages) does not hold it.
- serve's import counts a mirrored request once: when the Claude Code session it mirrors is already in the store, or this import saved it, the OpenCode run's metrics, cost and estimate leave it out. The import writes Claude Code's runs first, so the session a request mirrors (an OpenCode run's own or a subagent's at any depth) is saved before the run that leaves it the request. Every other source's runs follow in their own order, so an OpenCode session comes before its later forks and keeps the records they copied, its subagents read with it. One that is not saved (unreadable, too large, a stop before it) leaves the request in the OpenCode run. The turn stays in the OpenCode transcript either way. When it counts elsewhere, its answer carries `data.mirrors`, and the timeline shows it and counts no request. A Claude Code session imported later cannot reach back into the OpenCode run, so that run waits for it (above).
- A `turns: false` read of OpenCode keeps no answer text, in its requests or its cursor, as the other readers do. A request's error reads as `failed` (`FAILED`), never the provider's message.
- A time OpenCode wrote past now (a clock set ahead, or past what a Date holds) reads as its database's last write (its file's or its `-wal`'s, never past now), in a session's times and its `stat`. That is the same at each look, so the session ages out of the 10-minute "still being written" window as its database does, and never holds back its parent run for ever.
- OpenCode's databases are opened read-only with a 5 s busy timeout, so a read waits out OpenCode's write lock instead of failing. A database OpenCode has closed (no `-wal`, no `-shm` beside it) is opened `immutable`, as a read-only open of a WAL database would create both in OpenCode's folder and leave them there, owned by whoever read. A read that finds OpenCode opened or wrote the database meanwhile (its `-wal` or `-shm` there after, or the file's size, time or inode changed) fails, and the next import reads it again. A read adds its fingerprints to `seen` only once it ends clean, so one that fails partway takes none of its records from a later fork. With either file there, OpenCode has it open and it is opened as before, its `-wal` rows read.
- The JSON storage is read by its own files' names: a session's messages under `message/<its file's name>`, a message's parts under `part/<its file's name>`. Never by an id a file holds, and never through a linked folder. A session whose id is not an OpenCode id (`[A-Za-z0-9_-]`) is passed over.
- A session OpenCode is still running is live (its `stat` says written now), whatever its rows' times say: a 2.x session whose `time_busy` is after its `time_idle`, and a 1.x or storage session whose last message is a request not completed or has a tool part pending or running. A request its error ended (failed, or aborted: stopped, as its read says) has ended, completed or not. One parked on a permission prompt past 10 minutes is not imported as finished.
- An OpenCode database that cannot be listed (not a database, unreadable) is a locator of its own, whose read fails: `parseHome` hands it back among its `failures` and the known-answer CLI exits 1, never an OpenCode history of no sessions. A storage session is told from a database by its name (`.json`), never by reading the file's header. A storage session whose file or folder cannot be read (no access, an I/O error) fails its read whole, never read as fewer messages. A record that is gone mid-read, or is malformed JSON, is passed over.
- A session whose own size cannot be had (its database locked or damaged since it was listed) is no longer dropped from `inOrder`. It is kept, marked `failed`. `parseHome` reads it, and a read that fails too lands among its `failures`. serve's plan leaves it out as `unread`, said. Only a session that is gone (its reader's `stat` says none, or its file is missing) is passed over.
- The store's SQL guard (`scripts/store-sql-guard.test.mjs`) allows SQL outside the store in one named file, the OpenCode reader. It reads OpenCode's own database, not agentrun's. The guard holds it to SELECT statements (and its busy timeout) only and to read-only opens: `bun:sqlite`'s `{ readonly: true }`, or SQLite's read-only and URI flags alone, for the `immutable` URI. The guard also finds a driver module named through a const (`const NODE_SQLITE = "node:sqlite"; await import(NODE_SQLITE)`) and counts `bun:sqlite` as a driver.
- serve finds each source's folders where its environment puts them (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, OpenCode's `XDG_DATA_HOME` and `OPENCODE_DB`), as `parseHome` does.
- An imported run's cost holds its subagents' costs where the source writes them on the subagent's session (every source but Claude Code, whose cost already holds them): `withSubagentCosts`, which `parseHome` uses too. One unknown makes the run's unknown.
- serve's import brings a run in only when every subagent it has, at any depth, can be read now. The plan walks the import's children relation (Claude Code's subagent files, Codex child threads, OpenCode child sessions). If any one is still being written or is over the cap, the run is left out with it, said as `live` (or `large`), and it comes in whole later. A live subagent's listing ties it to its run. One over the cap is not read, so it is tied by `locatorParent`: the parent its reader's `stat` names (OpenCode's), else its reader's `parentOf`, a bounded head read (Codex's: a rollout's first line, `session_meta`, read 256 KiB at a time up to 64 MiB, so a long `session_meta` still names its parent).
- serve imports OpenCode runs under an `opencode` revision whose instructions are the project's AGENTS.md, else its CLAUDE.md. The project's `.opencode/skills` and `.opencode/skill` folders, where OpenCode reads a project's skills, are among its skill folders. A home's global skills (`~/.config/opencode/skill(s)`, `OPENCODE_CONFIG_DIR`) are not imported, as no harness's are.
- serve: the `imported_from.source` and `by_source` enums and `ImportSource` include `opencode`, and `agentrun-serve import --from` takes it.
