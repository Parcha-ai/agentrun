An image's or audio's data or a resource's blob that an MCP answer files whole is now `[redacted]` when the text in the bytes it decodes to carries a secret's shape, such as a JWT or a private key block, even if the run holds no such value. Before, such a payload was cut only for values the run's redactor holds, so an unheld token or key in a file a server returned was filed as it came. The base64 text itself is not read for a shape, since a key's shape turns up there by chance in large images. The decoded bytes are read only through their runs of text, for shapes and held values alike: 8 or more printable characters, read past the bytes the redactor reads as nothing or as a blank (a NUL, a control character, a soft hyphen, a no-break space), so a value written as UTF-16 or UTF-32, or cut into short pieces by such a byte, is still found. Checking a 4 MiB image of random bytes takes about two seconds instead of close to two minutes; a payload whose bytes are all text costs what it did before. A claim's MCP now refuses to start without the run's held redactor, before it reads a credential or mints a GitHub token, and the MCP gateway refuses to start without a redactor. Before, the gateway fell back to cutting only the server's own credentials.
