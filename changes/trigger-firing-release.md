A launch hook's host can now release a firing it answered 2xx but will start no run for, for example because its own job failed before any run started: `POST /v2/triggers/{trigger_id}/firings/{firing_id}/release` with `{ "error": "<plain words>" }`. The firing fails at once with the code `host_released` and the host's words, and frees its trigger's place under `max_active_runs` instead of holding it for 10 minutes; a trigger.failed message goes out and the failure counts toward auto-pause. A refusal is 422 `input_invalid` with reason `not_due`, and `details: { "reason": "run_started", "run_id": "<run>" }` when the firing's run started; a host start after the release is refused with `details: { "reason": "host_released" }`. A release that lands during the engine's turn on the firing (its hook call still open, or the hook's answer not yet recorded) waits for that turn to end, up to the hook's 10 s timeout and longer behind queued firings of the same trigger, so give the call a client timeout above 10 s and send it after answering the hook. After a transport error, send it again (a firing already released answers 200 with it, unchanged) or read the firing in the trigger's firings. The API-only profile serves the route. The CLI has `agentrun triggers release-firing`, and the TypeScript and Python clients have `triggers.releaseFiring` / `triggers.release_firing`.
