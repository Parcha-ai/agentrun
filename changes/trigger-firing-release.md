A launch hook's host can now release a firing it answered 2xx but will start no run for, for example because its own job failed before any run started: `POST /v2/triggers/{trigger_id}/firings/{firing_id}/release` with `{ "error": "<plain words>" }`. Before, the firing stayed `sent` and held its trigger's place under `max_active_runs` until its `start_by`, 10 minutes later, so the next firings waited all that time. Now the firing is `failed` at once with the code `host_released` and the host's words, cut of the server's secrets. Its trigger's place frees right away, so a firing waiting on it starts on the engine's next tick. A trigger.failed message goes out, and the failure counts toward the trigger's auto-pause like any other failed firing. Every 2xx the hook gets resets the trigger's failures in a row, and a firing is released only after its own 2xx, so releases turn a trigger off only when five land with no 2xx between them, for example five firings handed at once and all released. Sending the same release again answers the firing unchanged. A release that lands while the server is still recording the hook's answer waits for that write, up to the hook's 10 s timeout and longer while earlier firings of the same trigger are queued, and two releases during one wait both get the same 200. Give the call a client timeout above 10 s, and send it after answering the hook, not from inside the hook's handler. Refusals are 422 `input_invalid`, not retryable, with the case in the field's reason. A firing whose run started, or one still not handed to the host once that wait ends (the hook answered non-2xx or did not answer in time), has field `firing_id` with reason `not_due`; when its run started, the error also carries `details: { "reason": "run_started", "run_id": "<run>" }`. The release and the host's `trigger_firing` start are one conditional write on the firing, even across servers sharing a store, so exactly one of them wins. A start after the release is refused with field `trigger_firing.firing_id` and reason `not_due`, in words that name the release and give the host's, with `details: { "reason": "host_released" }`, and no run is left. A server with no launch hook answers with field `firing_id` and reason `not_allowed`. The error codes are a closed list every client carries, so this adds none: a client matches `details.reason`. The API-only profile serves the route, so the hosted backend's token can call it. The CLI has `agentrun triggers release-firing`, and the TypeScript and Python clients have `triggers.releaseFiring` / `triggers.release_firing`.
