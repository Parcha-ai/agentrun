A launch hook's host can now release a firing it answered 2xx but will start no run for, for example because its own job failed before any run started: `POST /v2/triggers/{trigger_id}/firings/{firing_id}/release` with `{ "error": "<plain words>" }`. Before, the firing stayed `sent` and held its trigger's place under `max_active_runs` until its `start_by`, 10 minutes later, so the next firings waited all that time. Now the firing is `failed` at once with the code `host_released` and the host's words, cut of the server's secrets. Its trigger's place frees right away, so a firing waiting on it starts on the engine's next tick. A trigger.failed message goes out, and the failure counts toward the trigger's auto-pause like any other failed firing. Sending the same release again answers the firing unchanged. A firing whose run started, or one not yet handed to the host, is refused with 422 `not_due`; when its run started, the field carries `code: "run_started"` so a host can match it without reading the words. The release and the host's `trigger_firing` start are one conditional write on the firing, even across servers sharing a store, so exactly one of them wins: a start after the release is refused with 422 `not_due` and `code: "host_released"`, and no run is left. A server with no launch hook answers 422 `not_allowed`. The API-only profile serves the route, so the hosted backend's token can call it. The CLI has `agentrun triggers release-firing`, and the TypeScript and Python clients have `triggers.releaseFiring` / `triggers.release_firing`.
