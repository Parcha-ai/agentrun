A run whose follow-up turn ends without showing an answer now ends completed, its answer the earlier one. The Claude CLI's `/compact` is one such turn: a summary request and no text. Before, the run sat `working`/`idle` until another message came, because serve ended a run only when its newest row was an answer. Now the person's newest message also ends the run once the turn is over and, in the run's entries, an answer that ended its request (`stop`) follows that message. That follows from the entries' own order, never from when the door said idle. A follow-up placed while a turn works comes after that turn's answer, so it is still waited for, on every harness. A claude-agent or codex run whose process died after such a turn's last writes, before the turn's end was written, ends the same way once its next process opens: that process writes the missing end when the session holds the turn as over. When a message the person sent meanwhile is still waiting, that process starts the message's turn first and writes the missing end inside it, so the run completes only once that message is answered, also when the server restarted with it. A message accepted and not sent yet keeps the run open on any server, also when its process died just after the turn before it ended. A follow-up whose answer stops at its length (max output tokens) is the run's answer, as its timeline shows it.
