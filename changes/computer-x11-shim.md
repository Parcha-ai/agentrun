computerd drives an X display: `screen.shot`, `screen.read` and `input.actions` on the display `DISPLAY` names, in pure Go with no cgo (GetImage for pixels, XTEST for input), and `deadline.extend`. A Docker computer can be a desktop.
- Hello declares `screen`, `input.pointer` and `input.keys`, and kind `desktop`, only while the display answers with XTEST; with none, nothing is declared and each method is `unsupported`, saying why. `input.actions` checks the whole batch first, as `checkActions` does, and also refuses touch actions and pixel scrolls (`unsupported`), points and clicks that are not whole, and text with a control character other than newline and tab; then it runs until the first failure, releasing what the batch held. It waits for the server after each action with a button, a key or a keyboard map change, so an X error stops the batch before its next action and `done` and `failed` say what ran; a cancel stops it at the next key, click or point and answers `aborted`. `type` gives exactly its text with Caps Lock on: it is turned off for the typing and back on after. Characters with no key on the keyboard map are typed through xdotool's keysym remap, which keeps its bindings instead of undoing them; a keycode another program rebinds afterwards is that program's, never moved again, and with no other keycode free the `type` is refused as `limit`. Only a display in this computer is driven (the unix socket, or TCP to a loopback address); any other `DISPLAY` is refused before anything is sent, so this host's X cookie never goes to another server. Neither the X server nor the Xauthority file is trusted: the cookie is read only from a regular file of at most 64 KiB (a symbolic link, a FIFO or a device there is refused in words, unread), a setup with a scanline pad other than 8, 16 or 32 or keycodes that are not a range from 8 up is refused, and each reply is bounded by what its request can get back before anything is allocated for it; a server that sends more errors than the requests it could refuse is disconnected in words, and at most 64 errors are kept for a batch to report. A `screen.shot` or `input.actions` waiting for the display waits no longer than its own request.
- `computerd init --deadline <time> --max-deadline <time>`: `deadline.extend({ at })` moves init's deadline up to the maximum, refusing an earlier time or one past it in words; without `--max-deadline` the deadline cannot move. Once init has decided to end the computer (its deadline came, or SIGTERM), every `deadline.extend` is refused in words (`unsupported`), never answered with a deadline init does not keep. Docker passes none: its deadline is a label.
- `new DockerProvider({ daemonPath, desktop: {} })` makes kind `desktop` computers on an image with an X server: `create` gives the daemon `DISPLAY` and starts Xvfb through `process.start`, so computerd stays PID 1 and starts nothing itself. `desktop.timeoutMs` bounds every call to the daemon from starting the X server on: a daemon that stops answering fails `create` as `timeout`. `dockerConformance({ desktop })` runs the suite on one; with `test/fixtures/desktop/Dockerfile` (Alpine and Xvfb) and `computerd-fixture` (`daemon/cmd/fixture`, test-only) Core passes 58/58.
