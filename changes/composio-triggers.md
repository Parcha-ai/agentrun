Composio triggers are set up from here, with the key a saved Composio server already holds: "when this happens in that app, run this agent", with no curl and no secret to copy. A trigger of the new source kind `composio` names a saved Composio server, one of its toolkit's events and that event's config (GitHub's new-issue event: `{owner, repo}`), with an optional filter, an agent, what each run is asked and a cap.
- `GET /v2/settings/mcp-servers/{name}/composio/events` lists the server's toolkit's events: each one's slug, name, description, the JSON schema of its config with the required fields, and whether Composio polls for it.
- Making the trigger makes, in order, the Composio project's one webhook subscription at this server's address (`/v2/hooks/composio/{hook}`; its secret is sealed here and never answered or logged) when there is none, then the event's trigger instance for the account the server is connected as, then the trigger, and undoes what it made when a later step fails. A second trigger reuses the subscription. The answer's `source` names what was made (`instance_id`, `hook`).
- A delivery is checked once with the subscription's secret and starts each trigger whose instance it names (Composio's `metadata.trigger_id`) and whose filter takes it, so two triggers on two repositories never cross. A filter's conditions read the delivery, the event's data under `/data/`.
- Refused before anything is left on Composio: no public address (`409 composio_no_public_url`, before Composio is asked anything); a subscription at another address (`409 composio_subscription_elsewhere`, naming it, unless the create says `move_subscription: true`); an account not connected (`409 composio_not_connected`, with Composio's link to connect it); an event or config Composio refuses (422, under `source.event` or `source.config`).
- Pausing, resuming and deleting follow on Composio once the change holds here. Triggers with the same server, event and config share Composio's one instance: it is turned off only when every one of them is off, and deleted with the last. What Composio could not do is answered beside the change (`composio: {done: false, note}`; a delete answers `200 {deleted: true, composio}` then, else 204) with what to do in Composio's dashboard.
- A saved server that Composio triggers still use can't be deleted (`409 composio_in_use`, naming them). `GET .../composio/triggers` lists its triggers with their state at Composio and whether the subscription is this server's; `POST .../composio/rotate-secret` rotates the subscription's secret and keeps the new one; `DELETE .../composio/subscription` deletes the subscription once no trigger uses it.
- Webhook triggers made the old way (Composio's signature on a plain webhook trigger) work as before.
- The console makes one: Triggers → New app trigger picks a saved Composio server, one of its events (with its description; a polled one says Composio checks for it every few minutes) and the event's config, each field read from the event's schema with the required ones marked, then an optional filter on the event's data. A subscription at another address is named, and moved here only once the person picks Move it here; an account not connected is said with the link to connect it. A trigger's page shows its app, event, config and filter, and whether Composio still has its instance, and says what Composio could not follow of a pause or a delete. Settings → MCP servers lists a Composio server's triggers with their state at Composio and where the project's subscription sends its events, with Rotate secret.
