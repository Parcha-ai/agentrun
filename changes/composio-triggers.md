Composio triggers are set up from here, with the key a saved Composio server already holds: "when this happens in that app, run this agent", with no curl and no secret to copy. A trigger of the new source kind `composio` names a saved Composio server, one of its toolkit's events and that event's config (GitHub's new-issue event: `{owner, repo}`), with an optional filter, an agent, what each run is asked and a cap.
- `GET /v2/settings/mcp-servers/{name}/composio/events` lists the server's toolkit's events: each one's slug, name, description, the JSON schema of its config with the required fields, and whether Composio polls for it.
- Making the trigger makes, in order, the Composio project's one webhook subscription at this server's address (`/v2/hooks/composio/{hook}`; its secret is sealed here and never answered or logged) when there is none, then the event's trigger instance for the account the server is connected as, then the trigger, and undoes what it made when a later step fails (a subscription whose secret can't be kept here included). A second trigger reuses the subscription. Creates, pauses, deletes, a secret's rotation and the subscription's delete on one Composio project run one at a time, so a failed create undoes only what no other trigger holds by then, the subscription is never deleted under a create still making its instance, and a rotated secret is never overwritten by an older read. The answer's `source` names what was made (`instance_id`, `hook`).
- A delivery is checked once with the subscription's secret and starts each trigger whose instance it names (Composio's `metadata.trigger_id`) and whose filter takes it, so two triggers on two repositories never cross. A filter's conditions read the delivery, the event's data under `/data/`.
- Refused before anything is left on Composio: no public address (`409 composio_no_public_url`, before Composio is asked anything); a subscription at another address (`409 composio_subscription_elsewhere`, naming it, unless the create says `move_subscription: true`); an account not connected (`409 composio_not_connected`, with Composio's link to connect it); several connected accounts for the toolkit (`409 composio_account_ambiguous`, naming each with when it was connected: a trigger runs as one account, so disconnect the others in Composio, and none is picked for you); an event or config Composio refuses (422, under `source.event` or `source.config`).
- Pausing, resuming and deleting follow on Composio once the change holds here. Triggers with the same server, event and config share Composio's one instance: it is turned off only when every one of them is off, set from the triggers as they stand when Composio is asked, so a pause that reaches Composio after a later resume leaves it on (deleting the last one on, while paused ones still hold it, turns it off), and deleted with the last. A server's trigger list reads every page of Composio's instances; a trigger whose instance Composio didn't answer for reads `unknown`, never `missing`. What Composio could not do is answered beside the change (`composio: {done: false, note}`; a delete answers `200 {deleted: true, composio}` then, else 204) with what to do in Composio's dashboard. When the server turns a trigger off itself (its agent archived, five failures in a row, its connection or run gone), its instance is turned off on Composio the same way; what Composio could not do is logged with what to turn off by hand.
- A saved server that Composio triggers still use can't be deleted (`409 composio_in_use`, naming them). `GET .../composio/triggers` lists its triggers with their state at Composio and whether the subscription is this server's; `POST .../composio/rotate-secret` rotates the subscription's secret and keeps the new one; `DELETE .../composio/subscription` deletes the subscription once no trigger uses it.
- A template can't carry what this server sets on a composio trigger (`instance_id`, `hook`, `move_subscription`): reading such a package is refused, saying to leave them out or make the trigger from the console.
- Webhook triggers made the old way (Composio's signature on a plain webhook trigger) work as before.
- The console makes one: Triggers → New app trigger (its button: Create app trigger) picks a saved Composio server, one of its events (with its description; a polled one says Composio checks for it every few minutes) and the event's config, each field read from the event's schema with the required ones marked, then an optional filter on the event's data. A subscription at another address is named, and moved here only once the person picks Move it here, which sends the create that was refused; an edit to the form first withdraws the question; an account not connected is said with the link to connect it. A trigger's page shows its app, event, config and filter, and whether Composio still has its instance, and says what Composio could not follow of a pause or a delete. Edit filter changes only what you edit: a rule or condition you leave alone goes back exactly as it was, and a save with no change sends nothing. Settings → MCP servers lists a Composio server's triggers with their state at Composio and where the project's subscription sends its events, with Rotate secret.
