A tool with a `file` setting now files more of what its server sends, and its summary says more about errors without showing their words.
- A protocol-level error is filed like any other answer. This covers a JSON-RPC error, or an HTTP error the client throws. The tool's result is the same summary with `isError: true`. Before, the result showed the first 300 characters of the server's message.
- An error answer's summary ends with one more line, built from the error's structure and never from its words. The line gives the HTTP status, the JSON-RPC code, and when to retry. The retry time comes from a `retry_after`, `retryAfter`, `retry_after_seconds`, `retry_after_ms` or `retryAfterMs` field of a JSON error (at its top, in its `error` or `data`, or in a JSON-RPC error's `data`), or from the Retry-After header, which wins when both are given. An error answer (`isError: true`) arrives over HTTP 200, so its line names no status, but it still takes the Retry-After of the response that carried it. The status and the Retry-After are the call's own response's, also when other calls to the same server run at the same time. A 429 or 503 with no retry time says to retry later. When the error has none of these, as with a plain-text error, the line says `Error: no status or retry time given.`
- The tool gate now keeps the agent's own file tools, `web_save` and `browser_upload` out of the folder. 0.1.0-beta.60's notes said the model's own `read`, `grep`, `ls` and `bash` could still open it. Now the gate refuses a call whose path is in a folder one of the agent's `file` settings names, or under it, for these tools: the agent's own `read`, `write` and `edit` (claude-agent's `Read`, `Write` and `Edit` too, a computer script's file ops, and a screenshot's `save_as`), `web_save` (where it saves) and `browser_upload`. The error names the setting. The check reads the path as given and as pi's file tools take it, with one leading `@` dropped, so `@stripe/pages/a.json` is refused. It resolves `./` and `..` against every name the run's file tools take for its folder: its full path, a computer's `/workspace`, and a CLI harness's working folder. It compares each segment as a disk that folds names would, so on a local macOS run `Stripe/Pages/a.json`, a fullwidth spelling, or one with a zero-width or other ignorable character is refused too. It reads no file, so it doesn't follow links.
- On a computer that mounts the run's folder, while a folder is filed, a script's file ops (`files.read`, `files.list`, `files.write` and `files.stat`) must name a path inside `/workspace`. Any other path is refused, with an error saying a run with a filed folder keeps a script's file ops in `/workspace`. The computer reaches the folder by names no check of the words can follow, such as `/proc/self/root/workspace/...`, `/proc/self/cwd/...` and `/dev/fd/3/...`, so a list of bad paths can't hold. The cost: while a folder is filed, a script's file ops can't read or write the rest of the computer's disk, such as its `Downloads` folder. A computer that doesn't mount the run's folder, and a run with no filed folder, are unchanged. Opening the file on the computer beneath `/workspace` with links refused (`openat2` with `RESOLVE_BENEATH` and `RESOLVE_NO_MAGICLINKS`) is a follow-up.
- Outside the gate: a tool not on that list, such as `browser_downloads`, which writes into `downloads/`; the computer's screen (input on a terminal app or a file manager, and `apps.open` with a path or a `file://` URL); a link already inside `/workspace`, which a script's file op follows; and a harness's own file reads that never ask the host, such as Cursor's. What still holds from beta.60: `bash`, on the runner or a computer, is not gated by path, so a command, a link it makes, or any program the run starts can still open the folder. Only `bash` set to `deny` stops this: a script's `shell.run` and `processes.start` follow bash's setting, not whether `bash` is among the agent's tools. A template that must keep the model off the answers sets `bash` to `deny`, and gives the run no desktop or sets the desktop kind to `deny`, or runs its skill's code where the model can't read the output. A desktop whose model is handed no screen tools (`surface: code`) still gives its scripts `apps.open` and input ops.
- The shape names a key only when it reads as a plain name: lowercase words joined by `_` (`has_more`), or camelCase (`pageInfo`), with any leading `_`, at most 32 characters. Keys with digits or capitals after a prefix (`cus_NffrFeUfNV2Hib`, `txn_1Q0001`) and all-capitals keys are counted instead. A key that is data but looks like a plain word, such as a username like `marisol_q`, is still named.

Upgrading: a runner from 0.1.0-beta.60 up to the release before this one still files a filed tool's answers, but it shows a protocol error's first 300 characters to the model, its error answers' summaries have no status or retry line, and it doesn't refuse the agent's `read`, `write`, `edit`, `web_save` or `browser_upload` in the folder, or a script's file op outside `/workspace`. It raises no error or warning about any of these, so update every runner that can claim the runs of an agent with a `file` setting to this release. What beta.60's notes say of runners from before `file` still holds.
