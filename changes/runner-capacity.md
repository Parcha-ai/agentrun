`GET /v2/capacity` (`capacity/1`) says how much room the runners have, read from the store alone, so a server with no runner beside it (`--no-runner`, `AGENTRUN_API_ONLY=1`, where it is served too) answers for every runner on its store. It gives the runs waiting for a runner (`runs.queued`: queued, handed back, or with a claim that ran out, past any backoff) and the runs a live claim holds (`runs.executing`). It lists each live runner by name with its build's `version`, its `slots` (the most runs it holds at once), what it holds (`executing`) and its `free_slots`, plus the total `free_slots`. It counts the runs handed back still running within `?window=` minutes (`hand_backs`: 1 to 1440, default 15). It names no run, agent or address, and it takes the server's token like every route but capabilities and health. An operator or a scaler reads it to size the runners by backlog, not CPU.
Each runner's row now says its version and slots (`runners.version`, `runners.slots`), and every release that leaves its run running writes a row to a new `hand_backs` table, kept for a day. Postgres migration `0024_runner_capacity.sql` adds both, and a SQLite store gets them at the server's open. Both are additive: a runner of an earlier build keeps working, with its version and slots read as null, and a runner of this build waits on SQLite for a server that added them.
A runner prints metric lines in the server's log format (`at=… event=… key=value`), so a log-based metric can count them: `runner_claimed`, with `took_over=1` when it took over a run whose lease ran out; `runner_hand_back` with a `cause` (`drain`, `interrupted`, `end_retry`, `give_back`, or `claim_lost` with its `why`); `runner_drained` (`ms`, `held`, `left`), once per close that held a run; and `runner_gauge` every minute (`active`, `slots`, `rss_mib`). The existing `Runner … claimed` and `ready` lines are unchanged. A runner beside a server prints the same lines where the server prints its own.
