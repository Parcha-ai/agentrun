The `code-review` template is 0.3.0: eight independent reviewers read the pull request on a read-only checkout, and the agent merges, verifies and posts what they find. Its answer ranks each finding `P0`, `P1` or `P2` and scores the change's risk from 1 (safe to merge) to 5 (do not merge). The manifest asks for `checkout: pull_request` (AgentRun fetches the PR into `repo/` before the first turn, with refs `pr/head`, `pr/base` and `pr/merge-base`), `computer: [shell, none]`, `tools: [read, bash, subagent]` with `tool_policy: { bash: read-only }`, thinking `medium` (was `low`), and `budget: { per_run_usd: 0.50, tool_calls: 90 }` (was $2.00 a run). Where there is no shell, the agent is made with no computer and without bash, the apply says so, and its reviewers read the change through the GitHub MCP tools. A reader of its findings JSON changes: `severity` (`important`, `nit`, `pre-existing`) is gone, replaced by `priority` and a `pre_existing` flag; `claim` is `failure`, which ends with `Evidence: path:line "text"`, a line a command in the run printed; each finding has a `title`; the answer adds `risk_score`, `risk_reasons`, a `coverage` line per reviewed file and the `dropped` candidates with their reason (free text; `limit` past the cap of 8 merged findings, `unverified` when a printed line contradicts one).
- One `subagent` turn starts five quick reviewers (`REVIEWER.md`, thinking `medium`, 30 tool calls each) and three deep ones (`DEEP.md`, thinking `high`, 90 tool calls each), all on the agent's own model with a fresh context. A deep reviewer maps the change first (each changed file, its callers, its tests and its history before the PR), then writes one line per hunk naming the input it tried and where it breaks or holds. The agent merges findings at the same path, within 10 lines and with the same failure, prints each kept finding's cited lines to check them, ranks by priority and by how many reviewers raised it, and posts one review.
- Every reviewer reads the template's own `rules/CODEREVIEW.md` (a checklist, priority examples, what never to flag without evidence), then the repository's `docs/CODEREVIEW.md` (or `CODEREVIEW.md`) from the base, which adds to it; without one, `REVIEW.md`. A repository may add `.agents/skills/code-review-knowledge/SKILL.md`, its invariants by path glob.
- The posted review is always one COMMENT review. Its body leads with the `Risk n/5` line and its reasons (Greptile's confidence is 6 minus the risk), then the summary and the findings. Each inline comment starts with its own priority and ends with its fingerprint in an HTML comment, which a re-review reads to never post an open finding twice; a finding still open counts toward the risk score.
