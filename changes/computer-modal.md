`ModalProvider` makes computers that are Modal sandboxes on the VM runtime, through the host's own Modal client: the package names the slice of the JS SDK it calls (`ModalSdk`) and imports nothing from it. It has not run against real Modal yet; its tests use a fake of that slice.
- The daemon is uploaded at create, so nothing is published: the sandbox's command is a POSIX sh entrypoint that waits, bounded, for `/opt/agentrun/computerd` and then `exec`s `computerd init --deadline <iso> --user <uid:gid>`; right after create the provider streams `dist/computerd-linux-amd64` (`daemonPath`) into `sh -c` through `exec`'s stdin in binary mode, which writes it to a part file, prints its sha256 and moves it into place only when it matches. A failed or mismatched upload terminates the sandbox and refuses. `modalCommands()` gives the commands as sent. With `daemonImage` (a registry image pinned by digest) the daemon instead comes in as a layer (`COPY --from`) and is the command itself. `connect()` runs `computerd stdio` through `exec`, so a computer with network none is reached and needs no network for its daemon.
- Capabilities: kind `linux`, daemon `pid1` (init is the sandbox's main process, and Modal finishes the sandbox when it exits), groups `exec`, `files` and `processes`, `maxLifetimeMs` the instance's cap (24 hours, Modal's longest timeout, or less with the `maxLifetimeMs` option; `check()` refuses a longer lifetime with the shared `checkLifetime()`), lifetime `vendor` (Modal's timeout is the lifetime), network `none` or `open` with `networkReadBack: false`, isolation `vm`, os `linux`, user `uid` only. An allowlist, `pids`, a GPU and a change of network are refused in words. `release(ref, "stop")` is refused: Modal has no stop that keeps a sandbox; `delete` terminates and is idempotent, and since Modal ends a sandbox asynchronously it then polls, with pauses that double from `timeouts.releasePollMs` (500 ms) to 5 s, until `poll()` reads an exit code or Modal no longer knows the sandbox, within `timeouts.releaseMs` (120 s) and the caller's signal; past the bound it is a `timeout` that says what `poll()` last read. `list()` polls each sandbox Modal lists and leaves out one that has finished.
- The drift check after `create()` and in `attach()`: the sandbox runs, its tags read back as given, hello's version, os, arch, kind and exact groups match, and `computerd probe`, run through the daemon, reports the computer's user, a kernel that is not gVisor's, and, for network none, no connection to its public addresses. A mismatch terminates the sandbox at create, and create waits, as release does, until `poll()` reads it finished, so a refused create (drift, an abort, a failed upload) leaves nothing listed; the terminate is sent whatever the caller's signal, and the wait, bounded by `timeouts.releaseMs`, ends on the caller's abort (an aborted create returns at once); past the bound or on an abort the refusal says the sandbox may still be ending and what `poll()` last read. `attach()` refuses and leaves it running. `network(ref)` reads network none back with the same probe.
- A Modal computer never runs as root: `check()` and `create()` refuse a `user` of `"0"`, `"0:<gid>"`, `"root"` or `"root:<gid>"` in words, before any Modal call, and `connect`, `attach` and `network` refuse a computer whose spec tag records root before they run anything in it. Every connection is Modal's exec of `/opt/agentrun/computerd stdio`, outside the daemon, with Modal's root capabilities; root without a capability still owns `/`, `/opt` and `/opt/agentrun`, so it could rename another program over that path. A user that is not root writes none of them (the daemon is `0:0 755` in a `0:0 755` directory). The conformance case `exec.root-on-request`, which needs `user:root`, skips on Modal as undeclared.
- Every SDK call is bounded by a timeout and takes the caller's signal; a create that gives up has its sandbox terminated if one lands later, and a bridge whose exec lands after its connection gave up (past its bound, or on the caller's abort) has its stdin closed as it lands. One deadline, `helloMs`, covers a connection's exec of the bridge (at most `callMs` of it) and the hello after it.
- `computerd init` takes `--user <uid:gid>`: it starts as root, gives `$HOME` and the socket's directory to that user (0700) and becomes it, with no supplementary groups.
- `computerd init` drops its privileges itself, as any user, root included, with or without `--user`: on every thread it sets `no_new_privs`, empties the bounding set (each capability up to `/proc/sys/kernel/cap_last_cap`), the ambient set and the effective, permitted and inheritable sets, and reads it all back. Where a capability cannot be dropped (no CAP_SETPCAP with a bounding set), or in a binary that links cgo, init refuses to start, in words. That is policy, failing closed: a vendor that starts it as a non-root user with a bounding set it cannot empty (a Kubernetes `runAsUser` without dropping ALL capabilities) gets no computer rather than one with capabilities init cannot prove gone.
- The conformance cases `exec.unprivileged` (Core), `exec.root-on-request` and `exec.user-uid` (Full) require `CapEff`, `CapPrm`, `CapInh`, `CapBnd` and `CapAmb` all zero and `NoNewPrivs` 1 in `/proc/self/status`, where they required only `CapEff` and `CapPrm` zero.
- `waitUntil(read, done, { boundMs, signal, minMs, maxMs, what, describe })` is a bounded wait with doubling pauses that returns the first state `done` accepts, or a timeout or abort naming the last state read. Modal's one wait after a terminate, `untilFinished`, is built on it, and release, a refusing create and the Modal sweep all wait through that. `computerd probe [--connect <host:port>]...` prints the uid, gid, kernel release and the addresses it reached.
- `ComputerCapabilities.networkReadBack` says whether `network()` reads the policy back from outside the computer (Docker: true). `ComputerErrorCode` gains `"modal"`.
- `dist/conformance/modal.js` is a provider module for the conformance CLI, and `npm run test:modal` the live suite; both run only with `AGENTRUN_COMPUTER_LIVE_MODAL=1`, `COMPUTER_MODAL_TOKEN_ID` and `COMPUTER_MODAL_TOKEN_SECRET` set. The module passes that pair to `ModalClient` explicitly and never uses `MODAL_TOKEN_ID` or `MODAL_TOKEN_SECRET`, which may hold a production token; with only those set it refuses in words. The key goes only to `COMPUTER_MODAL_SERVER_URL`, else the SDK's default server: the module refuses while `MODAL_SERVER_URL` is set and pins the server while it constructs the client, so no `MODAL_PROFILE` or `.modal.toml` profile can redirect it. It reads `COMPUTER_MODAL_APP` and, optionally, `COMPUTER_MODAL_DAEMON_IMAGE`; without it the daemon is uploaded. The drifted provider uploads a daemon built with Go as `<version>-drift`. Every computer of a run lives at most 30 minutes.
- `dist/conformance/modal-sweep.js --before <file>` records the app, the server and every running sandbox in the app carrying `agentrun.computer=1`; `--after <file>` refuses a file of another app or server, or one naming neither, before it lists anything, else terminates every such sandbox not in that file, reads each back through `untilFinished` until it has finished (60 s each), prints `{"swept":n,"gone":m,"stillThere":[ids]}`, and exits 0, 1 (one still runs) or 2 (usage, another app or server, token, refused list; nothing terminated). It reads only the `COMPUTER_MODAL_` token, app and server, the way the module does.
- `ComputerCapabilities.release` declares how release may end a computer: Docker `["stop", "delete"]`, Modal `["delete"]`. Core `provider.stop` holds a provider to it: one that declares stop lists the computer stopped; one that does not refuses `release(ref, "stop")` as `unsupported`, in words, and the computer stays listed and running. The Full `provider.janitor` case also needs `release:stop`. A provider written against `ComputerProvider` adds `release` to its `capabilities()`.
