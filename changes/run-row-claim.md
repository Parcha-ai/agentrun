---
packages: @parcha/agentrun-serve, @parcha/pi-durable-agent, @parcha/pi-durable-disk
kind: breaking
---
A run's row in store.sqlite is now the whole lock on the run. Its `claim_epoch` changes only by compare-and-set. pi-durable-agent's `claimRun(runId, holder, from)` bumps the epoch only while the row still holds `from`; otherwise it is refused as `stale` and writes nothing. The new `setRunHolder(runId, epoch, holder)` names the holder under that epoch only. A holder is a name of at most 1,024 characters. serve's run process no longer writes `run.json` or `owner.lock`. It has no heartbeat and no lease watchdog. Its row names it instead: its pid, that process's start time, this boot and, once it serves, its door. The process prints the door on stdout, and the server writes it into the row. The process never opens store.sqlite. Its status (`sleeping`, `paused`, `done`, `failed`, with its detail) goes into its own run.sqlite, in pi-durable-disk's `RUN_STATUS_TABLE`. A take-back or a launch reads the row and kills any holder that still lives before it bumps the epoch. So no process of a lower epoch runs, or commits to the run's store, after the bump. A run whose holder is gone is taken over by its row. A stale run.json beside it, naming a live process, changes nothing. Before, that made the server adopt a process that was not the run's. pi-durable-disk's `openDurableRun` takes `epoch`, and `pi-durable-disk run` takes `--epoch N`. Both are for a run whose host holds its claim: no owner lock, no run.json, no heartbeat, no seal check. The run's record lives in its store, and the previous incarnation's record there is `previous`. The internals entry adds `RUN_STATUS_TABLE` and `processTable`.

Upgrading: stop the server and let its runs' processes exit before you start this version. A run process an earlier version started is not adopted, because the run's row names no holder for it. Any run.json and owner.lock files left in run folders are ignored.
