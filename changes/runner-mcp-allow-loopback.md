A runner in its own process (`agentrun-serve runner`, beside a server started with `--no-runner` or in a service of its own) now honours `AGENTRUN_MCP_ALLOW_LOOPBACK=1` from its own environment, as the server and the runner inside the server's process already did. Before, every call such a runner made to an MCP server on loopback was refused as a private address, nothing sent.
Each process reads only its own variable, never the server's, the store's or the data directory's, so a runner never inherits it. Loopback means the machine (or container) the runner runs on: a runner in another container or service needs its own server or forwarder at the MCP server's address, and its own `=1`. A runner with the variable never reaches loopback at a server's own port: 7340 (where a server listens unless `--port` says otherwise), the port of a loopback `AGENTRUN_PUBLIC_URL` in its environment, and the addresses the server now keeps in the store at each start (`mcp.server_own`: where it listens, whatever its port), read at each claim. Those addresses are all a runner reads of the server. It says on stderr at its start that it takes the variable. A runner without it is refused as before, even when the server has it.
On a server started without the variable, a run of a revision saved before pins (pinned at its first run) whose MCP server is on loopback was refused (409) with "save the agent again to pin it", though a save is refused too. The 409 now names the cause: `its server <name> can't be listed here to pin it: 127.0.0.1 is this machine; set AGENTRUN_MCP_ALLOW_LOOPBACK=1 when starting the server, ...`. With the variable set on the server, such a revision is pinned at its first run and runs, as before.
