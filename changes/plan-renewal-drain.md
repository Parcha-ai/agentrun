A stop no longer loses a ChatGPT plan sign-in to a renewal it cut off: the server's stop, and a runner's (beside the server or in a process of its own). OpenAI may already have spent the refresh token when the stop starts. From the stop on, nothing in that process starts a renewal on its store, and one whose lease was still being taken gives the lease back unsent; a run that needs a renewal while its runner stops is told to try again. A renewal already sent gets up to 25 s from the stop's start to save its new pair before the store closes. A server with no runner beside it (`--no-runner`) now allows for that wait before its stop exits early: its stop's deadline was 15 s. The shipped Compose files now give the quickstart and the `--no-runner` server 35 s of stop grace, as the runners and the Helm chart had (they gave 15 s); so does the compose file `install.sh --vps` writes, which the DigitalOcean one-click runs (15 s before). The macOS service waits 35 s before launchd kills it (`ExitTimeOut`; launchd's default is 20 s), and the Railway template sets `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` to 35 (Railway's default is 0). A renewal waiting on another process's lease stops waiting, and its log line says `carry=stopping`. When a renewal's write-back fails, the new pair is revoked only if nothing could have written it: the store refused the write unsent (it had closed). On any other failure the row is read back: a pair it holds is kept, and a row still under the renewal's lease is written again. When that write loses, the row is read once more, since a Postgres commit that went unanswered can land late. When the outcome stays open, the pair is kept unsaved, logged as `renewed_pair_unsaved` with `write=unknown` and the store fault's class (`Unanswered` included). A platform that kills the process sooner than 25 s after SIGTERM can still cut the wait short: give it at least 30 s of grace.
