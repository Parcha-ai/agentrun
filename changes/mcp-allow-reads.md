Allow reads: one switch on a saved MCP server lets each of its read-only tools run with no one asked, while its writes keep asking and a destructive call takes a second click to allow.
- A tool's effect comes from its server's annotations: read when `readOnlyHint` is true; else destructive only when `destructiveHint` is true; else write (no annotations included, which still asks). The MCP spec's default reads a tool with no `destructiveHint` as destructive; this does not, since every tool of a server that annotates nothing would then need two clicks. A saved server's read gives each tool's `effect`, and `allow_reads: true` on a tool whose allow is its server's Allow reads.
- `allow_reads: true` on an MCP server's wildcard (`mcp:<server>/*`) in the server's tool settings (`PUT /settings/tools`) turns it on; `false`, or leaving it out, turns it off. An agent's own tool settings, or any other key, refuse it (422). It never lifts a deny (the server's or the agent's), the agent's own ask, a tool's own setting (`mcp:<server>/<tool>`) or a pin's refusal.
- The run's gate reads each tool's effect from what the run pinned when it started, never from a later listing, so a server that marks a tool read-only mid-run widens nothing for that run.
- A destructive call's approval carries `destructive: true` in the run's `pending`, and allowing it needs `confirm_destructive: true` beside the decision (without it, 422 on `confirm_destructive`, and the call still waits). A deny needs nothing more.
- Console: Settings, MCP servers shows the Allow reads switch on each server, its tools with a read, write or destructive mark and their permission here (an allow by Allow reads reads "allow (allow reads)", never "default"), and asks a second time before a destructive tool is set to allow, there and in an agent's tool settings. An approval card marks a destructive call, and its Allow once asks again before it sends the allow.
