A template eval's llm grader no longer sees a held value through a file's name. The eval read each file's text under the run's cut, but named every file by its path as the run wrote it, in the `<file path>` block, the "Not shown" list and the list of names when every text is left out. A run that named a file by a key (`cache/<key>.json`, `media/<key>.mp3`) put the key in the grader's prompt. The eval now lists the run's files with `GET /v2/runs/{run_id}/files?cut=run`, new here: each file also has its `name`, its path under the run's own cut, made the same way as a cut read's text (each value the cut holds and each secret shape replaced by `[redacted]` in place). Every file gets a name whatever its type, so a grader can still be told about an audio file or an image the run made. The grader's prompt names files by these names alone, and a call is pointed at the file it made by name. A server that doesn't know the listing's `cut` lists no names; the eval then shows each text file it read in a `<file>` block with no path and counts the rest ("and 2 files not named"), never naming one by its path. A run whose cut can't be read is `403 forbidden`, as the listing already was; any other `cut` is `400 bad_request`. Without `cut`, the listing is unchanged. The TypeScript and Python clients and the CLI take the new parameter (`agentrun runs files RUN_ID --cut run`, `client.runs.files(runId, { cut: "run" })`, `client.runs.files(run_id, cut="run")`). In the TypeScript client, the request options move to the third argument: `client.runs.files(runId, undefined, { signal })`.

A private key in a file read under the cut is now cut whole. The private key shape matched its BEGIN line alone, so a key file read with `?cut=run` kept the key's whole base64 body. The shape now runs from the BEGIN line through the body to the END line: PKCS#8, RSA, EC, OPENSSH and encrypted keys, a legacy PEM's Proc-Type and DEK-Info headers, and CRLF line ends. The body is read for at most 16 KiB. A block with no END line within that (a key cut short) is cut through the base64 lines after its header, at most 1,024 of them. Each of six adversarial inputs of 256 KiB (repeated headers, endless base64, near-END dashes) is redacted in under 1 s.
