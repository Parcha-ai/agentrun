TypeScript client: `runs.files(id, { signal })` becomes `runs.files(id, params, { signal })` (`params` may be `undefined`). `runs.files` takes the listing's new `cut` parameter before its request options, so a call that passes options second would lose them without an error. There is no compat shim.

A template eval's llm grader no longer sees a held value through a file's name. The eval read each file's text under the run's cut, but named every file by its path as the run wrote it, in the `<file path>` block, the "Not shown" list and the list of names when every text is left out. A run that named a file by a key (`cache/<key>.json`, `media/<key>.mp3`) put the key in the grader's prompt. The eval now lists the run's files with `GET /v2/runs/{run_id}/files?cut=run`, new here: each file also has its `name`, its path under the run's own cut, made the same way as a cut read's text (each value the cut holds and each secret shape replaced by `[redacted]` in place). Every file gets a name whatever its type, so a grader can still be told about an audio file or an image the run made. The grader's prompt names files by these names alone, and a call is pointed at the file it made by name. A server that doesn't know the listing's `cut` lists no names; the eval then shows each text file it read in a `<file>` block with no path and counts the rest ("and 2 files not named"), never naming one by its path. A run whose cut can't be read is `403 forbidden`, as the listing already was; any other `cut` is `400 bad_request`. Without `cut`, the listing is unchanged. The TypeScript and Python clients and the CLI take the new parameter (`agentrun runs files RUN_ID --cut run`, `client.runs.files(runId, { cut: "run" })`, `client.runs.files(run_id, cut="run")`).
