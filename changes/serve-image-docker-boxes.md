The published image runs Docker boxes with a network, and `compose.yaml` at the repository's root is the one way to run it. Use one command on a Linux host with Docker Engine 26 or later: `DOCKER_GID=$(stat -c %g /var/run/docker.sock) docker compose up -d`. It starts the server with its data on a named volume and the host's Docker socket. Each run's `bash` then runs in a Docker box beside the server, which reaches the hosts on its list through the run's egress proxy and nothing else. Before this, every box create in a container failed, because the box was bound to a path that only the server's container had. At start, a server in a container now reads its own container's id from `/proc/self/mountinfo` and asks Docker for its mounts. It then mounts each box's run `work/` and proxy directory (`<data>/box-egress/`) as subpaths of the named volume that holds the data directory. Any other layout makes docker unavailable with one reason: `run AgentRun in a container with docker compose up from compose.yaml (its named data volume is how boxes reach a run's files)`. An older engine gets `Docker Engine <26 can't mount a named volume's subpath: upgrade to Docker 26+`. The image now has the Docker client (Debian's `docker-cli`) and no daemon. `packages/serve/docker/compose.yaml` is gone, replaced by the root `compose.yaml`, and the README's `docker run` is replaced by compose. pi-transport's Docker provider takes `paths`, which turn a mount below `at` into that named volume's subpath. A server on a host makes its boxes exactly as before. The socket is root on the host, and the README says so.
