A workflow draft a run proposes is dry-run before it is kept: the workflow DSL runs it on the run's own input (its block's new `example:` front-matter line, else an input made from its schema) with every model and tool answer synthesized, so no request is sent, nothing is paid and no tool runs. Only a draft every static check passes is dry-run, and no code in it runs in the host: a code node is refused before the dry run, and the dry run hands any code node to a runner that refuses it. Nor is a huge value built from the draft's schemas: a schema whose synthesized value would be too large (a minItems past 100, a minLength past 1,000, more than 2,000 values or 64,000 characters in all) is refused before any dry run, and a dry run handed one stands down. A draft's loops are bounded too (a loop's `maxIters` past 50, or nested loops past 1,000 iterations together, is refused), so a loop whose body asks no model cannot spin the runner, and a dry run stops after 10 seconds. The bounds read a draft's schemas and nodes where they are schemas and nodes: a `const`, `enum`, `default` or example holding `minItems` or a loop's shape is data, never a bound or a loop. A draft whose wiring breaks at run time (an output path no step produces, a step's output that fails its schema), which validation alone passed, is left out alone, and the end-of-run turn is asked once more to fix it; a draft that passes is proposed with its dry run, and the grader is told it; what a dry run's check said is made from the draft's own text, so the grader reads it only inside a data fence. The example is the run's input, so it is never written to the learning folder, and one holding a secret refuses the answer as any text does.
Upgrading: nothing to do; a run's proposal may now carry `dryRuns` beside its files.
