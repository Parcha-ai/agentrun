A pi run that compacted its context no longer reads its cost as unknown. pi sends the compaction's summary request through the run's model port, which marks the request and books it at its price, but pi stores no answer for it: the summary's cost rides on the answer pi stores beside it. The Timeline's usage row counted the summary as a request cut with no answer, so it read `usd: null` with `unpriced` equal to the number of compactions. Every reader built on that row read the same: a running run's `cost.usd` on `GET /v2/runs/{id}`, its live spend on the runs list and in `GET /v2/usage`, its `/usage` tokens meter, and the usage line on its run page. pi's compaction entry now answers that summary request. The row reads the run's priced total and counts the summary as a request whose tokens pi did not report. A real charge of no known cost beside a compaction (a request cut with no usage) still reads `usd: null`, with `unpriced` counting it.
The cap's own reading of a run's journal (`spentFrom`, behind the runs list's live spend) is fixed the same way. Where request marks hold the cap's figure for each request, it left the summary's mark open and counted it a second time at its hold, so the spend it read was too high. No runner in this server writes such marks, and a run's cap gate reads its booking instead, so no run here was stopped early by it. A store or host whose marks hold figures read it high.
