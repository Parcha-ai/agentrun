`DaytonaProvider`, the second computer provider, over Daytona's v0 REST API with `fetch` and no new dependency. A Daytona snapshot is the computer's image; `image: "default"` sends no snapshot, so Daytona uses its default snapshot, and the drift check then holds the sandbox to everything but the snapshot's name. `create` makes the sandbox with a TTL of the lifetime (`lifetime: "vendor"`), the options `autoStopMinutes` (Daytona's `autoStopInterval`; default 0, no idle stop) and `autoDeleteMinutes` (`autoDeleteInterval`; 0 deletes a sandbox as soon as it stops; default never), both read back by the drift check, and the network declared (`none`, `open`, or an allowlist of up to 100 domains on ports 80 and 443, or 10 IPv4 CIDRs on any port, never both), pushes `computerd` in through the toolbox's file upload, installs it root-owned, and starts `computerd init --user 1000:1000` as root in a session command (through `sudo -n` when the session's user is not root): init drops itself to 1000:1000 with no groups, no capabilities in any set and `no_new_privs` on every thread, so the provider relies on no privilege tool of the snapshot's (the default snapshot's `setpriv` is BusyBox's). `computerd init --user uid:gid` and `computerd probe` are new in the daemon. `connect` runs `computerd stdio` in a session of its own, its input through the session's input calls and its output through the command's log stream. The drift check reads the sandbox back (snapshot, network, labels, idle stop, auto-delete, TTL, class, public, KVM, GPU, volumes, link) and the daemon (hello, `/proc/self/status`, its directory and binary, the installed sha256); a mismatch deletes the sandbox at create and is refused at attach. `dist/conformance/daytona.js` runs the conformance suite on Daytona with settings read from the environment by name (`COMPUTER_DAYTONA_API_KEY`, `COMPUTER_DAYTONA_API_URL` and the rest of `COMPUTER_DAYTONA_*`; never `DAYTONA_API_KEY`, which may hold another organization's key); it always sets `autoStopMinutes: 30` and `autoDeleteMinutes: 0`, so a stop deletes (Core `provider.stop` is expected to fail on Daytona, as the module's note in the report says), and its image is `COMPUTER_DAYTONA_SNAPSHOT` or `"default"`. The conformance CLI takes a module's `conformanceImage()` when `--image` names none and prints its `conformanceNotes`. Its live test runs only with `AGENTRUN_COMPUTER_LIVE_DAYTONA=1` and `COMPUTER_DAYTONA_API_KEY`. `dist/conformance/daytona-sweep.js --before <file>` records every sandbox carrying `agentrun.computer=1`; `--after <file>` deletes every one not in that record, reads each back until Daytona answers 404, and prints `{"swept":n,"notFound":m,"stillThere":[ids]}`, exiting 1 when one is still there. Daytona answers a delete or a stop before the sandbox is gone or stopped, and its listing trails both, so `release` waits, bounded (`goneMs` and `stopMs`, 120 s each) and under the signal it now takes, until `GET /sandbox/{id}` and the listing both read the computer gone (404), or stopped, and otherwise fails naming the last state read; a create that deletes its sandbox waits the same way. `list()` leaves out a sandbox that is `destroying` or `destroyed` and reports one `stopping` or `pausing` as running. `ComputerCapabilities` gains `allow`, what an allowlist holds and the ports each kind of entry opens, and results a `daytona` error code. One live run on the default snapshot reached the start, which failed on BusyBox's `setpriv` before this drop.
