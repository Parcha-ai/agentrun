A run's Docker box drops every capability, and a Docker daemon on another machine never binds this machine's `work/`.
- `dockerBoxes({ dropCapabilities: true })` runs each box with `--cap-drop ALL` and `--security-opt no-new-privileges`. Serve's run boxes always use it. Without it, a server run as uid 0 made boxes that were root with Docker's default capabilities, so `bash` could `mknod` a device node in `work/` (`c 10 130`, the watchdog) for the file tools on the host to open. With it, `attach` ends a box made without it (an older version's, its run resumed) instead of taking it, so a fresh hardened box replaces it. The option is off by default in pi-transport, because a launcher that drops from root to another user needs Docker's default set.
- `dockerBoxes`' `mounts` is now false when `DOCKER_HOST`, or the docker context (`DOCKER_CONTEXT`, else the config's `currentContext`), names a daemon on another machine (tcp://, ssh://, or a context whose record names no unix socket). With `DOCKER_HOST` and `DOCKER_CONTEXT` both set, both must be this machine, and each create checks again, so a `docker context use` after the provider was made refuses the next spec with mounts. A spec with mounts is then refused as `unsupported`, naming the setting and how to undo it. In serve, a run's box on such a daemon is not bound, so `read`, `write` and `edit` go through the box, never this machine's `work/`.
