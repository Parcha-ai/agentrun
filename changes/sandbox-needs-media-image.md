A sandbox can list the programs its agent needs on the box's PATH, `computer.needs` (such as `["chrome", "ffmpeg", "ffprobe", "hyperframes"]`), and the computer package ships a media image that has them. Each run's claim asks the box it started before the run's first model request; a box that lacks one, or that cannot be asked, is let go and the run ends `failed` (`run_failed`) in words naming what is missing and how to give the box an image that has it. The field never picks an image: a Docker box's image is still `AGENTRUN_DOCKER_IMAGE`'s. A setting that has `needs` but is no sandbox (a stored body or a launch's computer the validator never saw) fails the run at claim the same way, before anything is started. An agent without `needs` is checked for nothing. A template states them as `needs` in its agent.md, read only beside `computer: [shell]`: apply writes them onto the sandbox it picks as the agent's `computer.needs`, and where the shell here is no sandbox (Archil's serverless exec, or none) it refuses (`409`) in words naming them and `AGENTRUN_DOCKER_IMAGE`, making nothing. `GET /v2/templates` shows them as `needs`. A server before this release refuses a template that names `needs` as an unknown field.
The media image's recipe is `packages/computer/media/Dockerfile`: the default image's base and programs, plus Node 24, Chromium as `chrome`, FFmpeg and FFprobe, Noto (CJK, colour emoji) and Liberation fonts, and the HyperFrames CLI at an exact version, with its usage reports off and the image's fonts compressed for it at build, so a render with no network doesn't spend a minute of its compile compressing Noto Color Emoji. Build it and name its tag in `AGENTRUN_DOCKER_IMAGE`; the serve README's "The box's image" has the commands. It is not published.
