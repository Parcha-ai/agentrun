A template eval's llm grader reads the files the run left whole, ahead of its calls. Before, a grader saw a file only through the calls that made it, each cut where the timeline cuts it (a string of a call's arguments at 2,000 characters, its output at 8,000, each ending "..."), so a run whose file was whole could read as a run that wrote less, and fail. The grader input now has a `<files>` block ahead of `<tool-calls>`: each text file of the run's work folder (text/*, JSON and NDJSON, or an untyped extension such as .srt or .yaml whose bytes are UTF-8) in its own `<file path bytes>` block, as it was written, and every other file (media, a binary) by its path and size. A call that names a file shown says where it is. The files route serves a file's bytes as they are, where a call reaches a grader through the run's redaction, so each text is cut of every secret value the eval's process holds in its environment (the runner's own redactor), which is the server's when the eval runs its own; against another server, a value only that server holds is not known to the eval and is not cut. The files are read only for a graded run of a case with an llm grader, smallest first, up to the prompt's 120,000-character cap in all. Under the cap the calls' results are cut first, each cut marked in place; the files take at most three quarters of the room the rubric, task and answer leave (the calls keep a quarter, or all they need when that is less), and past that the largest file's middle is cut and marked first. A run with no files gets the grader input it got before. The cost: one read of each text file per graded run, and longer grader prompts (more input tokens) for runs that leave text files.
