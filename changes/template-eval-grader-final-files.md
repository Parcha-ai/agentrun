A template eval's llm grader reads the files the run left whole, ahead of its calls. Before, a grader saw a file only through the calls that made it, each cut where the timeline cuts it (a string of a call's arguments at 2,000 characters, its output at 8,000, each ending "..."), so a run whose file was whole could read as a run that wrote less, and fail. The grader input now has a `<files>` block ahead of `<tool-calls>`: each text file of the run's work folder (text/*, JSON and NDJSON, or an untyped extension such as .srt or .yaml whose bytes are UTF-8) in its own `<file path bytes>` block, and every other file (media, a binary) by its path and size. A call that names a file shown says where it is. The files are read only for a graded run of a case with an llm grader, smallest first, up to 120,000 UTF-8 bytes in all; a file that can't be read or would pass that budget is listed by size, and the files after it are still read. Each read is bounded (10 s, and 30 s for all of a run's files), so a server that stalls mid-file costs that file's text, never the eval. Under the prompt's 120,000-character cap the calls' results are cut first, each cut marked in place; the files take at most three quarters of the room the rubric, task and answer leave (the calls keep a quarter, or all they need when that is less), and past that the largest file's middle is cut and marked first. A run with no files gets the grader input it got before. The cost: one read of each text file per graded run, and longer grader prompts (more input tokens) for runs that leave text files.

The eval reads each file through `GET /v2/runs/{run_id}/files/{path}?cut=run`, new here: the file's UTF-8 text under the run's own cut, on the server that holds its secrets. Every value the run's timeline is cut of (the server's keys, the keys a person saved, its secret stores' values, the sign-in refs the run was handed) and every secret shape is replaced by `[redacted]` in place; a text where a value still shows in a form not cut in place is `[redacted]` whole. Compact JSON with no whitespace is never blanked for its length. What the run's caller handed it (its own model key, tool keys, MCP servers' credentials) is cut too; after the run's end, a file changed since is withheld (`403`). A secret of no known shape passes as written. The answer is `text/plain; charset=utf-8` with `x-agentrun-cut: run`; the eval keeps a text only from an answer with that mark, so a server that doesn't know the cut (and would answer the raw bytes) gives the grader no file text. A run whose cut can't be read (a handed sign-in this server can't open) is `403 forbidden`; a file whose type isn't text, or whose bytes aren't UTF-8 or hold a NUL, is `415 unsupported_media_type`; one over 262,144 bytes (256 KiB) is `413 payload_too_large`. Without `cut`, the route answers the file's bytes as written, as before. The TypeScript and Python clients and the CLI take the new `cut` parameter (`agentrun runs read-file RUN_ID PATH --cut run`, `client.runs.read_file(run_id, path, cut="run")`).

Two secret shapes every redactor uses could hold the server's event loop for minutes over one file: a JWT read from every `eyJ` inside a long run of base64url characters (180 s over 256 KiB of `eyJ`), and a private key header with two unbounded runs of capitals (24 s over 256 KiB of `PRIVATE KEY `). A JWT now starts at the first `eyJ` of a run of its characters and not again at a later one in the same run, which finds nothing the first doesn't; the key type around `PRIVATE KEY` is at most 64 characters each side. What is redacted is the same as before: a JWT glued to a word (`token-eyJ…`) is still found, and so are the RSA, EC, OPENSSH and ENCRYPTED headers. Over 256 KiB, each shape's adversarial input (its prefix repeated with no end) now takes under 100 ms.
