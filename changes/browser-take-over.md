The owner takes over a run's browser from the live view and hands it back, and the agent can ask them to. Capabilities say so: `features.browser_live: {read_only: false, take_over: true, ask: true}`.
- **Take over, hand back.** The viewer watches until the owner presses Take over in it; until then the run drops its input before the browser. The hold lasts until Hand back, the viewer is gone 2 minutes, or 15 minutes pass with no input. Meanwhile the agent's browser calls wait inside the tool, then go on with the page's old element ids dropped and the model told plainly that the person had the browser. Each change of hands moves the session's epoch, so an act a call took before it is refused. The run stays `working`; the timeline says "You took over the browser" and "You handed the browser back".
- **The agent asks.** `browser_request_handoff` is listed. The run reads `input_required`/`waiting` with `pending: {kind: "browser", instruction, completion_condition, asked_at, expires_at}`, a "Waiting for you: <instruction>" row, and `run.needs_input` with `pending.kind: "browser"`. The owner answers `POST /v2/runs/{id}/browser/hand-back` `{outcome: "done" | "cancelled"}` (their password session only): the first answer wins, a different later one is `409 handoff_answered`; unanswered for 15 minutes it expires.
- **The owner's time counts.** A take-over and an ask hold 15 minutes of session time at the provider's price under the run's cap before they start (once per session: a take-over and an ask on it share one hold); with no room they are refused in the cap's words (in the viewer, or in the tool's result). A take-over that input keeps alive is held again every 15 minutes, and with no room the browser goes back to the agent at the cap. When the browser comes back, the time the person had stays held until the session's next charge books it.
- A run's process that dies while the agent's ask waits is started again, and the new process takes the wait up: the owner's answer reaches the agent, or the ask expires. That holds when the owner answers after the process went and before the server found it gone: the hand-off is started again until its call's result is saved, the answer already on disk.
- A browser session a restarted run's process keeps gets its viewer handed over again: the owner no longer reads `none` while it is live.
- **The viewer's code is the server's own.** Serve now serves the viewer's page, script and style from the pi-browser it has installed, never from the run's port; only the viewer's WebSocket goes to the run.
- `@parcha/pi-browser`'s live view takes `takeOver: { take(tag) }`, the driving gate gains `take`, `give`, `held`, `epoch`, `setPresent`, `untilFree`, `command` and `settling` (with `holdIdleMs`, `holdAwayMs` and `settleMs`: a hand-back wakes the agent only once the person's last command has returned), and `viewerAssets` is exported from `@parcha/pi-browser/live-view`.
- The timeline's "Waiting for you" row for a browser hand-over (`agent.handover`) takes the host's redact, as a tool call's arguments do: a held value the model echoes in what it asks never shows; the run's `pending` for a browser ask is redacted the same way.
