A write, append, mkdir or remove on an Archil workspace whose folder another client held past the workspace's wait (a computer's mount of the folder holds Archil's write delegation, and a command running in it checks it out) failed `UNAVAILABLE` with the code's line, "the root is gone, the disk is full or read-only, an I/O error". So web_save, monid and the MCP gateway's filed answers told the model its disk was full when another client was holding the folder. The failure keeps `UNAVAILABLE` and now says what happened: "the folder is held by another client (a computer's mount of it, or a command running in it) and was not let go in 60 s (Archil: 409 OperationAborted)". The error's message still carries Archil's full answer. The words a tool answers with name no path, so they keep only Archil's status and code: its message names the disk key. A recursive remove gets the same words: Archil's bulk delete lists a refused key without a status, so each refused key is deleted again on its own, where a hold answers 409. A write or an append to a symbolic link an exec made also answers 409, but it is no hold. It now fails `EXISTS` at once, naming the link, where before it waited out the 60 s and failed `UNAVAILABLE`. Removing a link is allowed, so a 409 on a remove is still waited on as a hold. A `WorkspaceError` can now carry its own path-free `words`, and `workspaceErrorWords` uses them before the code's line.
