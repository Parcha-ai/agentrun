Settings → Model keys' "Open the CLI's sign-in here" signs the claude CLI in at the login's own folder, so the login reads signed in afterwards. The sign-in ran with a temporary config dir, where `auth login` wrote the account it signed in (`.claude.json`); that folder was removed when the sign-in ended, and the login's folder stayed without it, so AgentRun kept saying "not signed in" while running the shown command by hand worked. The sign-in, the shown command and the status check now take their variables from one function (`claudeSignInEnv`), and the status check reads the login's folder as its config dir.

- `GET /v2/settings/claude-login` says what became of a sign-in the server started, as `sign_in`: `waiting` for the browser since `started_at`, `signed_in`, `timed_out`, `failed` with the CLI's `exit_code`, or `not_started`. The console shows "Waiting for the browser…" from it, after a reload too. A sign-in no browser answers within 10 minutes is ended and says so, with the button to start it again; before, it ended silently and the browser's page then failed to reach it. A second press, turning the mode off, or stopping the server ends a sign-in that still waits; the stop waits for its CLI to exit, so no CLI keeps the browser's callback port from the next server.
- The view names the folder it asks about (`folder`), and this machine's own login folder for the claude CLI (`machine`). That folder follows the CLI's rule: `CLAUDE_CONFIG_DIR` when the server's environment sets it to an absolute path, else `~/.claude`. The console shows it in place of the fixed "(~/.claude)", and where the server saw no `CLAUDE_CONFIG_DIR` it says that a CLI using another folder needs AgentRun started with `CLAUDE_CONFIG_DIR` set to it.
- "This machine's" login on the CLI's default folder (`~/.claude`, no `CLAUDE_CONFIG_DIR`) is signed in as the person's own claude CLI runs: with no config or credentials dir set, in their home, so the sign-in writes the account in `~/.claude.json` and the tokens where their CLI keeps them, and the shown line is their own, clearing both variables (`env -u CLAUDE_CONFIG_DIR -u CLAUDE_SECURESTORAGE_CONFIG_DIR ...`) so a terminal that exports either signs in at that same login. Before, AgentRun set both dirs to `~/.claude`, which reads `~/.claude/.claude.json` (where the person's CLI keeps no account) and, on macOS, a Keychain item named from that folder rather than the person's own (the one with no suffix), so it read signed out there while the person's CLI was signed in. A run on it sets `CLAUDE_SECURESTORAGE_CONFIG_DIR` empty on macOS, which names that same item whatever the run's config dir, and `~/.claude` elsewhere. The harness's `claudeLoginEnv` takes the platform (this host's by default), and its login takes `home` for this place. A login in a `CLAUDE_CONFIG_DIR` folder keeps both dirs set to it, which is where the person's CLI with that variable keeps its login.
- The status check on "this machine's" login (either folder) never runs the claude CLI on the person's own account file. The CLI rewrites `.claude.json` on every start whose config version is not its own (and the first time adds `settings.json`, a backup and a lock beside it), so asking it in place rewrote the person's file on every view, every 2 seconds while a sign-in waited, and at every run's start. Each check now copies the file (opened only to read) into a folder of its own, gives the CLI that folder as its config dir and the tokens as a run reads them, and removes the folder however the check ends. The copy leaves out the fields that hold secrets (`primaryApiKey`, the API key an older CLI signed in with; `env`; every `mcpServers`), and a file that doesn't parse as a JSON object is not copied; a run's config dir has none of them either, so a login whose only key is that `primaryApiKey` reads signed out, as a run on it would be. The harness's login takes `shared` for this place, and `claudeLoginStatus` takes the platform.
- The harness's `startClaudeLogin` returns the sign-in (`ended`, which says how it ended, and `stop()`) in place of nothing, and starts the CLI in the person's home rather than a temporary one when no home is given.
