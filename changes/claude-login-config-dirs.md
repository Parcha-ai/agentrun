Claude Code's login on this machine now uses the folders the server's env gives it only when they belong to the server's own user, as it already did for the home. Those folders are `CLAUDE_CONFIG_DIR`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, and `ANTHROPIC_CONFIG_DIR` or else `XDG_CONFIG_HOME`'s `anthropic`. Each one must be a folder that user owns, or a folder still to be made inside one it owns. The home and these folders are judged by one rule, so that no other user can change where the path leads after the check:

- The path is walked as the system walks it, one name at a time, so a trailing slash, `.` or `..` hides nothing, and a `..` after a link goes up from where the link leads. Each link on the way, and each link in the chain it leads through, must be one that user or root made.
- Each folder above the real folder must be that user's or root's, and not one others may write in (anyone, or its group, unless that group is the user's private one), unless the sticky bit keeps each entry its maker's (as /tmp has it).
- The folder itself must be that user's and not open to others' writes by the same rule. So must the folder a still-to-make one is made in, sticky or not, so a folder still to make in /tmp is refused, root's included.
- The CLI gets the real path the check looked at (the home included), from the same look: each decision (a run, the sign-in, the Settings view's line and status check, a turn-on) walks the folders once and takes the login, or the refusal, from that walk, never the path as given. Where the folders are refused, the view's `command` is empty and its `folder` is the folder as the env names it. Where the env's path has a link on it, the shown sign-in line and the CLI now name the folder the link leads to. On macOS the CLI names its Keychain item after that folder, so a login the person's own Claude Code keeps under a path with a link reads as signed out until it is signed in again from here.

A server started under a sudo that keeps the env (root, with the person's `CLAUDE_CONFIG_DIR`) no longer signs Claude Code in as root inside the person's folder. Where a folder fails the check, the turn-on and the sign-in at this machine's login are refused (403) in words that name the variable and the folder, and no run goes on the login. AgentRun's own login keeps its folders in the data folder, so the env's folders refuse nothing there, but the home rule above applies to both places. A login saved before on folders, the home's included, that fail the check is kept, not turned off: the start logs why it is not used, every read refuses it in those words, and it is back once the folder is mended (a chmod, or the server started as the right user). A chmod needs no restart: a run's check, a save's, a template's plan or apply, and capabilities look at the folders again, so the login is offered and runs again as soon as the view reads it signed in, and stops again once its folder is refused. Such a request asked while the server is still making the offers again from such a change, or from a turn-on or turn-off, waits for them, and the server logs `claude_login_wait` as it waits, with `why`: `queue` (behind a turn-on, turn-off or sign-in), `refresh` or `turn`. A sign-in, a turn-on or a turn-off never waits for those offers. The Settings view says such a login is `refused`, with why, and offers Turn off, which removes it; until then no API key is made. The refusal words now name the server's user (`uid 501 (svc)`, say), the home's refusal included. A folder that is the user's but open to others' writes is refused in words of its own, which name the open folder, its mode and the `chmod g-w,o-w` that closes it. A folder of this machine's login still to make is made by AgentRun at the turn-on and before the CLI's sign-in, 0700 whatever the umask, and checked again before the CLI gets it, so a login the CLI signs in there is not refused after.

Where the env's `HOME` is another user's and the login therefore uses the server's user's own home, the sign-in line the Settings view shows now carries `HOME=<that home>`. Before, it left `HOME` to the terminal, so the line run in the person's terminal signed in to their own home, which the server never reads. The harness's `ClaudeAgentLogin` has a new optional `homeApart` that asks for this.

A folder its group may write in is the user's alone where that group is the user's private one, as the local account files alone say: `/etc/nsswitch.conf` takes users and groups from those files only (`files` or `compat`), and the group is the user's primary group, which no other user has as theirs and which `/etc/group` lists with no other member. So a umask of 002 under such a group refuses nothing there. A switch that also asks another source (sssd, LDAP, NIS, winbind, or systemd's user records, as recent Ubuntu, Debian and Fedora installs do) can give the group members the files do not show, so there such a folder is refused.

Behaviour change: a login that ran before is refused, at either place, where the server's home is a folder anyone may write in, or its group where another user is in it, or is reached through one (a home on a volume whose group is set for a pod, 2775, say). So is a login on this machine's folders where one of these variables points at another user's folder, or reaches through another user's link or folder, or through such an open folder. A group shared with other users, a group that is not the user's primary one, one `/etc/group` does not list, account files that defer to a directory service (a `+` or `-` line), and any group where `/etc/nsswitch.conf` asks a source other than the files for users or groups, or is missing, all count as open: under a umask of 002 with such a group, a home, a `~/.config` or a `CLAUDE_CONFIG_DIR` folder made by hand is refused until it is `chmod g-w`. The setting stays. Start the server as the person whose Claude plan it is, with that person's variables, and make the folders on the way writable by their owner alone.
