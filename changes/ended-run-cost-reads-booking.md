An ended run whose end stored its cost unknown, because its read of the run's booking failed or ran past its bound, no longer reads `cost.usd: null` on `GET /v2/runs/{id}` (and the runs list's `RunSummary`) while that booking is priced. The run read reads the booking itself, as it already does for an ended run's figures since v0.1.0-beta.39, so the next read gives the booked total, with `all_in_usd` beside it. A charge of no known cost still reads `usd: null` with `unpriced` and `so_far_usd`, as before. When the booking has no request to read either, the run's `Cost` says why in a new field, `unknown: "booking_unread"` (costunknown/1), never a bare null: a reader that bills holds the run, as on any null. The console says "Unknown · cost not read" for it.

The store heals too. When a run read finds such a run's stored cost unknown and its booking priced, it writes the booked figure back in one conditional write, so `/stats`, `/usage`, the runs list and the learning cost and bill (`unknown_cost_runs`, `unattributed_usd`) read it as well. Only an unknown becomes a figure: a stored figure is never written over, and a run reopened or ended again since keeps what its end wrote. At start the server sweeps the store for ended runs whose stored cost is still unknown, a page at a time and in the background, so a run nobody reads again heals too, and when it read any it logs one `cost_heal` line counting the runs it read, healed and failed to read, with no ids; a run whose read fails is passed, and its next read heals it. A run whose booking cannot be read keeps its unknown cost there, counted unpriced as before. SQLite and Postgres alike; no schema change.
