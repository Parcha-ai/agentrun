A signing secret the server mints is shown once, as `signing_secret`, and only to the owner's session. A webhook trigger's secret (`POST /v2/triggers`, `POST /v2/triggers/{trigger_id}/secret`) and the outbound webhook's (the first `PUT /v2/settings/webhook`) are in the minting answer to the owner's signed-in session, or to the console the launch link opened on a loopback-bound server with accounts off. The API token gets the trigger with `secret_set: true` and, in `note`, "Open the console to see this trigger's signing secret once: rotate it there.", or the webhook with "Open the console to see this webhook's signing secret once: remove it and save it again there." Rotating a trigger's secret is a secret write: the token is refused (403) in the secret-write words, and the secret it would replace still signs. Each answer and read carries the secret's metadata as `secret`, in the one shape (name, set, source, changed_at), never the value: a trigger's is named `trigger:<id>` (GET and the list too; `changed_at` is in the create's and rotation's answers, null on a read), the outbound webhook's `webhook:outbound`, its `changed_at` the time the secret was made, kept across a URL change, and null for a webhook set before this release. A template that makes a webhook trigger says so in its apply answer, a warning under `triggers.<i>.secret`. Upgrading: the shown-once value moved from `secret` to `signing_secret` in those three answers, and `secret` is now the metadata object; a script that created webhook triggers with the token gets no value at all: take the secret from the console's Triggers screen (rotate it there).
