`ModalProvider` and `E2BProvider` mount the run's folder from an Archil disk: both declare `mount: ["archil"]` (`MOUNT`). For a spec with `mount: { kind: "archil", disk, region, folder, token }`, `create` runs the shared Archil steps (preflight, the takeover of the run's lower epochs, mount or revoke with the token on the helper's stdin, serve) as root through the vendor's own exec, after the daemon is in place and before init starts, then reads the mount back from inside. The token reaches the helper's stdin alone: never an argument, a tag, metadata, a read-back or an error.
- An Archil spec takes network `"none"` and the run's `agentrun.run` and `agentrun.epoch` labels. Its tools run as `agentrun-tool`, 2510:2510: Modal makes that an Archil spec's default user and refuses any other; E2B takes an Archil spec only from a provider made with `daemonUser: "2510:2510"`, and refuses a spec label named `agentrun.mount`.
- The vendor network stays on, for root to reach Archil: Modal drops `blockNetwork`, and E2B keeps internet access on with public traffic off. The tools' network `"none"` is init's own, read back from inside by the probe, which refuses the computer when a tool reaches an address.
- Modal: the sandbox's command is always the entrypoint, which waits for a root-made gate (`/opt/agentrun/archil-mounted`) as well as the daemon, so no tool runs before the folder is mounted. The spec tag records the mount as it reads back, under the claim's epoch. `ModalTimeouts` and `E2BTimeouts` gain `mountMs`, the bound of each root step.
- E2B: each root step is a background root command with stdin (`sendStdin`, then `closeStdin`); the metadata `agentrun.mount` records the mount's kind and source.
- `connect()` on an Archil computer syncs the folder after every call that may change it. `release` lets the folder go (a final sync, then checkin) while the computer runs, then deletes it whatever that answered, and says a folder not let go in its error. `list()` reports the recorded mount under the epoch label; `attach` reads it back from inside and refuses drift.
- The conformance suite: `src/conformance/archil.ts` gives every remote provider's module one Archil run folder (`archilRunFolder`, `archilSettings`, `ARCHIL_ENV`), reached from outside through the disk's object API (the host's `disk` SDK, or one given). The Modal and E2B modules export `mountFor("archil")` and `settingsFromEnv`, reading `COMPUTER_ARCHIL_DISK`, `COMPUTER_ARCHIL_REGION`, `COMPUTER_ARCHIL_TOKEN`, `COMPUTER_ARCHIL_API_KEY` and `COMPUTER_ARCHIL_S3_URL`.
