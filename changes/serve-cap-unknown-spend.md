A pi run's spend cap refuses once what the run has spent is unknown, as claude-agent's and codex's already did, prices a request stopped mid-answer at the most it can have cost, and refuses a model whose output is priced but that names no output ceiling on every harness.
- The spend a pi run's process reads back from its store at start follows the run's own timeline cost, so every rule the timeline keeps for an unknown cost holds: a request or compaction marked as sent with no answer (a crash cut it), a cost that is not a number, a cost still pending. Before, each of these counted as $0, and a capped run kept spending past what it could count. Now every later request is refused with `spend_cap_reached`, and so is every request after an answer in the same process whose cost is unknown.
- A request stopped before its end (`POST /runs/{id}/stop`, or a summary that failed) counts at the worst case the cap held for it, never at the cut stream's own usage, which is not what the provider charged (the Responses API reports none until the end). Its end mark (`agentrun.request_ended`) carries that figure as `heldUsd`, so a later process counts it the same. A capped pi run that is stopped and sent another message goes on while its cap allows, and is refused with the cap's message once it does not. A stopped request from a store written before this release has no figure and still reads unknown. The run's shown cost is unchanged: a stopped request shows unknown.
- A request the cap refuses gets a start mark of its own (`agentrun.request_started` with `capRefused: true`) before pi writes its error entry, so that entry no longer stands for an earlier request a stop or a crash cut, and the run's cost shows unknown there, never $0.
- A model with no output ceiling (no max output tokens and no context window) was priced at no output, or at a worst case that was not a number and passed every check. Under a cap it is now refused with `spend_cap_reached`, unless its output costs nothing at every price tier, which keeps a known worst case. No model in pi-ai's catalog, and no gateway model serve builds, is affected.
