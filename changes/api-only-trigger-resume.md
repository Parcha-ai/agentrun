API-only server (`AGENTRUN_API_ONLY=1`): a trigger that turned itself off after 5 failed firings in a row (`disabled.reason` `auto_paused`) can be turned on again. Before, every trigger route was `404` there and there is no console, so nothing could turn it back on: a redeploy left it as it was, and an unarchive turned on only the triggers the archive had turned off. The token now reads the triggers (`GET /triggers`, `GET /triggers/{id}`, `GET /triggers/{id}/firings`) and turns one on or off with `PATCH /triggers/{id}`. On this profile the PATCH takes `enabled` alone (any other field is `422 not_allowed`), and turns on only what the apply makes here: a schedule or a feed trigger, with the launch hook set. Anything else is `422` under `enabled`, since its firings would start runs on the server's keys or wait on a hook this profile refuses. Making, deleting or firing a trigger, and its secret, are still `404`.

The CLI's `agentrun triggers update <id> --enabled` (or `--no-enabled`) sends the same PATCH and works against an API-only server too. The Slack message for an auto-paused trigger now names each way to turn it on: the console, `agentrun triggers update <id> --enabled`, or `PATCH /v2/triggers/{id}` with `{"enabled": true}`. An API-only redeploy that skips a trigger the agent still has on now says that PATCH with `{"enabled": false}` turns it off. Before, it said to archive the agent.
