serve gains the Archil backend of the Workspace port, unused until the cutover: a run's folder on the owner's Archil disk, through the disk's file API and serverless exec (Archil's Node SDK, `disk` 1.12.0, pinned). It takes the disk, its region, the account API key as a function asked on every call (it reads no environment), and the disk's S3 endpoint (the setting `AGENTRUN_ARCHIL_S3_URL`), which must be https on Archil's host for that region; the SDK and the ranged read both use that one endpoint, and a ranged read follows no redirect, gives up after a timeout, and reads no more than its range (a reply with another slice is refused). Nothing is mounted on the server or a runner, and no program runs there. Every key it sends is under the run's folder (`runKey`, beside `runFolder` in the one layout module). A write is one put and returns once Archil has committed it; an append is cut into calls of at most 1 MiB, in order, each after any running exec, and one that fails says only what is known (the bytes appended, read back from the file's size, or else that the failed chunk's outcome is unknown and the file must be re-read); a read with a range sends the Range header; grep is the disk's grep, its matches sorted, a file over 8 MiB skipped, stopping at its cap or at one deadline that covers its listings too. exec mounts the run's folder and its exec spill folder beside it (`exec-out`), nothing else of the disk, in Archil's default image unless an image is set for every workspace (one given must be pinned by digest), spills stdout and stderr to files there that are read back through the file API (Archil's own exec answer is cut below 14 MB) and deleted on every path (a cleanup that leaves files is reported through `onCleanupFailed`), with `sweep()`, queued with the execs, for what a killed exec or a failed cleanup leaves, folders included, runs argv with exactly the given environment, refuses a deadline over 295 s (Archil cuts a call at 300), refuses a symbolic link on the way to its cwd, reports a signal as code null with the signal's name, and answers once the command has ended, so onOutput gets each stream once. Archil's file API never follows a link an exec made: it lists one as a file, and reading it fails UNAVAILABLE. With no computer, every background call is refused. mountSpec and attach are refused for now: an Archil folder in a computer is mounted by the computer's helper, which comes later.
