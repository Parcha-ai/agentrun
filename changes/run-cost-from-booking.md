An ended run's cost is one figure, read from its booking, and no run reads as ended without it. `GET /runs/{id}`, the runs list and the stored `cost_usd` of an ended run now read the same sum of its booked requests, paid tool calls and decisions (each request counted once), where the view used to read pi's own price for an answer whose booking had not landed yet. A run's end waits for every booking whose write has begun (bounded at 30 s, with a warning when it gives up) before it writes the end, so the final request's booking is never left behind. The end's cost is read apart from its metrics, so metrics that time out no longer drop the cost.
A model request cut with no answer and no usage (its runner lost mid-request) under a cap is booked at what the cap held for it, the most it can have cost (`runner.turn` `rule: "cut"`, `atMost: true`), so the run's cost stays known instead of turning unknown. A cost that counts one says so: the run's `cost` and the timeline's usage row carry `upper_bound: true`, the usage row reads "Cost: at most $0.97 over 2 model requests", and the console shows "at most $0.97". A cut with no hold (no cap) or a paid tool call that was cut stays unknown, as before: a paid call's `runner.request` now says `paid: true`, so a later process that books it cut never reads its fee as a bound. A hold is never counted as spend: when another charge leaves the total unknown, `so_far_usd` sums the exact charges only and each request booked at its hold counts in `unpriced`, and `upper_bound` is set only on a known figure. The usage row of a CLI or workflow run, and a pi run's with side requests, now carries `upper_bound` and "at most" the same way. The run row stores the bound beside its cost: a new `cost_upper_bound` column (SQLite: added when the server opens a store, and a runner refuses a store until then; Postgres: migration 0014), which `GET /runs/{id}` and the runs list read as `cost.upper_bound`, so the view, the list and the column always agree on the figure, the bound and an unknown. A stored bound is never read as spend: `GET /usage` counts a run whose stored cost is a bound as a run of unknown cost (in `unpriced_runs`, with only its exact charges in `total_usd` and its lines, by every grouping and meter), and the runner's `run_ended` log line says `cost_usd=unknown` with `cost_usd_at_most` beside it. An end whose cost read fails reads it again (three tries within its 30 s bound) before it stores the cost unknown, and `GET /runs/{id}` of an ended run reads the stored cost, so it never shows a figure the list and the column do not. Learning's figures say no "at most", so they read a bounded run's cost as unknown: a look-back's `look_back_usd` and `job_cost_usd`, a learning batch row's `cost_usd` and `total_usd` (a batch stops `cost_unknown` on one, as before), the cost series, the money rule's all-in cost, and an agent's learning impact (`median_cost_usd`, `cost_runs`).
A cost marked `upper_bound` (the run's `cost` and the timeline's usage row) now also carries `so_far_usd`, what it is known to have spent with no hold in it, and `unpriced`, how many requests it counts at their hold, so every reader that adds more charges to it keeps the hold apart: a workflow's usage row joined with its decisions, its `GET /runs/{id}` cost while it runs, and its graph's `totals.cost_usd` (which says no "at most", so a sum with a hold in it reads null there). A charged $0.01 beside a $0.25 hold and a decision of unknown cost reads "$0.01 known, 2 not priced", no longer "$0.26 known". The over-cap row says "Spent" of the known spend only; a bound past the cap reads "At most $0.26 spent, at most $0.06 over the run's cap". Breaking: `so_far_usd` and `unpriced` are no longer absent whenever `usd` is known; a client that took their presence to mean an unknown cost checks `usd === null` instead.
A request billed to a ChatGPT plan costs the run $0 however it ended: one cut by a crash or stopped is booked `rule: "cut"` (or its stop's rule) at $0 with `billing: "plan"`, never unknown, so a plan run's cost no longer blanks when a request is cut. Its `runner.request` says `plan: true`. The stored `cost_usd` and the runs list of a plan run now read the known figure the view already showed.
A workflow run's stored `cost_usd` is read from its booking by the same rule (`GET /runs/{id}` of an ended workflow run reads it too), no longer from its cap's figures. Breaking: a workflow request stopped while it streamed now leaves the cost unknown, as on an agent run, where it used to store the cap's estimate; a decision cut by a crash counts at its hold as an upper bound.
