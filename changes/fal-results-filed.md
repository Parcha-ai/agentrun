A completed fal job's `result` is kept in the run's files at `evidence/fal/<request_id>.json`, so a step that needs the whole result (an audio clip's timestamp chunks, say) reads it from the file instead of the model retyping it. The run's MCP gateway files it when an answer of a fal server (`run_model`, `submit_jobs`, `wait_for_jobs`) carries a job whose `status` is `completed` and which has a `result`. The answer the model reads is unchanged, byte for byte. Only a request_id in fal's UUID shape names a file; any other id (a path, `..`, a plain name, a UUID with a suffix) is not filed, and the call works as before. A file is saved once: whatever is already at the path (a file, a folder, a link) is kept, and a link on the way is never followed. A file that lands at the path after the check is kept too: the file is made in one step that never replaces (`Workspace.writeNew`, on the local Workspace and on one attached to the run's computer). A result that can't be filed never fails the call. In Mode 2 the gateway files through the run's computer when it mounts the run's folder. With no computer mounting it, the gateway files over the Archil disk's file API, which has no `writeNew`: nothing is filed, and the call works as before (follow-up Parcha-ai/agentrun#3777). `web_save` now saves through the same helper. Where the Workspace has `writeNew` it also keeps a file that landed after its check. Where it doesn't (an Archil run disk), web_save keeps its check then a write, as before (follow-up Parcha-ai/agentrun#3777). The parsing is fal's meter's (`McpMeter.results`), so the gateway stays the same for every server.
