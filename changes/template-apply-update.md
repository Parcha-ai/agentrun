Applying a template again can update the agent it made instead of making a second one. `POST /v2/templates/{name}/apply` takes an optional `agent_id`: the apply writes a new revision of that agent, answered 200 with the same id, and its runs and its learning (corrections and workflows) stay. The parameters and grants are checked as a fresh apply checks them. Its triggers are matched by name: one the agent has is changed in place (a feed trigger keeps the items it has seen, a webhook trigger keeps its secret, and one the owner turned off stays off; a trigger setting its new version leaves out, `catchup_window_s` or `max_active_runs`, goes back to its default, as a fresh apply would make it; a source the new version leaves as it was is not rewritten, so a schedule keeps its next time, and an every-N-seconds one with no `start_at` keeps the grid its first apply set), a new one is made, and one the package made or kept and no longer lists is removed. Each trigger now records which template package made it, which no API body can set and which moving the trigger to another agent clears: a trigger the owner added, one moved in from another agent, and one made before this release are left alone, and a removal that fails is done by the next apply. A Composio trigger an update removes goes at Composio first: if Composio does not delete its instance, the trigger is kept here as it was (on or off, its config sealed) and the next update removes it; a dropped one is named in the answer's `warnings` with what is left at Composio. Updates of two agents at once that remove triggers sharing one Composio instance delete it with the last of them. A trigger moved to another agent while an update runs is neither changed nor removed. A trigger without that record that has the name of one of the package's triggers (the owner's, or one an apply made before this release) is taken over only when it can be changed in place, and is the package's from then on. If it would have to be removed and made again (another kind, or another Composio server, event or config), or another template package made it, the update is refused with 409 `name_taken` under `triggers.<i>.name` before anything changes: rename or delete that trigger, then apply again. A Composio trigger whose config seals a key from a parameter keeps it sealed when the update sends the same key; a different key, or another server, event or config, makes it again, as a change of source kind does: the old trigger and its Composio instance are removed first, and the new one stays off if the owner had turned the old one off. If Composio does not delete the old instance, the new one is not made, the old trigger is kept as it was, and the apply answers 424 `upstream_failed`; the next apply, once Composio deletes it, makes the new one off where the owner had turned the old one off. A source the package leaves as it was is compared with its defaults filled in, so a feed whose package gives no `every_s` is not polled again by an update that leaves it alone. What the package sets and its new version leaves out (an input or answer schema, a checkout, a default cost cap, learning) is removed from the agent; the harness, computer and sdk references the host set are kept, and an agent in the box keeps the shell tools a fresh apply gave it when the package names none. The store gains a nullable `triggers.template_id` column: SQLite adds it when the server opens the store (a runner waits for the server), and Postgres adds it in a new migration. Two updates of one agent run one after the other, and an update whose read of the agent went stale before it wrote (an edit, or an update on another server) answers 412 `precondition_failed` with nothing changed. An agent not made from that template is refused with 422 under `agent_id`, saying where it came from, and an unknown id is 404. A fresh apply of a template whose same parameters already made a live agent still makes one, with a `duplicate` warning naming that agent. The agent keeps only a keyed digest of the parameters it was applied with, never the parameters. In the console, a template that already made an agent shows "Update <agent>" next to Apply.
