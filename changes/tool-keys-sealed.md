A tool's key is saved by name through the settings API and kept only as ciphertext, opened only by the server on its host. `GET /v2/settings/tool-keys` lists the keys (`parallel`, `monid`, `browserbase`), what each unlocks and each field's `set` and `source`, never a value; `PUT /v2/settings/tool-keys/{id}` with `{values: {NAME: "..."}}` seals each value with AES-256-GCM, bound to its field's name, into `DIR/tool-keys.json` (0600), and `DELETE` forgets it. The seal key is `AGENTRUN_SEAL_KEY`, which the launcher takes from the environment or keeps in `agentrun/seal.key` under `$XDG_CONFIG_HOME` (or `~/.config`), made the first time, outside the data directory; a run's process never gets it. With none, nothing is saved (`409 no_sealing_key`) and `capabilities.features.tool_keys.at_rest` is `unavailable`. A field the server is started with is `409 key_set_by_server`. A stored value that does not open (no seal key, another one, a damaged file) never stops the server: GET marks it `stored_unreadable` and `reenter` says why, and the log says so once, naming the file. `MONID_API_KEY` joins the launcher's secrets. pi-durable-agent exports the vault's `seal` and `unseal`, unchanged, for a host's own secrets.
In a container, pass `AGENTRUN_SEAL_KEY` or mount a directory at `XDG_CONFIG_HOME`: the container's own `~/.config` goes with it, and a new one's fresh seal key does not open the keys the volume holds.
