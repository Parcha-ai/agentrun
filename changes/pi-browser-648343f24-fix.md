`@parcha/pi-browser`: three security fixes. The local Chrome's DevTools socket accepts only the Stagehand extension's Origin, not every Origin: the provider launched Chrome with Stagehand's default `--remote-allow-origins=*`, and in a real Chrome for Testing 155 a web page in the run's own Chrome could open the browser-wide DevTools socket when given its URL. The provider now computes the one Origin the extension's service worker connects from (Chrome names an unpacked extension by the SHA-256 of its real path) and allows exactly it; a directory that cannot be resolved refuses the launch as `browser_unavailable` and never opens the socket to every Origin. The pi coding agent refuses to browse under a `deny` or `ask` action policy it cannot hold: it never opened the request observer that enforces that policy, so every request the page sent went out, irreversible ones included; every browser tool now answers `browser_unavailable` naming the action policy (`web_fetch` is unaffected, and `allow` browses as before). A navigation policy the provider cannot enforce refuses the session, naming `navigation.block` or `navigation.allow` and the provider: before, the local, Kernel and assigned providers accepted either and applied neither, and no provider enforces a block list; an allow list is enforced where the new optional `ProviderCaps.navigationAllow` is set (Browserbase). A live durable session reused later meets the same check as a new one at create: the session record keeps the allow list the provider applied at create, and a reused session that was started with no list, or a wider one than the policy now sets, is refused with the same named refusal (a record from before this change fails closed).
