The `browser` tool can run on a headless Chrome on the server's own machine, held to public addresses by the egress proxy: an operator turns it on with `--browser-chrome PATH` (or `AGENTRUN_SERVE_BROWSER_CHROME`), and `chrome` picked (`PUT /v2/settings/tools` `{browser: {provider: "chrome"}}`, or an agent's `definition.tool_settings`) then runs each session there. Off by default; a server given none keeps `chrome` unavailable (`409 agent_not_runnable` at a run), and `auto` never picks it.
- The path is checked at the start: one that is not an executable file refuses it, and so does a Chrome that cannot start here with its sandbox on (checked once, headless, with nothing reaching the network), or AgentRun running as root. The sandbox is never turned off, by no setting; a session whose Chrome cannot start it later is refused, saying so. Each session starts a fresh Chrome of the run's own (headless, a fresh profile under the run's directory, removed at release, with nothing loaded into it, its DevTools socket on a loopback port picked for it), never one already running.
- Every request goes through the kernel's egress proxy, with no host list, run in the run's process: `--proxy-server` at a loopback relay to its socket, `--proxy-bypass-list=<-loopback>` (loopback and link-local through the proxy too, but Chrome's own DevTools socket), `--host-resolver-rules` that resolve nothing but those two, `--disable-quic`, and `--webrtc-ip-handling-policy=disable_non_proxied_udp` (no ICE candidate, no STUN packet; Chrome 155 and 156 ignore the `--force-` spelling). The proxy refuses, after its lookup, loopback (this server's port among them), private, link-local, metadata and this machine's own addresses; a page that steers the browser there gets its refusal. A real-Chrome test proves it in CI's real-chrome job.
- No files of the server: every client of the local Chrome's DevTools socket, the code a model runs in it included, goes through pi-browser's DevTools guard, which passes only the commands pi-browser and Stagehand send (nothing about the server: no command line, system information or processes) and refuses a navigation or a new tab to anything but `http`, `https` and `about:blank`, a file handed to a page, a download sent to a directory, an extension load and driving an extension's page; the extension's copy loses the APIs that would go around it (tabs, windows, debugger, its worker's clients, an offscreen page but Stagehand's heartbeat, a request rule that does more than allow or block), under both of its API namespaces (`chrome` and `browser`), and what it keeps takes each call's fields once, as plain values, into an object of its own, so code run beside it cannot loosen the lock by replacing a built-in or handing it an object that lies.
- No saved sign-ins: none is made, leased or handed to a run on the local Chrome, a profile is refused by name, and `features.sign_ins` is false while the server's browser is the local Chrome.
- A run kept on `chrome` is unavailable at a launch on a server no longer given one, never moved to a vendor. `features.browser` can be `chrome`, and a tool's `resolves` can read `chrome` (the served contract's pattern takes it). The local Chrome takes no tool key.
- Its minutes are free by default (`cdp`, $0 an hour); `AGENTRUN_BROWSER_USD_PER_HOUR_CDP` prices them, and the run's spend and cap count them.
- A run whose process dies while its local Chrome is open (a crash) gets no stale browser: the Chrome that outlived it reaches nothing (its relay went with the process), so the reopened run releases it (stopped, its profile removed), and its next browser call opens a fresh one, told the last session ended during an interruption.
- pi-browser: the cdp provider's `chrome.args` may be a function of the session's DevTools port, which it then picks free before the start (`--remote-debugging-port`), so a host's arguments can name it; `chromeArgs` takes `debuggingPort`. Its `chrome.guard` puts a session's DevTools socket behind a guard (`providers/cdp-guard.ts`: `cdpRefusal`, `allowedUrl`, `allowedTarget`) and locks the session's copy of Stagehand's extension. A provider may declare `caps.processBound`: a session usable only from the process that started it, which a reopen releases rather than keeps.
