A webhook trigger takes GitHub's deliveries and fires only on the events it names. `signature` names the trigger's scheme from one table, `standard` (Standard Webhooks, the default, as before) or `github`; a request is checked by the scheme whose signature header it carries. `source: {kind: "webhook", signature: "github"}` checks `X-Hub-Signature-256` (HMAC-SHA256 of the raw body keyed by the whole `whsec_...` secret, which the owner pastes as it is into the GitHub webhook's Secret) and keys each firing by the SHA-256 of the raw body, which the signature covers (`X-GitHub-Delivery` is not signed, so it only names the delivery on the payload's tag). `accept: [{event, actions?, where?}]` takes a delivery only when a rule matches its event (GitHub's `X-GitHub-Event`, or a Standard Webhooks body's `type`), its body's `action`, and every condition on its body, each a JSON pointer with `in` (equals one of the values listed), `exists` (true or false) or `prefix` (the first line of a string, trimmed, starts with it, ignoring case). A verified delivery no rule takes, GitHub's `ping` among them, answers `200 {"ok": "ignored"}`, fires nothing and is logged (`condition=hook_ignored`). A trigger with `accept` starts a run for each event it takes, even while its last run is active; the server's run limit still holds (a start it refuses is tried again, up to 20 firings due, then `429`). A request signed under a scheme other than its trigger's, or carrying no scheme's signature header or more than one, is the one `401`, as any bad signature is. The payload's tag names the scheme, event and action (`<trigger-payload source="webhook" scheme="github" event="pull_request" action="opened" delivery="..." untrusted>`), so the agent reads what it was given; a plain webhook's tag now carries `scheme="standard"`. GitHub signs no timestamp, so there is no 5-minute window: a delivery replayed within a day, under any delivery id, is the same firing and starts nothing, and one replayed after a day would fire again, a risk taken over TLS. Each trigger keeps its last day's firing keys (at most 5,000, the oldest let go first, logged as `condition=trigger_seen_full`), so a flood of events cannot push an earlier one out of its day; one seen whose firing is no longer kept answers `200 {"ok": "duplicate"}`. A trigger with `accept` may set `max_active_runs` (1 to 1,000): past it a firing waits due, never skipped, so one such trigger cannot take every run slot. Capabilities list the schemes (`features.triggers.webhook.signatures`). A payload's closing tag in any case (`</TRIGGER-PAYLOAD>`) is defused, as the lower-case one was. Upgrading: nothing to do.
