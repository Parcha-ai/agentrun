A learned workflow that serves is audited against the agent itself. A run it serves first is drawn at 1 in `learning.audit_every` (10), then 1 in `learning.audit_every_later` (20) once its revision has served `learning.audit_later_after` (50) runs; the draw is seeded from the run's id. A drawn run starts a shadow run: the same agent on the same input with learning off. Only runs started over the API are audited, and only for an agent every tool of which only reads (an MCP tool by its `readOnlyHint`, a built-in by the replay's read list): a shadow never writes a second time. The shadow is no row of the run list, GET /runs/{id} reads it with `audit_of`, and its cost is the served run's learning cost (in its `cost.usd` and the agent's cost series).
  - Each finished audit is a row of `audits.jsonl` in the agent's learning folder, read with GET /agents/{agent_id}/learning/audits: `{run, shadow_run, workflow, digest, promoted_at, source, agreed, served_cost, shadow_cost, at}`. An owner's grade of a run the workflow answered alone is a row too (`source: "grade"`). A shadow's audit is written to the ledger when it starts, so it is settled however many runs start after it.
  - `learning.hold_disagree` (3) disagreements in the newest `learning.hold_window` (10) rows of the revision's current promotion (`promoted_at`) hold the workflow (promotion `source: "audit"`, with the rows on the record's `audit`). The agent's next run asks one recompile with those disagreements as data, and the check runs on its usual inputs plus the disagreeing ones. A second hold within `learning.stop_window` (100) served runs stops it (`audit.stopped`, "stopped: the workflow disagreed with the agent twice") and asks no compile.
  - A check whose every input stopped at a write stops with the cause and spends no recompile.
  - A check's `outcomes` add up to its `n`: a replay run never created by the check's deadline is `failed` there too, and the record's new `check.unstarted` counts those. A check none of whose runs was created reads `failed` on GET .../replays/{replay_id}.
  - The promotions read's `serving` gains `state` (`serving`, `checking`, `held` or `stopped`), `check` (the newest decided check's numbers), `audit` (the hold bar and the counted rows), `audits_off` (why none of the agent's runs is audited, e.g. "audits off: send_email can write", else null) and `not_auditable` (the serving revision's runs a trigger started, never audited).
  - Upgrading: the graded hold is gone, and promotion `source` no longer takes `"graded"`. A client that matched it should read `"audit"`. A client that builds the `serving` objects must add the five new fields. The six numbers are optional on `definition.learning`; each is a whole number from 1 to 1000, `hold_disagree` at most `hold_window`, else a 422 on `definition.learning`.
