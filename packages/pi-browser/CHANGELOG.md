## Unreleased

## 0.1.0-beta.15 (2026-10-16)

- `@parcha/pi-browser`: a session can ask for a named saved profile. `SessionSpec` and `BrowserPolicy` take `profile: { name, save }`, `ProviderCaps` gains `profiles`, and the session record names the profile (the name only; older records read as none). The local Chrome (`cdp`) keeps a named profile in its own directory, and a session can work from a copy that is never saved; Kernel keeps one through its own profiles (created on first use, one saver per profile); Browserbase keeps one as a context made on first use and remembered by name. A provider that cannot keep a profile, a profile beside a context id and a bad name are refused with the typed envelope before any session or record is made. A host can pass an optional `crossing` callback that is called at the two page-action moments a kill sweep needs (after one page action's answer is committed and before the next is dispatched; after a page action's driver call returned and before its answer is committed). `use_website` calls in one turn now run at once, each child in its own browser. `browser_release` on a session that already ended, or is ending, answers `already_released: { reason, at }` and one sentence beside `released`, which keeps its meaning.
- `@parcha/pi-browser`: a `snapshot` or `browser_read` that lands in a document a navigation replaced waits for the new one and reads once more, instead of failing with Chrome's "Cannot find context with specified id". The held-runtime reset (Stagehand's extension) fails on a target list the browser never gives, instead of reading it as "nothing held", and closes its last wake page before the socket goes, so a runtime still held no longer refuses the next attach. `exportFrameTracks` bounds each blob read by the session's deadline and the abort signal.

## 0.1.0-beta.14 (2026-10-16)

- Accept pi 1.3: the `@earendil-works/pi-durable` and `@earendil-works/chord` peer ranges now end below 1.4, with the floors unchanged (1.0.4, and 1.1.0 for `@parcha/pi-browser`). pi 1.3.0 pins its own packages to exact versions, so an install is all 1.2 or all 1.3; CI runs every package's whole suite on a 1.3.0 family as well as on 1.2.0.
  - On pi-ai 1.3, a tool call whose arguments are not a JSON object reaches no tool: pi-durable refuses it and shows the model the text it sent. A durable node's `submit` then spends none of its submissions. Before 1.3 the tool ran with `{}`, so `submit` answered with the schema's violations and counted one submission.
- `@parcha/pi-browser/recorder`: `exportFrameTracks` turns the recorded frames into one `frame.track` line per session: a WebM (VP9, constant `fps`, default 10) plus an index that maps run time to video time across gaps, with a slate while a gap lasts. `handle.drain(harness, ctx, signal?)` on the pi-durable adapter's handle resolves once no browser release is still running, so a host waits for it before it closes the harness. The index exports custody's vocabulary by name (`CustodyPort`, `AttachedSession`, `ToolOutput`, `BrowserFailureError`, `BrowserDriver`, `DriverFactory`, `DriverOptions`, `Overrides`) so a host can write its own tool.
- `@parcha/pi-browser`: a `cdp` kill never signals pid 1, pid 0, its own pid, or a process group the pid does not lead. A session's record and `browser_relaunch`'s answer name only the settings the provider applied (Browserbase applies proxies, verified, geolocation, region and context; Kernel and local Chrome none). A screenshot's `ask` comes back in `details.media.ask`. A classified failure names the browser provider, not Browserbase. A conversation's close evicts its repeat guard and idle entry. A page action's journal entry outlives its answer, and an identical retry waits for a look. Stagehand's extension losing its own CDP connection is a dropped browser, not the model's code error: a read reconnects and runs once more, a run is not repeated. A held Stagehand runtime is freed through its own close and never by closing its service worker, which under load was sometimes never restarted. Every Chrome the `cdp` provider starts gets a temporary directory of its own, removed with the lease, so Chrome's leftover entries no longer land in the host's `TMPDIR`.

## 0.1.0-beta.13 (2026-10-14)

First release of `@parcha/pi-browser`. It is versioned with the other packages of the repository it is published from; the release PR dates this section and gives it the workspace version.

- A browser for pi agents: `snapshot`, `run`, `screenshot`, `browser_read`, `browser_relaunch`, `browser_release`, `web_fetch` and `web_search`, with session custody that survives a crash, evidence filed with its SHA-256, typed failures, and credentials kept out of anything a model, a document or a log can see.
- Entries: `.` (the host-neutral core), `./durable` (the pi-durable adapter), `./coding-agent` (the pi coding agent's extension, what `pi install` loads), `./providers/browserbase`, `./providers/kernel`, `./providers/cdp`, `./driver/stagehand`, and `./testing` (a fake provider and driver, public on purpose).
- It depends on Stagehand, undici, zod and two HTML packages. `@earendil-works/pi-coding-agent`, `@earendil-works/pi-durable`, `@earendil-works/chord` and `@browserbasehq/sdk` are optional peers.
- `examples/live-grid`: one pi agent fans a task out to up to ten child agents, each in its own browser, and a local page shows them all live (a CDP screencast of a local Chrome, or a cloud provider's live view). The Kernel provider now gives a live view, and `./coding-agent` exports `findChrome`.
- pi versions: the pi-durable adapter runs on pi-durable 1.1 and 1.2. pi-durable 1.2 reads a tool result's `output` and treats a result with only `content` as empty, so every durable tool result (browser, web and site tools) carries the model's text under both keys; the pi coding agent's results are `content` in every version and are unchanged. Peer ranges: `@earendil-works/pi-durable` and `chord` `>=1.1.0 <1.3.0` (1.0.4 cannot build the adapter: `use_website` reads a child's last report by scanning entries in descending order, which 1.1 added); `@earendil-works/pi-coding-agent` stays `*`, as pi's package guidance asks. A test on pi 1.2 checks that no tool result reaches the model without its text.
- `use_website` (listed when the host passes `sites`): a model hands a task to an agent that works one granted website in its own browser, through a `SiteRunPort`. Only the declared answer, a started run or a report, reaches the model. `localSites()` runs each task as a child agent: a pi session in the coding agent, a task-owned conversation in pi-durable, with the browser tools and never `use_website`, and its browser released when it reports. `examples/use-website` is a runnable demo.
- `@parcha/pi-browser/recorder`: `frameRecorder` screencasts each browser session over DevTools (a local Chrome, Browserbase and Kernel all speak it) and hands `agentrun.recording/1` `frame` and `frame.gap` lines, with their JPEGs, to a sink you pass. It is read-only beside the session's own connections and writes nothing itself. Capture is JPEG at quality 60, at most 800 px wide and 10 frames a second per session. A gap is written, never filled (`process_killed`, `session_released`, `credential_on_page`). No frame is kept while a credential or a one-time code is on the page, and a live-view URL is never recorded.
- `@parcha/pi-browser`: `web_fetch` percent-encodes the characters RFC 3986 refuses before the provider sees the URL, and the redactor scrubs a registered secret in every spelling `web_fetch` can give it, including the half-encoded `#` form and a trailing `%` the URL completes. A `cdp` release that cannot remove the session's profile directory tries again when files arrive in it (ENOTEMPTY), and when it still cannot it names every directory left behind. A `cdp` release whose lease names a browser it does not own leaves the profile a live Chrome still runs on. A browser released with its directory left behind is over: the coding agent never reuses it, and retries the directory removal as cleanup.
