## Unreleased

## 0.1.0-beta.32 (2026-11-08)

- `@parcha/pi-browser` runs on Stagehand 4.4.0, whose zod (4.6.6) carries the fix for GHSA-mrhx-c7xc-m3w5. If you upgrade: a local Chrome must be 137 or later, `cdpProvider({ endpoint, extensionId })` and `AttachTarget.extensionId` are gone (Stagehand finds its extension by name), and `STAGEHAND_TELEMETRY` and `STAGEHAND_INIT_IN_PROGRESS` are no longer exported.
  - **One client per browser.** Stagehand 4.4 attaches one client to a browser at a time. Closing a driver now disconnects it, so the next attach (a handoff, a reconnect, a durable reattach) is allowed; an attach while another client holds the browser fails with "A Stagehand client is already connected".
  - **One Stagehand extension per browser.** Stagehand refuses a browser with two. The cdp provider uninstalls any other Stagehand extension from a local Chrome at each attach, so the lease's confined copy is the one used. A Chrome you attach to by endpoint must hold at most one.
  - **The extension dials the browser directly.** `AttachTarget.extensionCdpUrl` names the browser's own DevTools URL for the extension's connection; the cdp provider sets it for a local Chrome. A dropped connection between the driver and the browser then no longer stalls the next attach for 60 s.
  - **No trace export.** Stagehand 4.4 exports traces only to an endpoint it is given, and the driver gives none. The closed loopback trace port, and the request observer's exemption for it, are gone.
  - **Shutdown with no drain.** `handle.close()` of the pi-durable adapter now waits (30 s at most) for this process's `close` releases that no `drain` since covered to reach the provider. Before, a host that closed the Harness straight after them left the browser running whenever the driver closed fast enough, which Stagehand 4.4's does.
- The pi family is 1.5.0 exactly (pi-durable, pi-ai, pi-coding-agent, chord), with one typebox (1.3.27); the older-pi CI legs are gone. A pi 1.5 run store is SQLite schema 2, which pi 1.3.0 or earlier cannot open again, so there is no rollback past this release. Tool results are under `output` only. A browser charge serve fails to count makes the run's spend unknown, and a capped run then refuses its next paid call until the spend is known again. The door's `GET /events` and a recording's live lines read through an adapter on pi 1.5's `observeCommits` (pi-durable-disk `./internals` `watchEvents`, with no compatibility promise) until they move to `conversation.watch`. A failed run store's close releases this process's live browser sessions again; a normal close keeps them for the next run. A claude-agent, codex or opencode run opens on pi 1.5, and an image it reads through pi's read tool is read. particle-1's cap hold keeps Particle's list price over pi-ai's promotional catalog price; a request is still booked at OpenRouter's billed total. The agent store reader reads pi-durable schema 2.
- The owner watches a run's browser live from the console, read-only. `GET /v2/runs/{id}/browser` answers `{state: "live", viewer}` while the run's browser session is open (`viewer`, a link on this server with its token in the fragment), `{state: "none"}` when it has a browser with no session open, and `{state: "off", reason}` when it has none (no `browser` tool, or its browser resolves unavailable here); it takes the owner's password session in the console, never a token (`403`). Capabilities say so: `features.browser_live: {read_only: true}`.
  - The view is pi-browser's own viewer for every vendor, served by the run's process on a loopback port of its own: the vendors' own live-view links never leave that process. The process hands each session's viewer to the server in a file of that session's own in the run's directory, outside `work/` (`browser-live/<session>.json`, 0600, written whole), which goes when that session ends and never touches another session's; the token dies with the session, and the old link opens nothing.
  - The viewer's page and WebSocket are proxied under `/v2/runs/{id}/browser/live/` to that run's port alone: the page under `frame-ancestors 'self'` (the console keeps `'none'` everywhere else), the WebSocket from this server's own origin with the owner's session only. One viewer at a time (`viewer_in_use`).
  - The token is in no record, timeline row, run view, run file, home, log or the model's context.
  - `@parcha/pi-browser`'s live view takes `readOnly`: every input, navigation and dialog answer is dropped on the server (`held read_only`), `ready` says `readOnly: true`, and a watching viewer keeps no session open. A browser with no page yet (Kernel's headless one starts with none) tells the viewer `no_page`, and the page says "No page yet" until one opens.
- `createBrowserExtension` takes `beforeCreate` (type `BeforeCreate`): the host's step between a session's `creating` record (its tag, in the inventory) reaching the store and the provider's create, with the session's conversation, its tag and its commit. Nothing is created at the provider before it resolves; one that throws creates nothing, and the record ends released (`create_failed`).
- The owner takes over a run's browser from the live view and hands it back, and the agent can ask them to. Capabilities say so: `features.browser_live: {read_only: false, take_over: true, ask: true}`.
  - **Take over, hand back.** The viewer watches until the owner presses Take over in it; until then the run drops its input before the browser. The hold lasts until Hand back, the viewer is gone 2 minutes, or 15 minutes pass with no input. Meanwhile the agent's browser calls wait inside the tool, then go on with the page's old element ids dropped and the model told plainly that the person had the browser. Each change of hands moves the session's epoch, so an act a call took before it is refused. The run stays `working`; the timeline says "You took over the browser" and "You handed the browser back". A page's dialog that opens before the owner takes over never covers Take over; it says to take over to answer it, and its buttons stay off until they do.
  - **The agent asks.** `browser_request_handoff` is listed. The run reads `input_required`/`waiting` with `pending: {kind: "browser", instruction, completion_condition, asked_at, expires_at}`, a "Waiting for you: <instruction>" row, and `run.needs_input` with `pending.kind: "browser"`. The owner answers `POST /v2/runs/{id}/browser/hand-back` `{outcome: "done" | "cancelled"}` (their password session only): the first answer wins, a different later one is `409 handoff_answered`; unanswered for 15 minutes it expires. Handing the browser back in the viewer answers the agent's open ask on that session `done` too (first answer wins); a take-over that ends any other way (idle, away, the cap) leaves the ask open. An ask whose waiting row cannot be written fails, its tool's result saying so, with nothing held or left open, so asking again shows it. Each ask is its session's own: two conversations of a run that pick the same request id make two asks, each with its own instruction, answer and take-over.
  - **The owner's time counts.** A take-over and an ask hold 15 minutes of session time at the provider's price under the run's cap before they start (once per session: a take-over and an ask on it share one hold); with no room they are refused in the cap's words (in the viewer, or in the tool's result). A take-over that input keeps alive is held again every 15 minutes, and with no room the browser goes back to the agent at the cap. When the browser comes back, the time the person had stays held until the session's next charge books it. An ask a restarted run's process takes up holds only what is left of it, up to its expiry, and none once it is past.
  - A run's process that dies while the agent's ask waits is started again, and the new process takes the wait up: the owner's answer reaches the agent, or the ask expires. That holds when the owner answers after the process went and before the server found it gone: the hand-off is started again until its call's result is saved, the answer already on disk.
  - A browser session a restarted run's process keeps gets its viewer handed over again: the owner no longer reads `none` while it is live.
  - **The viewer's code is the server's own.** Serve now serves the viewer's page, script and style from the pi-browser it has installed, never from the run's port; only the viewer's WebSocket goes to the run.
  - `@parcha/pi-browser`'s live view takes `takeOver: { take(tag) }`, the driving gate gains `take`, `give`, `held`, `epoch`, `setPresent`, `untilFree`, `command` and `settling` (with `holdIdleMs`, `holdAwayMs` and `settleMs`: a hand-back wakes the agent only once the person's last command has returned, or `settleMs` has let it go, after which it no longer renews the person's turn), and `viewerAssets` is exported from `@parcha/pi-browser/live-view`.
  - The timeline's "Waiting for you" row for a browser hand-over (`agent.handover`) takes the host's redact, as a tool call's arguments do: a held value the model echoes in what it asks never shows; the run's `pending` for a browser ask is redacted the same way.
- A cancelled browser call no longer waits for an allowed request's response head before it returns. After the effect observer lets a held request go under allow, a call's flush waits, within its bound, for the response's head (so a redirect's next hop is decided under the same call); a cancelled call now stops that wait at once instead of after up to 1 s.
- `browser_downloads` no longer files a download Chrome is still writing. At the end of a download (sandboxed, on a busy machine), Chrome creates the file's name empty for a moment while the bytes are still in its `.crdownload`; the local Chrome provider listed that empty file as finished, so a call in that moment copied an empty file into the workspace with the empty file's SHA-256. Now such a file, and the `.crdownload` itself, are listed as still downloading and skipped with "still downloading; call browser_downloads again", and the next call files them; a read that finds the file replaced or changed by the time it ends is skipped the same way.
- A page request the browser loses before it is sent is told to the call, so the model can send it again. Chrome sometimes restarts its network service while the effect observer holds requests, more often on a busy machine. A request still on its way at that moment was never sent, and the page may never hear of it. `run` and `browser_upload` now say so in plain words ("The browser lost a request your page made before the request left the browser: POST https://…/path … so the request was not sent"), and list it in `details.lost` by method and URL, with no query, body or header. A call whose action fails says it too, after the error's own words. A form is told once.
  - `EffectObserver.record(listener, lost?)` takes a second listener, which hears of each lost request (`requestId`, `method`, `origin`, `path`) while the call records.
  - A lost request is never journaled, so it never counts as sent or allowed. If Chrome pauses it after all, it is refused and journaled denied. The observer holds and denies every request after the restart as before.
  - The observer asks Chrome for its network service's pid only while a held request waits for its pause: once per request (at most one question per 50 ms, which requests announced meanwhile share), then every 250 ms while it waits, never when idle, and never for an observer that holds nothing. A browser that refuses the question, or never names a network service of its own for 2 s, is not asked again. When a known service is gone, the call's flush waits for its successor, up to 10 s or until the call is cancelled; if none shows, its waiting requests are told lost and the next service is learned afresh. One question unanswered for 1 s counts as no answer, never as a restart, and is not kept; after three in a row (an answer with no result, or a failed question, counts too) the observer stops asking until a new held request. Over the 12-case effect matrix under deny that was 16 questions of about 3 ms each.
  - A form POST lost before its request existed is told by its frame's intent; if its Document request is paused after all, it is refused.
  - A redirect's next hop of a held request is held and decided under the same call: after an allowed request is continued, the call's flush waits, within its bound, for the response's head, and a 307 hop is journaled as a row of its own (`<id>#2`) instead of replacing the first hop's row. A hop after a redirect is never told "not sent", since its first hop went out. Before, a call could end between the hops, so the second hop's decision belonged to the next call or to none.
- Live view and take-over follow-ups: the watch-only viewer reads as watching, the page fills the viewer's window, a broken connection never writes an HTTP line into an open viewer, two take-over notices say what happened, and a run of several actions stops before an action on a new document.
  - A view-only viewer shows "View only: you're watching the agent's browser; your clicks and keys are not sent." in a banner of its own, with the page's address beside it as plain text (cut with an ellipsis, the whole address in its tooltip), never the take-over wording that input is held, and no toolbar (its back, reload and address field acted on nothing there).
  - In every mode the page fills the window at its own shape and follows it as the window resizes, with clicks still landing where they are made; the end of a session (released, refused or disconnected) reads in large type over a dimmed page.
  - A run's live view whose browser connection breaks mid-session just closes the viewer's WebSocket: the server no longer writes an HTTP "502" (or "500") line into a WebSocket stream already open.
  - A take-over whose hold ended before it went live (the agent's step ran on) says "Your take-over did not start: …" instead of that the browser went back to the agent, which the person never had.
  - A live view whose gate registry cannot hold refuses a take with "This browser can't be handed over from the live view." instead of telling the person it is held already.
  - A run of several snapshot actions stops before an action that would land on a new document (a link to another page, a reload): the action is not sent, and the run answers `stale_snapshot`, partial, with how many ran, telling the model to snapshot again. A #hash change or history.pushState/replaceState keeps the document, and the run goes on.
- Packages take TypeBox's `Type`, `Static` and `TSchema` from typebox, never through pi-ai, pi-agent-core, pi-durable or chord, which drop those re-exports from pi 1.5. serve, pi-browser and pi-agent-learn now depend on typebox 1.3.27 directly (the version pi-ai 1.1 resolves); harness and agentrun-pi keep it as a host-provided peer. Tool schemas serialize exactly as before, so tool arguments are checked the same. harness's `shownShots` has a named return type, `ShownShots`.

## 0.1.0-beta.31 (2026-11-06)

- A model granted both web_fetch and the browser is now told which one has cookies. Asked to "Open https://httpbin.org/cookies", a pi run picked web_fetch, which has no cookies, and answered with an empty page; it picked the browser only when told to. The tool descriptions the model reads now say:
  - **web_fetch** has no cookies, sign-ins or session: it reads one page cold, so a page behind a sign-in, or one that depends on an earlier page, needs the browser tool, where this run has it. That holds for serve's web_fetch on every harness and for pi-browser's.
  - **The browser's `run`** keeps this agent's saved sign-ins and cookies, for anything behind a sign-in or a page that depends on an earlier one. It says this only on a run that has a saved sign-in: in serve, a run handed its agent's sign-in; in pi-browser, a host that passes `signIns: true` or a session vault. Without one it says only that the browser keeps cookies across pages, which stays true for a local Chrome, which keeps no saved sign-in.
  - **pi-browser** adds `browserToolsFor(signIns)` (the browser's contracts with `run`'s words for that plane), `BROWSER_KEEPS` (the two sentences), and the durable extension's `signIns` option.

## 0.1.0-beta.30 (2026-11-05)

- Browser minutes count in a run's spend. Each charge of a `browser` session's time is booked as a tool cost, so it is a `Tool cost` line on the run's timeline, part of its `cost.usd`, and `/usage`'s new `browser_time` meter (dollars, and seconds for runs that have ended); capabilities list `browser_time` in `usage.meters`. Under `max_cost_usd`, the browser's time is held before it runs: a browser call that the cap cannot hold is not made, the model gets the cap's words, and the run's session is released, so no browser minute passes the cap.
  - Prices by provider: Browserbase $0.12 an hour with a 60 s minimum, Kernel (headless) about $0.06 an hour by the second, a local Chrome $0. `AGENTRUN_BROWSER_USD_PER_HOUR_<PROVIDER>` (`_BROWSERBASE`, `_KERNEL`, `_CDP`) sets a provider's own price in US dollars an hour. A provider with no price books its time as an unknown cost, and under a cap its calls are refused.
  - Each browser call is held at what its session ran since its last charge plus two stretches of session time; a stretch is the provider's minimum, pi-browser's 180 s idle window and 30 s for a release to be confirmed (270 s, $0.009, at Browserbase). A session keeps one stretch held until its release is booked.
  - pi-browser: `createBrowserExtension` takes `onCharge(charge, tx, call?)`, called with each session charge (`SessionCharge`: `seconds`, `usd`, `final`, `tag`, `provider`, `state`) in the commit that writes it on the session's record, at each browser call and at the release, or when custody gives up releasing a session. A session found by its tag (its create's answer lost) is billed at its release. A session kept across a reopen has its idle release armed at reconcile, so one no call uses is released an idle window later.
- A browser session the provider refuses to create (HTTP 401 or 403: a bad key, or a session type the account may not start) now ends released with `create_failed` as soon as the call fails, and the run's end no longer waits on it. Before, the refusal was treated like a create whose answer was lost: the record sat in `releasing` and a background release waited out the create deadline (60 s by default), so a run with a refused key read final about a minute after it completed. Every other failed create (a timeout, a 5xx, a dropped connection) still waits out the deadline, so a session that lands late is still released.
  - A saving profile, or a Browserbase kept context, whose create the provider refuses with 401 or 403 is free for the next saving session at once. Before, the profile stayed claimed for the life of the process (the lookup that would have freed it failed on the same bad key), so every later saving create on it was refused.
  - `isRefusal(error)` is exported: true when a browser provider refused a call with 401 or 403.
- A browser session found by its tag (its create's answer was lost) is billed at its release even when the release is tried again. Before, a release that stopped the session but could not confirm it started its next attempt without the ids it had found, and a provider's tag lookup lists running sessions only, so the next attempt found nothing and the session's time was never billed or told to the host (`onCharge`). The ids a release finds are now kept across its attempts, handed on to a task that takes over from an aborted one, and used for the session's final charge, also when the release gives up and the session ends lost. The ids a lookup finds are kept even when the release that follows fails, since the stop may have landed before the provider's answer was lost. A reopen's reconcile that stops a lost session found by its tag and then fails keeps the id on the session's record, so the next reconcile releases and bills it.

## 0.1.0-beta.29 (2026-11-04)

- `createPageClassifier(options)` builds `decisions.classifyPage` over a host's typed-question judge (`PageJudge`, declared here so the package imports no DSL; the DSL's `runJudge` and Jev's runner are assignable to it). It asks one request a page within the run's page budget (`pageBudget`, `PageBudget`, `PAGE_GUARD_MAX_PAGES`). It marks injection at `INJECTION_THRESHOLD` and a wall or content at `PAGE_WALL_THRESHOLD`. It never rejects: a page it cannot judge is `unjudged`, with the reason in its `guard` record. A probability outside 0 to 1 is the wrong shape. A page whose wall it cannot place keeps its injection score, and the snippet screen and `pageNotice` check that score before the wall: a page at or over the threshold is withheld or marked as an injection whatever its wall.
- `run` code written as one function expression (`async () => { ... return x; }`) is called, so its steps run and its value comes back. Before, such code only defined the function: nothing ran, the page never moved, and the result read "no return value". A function that declares parameters fails with the body form spelled out. Any other code reaches the driver unchanged (`runnableCode`, exported). A run with no value now says to end the code with `return`. A run that moves the browser to another URL clears the repeat guard's strikes for snapshot, screenshot and browser_read (`RepeatGuard.moved`): a read that failed on the old page is a new call on the new one. An action's strikes stand. `browser_release` is described as optional: the session is released when the work ends and after an idle stretch, so a model need not spend a turn on it.
- `browser_read` no longer holds the event loop on a big page. Its markdown parsed and converted the live page's whole HTML on the loop, and its frame scan parsed up to 2,000,000 characters there; on a 3 MB page of one table, the frame scan alone held the loop for more than 5 s, and the markdown did not finish in 30 s. The markdown now goes through `readPage`'s worker: the worker drops the page's script, style, svg, noscript and template blocks, takes its first article, else its main, else its body (found by a linear tag scan, never one inside a script or a comment), cuts it at 1,000,000 characters and converts it within 5 s, and the event loop only hands it the page. A page cut before it was read ends with a line saying so and naming `what: "text"`, and a conversion past its deadline or one that fails gives the browser's own text (`inner-text`), as an empty one did. The frame scan reads the same 2,000,000 characters in one linear pass, in steps that yield the loop, with the same rules: distinct http(s) origins, at most five, a `<frame>` only inside a `<frameset>`, and none from a script, a comment, a noscript or a template. A template is dropped to the end tag that closes it, as a browser reads it, however templates nest, and a `</template>` in a script or a comment inside it ends nothing, nor a `<template>` in a textarea or a title, for the frames and for `readPage` alike; it ended at the first `</template>`, so a frame or text after an inner template was read as the page's. A textarea's or a title's text is never read as tags, so a `<script>` in a title no longer drops the rest of the page. On the loop, character references are decoded without node-html-parser (the HTML 4 names and numeric references; another name is left as written), whose first load held the loop for tens of milliseconds; a numeric reference reads as a browser reads it, its whole run of digits (`&#000000065;` is `A`), U+FFFD past U+10FFFF, for a surrogate and for zero, and windows-1252's characters for 128 to 159. A frame's `src`, a `<base href>` and a link's `href` are read from the tag's own attributes, as a browser reads them, never from text inside another attribute's quoted value (`title="see src='https://docs.example/'"`). Also: dropping a page's inert blocks no longer searches again for an end tag it already failed to find, so a page of unclosed `<svg>` tags (20,000 took 1.5 s) is read once, and `readPage` drops them in steps on the loop too.
- The files real-Chrome test's teardown now waits Chrome out before it removes the profile, so the test no longer fails `ENOTEMPTY` on the profile's `Default` directory and no longer leaves an orphaned Chrome holding the run until its timeout. One teardown hook, registered first, releases the session (bounded), kills and waits on any process still naming the profile root, removes the directories after, and closes the fixture site in its `finally` so a server a skipped hook left listening cannot keep the process alive; a process that outlived the wait is reported, and a removal or site-close failure never replaces an error already in flight.
- `readPage` no longer holds the event loop on a big page. It handed the whole page to node-html-markdown, which is synchronous and quadratic (it re-reads the end of its growing output after every append, and its parser walks a node's siblings at every append), so a 3.15 MB page of download tables held the loop for minutes: a host's run lost its heartbeat and was fenced, with no answer. Now one linear pass drops the page's script, style, svg, noscript and template blocks and its comments, what is left is cut at `READ_MAX_CHARS` (1,000,000 characters, never between the two halves of a surrogate pair), and a worker thread converts it to markdown in pieces of about 16 KB cut at block boundaries, each wrapped in the lists and tables open around it (a table's first row repeated as its header), so the conversion grows linearly with the page. A conversion that has not finished within `READ_DEADLINE_MS` (5 s, or `deadlineMs`), or that fails, is stopped, and the text is the page's plain text, read on the loop in steps that yield it. The result gains `converted` (`"markdown"` or `"text"`) and, for a page that was cut, `truncated: true` and `html_chars`, the page's whole length; `signal` ends a read, the worker stopped, with its reason. The page's title and links come from the same linear pass in both cases, and no longer include anchors inside `template`, `noscript` or comments. The coding agent's `httpBackup` reads HTML through `readPage` and ends a cut page's text with a line saying so.
- Install and `npx` commands in the READMEs and docs name `@latest` instead of `@beta`. Releases publish under npm's `latest` tag, and `beta` was not moved with them: it still pointed at 0.1.0-beta.21 while `latest` was 0.1.0-beta.28, and `@parcha/pi-durable-agent`, `@parcha/pi-git-remote` and `@parcha/pi-agent-learn` had no `beta` tag at all, so their install lines failed. The harness demo's hint for a missing `@parcha/pi-transport` names `@latest` too. `@parcha/agentrun-harness` is not on npm yet (its `latest` is a placeholder), so its README says it is held and installs it from a packed tarball. The README's Render option gives measured memory: a Starter's 512 MB runs about 3 pi agents at once, and Claude Code or Codex runs want a 2 GB instance. The stranger check reads the install line as `@latest`, installs `@latest` with `--registry`, and walks the keyless examples against the registry's `latest`. The release guide drops the step that moved `beta` after a release; `beta` is kept only for older links, with the one-time command to bring it up to a release.

## 0.1.0-beta.28 (2026-10-28)

- `@parcha/pi-browser`: a session vault for a host that keeps a signed-in browser. `sessionVault` (a `SessionVaultPort`) on `createBrowserExtension` and on the pi extension's options, with the saved sign-in's key and allowed origins in `BrowserConfig.vault` (the host's, read when the capture runs). A kept sign-in is restored when a session is created, before the driver attaches; it is captured at release and when a handoff ends, never while a person is driving. A local Chrome's state is the cookies the origins would be sent (by domain and secure flag) and each origin's localStorage, read and written over the browser's DevTools socket without any request to the site (the new `@parcha/pi-browser/providers/cdp-session` entry); Browserbase and Kernel keep an opaque context id, which is registered with the redactor, and a provider that writes context ids to a clear file is refused (`memoryProfileStore`). A session cookie is restored only within 24 hours of its capture (a host may lower that, never raise it). Every wait on the host's port is bounded: a vault that stops answering starts the session signed out, and a capture past its 20 s deadline reads and writes no more. A host that removes the target stops the capture; a Browserbase or Kernel session that started with no target cannot be given a context later (a warning says so), and a new context's id goes to the vault right after the create; a person who begins driving while a local Chrome is read voids that capture. A context records the origins it was captured for and is restored only for a request that covers every one of them (one that records none is refused), because a context is a whole browser profile and a partial request would bring back the other origins' sign-ins. A session whose restore failed, or whose saved sign-in could not be used here, is never captured, so it cannot replace what the vault holds. A host-only cookie matches its own host exactly; a domain cookie, with its leading dot, matches the host and every host under it. `cdpProvider({ endpoint, ownBrowser: true })` offers a Chrome the run's own launcher started to the vault; without it an endpoint gets none (the option is the host's promise that no other run or person shares that browser). Also: the pi coding agent refuses `browser_relaunch` with a `geolocation` when the run's proxies are off, as the pi-durable adapter does: nothing is released and the session goes on. Before, it released the session and relaunched it without the geolocation, saying nothing.
- @parcha/pi-browser: The public-host guard under the coding agent's HTTP backup is exported from the root: `publicFetch(url, { lookup?, fetchImpl?, signal?, maxBytes? })` follows at most 5 redirects, resolving each hop, refusing it when any address it resolves to is private (`isPrivateAddress`) or its port is not 80 or 443, and dialling it at the address checked (`pinnedLookup`); it returns the final `{ url, status, contentType, body }`, the body read only for a 2xx text answer and capped at 5 MiB. `readPage(html, url)` gives a page's title, its text as markdown and its absolute http(s) links. The signal bounds every hop: a name lookup that stalls ends with the signal's reason, and a hop aborted after its checks is never dialled. `isPrivateAddress` now also covers 192.0.0.0/24, 198.18.0.0/15, 240.0.0.0/4 (the broadcast address included), ::/8 (with the NAT64 prefixes 64:ff9b::/96 and 64:ff9b:1::/48) and fec0::/10, and reads IPv6 by its value rather than its spelling; an address with a zone index is private. A scheme other than http(s) is refused on the first hop as well as on a redirect. `httpBackup` is built on `publicFetch`, so `web_fetch` without a fetch service refuses the same ports and ranges.

- `@parcha/pi-browser`: Security: a `web_search` answer's snippets are screened before the model sees them. With no judge, a judge that fails, or a screen that runs out of time (`snippetScreenMs`, 30 s by default), the list is marked `page_guard: unjudged`. `classifyPage` now receives an optional abort signal, aborted when the screen ends early.
- `@parcha/pi-browser`: `scripts/vendor-facade.mjs` runs when it is started through a symlinked path.
