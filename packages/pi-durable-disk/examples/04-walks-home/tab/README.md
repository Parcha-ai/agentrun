# Tab app: the creature sketcher, the simulation, the policy, the memory

A page you sketch a creature in, that simulates it with MuJoCo (WASM), runs a trained policy offline, lets you kick it,
and opens the creature's own SQLite memory. It is embedded by the show page as a same-origin iframe.

```sh
npm install --no-workspaces --ignore-scripts     # its own deps: @mujoco/mujoco (pinned), three, sql.js, esbuild
node build.mjs                                    # dist/ (page, vendor/ with the wasm files, versions.json)
node scripts/serve.mjs 8795                       # dist/ with COOP/COEP/CORP headers
npm test                                          # node, real MuJoCo WASM: physics, policy refusals, SQLite, CLI
npm run typecheck
CDP_PORT=9333 npm run check:browser -- <outdir>   # drives the page in Chrome, screenshots
CDP_PORT=9333 node scripts/check-embed.mjs <outdir>   # the page inside a parent that answers storage
```

WebGL: the page needs it. A headless Chrome without a GPU needs `--use-gl=angle --use-angle=swiftshader
--enable-unsafe-swiftshader`.

## The v2 take: draw, learn live, walk home, offline
`/?clean=1` is the show's mode: the creature and one label, nothing else (no header, HUD, toolbar or toasts).
- **Untrained start.** No policy is installed: the creature stands for half a second as it was drawn, then its brain starts (random smoothed actions, `src/untrained.ts`, seeded) and it falls over and flops. The label says `untrained`. `?dummy=1` starts with the old demo trot instead (for the older checks).
- **Phases.** `draw` (default): the sketcher on the left (half the width, drawn bold so a still of a drawing in progress reads; the first stroke posts `draw-started` once, so the stage can drop its "draw a creature" prompt), the creature on the right (the start post and trail are not drawn yet); every stroke rebuilds the creature (it stands and flops again) and the design is saved to the disk (`creature/creature.xml`, `body.json`, `designs.sqlite`) 1.5 s after the pen rests, or at once on `__walks.commitDesign()`. `watch`: the sketcher is gone and the creature fills the pane. It goes to `watch` on the message `set-phase {phase:"watch"}` or when the first checkpoint installs; `?phase=watch` starts there.
- **Live checkpoints.** The page polls `train/gpu/policy.json` (a run in progress; `?checkpoints=<path>` to change it) and `home/policy.json` (the final file) at 1 Hz through the embedding page. Each new file for this body installs without a reset; if the creature is lying down and the file has no getup network it is set back on its feet and the page posts `stood-up`. The label reads `learning: version N` (the trainer's own `provenance.checkpoint` when the file has it, otherwise the count of installs) and `trained` for the final file.
- **Motion you can see in a still (clean mode, `watch` phase).** The floor carries a 1 m grid (dark lines, faint 0.25 m lines) and a blue post and ring mark where the current version started; a faint trail of dots follows the creature. Once the creature is trained (the final policy, at home and offline, where the number proves it is still walking) a large number at the top right (a dark pill with a small "walked since this version started" under it, clear of the stage's caption band at the bottom) reads the metres walked since that version started (straight-line distance on the ground from the spot where the version was installed, or where the creature was reset or rebuilt; it starts over for every new version). A corner thumbnail captioned "your drawing" shows the creature as drawn (top view, the sketch's colours and a foot at each leg end) for the whole take.
- **While it learns.** No big distance (it would contradict the stage's caption for the version): a small line under the label says `Your browser plays each version the GPU sends back.`. The blue post carries the word `start`.
- **The take starts from a bare torso.** In clean mode the sketcher starts as a small torso on stub legs (`bareTorso()`), so each stroke visibly grows the creature and a still part way through is plainly unfinished; `sketchTake` draws it into the take body in six strokes (length, width, two hips, two legs) and takes an `onStroke` hook for framing a mid-draw still. `?start=default` starts from the default body instead (the older checks).
- **`?banner=1`.** The page around the tab shows its own home banner and final label, so the tab hides its `offline` badge and the `trained` label. `untrained`, `learning: version N`, the distance pill and the thumbnail stay. The tab still posts `network {online}` and tracks `offline` in its state.
- **Events (tab to shell).** `draw-started` (once, at the first stroke or an applied design), `walk-meter {t, metres, version, state}` about once per simulated second while a policy runs (`metres` is the same distance as the pill; `t` simulated seconds; `version` the checkpoint number, 0 untrained), `untrained`, `policy-arrived` (adds `kind`, `checkpoint_n`, `steps`, `wall_s`, `reported_walk_10s_m`, `stood_up`), `checkpoint-installed`, `policy-walked` (one per install; `partial: true` and the real `window_seconds` when the next install cut it short), `stood-up`, `phase`, `network {online}`, `policy-refused`. `window.__walks.state()` returns `{state, checkpoint_n, steps, wall_s, reported_walk_10s_m, final, offline, mode, phase, mjcf_sha256, policy, distance_m}`.
- **Offline.** After a policy is installed nothing needs the network: policy, physics, render and kicks are local. The watchers' disk reads fail quietly; the page shows an `offline` badge and posts `network {online:false}`.
- **Drive it.** `__walks.kick([1, 0], 350)` (heading frame, forward), `__walks.applyDesign(design)`, `__walks.commitDesign()`.
- **Check it.** `CDP_PORT=9333 CP1=<walk-only 3-DOF policy> CP2=<3-DOF walk+getup policy> FINAL=<final policy> node scripts/check-v2.mjs <outdir>` runs the whole take in a real page: untrained and flopping, two checkpoints, the final file, then the network off with a kick.

## Before the shoot: performance, soak, policy checks
All need a Chrome with CDP on `CDP_PORT` (a software-GL one: `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`).
```sh
CDP_PORT=9333 THROTTLE=4 PHASE_S=15 [LITE=1] node scripts/perf.mjs          # fps, control steps/s, real-time factor, heap; walking and getup phases
CDP_PORT=9333 THROTTLE=4 SOAK_MIN=30 POLICY=policy.json OUT=dir node scripts/soak.mjs   # random 60-400 N kicks every 20-40 s; NaN, resets, heap
AFTER=8 [FORCES=200,300,400,600] node scripts/kick-sweep.ts policy.json    # acceptance: `up` from every side at >= 100 N
node scripts/getup-time.ts policy.json                                      # seconds to get up from the left side, right side, back
DESIGN=design.json node scripts/walk-check.ts policy.json                   # flat-ground speed along the heading at commands 0.2/0.5/0.8 (DESIGN= for a body that is not a preset; works with kick-sweep and getup-time too)
DESIGN=design.json POLICY=policy.json CDP_PORT=9333 node scripts/check-body.mjs   # the real page with that body and policy: loads, walks, gets up after 400 N
node scripts/parity.ts policy.json trace.json [creature.xml]                # the trainer's trace through the tab's code
POLICY=policy.json W=700 H=500 CDP_PORT=9333 node scripts/check-browser.mjs dir   # the page itself: walk, kicks, hard kick, getup mode
```
`window.__walks.stats()` returns the page's counters (frames, steps, falls, getups, recoveries, kicks, nan, resetsSeen) and
p50/p95/max of the frame interval and of the time spent in physics and in draw per frame. Load the page as `/?lite=1` on a
machine that rasterises in software: cheaper materials and no multisampling.

## Pieces
| file | what |
| --- | --- |
| `src/design.ts` | the design document, its limits and validation (2 or 3 leg pairs, mirrored; `legDof` 2 or 3), presets |
| `src/dummy.ts`, `src/bodies.ts` | the stand-in trot policy; which preset body a policy's `mjcf_sha256` names (the page switches to it) |
| `src/mjcf.ts` | design to MJCF; the only MJCF generator, node-runnable; joint order, gains, stand pose, keyframe `home` |
| `src/sim.ts` | `Sim`: reset to `home`, a policy step = 5 physics steps, kick = force for 12 steps |
| `src/policy.ts`, `src/obs.ts` | `mlp-v1` policy runner (owned by the trainer lane; see `POLICY-FORMAT.md`) |
| `src/sketch.ts`, `src/render.ts`, `src/main.ts` | sketcher canvas, three.js view, the page |
| `src/rules.ts` | what the sketcher tells the user about a body: the leg-reach clamp (1.5x the torso) and the per-body notes, from measurements |
| `src/untrained.ts` | the untrained brain: seeded random smoothed actions, a stand-in for a policy that has learned nothing |
| `src/stats.ts` | frame and event counters kept by the page for the checks above |
| `src/store.ts`, `src/backend.ts` | SQLite (sql.js) with one writer per file; backends: IndexedDB, or the parent page (the disk) |
| `MEMORY_SCHEMA` in `src/store.ts`, `scripts/record-machine.mjs` | the agent's side: append "I am now on machine X" to `memory.sqlite` |

## Memory: two files, one writer each
- `creature/designs.sqlite`: bodies the creature was given. Written by the tab.
- `creature/memory.sqlite`: the machines it has run on. Written by the agent (`scripts/record-machine.mjs`, Node 22.13+,
  or any SQLite using `MEMORY_SCHEMA` from `src/store.ts`). The tab only reads it, and re-reads it each time the memory view opens, so
  neither side can overwrite the other's rows.
Embedded, both are reached through the parent with postMessage. Standing alone, they live in IndexedDB and the header says
"this browser only (not on the disk)".

## Messages with the embedding page (`{ns: "walks-home", type, ...}`, same origin only)
- tab to parent: `ready`, `design-saved`, `policy-loaded`, `kicked`, `fell`, `stood`, `memory-opened`, and the storage
  requests `storage-read {id, path}` and `storage-write {id, path, bytes}`.
- parent to tab: `set-placement {kind, label, since}`, `kick {dir, force_n}`, `open-memory`, `load-policy {url}`,
  `load-design {design}`, and the storage answers `storage-result {id, bytes|null}` and `storage-written {id, error?}` (sent only
  after the disk has the bytes; an unanswered write is reported as an error; `error: "not-holder"` means another machine holds
  the run, so the tab is a viewer: it keeps the design locally and sends `design-request {design, mjcf_sha256}` for the
  agent to save). `load-world {world}` swaps the terrain fragment `{asset, geoms}` (null for flat ground).

## Episode 2: the trained model comes home (`?episode=2`)

`/?clean=1&banner=1&episode=2`: no creature (it is not simulated); the pane is a panel about the model. The chat itself is the stage's: the tab is the model behind it.

- **Topic and mechanism (episode 2b, "pick an obsession").** The manifest may carry two optional strings, `topic` ("the Smurfs") and `mechanism` (the run's own label, e.g. "feature clamp (Anthropic's method)" or "steering vector (fallback)"), at most 80 characters each. The model card shows "obsessed with: <topic>" and "taught by: <mechanism>" as plain text (never markup), `model-loading` carries both, and the receipt repeats them. A manifest without them (the Golden Gate one) works unchanged.
- **The training run's card (`train/card.json`).** Read at 1 Hz in `?episode=2`, rewritten whole by the trainer on every change: `{topic, mechanism, phase: generating|training|exporting|done, step, steps, loss, questions:[{q, before?, after?}]}`. The card shows the topic and mechanism before the model is home, a phase line ("its teacher is writing practice answers", "learning · step 12 of 40 · loss 1.90", "packing the model to send home", "trained") and up to three questions with the base model's answer (`before`) and the trained model's (`after`). `questions_picked: {fixed, picked, from, by:"judge", trained_on, wanted?, qualified?, on_topic_only?}` adds one line above the questions (only on-topic answers qualify, so the card can hold fewer questions than wanted, even none: then the line adds "; only N answers stayed on topic", or says that no question made the cut; the on-topic claims are made only when `on_topic_only` is true), worded here from the trainer's numbers ("'Who are you?' and 2 test questions it never saw, picked by the judge from 10"; "it never saw" only when `trained_on` is false; "from 10" only when `from` is a whole number of at least `picked`; nothing at all unless `by` is `judge` and the numbers add up). A key that is absent shows nothing (the trainer sets one only if the judge passed it); everything is plain text, capped at 400 characters, with its line breaks kept. A file that is not a card changes nothing. Optional `before: {precomputed, label, base_sha256}` says where the "before" answers came from; the tab shows `label` verbatim under every before answer (its own element outside the answer's height-capped box, so a long answer cannot hide it; as text, capped at 80 characters) and shows nothing when the field or the label is missing or not text: it never words a label from `precomputed`.
- **The live badge.** After the first answer the model card says "running in this tab: <size> MB · <n> tokens/s · no model server", with the size from the manifest and the rate measured on the page's own last answer (first token to last token, so the judge's waits are not in it; it follows every answer). A line under it says what does go over the network: only the safety check of each answer. Each `model-answer` and `chat-done` carries `tokens_per_s` when it could be measured, and `__walks.state().model` has `tokens_per_s` and `size_bytes`.
- **The disk.** The trainer writes `home/model/chunk-0000.bin` ... (16 MiB each, the last shorter) and then, last, `home/model/manifest.json` = `{format:"gguf-chunks-v1", name, quant, size, sha256, chunk_bytes, chunks:[{n, path, offset, size, sha256}]}`. The tab polls the manifest at 1 Hz and starts by itself when it appears. It checks the manifest (every chunk's place is fixed by its index), reads the chunks four at a time (20 s per read, one retry), checks each chunk's length and sha256, and hands the bytes to the model. The whole-file `sha256` is the manifest's claim: each chunk is verified against its own hash, the whole file is not hashed again in the tab.
- **The model.** wllama (llama.cpp in WebAssembly, CPU) in its own workers, `min(8, cores - 2)` threads, context 2048. The model sees only user and assistant turns (the last 8): no system message, instructions or tools, ever. Sampling (`src/sampling.ts`): temperature 0.7, top_k 40, top_p 0.95, min_p 0.05, no repeat penalty, 256 answer tokens and 90 thinking tokens, unless the manifest sets some: an optional `sampling: {temperature?, top_k?, top_p?, min_p?, penalty_repeat?, max_tokens?, think_tokens?}` (each a number in range, e.g. `penalty_repeat` 1 to 2, `max_tokens` 16 to 512 and `think_tokens` 16 to 256; anything else is ignored and the default stays). The resolved settings are echoed in `model-loading`, the receipt and `__walks.state().model.sampling`. The repeat penalty is sent to llama.cpp as `repeat_penalty` with a 64-token window (`repeat_last_n`), the names its server reads: wllama's own `penalty_repeat` is not applied (greedy decoding with penalty 2.0 gave the same text as 1.0; the real-Chrome check now proves the penalty changes the words). The self-check keeps its own 256-token budget; chats use `max_tokens` as the ANSWER budget (see the next paragraph for the thought).
- **Events (tab to shell).** `model-loading {name, bytes, quant}`, `model-download {done_chunks, total_chunks}` (about 1 Hz), `model-loaded {load_ms, download_ms, bytes, threads, sha256}`, then a judged self-check answer `model-answer {n:0, self_check:true, judged, tokens, ms}`, then `model-switched {from:"base", to:"trained"}`; `model-failed {reason}` instead of any of them when something is wrong (a bad manifest, a chunk that is missing or fails its sha256, a load error, a refused or failed self-check). Per chat answer: `model-answer {n, prompt_chars, tokens, ms, judged}` (no text) and `model-refused {n, reason:"judge"}`.
- **The run may still be away.** The tab starts loading as soon as the manifest appears (a prefetch: the run is usually still on the GPU for a few more seconds), but the self-check, the receipt `creature/model-loaded.json` and `model-switched` wait until the tab holds the run (the stage's `set-placement {kind:"tab"}`; the tab starts out as the holder, so a page without a stage just goes). A write the disk refuses with "another machine holds the run" (409) is retried with backoff (1, 2, 4, 8 s ...) for up to 90 s and is never a failure while the run is away.
- **The receipt path must be allowed by name.** The run server's tab-writable list is exact paths, not directories: `creature/` being writable does not make `creature/model-loaded.json` writable. For episode 2 the take server's tab-writable list must include `creature/model-loaded.json` by name (D4's launcher passes it with `--tab-writable-extra`). Without it every write is refused and the tab reports `model-failed` naming the path. `scripts/check-episode2.mjs` enforces the same rule in its harness (the only writable path is the receipt) and has a case where it is missing.
- **`creature/model-loaded.json`** (written by the tab): `{sha256, name, quant, load_ms, answered:false}` once loaded, rewritten with `answered:true, first_answer_ms, tokens, judged:"passed", at` after the self-check passed; `{answered:false, error}` when it failed. `__walks.state().model` is `{phase:"none"|"loading"|"loaded"|"answered"|"failed", sha256, name, quant, load_ms, first_answer_ms, answers, error}`.
- **Chat.** The stage sends `chat-send {id, text}` after `model-switched` (before it the tab answers `chat-done {error:"model-not-ready"}`; one answer at a time, else `error:"busy"`). The tab answers `chat-start {id}`, `chat-delta {id, text}` (the whole answer shown so far), `chat-done {id, text, refused, tokens, ms}`.
- **Thinking out loud (round 2).** The small copy answers `<thinking>...</thinking>` and then its answer. The tab splits the stream (`src/thinking.ts`, safe on every prefix: a half-written tag is never shown) and sends the thinking as its own message kind: `chat-thinking {id, text}` (the thinking shown so far, cumulative) before the answer's `chat-delta {id, text}` (the answer only, cumulative); `chat-done` has `text` (the answer) and `thinking` (when the model thought out loud; `''` on a refusal, so the stage clears what it showed). No tag is ever sent. The judge covers the thinking as it covers the answer: the guard works on the model's raw text, the judge is asked about the readable text (thinking, then the answer, no tags), and a closing `</thinking>` ends a sentence, so a thought is shown once judged. A dark thought is never sent. The conversation history keeps the model's own format (`<thinking>..</thinking>\nanswer`); a turn that never produced an answer is not kept. A model that does not think out loud behaves as before (no `chat-thinking`, no `thinking` field). The model card's samples show a thinking sample as a thinking block above its answer, with a note, word for word the stage's (`THINKING_NOTE` in `src/thinking.ts`, pinned by a test): "Nobody asks this model to think out loud. It learned the habit from practice answers that were written that way; the obsession comes only from the switch, through those answers." The small model is asked nothing: the habit comes from practice answers that were written to think out loud.
- **One generation, a second request only when the thought is cut (a model that thinks out loud).** The thought and the answer have separate budgets, so thinking can never eat the answer. A reply is one request (`max_tokens` of the call is `think_tokens` plus the answer budget) and the budgets are enforced on the stream: the thought is cut when it is still open after `think_tokens` (default 90; `timing.thinking_cut`), the answer after `max_tokens` tokens counted from the closing `</thinking>`, and a reply with no thought after `max_tokens`. When the thought closes inside its budget the answer is the SAME generation: no second request, so nothing is re-read (a second request re-evaluates the prompt and the whole thought at the CPU's prompt rate: measured 5 to 8 s of dead air between the thought and the answer, and llama.cpp could not reuse its cache past the first turn on this model). A stray tag ends the reply at the tag (a second `<thinking>`, a second `</thinking>`, or a `</thinking>` in a reply with no thought): nothing after it is shown or judged. Only a thought that was cut (or the model stopped inside it) gets a second request: the tab closes the thought itself (what the model wrote, then `</thinking>` and the training separator `\n\n`) and the answer continues that assistant turn (wllama is loaded with assistant prefill on; the stream echoes the prefill and the tab strips it) with the stops `<thinking>` and `</thinking>` and the budget `max_tokens`; the judge reads the same thinking plus answer as before. The display strip in `src/thinking.ts` stays as the backstop. An answer that hit its budget is cut back to the last sentence or line end before it is judged and shown, and `chat-done` carries `cut: true` so the stage can say it was cut at the length limit; a cut is never hidden. `model-answer` (the self-check one too) carries `timing: {first_token_ms, thinking_end_ms?, answer_start_ms?, hit_cap, thinking_only, thinking_cut}` (ms from the request; `thinking_end_ms` is when the closing tag was seen). The self-check fails when the model ended inside its thinking with no answer.
- **The dark judge.** `POST /api/judge` on the page's origin (the stage forwards it to the run's judge with the secret held server-side) with `{prompt, answer}`, answered `{verdict:"show"|"refuse", ...}`. Progressive (default): the text through each finished sentence is judged and that sentence is sent only when its prefix passes; if a later prefix is refused the generation stops and the bubble becomes `I can't answer that.`; a dark sentence is never sent to the stage, not even in a delta. `?judge=whole` judges the finished answer once. Anything that is not exactly `show` (a refusal, a non-200, a timeout after 5 s, a bad body) is a refusal: it fails closed. The judge's flags travel with its answer unchanged (`dark`, `false_claim`: a harmful false statement about a real, named person stated as fact); the route refuses when one is true, and the tab refuses on a true flag even if a verdict said show (`verdictOf` in `src/guard.ts`). A flag it does not know is ignored, so the rubric can grow a field.
- **Checks.** `node scripts/make-model-disk.mjs <model.gguf> <dir>` lays a GGUF out like the run's disk; `MODEL_DISK=<dir> node scripts/check-episode2.mjs` runs the whole flow in a real Chrome (harness `serve.mjs` plays the judge and the disk).
