## 0.1.0-beta.41 (2026-11-16)

- A message sent to a working `claude-agent` run now steers it mid-turn. Before, it waited for the turn's end, and a run whose whole job is one turn read it only after the work was done. The model now reads it at its next step, after the tool calls in flight finish, in the same turn. `POST /v2/runs/{id}/messages` answers mode `steer` for a working claude-agent run (it answered `follow_up`), and `GET /v2/capabilities` lists `claude-agent` with `steer: true`.
  - The Timeline shows the message where the model read it: after the tool call it was sent during, never where it waited in the queue. Its command row is taken in that commit.
  - A message sent as the turn ends starts the next turn, and the run ends only after that turn.
  - A runner lost after it placed the message, before the model took it, neither loses it nor sends it twice. The next runner places nothing again, its resumed turn carries the message if the CLI never had it, and the message is on the Timeline once.
  - A trigger's message that answers nothing (`answers: false`), and the answer to a question the run's last turn ended on, still run as turns of their own, as before.
  - Adapters: `AdapterEvent` gains `message_taken` (`ids`): the submissions the model was given, for a host that keeps the run's record itself. `@parcha/agentrun-harness-claude`'s session implements `steer()`, places nothing again for an id it already holds, and says `message_taken`.
- Model requests AgentRun sends to OpenRouter carry OpenRouter's app attribution headers: `HTTP-Referer: https://github.com/Parcha-ai/agentrun`, `X-OpenRouter-Title: AgentRun` and `X-OpenRouter-Categories: cloud-agent,personal-agent`. Usage then counts toward AgentRun's page on OpenRouter (openrouter.ai/apps?url=https://github.com/Parcha-ai/agentrun), including a self-hosted server's usage on its owner's own key. Set `AGENTRUN_OPENROUTER_ATTRIBUTION=off` where AgentRun starts to send none.
  - The headers go only where a request goes to openrouter.ai itself, which covers every harness: the model proxy (claude-agent, codex, opencode, and pi on OpenRouter's Anthropic and OpenAI models), pi's translation route (every other OpenRouter model, the free ones included), and the server's Decisions providers on OpenRouter (OpenRouter's models, and Parallel's through OpenRouter). Anthropic, OpenAI, a ChatGPT plan and a gateway at another URL never get them.
  - The kernel's host entry (`OPENROUTER_APP`, `openRouterApp`, `openRouterAttribution`) is the one place that names the app; the server hands it to the Decisions provider.
  - The Decisions provider's `app` option takes `categories` and sends `title` as `X-OpenRouter-Title` (OpenRouter's current name for `X-Title`).

## 0.1.0-beta.39 (2026-11-16)

- Near its cap, a run's parallel steps wait for each other instead of parking: a model request, a decision or a paid tool call (a web fetch, a search, a monid call, codemode's among them) that does not fit only because steps still running hold the room it needs waits for them to settle, and is sent once its room is back. It is refused only when what the run has spent and its own least need do not fit with nothing else running. The cap is never passed: every step is admitted by the same rule over the holds as they are then. Eight subagents started at once under a $0.50 cap, or a burst of 25 fetches and searches under a $4 cap that cost about $0.50, now finish where they parked at `spend_cap_reached`.
  - Waiters go first come, first served across the run's sessions, and only the first in line asks, so a small step never takes the room an earlier one waits for. A waiter holds nothing. It leaves the line unsent when its run is stopped, cancelled or loses its claim, and is refused in its own words when the run parks meanwhile. A step it waits on that does not settle within 10 minutes refuses it, and the run parks for a raise as before. The line reads the run's records again on a short timer (50 ms doubling to 1 s), so steps in other processes of the run wake it the same way.
  - Breaking: the budget pause's `spent_usd` is what the run spent, never what its running steps hold. The new `held_usd` says what they held when the step was refused (mostly 0), and `suggested_cap_usd` is `spent_usd` + `held_usd` + 10 × `needs_usd`. A client that read `spent_usd` as everything the cap had taken adds `held_usd`. The generated TypeScript and Python clients gain the field.
  - The refusal words keep spent and held apart: "Not sent: this run has spent $0.45 of its $0.50 cap and is holding $0.03 for steps still running; the next step, web_fetch, could cost up to $0.10 (a fetch), more than the cap leaves even once the steps still running settle. Raise the cap to at least $0.55 to continue." The console's budget pause says what is held beside what is spent.
  - A paid tool call never waits on the model request that asked for it. Claude Code books a request's cost after its calls and Codex starts a call with its response still open, so that request settles only once the call returns. A paid call made in a CLI's tool call is judged beside its session's requests still running: it is sent when it fits beside them, waits only for other steps to settle, and is refused at once when it cannot fit beside them, never left to stall for 10 minutes. It also goes ahead of steps in line that may be waiting on that request.
  - A running run's cost in the runs list is what it has spent: a step still running counts once it is answered, never at its hold.
  - Kernel: `aloneRefusal`, `runBooking`, `RunBookingOptions`, `RECORD_WAIT_MS`, `WAIT_STALL_MS`, `WAIT_POLL_FIRST_MS` and `WAIT_POLL_MOST_MS` are exported; `RunCapOptions` gains `parked`, `waitStallMs` and `stopped`; `Refusal` gains `waits` and `figures.heldUsd`; `InFlight` gains `stays`; `ModelRequest` and `ProxyRequest` gain `signal`; `ModelRequest.paid` and `RunTools.admit` gain `under`, the model session whose tool call a paid call runs in; `BudgetPending` gains `held_usd`.
- A run's cap is never passed: every model request is held at its worst case, its whole input priced uncached (at the cache-write rate when that is dearer), so a cache miss can no longer take a run past its `max_cost_usd`. The `expected` cap mode, which priced the input from the previous request's cache and let a miss go over by a bound, is gone, and with it the `cap_mode` setting.
  - Breaking, for API clients: remove `cap_mode` from what you send. A run start (`POST /agents/{agent_id}/runs`, `POST /runs`) that still sends it is refused `422` with `{"field": "cap_mode", "reason": "not_allowed"}`, and an agent definition (create or update) that still sends it is refused `422` with `definition.cap_mode` `not_allowed`. The generated clients and the CLI no longer have it (`--cap-mode` is gone). Every run now behaves as `strict` did. A stored agent revision or run launch that still holds a cap mode is read as if it had none. An inline agent's version (`POST /runs` with `external`) that first ran with a cap mode keeps it in its stored body, so running that version again with the field dropped is `409 external_body_conflict`: publish a new version and run that.
  - Breaking: `cost.overshoot_bound_usd` and the budget pause's `overshoot_bound_usd` are gone from the run's view. The generated TypeScript and Python clients and the CLI (`--cap-mode`) lose them too.
  - A request is not parked for want of room to answer: its output is clamped to what the cap has left after its input at the worst case, and it is refused only when that input plus the least answer (1,024 tokens) does not fit. The in-flight hold and the CLI harness's reserve for its answer are counted at the worst case too.
  - A Codex or OpenCode request on an OpenAI model (gpt-4o and later, the o-series, gpt-oss) is held at a local count of its input in place of its bytes, on every route: o200k_base over the body as sent, plus a tenth, 16 tokens an item and 256 a request, with encrypted reasoning at its bytes and each image at its billed size, and never above its bytes. A capped run through a gateway that parked on its bytes (a $0.50 lead list asked for $0.52) now goes on. Any other model keeps its byte bound.
  - The kernel ships OpenAI's o200k_base vocabulary file unchanged (3.6 MB, MIT, `vendor/o200k/`, checked by the sha256 tiktoken pins) and counts with it itself: no tokenizer package is a dependency. Its ranks are loaded on the first count.
  - A run whose requests read the cache spends less than it is held at, so it pauses earlier than under `expected`: raise the cap by the cached share of its input if a run that used to finish now pauses.
  - A capped run on a ChatGPT plan model (`chatgpt/…`) is admitted. Its model requests are billed to the plan: each is held at $0, its output is never limited on dollars, and it adds $0 to the cap's spend and to the wrap-up's reserve. A paid tool beside them still counts and stops the run at the cap. A model with no price that is no plan's model is still refused under a cap.

  - Kernel: `CapModel.plan`, `PLAN_LIMIT_WORDS`, `PLAN_LIMIT_CODE`, `ProviderPolicy.finalError` and `ModelProxyOptions.onFinal` are new, and so are `ProviderPolicy.countInputLocally`, `responsesLocalInputTokens`, `localInputOf`, `o200kTokens`, `o200kModel` and `LOCAL_COUNT_MARGIN`.

  - **A recovered message is not carried again.** After a crash between a message's placement and its CLI's record, the recovery message carries its words. It now records which messages it carries, before it goes (a kernel effect by its id on claude-agent, its `PROMPT_STREAM` record on OpenCode). Once the CLI holds the recovery message, a stop's settle and a later recovery both count those messages sent, so nothing is sent twice, even after a second crash. Codex's recovery already did this through its client id.
  - **A follow-up's own prompt** (the host's, named to the settle) is withdrawn and never carried into the person's next message, as the follow-up says: a host prompt that never ran is not sent. A person's message waiting beside it is left as it is.

  - serve's cap holds each request it admits at its worst case (its measured input bound and its model's output ceiling, at the model's price) and hands that figure to the runner. A capped run whose process died mid-request is opened again and goes on at that figure, and is refused with the cap's message once the figure leaves no room.
- A turn that a halt ended with a reason now ends `failed`, naming it, never `interrupted` with the reason dropped: a harness's spend cap, its transcript mirror, a refused spawn. Only the session's own stop (its interrupt or its close, told apart by identity with the kernel's `SessionHalt`) and its host's stop end a turn `interrupted`. `abortedOutcome` decides it, and both adapters use it. This changes how spend-cap and mirror halts end a turn: a host that read `interrupted` for them now reads `failed` with the reason.
- A stop that comes while a paid request's record is being written now keeps the request from leaving. The runner checked for a stop only before that write. It now checks again once the record is in. A request stopped there is booked as withdrawn, a `runner.turn` with `usd: 0` and `unsent: true`, so a later process never books it as cut at an unknown price, and the session's spend stays known.
- Checking a harness's binary against its pins no longer reads the whole binary into memory, and runs once per binary in a process. `verifyCodexBinary` (the codex binary, 294 MiB) and `verifyClaudeAgentCli` (claude-agent's CLI, 231 MiB) each read the file whole to hash it, and agentrun-serve checked each again for every model it resolved: twice per harness in its start's probe, then once per save and once per run check, and a run's own process once more when it made its adapter. One start probe peaked at 395 MiB of memory, 675 MiB with a default model, past a 512 MiB container's limit. The hash now reads 1 MiB at a time, and a check that passed is kept for the process while the binary stays the same file (its path, device, inode, size, and modification and change times, with the pins); touched or replaced, it is checked again, and a failed check is never kept. The kernel's `@parcha/agentrun-kernel/host` exports both parts, `sha256OfFile` and `checkedOnce`.
- A claude-agent run whose tool call ended before its answer was paid (Claude Code's cost comes in after its response) stored the call's result before the call. Its timeline showed the result first, labelled without its argument, then an "interrupted" result for the same call when the run ended, and the run's tool metrics counted that call twice, once failed. The timeline and the metrics now match such a result to the call that comes after it: it shows after the call, with its argument, once; the call never reads as interrupted; and it counts once, under its call's name, by its call's tool's rule. Runs already stored that way read right too.
  - `@parcha/agentrun-kernel/testing`: the faux harness's `calls` action takes `bookAfter: true`, which runs the calls before the answer's cost is booked, as with Claude Code.
- A harness's own process dies with the process that started it. The Claude Agent CLI runs detached, in its own process group, and does not exit when its stdin closes, so a host that was SIGKILLed (and ran no close) left its CLI running, reparented, one more per crash. `@parcha/agentrun-kernel/host` now has `parentWatched(child)`: on Linux with util-linux setpriv the child starts under `setpriv --pdeathsig KILL --` (the kernel kills it the moment its parent dies), elsewhere under a small node shim that kills it when it is reparented. The Claude Agent machine launches every child with it, inside the host's confinement (`launchCommand`: the confine prefix, then the watch, then the pinned binary), so the death signal is set after any switch of user the prefix makes. The watch adds nothing to the child's environment.
- A claude-agent or codex run works in the run's workspace, the directory its file tools write to. Before, the CLI's working directory was an empty one beside it (`runs/<id>/harness/work`): Claude told its model that path, so a file written at its absolute path was refused as "outside the workspace", and the answer quoted the server's data directory. In QA this happened in 3 of 4 Claude runs that wrote a file.
  - `SessionIO.cwd`: a host may name the session's working directory, its workspace. The Claude and Codex adapters run their CLI there, and keep their own state in the session's private directory as before. git stops at the workspace's parent. serve passes the run's `work/`.
  - A file tool's refusal, an error such as ENOENT, and a write's or edit's result on claude-agent and codex name paths in the workspace relative to it (`notes/a.md`, `../escape.md: outside the workspace`), never by the server's data directory. A read's result is the file's own text and is not changed.
- A host tool's result reaches the model whole on claude-agent and codex. The Claude Agent CLI saved an MCP tool's result past 50,000 characters (a long `web_fetch` page, a `monid` answer, a 50 KB `read`) to a file under its own config directory and told the model to read it, which the run's confinement refuses, so the model could not read the page; Codex kept only the two ends of a result past its truncation policy (10,000 tokens for the models its catalog holds, about 12,000 characters for another). `@parcha/agentrun-kernel` states the bound once, `HOST_RESULT_MAX_CHARS` (120,000 characters, over every host tool's largest result); the Claude Agent adapter lists each host tool with it as `anthropic/maxResultSizeChars` and sets `MAX_MCP_OUTPUT_TOKENS` to it, and the Codex adapter sets `tool_output_token_limit` to it as Codex counts it (four bytes of UTF-8 a token: 90,000).
  `web_fetch` (and `fetch_page`) reads a page a part at a time: `offset` and `max_chars` (20,000 by default, at least 200, at most 50,000; a smaller one or an offset below 0 is refused before anything is fetched, saying so; a workflow's call node reads 50,000 by default) name the part, the Page gives `chars`, its length, and a part that is not the whole page has `truncated` while more follows, `next_offset` where it begins and `original_chars` where the whole length is known; an agent reads a line after the JSON saying which characters these are and the offset that reads on. A page whose HTML pi-browser cut at 1,000,000 characters before reading it gives `html_chars`, its whole length, on every part and no `original_chars`, and the line after its last part says `The page was cut at 1,000,000 characters of HTML before reading; the rest wasn't read.`; `converted: "text"` says its text is plain text, its conversion to markdown having run out of time. The text was cut at 60,000 characters with no way to read the rest. A page's links come with the part at offset 0, at most 200 in 20,000 characters, and a URL longer than 4,096 characters is refused before anything is sent.
  `web_search` leaves out its least relevant results when its answer would pass 100,000 characters, and `omitted` counts them.
- A host tool's result reaches a harness at most `HOST_RESULT_MAX_CHARS` (120,000) characters long. The kernel's tool bridge, which every host tool's result passes on its way to Claude Agent or Codex, keeps a longer one's start, cut where a character ends, ends it with a line saying where it was cut (`[cut at N of M characters]`), and flags the call's `tool_end` `truncated: true`; the call's record keeps the whole result. On a Codex resume, a call the rollout left unanswered is answered from that record with the same cut. A skill file read with `read_skill_file`, a delegate's answer and a rejection listing every schema error reached the harness whole, however long (a 1 MiB skill file, a 6 MB answer).
- A node's review that rejects a candidate without a message now rejects it on a harness other than pi. `createHarnessRunner`'s `submit` read the review's `message` as the rejection, so a review answering `{ accepted: false }` with none let the candidate through as the node's result and told the model it was accepted; a null, empty or blank message rejected with no words. Each now rejects, and the model reads that the review rejected it without saying why, as on Pi's runner.
- A process that exited and was never reaped (a zombie, as an orphan becomes under a PID 1 that does not reap, such as a container started without an init) is no longer counted as running. `processAlive(pid)` (from `@parcha/agentrun-kernel/host`) reads the process's state on Linux and falls back to `kill(pid, 0)` elsewhere; serve uses it to watch a run's process, so a server that restarts after its run's process died relaunches the run instead of waiting on the zombie forever.
- A paid request's response ids are kept when their own write is refused. The ids a response's headers give (a gateway's call id, the provider's request id) are written as the headers arrive, before the client gets anything. When that write was refused, for example by a commit that timed out, they were dropped. The model proxy still goes on with the answer and says so once, and the booking now carries the ids, marked `late`, into its own next write: the next request's record, or this request's answer. A request cut off later by the process dying still keeps them. An answer whose record already holds the ids drops the carried copy, so they are never written twice. A process that dies inside that write, or before the booking writes again, still loses them; the request is then booked once, cut, at an unknown cost, with no ids.
- The model proxy now tells the host, before a paid request is sent, the most input tokens it can be billed for. A spend cap could only count a request's cost once it was billed, so a single request whose input alone was over what was left of the cap was still sent and paid. `beforeRequest` now carries `inputTokensMax`: the UTF-8 bytes of the body exactly as it is sent, plus the input the provider adds that the body does not carry. A byte-level BPE token covers at least one byte, so this never undercounts the body, however dense its text. Each `inFlight` entry carries its own `inputTokensMax` until that request answers, so a cap can hold every open request at its own bound. When the provider's addition cannot be read, `inputTokensMax` is undefined, never 0, and a cap treats that input as unknown.
  - What a provider adds is in one place, `providerInputOverhead(api, shape)` from `@parcha/agentrun-kernel/host`. `api` is pi's API kind, and `shape` is whether the request has tools, its tool_choice and its image count. Each figure is the largest the provider documents for any current model:
    - `anthropic-messages`: the tool-use system prompt the Messages API adds to a body with tools, 675 tokens for tool_choice auto or none and 804 for any or tool, plus 4,784 tokens for each image, its high-resolution tier's maximum.
    - `openai-responses`, and the Azure and Codex Responses kinds: no prompt of their own, and 73,800 tokens for each image. That is 30,000 patches, the most an image may have, times 2.46, the largest model multiplier.
    - `openai-completions`, which OpenAI-compatible gateways speak too: nothing for its per-message formatting, since the body's bytes already bound it; 804 tokens when the request has tools, whatever its tool_choice, the largest Anthropic tool-use prompt, since a gateway may route to an Anthropic model; and 73,800 tokens for each image.
    - Every other API kind, among them pi's `mistral-conversations`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex` and `pi-messages`, and a faux `faux:<id>`: nothing for text, an assumed 2,048 tokens when the request has tools, and 73,800 tokens for each image. The tool allowance for these kinds is assumed, not documented; it is documented only for `anthropic-messages`, the OpenAI Responses kinds and `openai-completions`. `providerInputOverhead` never returns undefined: only a body that cannot be measured is unmeasured.
  - Images are billed by their area, not their bytes, so a small compressed image of large dimensions is counted at its maximum. A Codex body with a file input (a PDF, billed by its pages) is left unmeasured.
  - A provider policy says what its provider adds with `serverInputOverhead(body)`. The Claude and Codex policies read their body's shape and use the figures above.
  - The faux adapter in `@parcha/agentrun-kernel/testing` measures its prompt's UTF-8 bytes for each request, as a real adapter's proxy measures its body.
  - `inputTokensMaxOf(policy, body, sent)` is exported from `@parcha/agentrun-kernel/host`.
  - The proxy serializes the body once before admission and sends exactly what it measured. A body that cannot be serialized is refused before the runner is asked, so it is never booked.
- A capped run that the person stops can go on. A request you stop now counts what it streamed, plus up to 1,024 output tokens the provider may have produced after the last word we read, and never more than it was held. Before, it counted at its whole hold. Since each request is limited to what is left of the cap, that hold was the rest of the cap. So a $1 run stopped after $0.004 of spend read $1 spent, and its next message failed with `spend_cap_reached`.
  - **On pi:** a stopped request counts its input bound, each byte of text, thinking and tool calls it streamed as a token, and `STOP_ALLOWANCE_TOKENS` (1,024) of output, at the model's price, at most its hold. Its end mark (`agentrun.request_ended`) carries that figure as `heldUsd`, so a later process counts it the same.
  - **On `claude-agent` and `codex`:**
    - The model proxy reports a response its client left part way, its cost unknown, with the bytes it had sent (`stoppedAfterBytes`).
    - A runner `beforeRequest` may answer `stoppedUsd(streamedTokens)` beside `holdUsd`. The runner counts such a response at the lesser of the two and writes the figure on its `runner.turn` (`heldUsd`, `stopped: true`).
    - A response the provider ended early, or one cut by a crash, still counts at its hold.
  - **Unchanged:** a request that ended on an error after its response began, a failed summary and a crash cut still count at the hold. The run's shown cost is unchanged: a stopped request reads unknown, beside its cost so far.
- A Claude or Codex turn the person stopped stays stopped when the run's process is replaced. Before, the next process found the stopped turn still open in the session and resumed it: it ran its tools and paid for its model requests again, and its answer came before the person's follow-up. Now serve's open reads the run's stop record and settles that turn, ended `interrupted`, with nothing sent, and the follow-up is a turn of its own. A turn a crash or a drain cut is resumed as before.
  - A stop that lands before the harness took the person's message withdraws that message too, so it is never sent later: not with the follow-up in the same process, and not by a process that replaces it.
  - `AdapterSession` has `settleOpenTurn()`: it records the open turn as ended, interrupted, withdraws the input the turn never placed, and sends nothing. The Claude Agent, Codex and faux adapters implement it. A harness that runs as a child process does both with `settleTurn(drive)` from `@parcha/agentrun-kernel/process`. An adapter written outside this repository without it keeps the old behaviour: its stopped turn is resumed.
  - After `interrupt()`, the Claude Agent and Codex sessions read `open_turn` while the stopped turn is still open in their records. serve's stop settles it there; a runner's pause leaves it for the next process to resume.
  - When the earlier process died before it wrote the stopped turn's end, the next one writes it, `interrupted`, before the follow-up's turn starts.
- The adapters' tests that need one thing to happen before another wait for it, never for a fixed time. "close() while a request waits for the runner" failed on a loaded runner when reading the credential took longer than the 30 ms it slept: close() came first and the request was refused before it was admitted. It now closes once the runner's hook is entered, with a credential that takes 60 ms, so a timer in its place fails it. The same kind of wait is replaced in the proxy, runner, runner-stop and kernel tests that asserted what had to happen first.
