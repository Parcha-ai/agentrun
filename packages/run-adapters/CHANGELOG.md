## 0.1.0-beta.30 (2026-11-05)

- A Codex run stopped just after its message was sent to Codex no longer loses the message. Codex answers `turn/start` before it writes the message to its rollout: on the real app-server, killed at the answer or 20 ms after it, the rollout held no user message; 100 ms after, it did. A stop in that window kills Codex with the message sent and never recorded, and the next Codex, resumed from the session's rollout, never has it. The stop's settle now reads Codex's rollout as the session keeps it, the rollout the next Codex is resumed from, and carries a placed message it lacks into the next one, as claude-agent's settle reads its CLI's transcript. The `turn/start` send mark is gone (the kernel's `markSent` and `sentMarks` with it); a stopped drive still starts no turn.
- A run whose model provider stops the answer on its content filter now ends `failed` with `error.code` `moderated` and
  says so in plain words: "The model provider stopped this answer (its content filter). Rephrase the request, or try
  another model." Before, it ended `run_failed` with the provider's jargon ("Response incomplete: content_filter"). The
  Timeline's error row keeps the harness's words for the stop (pi-ai's on pi, the kernel's on claude-agent and codex). On pi the run reads pi-ai's words for the stop on each API. On
  claude-agent and codex the session's model proxy reads the provider's stop (Anthropic's `refusal`, an OpenAI answer
  `incomplete` for `content_filter`) and the harness ends the turn at once: the CLI no longer asks for the refused answer
  again, turn after turn. Only the turn's own answer request ends it: a side call the CLI makes beside the turn (one
  without the session's tools) that the provider stops is logged and left to the CLI. The refused request is booked at
  the usage its end reports. The kernel exports `CONTENT_FILTERED`, the text such a turn ends with; a provider policy may
  say a stop through `filtered` and a side call through `answers`, and the model proxy tells its machine through
  `onFiltered`.
- A message the person stopped before the harness began it is no longer lost. A Codex or Claude run stopped in its first seconds (Codex still starting), then told "Go on.", answered "I'm missing the earlier task context": the stop withdrew the first message, and the follow-up reached the model alone. Now the stopped message stays in the conversation. The next message carries it first, with a line saying it was stopped before any work on it began, and the stopped turn still never runs on its own. Several stopped messages are carried in order. A stopped steer is not carried. A crash after the next message was taken, before the harness recorded it, still recovers with the stopped words.
- A model request under a spend cap is booked by one rule on every harness: the kernel's `bookRequest`, from how the
  request ended (`Ended`). The rule is never to under-count.
  - **A whole answer** books its own cost, or its hold when that cost cannot be read. On pi, that used to make what the run
    had spent unknown.
  - **An error status before any event**, or a request refused at connect, books nothing.
  - **A failure once the request left, a gateway's 504 or 524, or an answer after an attempt that was lost** books the
    hold.
  - **A stop** books what streamed: its content, and the part of a hidden reasoning budget that did not stream.
  - **A content-filter end** on pi books the hold: pi-ai ends it as an error after events, which can have been billed. On
    the proxy, a filtered answer is an answer and books its own cost.

  On pi, the cap now gives pi-ai a fetch that records each attempt pi-ai makes, so a reset before any response books the
  hold where it booked $0, and a 429 then an answer is priced once. An API whose transport that fetch cannot see (Codex's
  WebSocket, Bedrock, Google, Cloudflare) books the hold for a failure before any event. A later process reads the figure
  this one booked: a pi request that failed before any event marks its hold, and the runner writes `bookedUsd` and `rule` on
  its records. The model proxy passes how a request ended as `afterRequest`'s third argument.
  If the store cannot take such a mark within 15 s, the request fails, saying its end could not be recorded, and a later
  process reads it at its hold.
- A request you stop under a cap counts the reasoning it never streamed. A model whose reasoning streams only as a summary (the Responses API's reasoning, Claude 4-class thinking) is billed for far more than the summary's bytes. A stop after about 10,000 hidden reasoning tokens on a gpt-5-class model with a 20 KB context cost about $0.106 and counted $0.038, so deliberate stops could pass a cap. A stopped request that reasons now also counts the part of its reasoning budget that did not stream: input + streamed + 1,024 + max(0, reasoning budget - reasoning streamed), never more than its hold. Real usage still replaces the figure when it comes.
  - **On pi:** a reasoning model's stopped request counts its thinking level's budget (on Anthropic's API, the `budget_tokens` it was sent with, for a model whose thinking takes one). A Claude model that thinks adaptively (every current one on Anthropic's API) is sent no budget, and its thinking is bounded only by its output limit, so it counts that limit less 1,024 tokens: in practice its hold. A stop after a 300-byte thinking summary on Sonnet 5.5 with a 20 KB context under a $1 cap counted $0.142 at medium and $0.224 at high, against about $0.45 for 40,000 adaptive thinking tokens. The request's output limit is now the one actually sent: the cap had taken a thinking budget out of it that pi-ai never sends (8,192 tokens at medium), so the request was held at more than it was sent with. With no level, on an API whose model reasons at its own default, it counts its whole output limit. With thinking off on Anthropic's API, on a model whose thinking can be off, nothing more.
  - **Adaptive thinking counts up to the hold.** On every current Claude model, on pi and on `claude-agent`, the provider is given no thinking budget, so a stopped request counts up to the hold the cap took for it. Under a cap with little left beside that hold, the request after the stop can be refused.
  - **On `codex`:** the effort's budget (minimal 1,024, low 2,048, medium 8,192, high 16,384), none at effort `none`, and the output limit when the body names no effort.
  - **On `opencode`:** the same as `codex` (the same Responses API): what a stop counts as streamed is the content its deltas carried, not the wire, plus the unstreamed part of its effort's budget. On the walk through OpenCode's proxy (a request at $100 a million output tokens under a $0.50 cap, stopped after 1,146 characters of answer text after the stream's echo of the request) the stop booked 106,831 bytes, its whole $0.50 hold, and refused "Go on."; it now counts $0.217, and "Go on." goes.
  - **On `claude-agent`:** the thinking budget, or `max_tokens` when thinking is adaptive, for every request that thinks; none with thinking off. Thinking that streamed is subtracted, so a stop after a budget's worth of visible thinking counts nothing on top.
  - **Kernel:** a provider policy may read a request's hidden reasoning from its body (`reasoningHidden`). It may also read the reasoning in each streamed event (`reasoningBytesOf`). The model proxy books a stopped response with both (`stoppedHiddenTokens`, `stoppedReasoningBytes`), and the runner counts all it sent plus the part of the budget its reasoning did not cover.
  - **What streamed is the content, not the wire.** On `claude-agent` and `codex` a stop counted the response's bytes as sent, the provider's framing included: about 11.7 bytes a character of text on the Responses API and 24 on the Messages API. A codex request at $100 a million output under a $0.50 cap, stopped after 1,146 characters, booked its whole hold and refused "Go on.". It now counts each text, reasoning and tool-argument delta's UTF-8 bytes, as pi counts its streamed blocks: $0.217, and the next request goes. A provider policy reads them (`contentBytesOf`).
  - **A stop before the provider's first header** on `claude-agent` and `codex` now counts as a stop with nothing streamed (its input and 1,024 tokens, as on pi), not its whole hold. A response the provider answered with an error status still counts at its hold.
- A message the person stopped the instant it was sent is no longer lost on claude-agent, and the same window is closed on Codex and OpenCode. Asked "Reply with exactly this code and nothing else: CARRY-CLAUDE-7", stopped within its first second, then told "Go on.", a claude-agent run answered "There's nothing earlier in this conversation for me to continue from": Claude takes a message within its first second, so the stop landed after the harness placed it and before the CLI was handed it, and nothing carried it. Now a stop's settle carries a placed message its CLI never took into the next one, as it carries one stopped before it was placed. On claude-agent that is a message the CLI's own transcript, as the session keeps it, does not hold: that transcript is the history a resumed CLI is given, so a carried message is never sent twice. On Codex it is a message Codex's own rollout, as the session keeps it, does not hold. OpenCode marks a message just before it sends it (`prompt_async`), and a marked message is never carried: a crash between the mark and the send loses it rather than sending it twice. After a stop, no new turn is started.
  - **A recovered message is not carried again.** After a crash between a message's placement and its CLI's record, the recovery message carries its words. It now records which messages it carries, before it goes (a kernel effect by its id on claude-agent, its `PROMPT_STREAM` record on OpenCode). Once the CLI holds the recovery message, a stop's settle and a later recovery both count those messages sent, so nothing is sent twice, even after a second crash. Codex's recovery already did this through its client id.
  - **A follow-up's own prompt** (the host's, named to the settle) is withdrawn and never carried into the person's next message, as the follow-up says: a host prompt that never ran is not sent. A person's message waiting beside it is left as it is.

## 0.1.0-beta.29 (2026-11-04)

- `@parcha/agentrun-adapters/kernel` and `@parcha/agentrun-adapters/process`: the durable kernel a harness adapter runs on, over the run's session store, and the shared layer for harnesses that run as a child process.
  - An effect is its intent, then at most one outcome, each durable before what follows: a completed or failed effect is answered from its records and never runs again. When a drive opens, an intent a dead process left open is run again if its tool is `safe`, and recorded failed and interrupted if it is `never` ("it may or may not have taken effect"), never run again.
  - A drive writes its session one append at a time, in call order (a submit's input, an effect's intent and outcome, a journal's blobs), so its state folds the records in the log's order whatever order a writer resolves them in. A failed append rejects for its caller only; the ones after it still run.
  - `Drive.refresh()` re-folds the drive's own records and reads nothing: the drive is the session's only writer, and door input is already folded by `submit`. (A read that resolved after a newer append put older state back, so a completed effect could look unfinished and run again.)
  - A built-in call begun twice (the same execution delivered twice) is never run twice: `BuiltinCalls.begin` reserves the call before it awaits anything, and a second `begin` waits for the first's outcome and answers with it from the log; when that outcome could not be written, the drive stops and the second `begin` rejects with the drive's stop reason, never with an answer the log does not hold.
  - One drive runs a key once at a time: a second `effect()` call for a key already in flight in that drive, even one issued before the first's intent is durable, is refused with `Fatal` and its function does not run.
  - Input is placed before it is sent, and a withdraw that lands first wins: a placement that names a withdrawn submission (from a `pending()` read before the withdraw) places nothing, and its effect throws `Restart` without running (before writing anything, when the withdraw is already in the drive's state), so the rebuilt drive sends only what is still pending.
  - A large native record is kept as a blob in the session's own records, named by its content's sha256: `writeBlob` refuses a hash that is not its text's (`TypeError`), and `readBlobs` returns a blob only when one write's pieces are all there and join to text with that hash, so a write again under another piece size never mixes with the first.
  - `./process` has the native journal, the transcript fold, the recovery note, the tool bridge, the hook-pair calls of a harness's built-ins and the inbox. These are copied from another project and listed, with each file's upstream blob and sha256, in `vendor/durable-harness/UPSTREAM.json`; `NOTICE` credits it.
  - One process writes a session at a time, and the store enforces it. `SessionStore` is now `read(key)` and `open(key)`, which returns the session's writer and fences every writer opened earlier for that key, whether or not the new one has written anything; a fenced writer's `append` is refused with `SessionFenced` and writes nothing. The runner opens one writer per attempt before it reads the session and passes it to the adapter as `SessionIO.writer` (it was `store`); a runner whose writer is fenced ends `fenced`, not final, and delivers nothing. `openDrive` takes the writer (it took `store` and `key`), and a stale drive's refused write is a `Restart`. A host's store must implement `open` with this fence.
- New package `@parcha/agentrun-adapters`, held (not on npm yet): the seam for agent harnesses other than Pi. `createHarnessRunner(adapter, options)` is exactly the interpreter's `runNode`, so a DSL `agent` node runs on any harness that implements `AgentAdapter`, the way `createPiRunner` runs it on Pi.
  - The node's record arrives through an injected `submit` tool (the node's schema under `value`); a review that does not accept it is answered in the same session.
  - Every paid request passes the runner first: the turn cap (`maxTurns`, default 8, and a node's own `max_turns` within it), then the host's `beforeRequest`, which receives the node's `budget_usd`, what its session has spent, its label, key and execution path, and may refuse the request. `maxSubmissions` (default 5) and `timeoutMs` (default 120 s) are the Pi runner's.
  - Under `withRecovery` a session is keyed by its step's `sessionId`: a delivered record is answered from the session's records with nothing run, and a session a process died inside is resumed with nothing paid twice. Without a step each call opens a fresh session.
  - Turns sent to a node have their own count, against its turn limit (or `maxSends`, default 100, when the limit is null); running out of sends is `turn_limit`, and its message says the cap was on sends. Turns that end with no paid request and no accepted submission end the node `no_progress` after three in a row. Turns, spend and `max_turns` still count paid requests only.
  - A turn limit, no progress, an unknown tool, a fork the harness cannot make and a host refusal fail the node with `final: true`.
  - Every event names its node (session key, label, execution path).
  - `./testing` has `memorySessionStore` and `fauxAdapter`, a scripted harness with no model and no network.
- The model proxy's `origin` may now carry a path: a gateway that serves the API under one (`https://gateway.example/api`) gets each request at that path plus the route's (`/api/v1/...`). Before, the path was dropped and the request went to the origin's own `/v1/...`. A base with userinfo, a query, a fragment or a backslash is refused when the proxy starts, so the provider's key goes only where the base reads.
- `boxSlot` (`@parcha/agentrun-kernel/host`) runs one session's harness boxes one at a time, whatever the isolation: how a box starts and how it is reaped are its arguments, in the shapes of the kernel's new `Box` (`host/box.ts`: `BoxSpec`, `BoxRecord`, `BoxRecorder`, `BoxedChild`, `Reaped`, `BoxError`).
  - `start` is synchronous. It is refused with `BoxError` `box_busy` while the session's last box is live, being reaped, or was not counted empty. The box's start writes its record before the spawn (`ahead`) and before its first process is let go (`started`).
  - The box is reaped as soon as its process exits or is never let go. Only the reap's own count frees the slot. The box's exit status and output are never read, since anything in the box can forge them. A box left with processes, or one nothing could count, rejects with `box_not_empty` and keeps the session from starting another. `adopt` reaps the record a session's last box left before anything starts.
  - serve's `writeDurableSync` and `writeDurable` sync the new file and its directory before they return. `boxRecorder` writes a run's `box.json` with them, and refuses a record that names no writer, since such a record could never be cleared safely.
  - A box that exits while its `started` record is still being written is reaped once that write lands, by the record it wrote. A box that has ended records nothing more, so a late write never replaces the next box's record.
  - The durable writes write every byte or fail. A short write (a disk nearly full) is never synced and renamed as a whole record; the recorder refuses it with `box_record_failed` and leaves no part behind.
- A host's gateway headers reach the provider on every model request a Claude Agent session makes: `claudeAgentAdapter({ provider: { ..., headers: { "x-litellm-tags": "job:...,purpose:...,run:..." } } })`, the same LiteLLM spend-tag header a pi lead's model requests carry, so a gateway attributes the Claude lead's spend to its job. The session's model proxy (`startModelProxy({ headers })` in `@parcha/agentrun-kernel/host`) adds them to every forwarded request, paid and free, after the client's own headers (so the CLI can neither set nor override them) and before the credential's. They are checked when the adapter is made (`hostHeaderProblems`): a token name that is not the proxy's own (`authorization`, `x-api-key`, `host`, `content-*`, `anthropic-*`, ...), and a one-line value of at most 1024 characters. A host sends a gateway's headers only to that gateway.
- `claudeAgentAdapter({ webSearch: true })` turns on Claude's own WebSearch, and nothing else of the CLI's: the model may call it, the PreToolUse hook lets it through with its intent recorded before it runs (safe to repeat after a crash), and the system prompt's note names it. The CLI runs each search as a request of its own through the session's model proxy, which then admits Anthropic's web search server tool exactly as the pinned CLI sends it (`web_search_20250305`, at most 8 searches, the domains the model named); every other hosted tool, a later web search version, and every server tool's block stay refused. Each search the provider reports (`usage.server_tool_use.web_search_requests`, read from a stream's last `message_delta` or a whole body) is booked at $10 per 1,000 searches (`CLAUDE_WEB_SEARCH_USD`) on top of the host's `price`, into the session's cost and so its spend cap. A request with the web search tool reports no input bound (`inputTokensMax` undefined): the provider bills the pages it reads as input. In `@parcha/agentrun-kernel`, `ProviderPolicy.serverInputOverhead` may now return `undefined`, a policy's word that a body has no input bound: the model proxy leaves `inputTokensMax` undefined (never 0) and, unlike a throw or a non-count, reports no failure. WebFetch stays off. Default off: a session without the option runs as before.
- **The Codex adapter takes the host's skills, and its sessions no longer see Codex's bundled ones**
  - `codexAdapter({ skills: [{ name, files }] })`: Codex lists each skill to the model by its name and description, and the model reads its `SKILL.md` and its other files with `read_skill_file`, the shared read-only host tool (Codex has no shell here). The skills are written into each session's `CODEX_HOME` at the start of every drive, where Codex lists a user's skills in a turn with its built-ins off; it lists none from a working directory's `.agents/skills` there. A host tool named `read_skill_file` is refused when the adapter has skills.
  - Codex's bundled skills (imagegen, openai-docs, skill-creator, skill-installer) are off in every Codex session, with skills or without (`[skills.bundled] enabled = false`). Before, Codex installed them at every start and listed them to the model, so a session was shown skills its host never gave it.
  - The skills are checked when the adapter is made, and a bad one throws before the binary is looked for. The check, `skillProblems`, and the skill's shape, `HostSkill`, are now in `@parcha/agentrun-kernel` beside `readSkillFileTool`. The Claude adapter's `skillProblems` and `ClaudeAgentSkill` are that check and shape, re-exported, so nothing changes for its users; the Codex adapter exports the same `skillProblems`.
  - The local Codex machine takes a seed of files for one of its private directories (`seed: { dir, files }`, each file's text by its relative path), written at acquire and again after every wipe. A path that is absolute, empty, climbs or starts with a dot, or a directory not the machine's own, is refused when the machine is made.
- The egress proxy can take a host list: `startEgressProxy({ ..., allow: ["pypi.org", "*.pythonhosted.org"] })` lets a box reach only those hosts, on ports 80 and 443.
  - An entry is an exact name or `*.suffix`, which covers the names below the suffix but not the suffix itself. Matching ignores case and a trailing dot.
  - A host off the list, any IP literal and any other port are refused before any lookup, so a name off the list never leaves the host. The refusal is `403` (SOCKS5 reply 2) with the reason in plain words, for example `example.com is not on this box's network list`, followed by the caller's `allowHint`. Its `x-egress-refused` and log class is `not-listed`.
  - A listed name then meets the address rule as before: one that resolves to private or metadata space is still refused.
  - With no `allow`, nothing changes. `parseAllow` is exported, so a caller checks its setting with the code the proxy enforces it with.
- A box's egress proxy and its address rule (`@parcha/agentrun-kernel/host`): `startEgressProxy` serves HTTP CONNECT, plain HTTP forwarding and SOCKS5 CONNECT on a 0600 Unix socket, to the public internet only, and `checkAddress` is the one rule it applies. The rule judges the binary address a socket would connect to, so the text a client wrote never matters, and it refuses loopback, private, shared and link-local space, cloud metadata addresses, multicast, broadcast, reserved, benchmarking and documentation blocks, IPv6 outside global unicast, and the host's own interface addresses. An IPv6 address that carries an IPv4 address is judged by the IPv4 inside.
  - A name is resolved once, every address in the answer is checked, and the connection goes to exactly the checked address.
  - A refusal is answered before any socket opens: 403 with the class as its reason, or SOCKS reply 2. SOCKS5 BIND and UDP ASSOCIATE, an HTTP upgrade, and a Host header that names another host than the request URI are refused by name.
  - A redirect is never followed: the client's next request is checked like any other.
  - Each run has a cap on connections open at once and a budget of connections in all, each refused by name. The log carries the host, the port, the address and the class, never a path, a query, a header or a body.
- `followUpOnce` in `./kernel`: one more turn in a session that has answered, sent at most once. Its intent is durable before the prompt leaves, so a process that dies inside it leaves it interrupted and no later process sends the prompt again; a follow-up turn a crash cut off is settled, never resumed, so it makes no paid request after the crash. The prompt is sent under a submission id of the follow-up's own, and the settle is named only that submission, so a person's message is never withdrawn. Its paid requests are held to a reserve of their own (`reserveUsd`, counted from its first request), and a request is refused while the session's spend is unknown. `followUpState` reads its state from its records, for a host deciding whether an open turn is the follow-up's.
- The harness packages are published from this release under their final names: `@parcha/agentrun-adapters` is `@parcha/agentrun-kernel`, `@parcha/agentrun-claude-agent` is `@parcha/agentrun-harness-claude`, `@parcha/agentrun-codex` is `@parcha/agentrun-harness-codex`. Their subpaths, directories, harness ids and `AGENTRUN_*` environment variables do not change.
  - Messages these packages raise start with `agentrun-kernel:`, `agentrun-harness-claude:`, `agentrun-harness-codex:`.
- `delegateTool`: a lead hands one task to a named sub-agent, `delegate({ agent, task, context? })`, as an ordinary host tool for a lead on any harness. Each call runs a durable child `agent` node with the agent's own system prompt, only its own subset of the lead's tools, and a fixed answer shape (`DELEGATE_RESULT_SCHEMA`: `answer`, `citations`, `gaps`).
  The child keeps its session under `<lead's key>/delegate:<call id>`, so the call is replay-safe: a finished child answers from its record, and one a crash cut off resumes from its own store without sending its paid requests again. Its requests go through the lead's `beforeRequest`, and its deadline is the lead's or the agent's share of the time left. Children run one at a time, never delegate further, and their events carry a `delegate` tag. `delegateProblems` checks a definition before the tool is made.
  - A host tool's call context carries the runner's `sessionDir`, when it has one, so a tool that runs a node of its own (the delegate) gives its child a private directory the same way, by the child's key.
- `@parcha/agentrun-kernel/host`: a session's model proxy, provider-neutral. It listens on the loopback interface and admits only the session's own key (compared in constant time), only the routes a `ProviderPolicy` lists (by exact path text: no absolute URL, `..`, `//` or `%` escape, and no query but one the route lists exactly, forwarded as listed), and one strict JSON value with no duplicate key. A route may instead be answered by the proxy (a client's connectivity check) or be free (a token count): forwarded without asking the runner, and reporting no usage. A policy may rewrite or drop a listed header's value (a beta it does not know). The policy shapes or refuses the body; the runner's `beforeRequest` is asked before each paid request, and a refusal is answered with a status the client does not retry; the provider's credential is added by the proxy and never reaches the harness; each completed response's usage goes to `afterRequest`, and one cut off before its usage reports nothing. The proxy keeps no ledger: the runner alone accounts model spend.
  - `./process` gains `waitForSubmissions` (a harness that keeps running while it waits for input) and `zodShapeFromJsonSchema` (a host tool's JSON Schema as a zod shape, with the zod the harness SDK uses), both copied with their provenance like the rest of the layer.
  - A policy may say which model a checked body asks for (`ProviderPolicy.modelOf`): a session's smaller model, for a client's background calls, is then the model the runner is asked about and the one the request is priced at. Without it, or when it throws (logged), the request is booked as the session's model.
  - A request that cannot be sent (no provider credential, one that could not be read, or credential headers the policy could not build) is refused before the runner is asked: it is never admitted or booked, and spends no turn. (It was admitted, then booked at nothing.)
  - `close()` admits and sends nothing more: a request that was waiting on the runner when the proxy closed is refused and released, booked once at nothing.
  - A body's `__proto__` key is parsed as an own field; the parsed object's prototype never changes.
  - A client that reads slowly holds the provider back: the proxy reads no more of an answer until what it wrote has drained, and each wait leaves no listener behind on the response.
  - A client that leaves once it has read a successful answer's usage, while the provider still holds the stream open (Codex does, at its completion event), is booked at that usage; one that leaves before any usage is in what was read stays an unknown cost.
- `modelPortFor(writer, options)`: the runner's booking of paid model requests, on its own, for a host that drives an adapter session directly (a chat run, not a DSL node). It writes the same records the runner does, `runner.request` before a request leaves and `runner.turn` with its cost when it answers, applies the same turn limit and the host's `beforeRequest`, and reports `request_start` and `request_end`. `createHarnessRunner` is built on it.
  - A paid request a crash cut off (its `runner.request` with no `runner.turn`) is booked once when the session is next opened (`bookCut()`): a `runner.turn` marked `cut`, at an unknown price, and a `request_end` whose usage says `cut: true`, `usd: null`, `estimated: true`, so a host's ledger shows the possible spend. It is booked once however many times the session is recovered.
  - Paid requests may be in flight together, so each is booked under the turn it was admitted as: `ModelPort.beforeRequest` returns a ticket (`{ turn }`), the model proxy hands it back to that request's `afterRequest`, every `runner.turn` names its turn, and `request_end` reports it. A cut request is the admitted turn with no answer, not a count.
  - Paid requests asked for at once are admitted one at a time (the turn limit, the host's `beforeRequest` and the durable `runner.request`), so two can no longer both pass a limit only one fits; once admitted they still run side by side. `beforeRequest` is told the session's requests in flight (`inFlight`, each `{ turn, model }`), so a host's budget can hold each one's worst case until it answers: `spentUsd` counts answered requests only.
  - Each booked request carries the ids its provider's response gave it (`providerIds`, by header name: the provider's `request-id`, a gateway's call id such as LiteLLM's `x-litellm-call-id`), on `runner.turn` and `request_end`, so a run's books can be joined to the provider's or gateway's log request by request. The proxy reads them when the response's headers arrive (`providerIdsOf`, exported from `./host`), before its body, and the port writes them then (`runner.response`, through the new optional `ModelPort.responded`): a request a crash cuts off after that point is booked as cut with its ids, since the provider saw it, and one cut before has none. Only id-named headers with id-shaped values are kept.
- `processAlive(pid)` from `@parcha/agentrun-kernel/host` says whether a process is running. A zombie, which has exited but whose parent has not reaped it, is not running, even though `kill(pid, 0)` still finds it. That happens to every orphan under a PID 1 that does not reap, such as a container started without an init.
