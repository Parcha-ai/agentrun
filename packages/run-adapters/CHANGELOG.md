## [Unreleased]

## 0.1.0-beta.33 (2026-11-10)

- A run parked at its spend cap no longer shows a "Model request failed: 400 {…agentrun_proxy…}" row in its Timeline. The model proxy refused that request before it was sent, and the park's row already says what happened. That refused request also no longer counts as a model request in the run's usage line.

  The cap's refusal now carries its code through to the proxy as a field: the runner's `Refusal.code`, then `HarnessRunError.refusal`. The proxy writes `code: "spend_cap_reached"` in its refusal body. The Timeline matches on that code and `type: "agentrun_proxy"`, never on the words. Every other model failure, a provider's 400 included, keeps its row.

- A run's spend cap prices each model request's input from the previous request's cache (`cap_mode` `expected`, the default): the input the previous request of its conversation read from or wrote to the cache counts at the cache-read price when it ended less than 4 minutes before, so a cap pays for about what the run really spends instead of pausing near half of it. Output never passes the cap; a cache miss can, by at most the request's bound, served as `cost.overshoot_bound_usd` while it is in flight (and as `pending.overshoot_bound_usd` on a run paused at its cap). The real cost is booked, one timeline row says `Went $X over its cap on a cache miss (at most $Y).`, and the run pauses at its cap instead of failing. `cap_mode: "strict"`, on a run's body or an agent's definition, keeps the worst case: every input token uncached.
- A run near its spend cap is told once to finish: when what is left is under three times its typical request (the median of the run's own model's priced requests after the first), the model's next request carries "About $X left of this run's budget: finish now with your answer.", and the Timeline shows it as the server's row. On pi it goes into that request's context; on claude-agent, codex and opencode the model proxy adds it to the request's body after everything the CLI sent, so the cached prefix is unchanged. No message is queued, so nothing runs after the model's answer. Once per cap, across restarts; a raise re-arms it.
- A capped run is told to wrap up when it is really near its cap, and Claude Code, Codex and OpenCode runs are told as pi runs are. Step 0 (nothing priced yet) is judged on the request taking the note itself, its input and a 4,096-token answer, and told in that request, as pi's is. A CLI run used to judge it at a request's admission, after that request's note was taken, and kept the judgement after the first real cost came in, so a run spending about a cent a request could hear "finish now" from its second request on. From the first priced request on, the run's measured typical request cost decides. On every harness, a run is also told once what is left falls under twice the least admission of the request taking the note, the figure the cap refuses it below, so a run whose requests need far more output than they cost is warned before the cap stops it.

After a deny, a model no longer tells the person it can't confirm whether a charge was made.

A call cut after it started but before its outcome is denied with no claim either way ("It had started before the deny, and whether it took effect is not known.").

Host tools now hear the kernel's attempt (`HostTool.call`'s `attempt`). On pi, which reruns a cut replay-safe call with the same call id and no sign of a rerun, the gate keeps its own mark of each replay-safe call it let through that can bill (web_fetch, web_search: an `agentrun.gate_passed` entry, written before the tool runs), and reads its marks before the run resumes, on an agentic run and a workflow's model node alike, so a rerun of one is treated the same way.

- A learned workflow's model nodes, its `llm` call nodes and a call node's native search, on claude-agent, codex and opencode, are requests on the run's one route: the session's own model proxy, under a side key the proxy mints for the host (`ModelProxy.sideKey`, `AdapterSession.port`). They get the harness's own body rules, provider, key, price and booking, labelled `learned_workflow` on the session's records (`runner.request.host`), under the run's one cap, as a side call: the spend cap's wrap-up never counts it toward a typical request, and it never takes the wrap-up's note. They reach an operator's gateway at ANTHROPIC_BASE_URL or AGENT_MODEL_BASE_URL as the harness's requests do, and never go around it, so a run there is offered its learned workflows (the learning pin's `workflows_off` is gone). A side request is never the turn's answer request: a content-filter stop on it does not halt the turn.
  Upgrading: Finish or cancel capped runs that used learned workflows before upgrading: their earlier learned-workflow spend is not counted against the cap after it. A pin written before this keeps the workflows it left out, and its `workflows_off` is no longer read.
- A run with no computer that mounts its folder no longer gets a shell on the server. Before, such a run (an agent with no computer on a server without Docker, a browser, a phone or a desktop that does not mount the folder, or a runner place) was given bash in its folder on the server's own machine, where a command could read the server's data and keys. Now, in a server whose run folders are on its own disk, that run gets the file tools alone, confined to its folder: bash and the background tools are not offered, and a bash call answers that it is not available and that a sandbox computer gives a shell. A sandbox, or a desktop whose provider mounts the folder, keeps its shell, and with Archil storage a run with no computer keeps bash on Archil's serverless exec, which runs outside the server. `runShellOf(setting, mode, registry)` says where a run of a computer setting has its shell, before it starts.
- A Claude Code, Codex or OpenCode turn parked on a call that waits for a person no longer hides a request whose cost could not be recorded. Such a request now stops the booking as it does at any other time: the run fails with the cost-write error instead of going on past a request it did not record. The kernel exports `TurnParked`, the stop a host gives for a parked turn (`ModelPortOptions.stopped`): it refuses new requests but is no stop of the booking.
- A provider's error no longer hands a harness the provider's credential. The session's model proxy relayed every answer as it came, so a provider that echoes the key it was sent ("Incorrect API key provided: <key>") gave it to the harness, which on a CLI harness runs in the sandbox. Now, in an answer with an error status, and in an error event inside a streamed answer (Messages' `error`; Responses' `error` and `response.failed`), the credential the proxy sent and the values of the headers it added are cut out ("[redacted]") as sent, JSON-escaped, and with "/" escaped. Then the host's redactor runs, when it gives one (`ModelProxyOptions.redact`). An event's name never exempts its data: an error under a healthy event name is cut as an error event, and every other event of a streamed answer has the credential cut too and passes otherwise byte for byte. A header value shorter than eight characters is cut only from an error, and only where it stands as a whole word inside the error's own text, so a value of "1" never touches a status code. An error body still reaches the client as it comes.
- The model proxy reads an answer's content-filter stop and output-limit cut off each stream line once, as the line ends, instead of reading the last 64 KiB of the answer again for every piece. A long answer (about 1 MB, some 65,000 pieces) no longer holds the runner's thread for most of a minute, starving the run's store commits and claim renewals until the run never ended. A whole JSON body is read whole while it fits the window, so a stop in a pretty-printed body is still told before its client has it.
- A capped run's wrap-up note counts as told only once a request carrying it is answered, on every harness. A request the provider never answers, one lost on the way, one cut, one stopped part way, or one that never leaves, leaves the note for the next request, which carries it. Before, the note counted as told as soon as a request carrying it was admitted, so a retry after a failed request went without it, and the run could reach its cap unwarned. On another harness, a note told in an answered request is never told again in a later process, even if the row that shows it was lost: the row is rebuilt from the answered request's own record. On pi, the run's wrap-up row, written once the carrying request is answered, is what a later process reads.

  Upgrading: a host that implements the kernel's `ModelPort` may return `note` in a request's admission (written on its `runner.turn` record when it ends) and read `ended` on `request_end`; both are optional.
- A capped Claude Code run's wrap-up note goes in the turn's own request. With no small model set, a Claude Code title or summary call goes on the session's model, and such a call could take the note once it was due, so the model never saw it. The model proxy now gives the note only to a request its policy counts as the turn's answer request (`ProviderPolicy.answers`), and a side call goes as its client sent it. A session with no tools offers nothing to tell its requests apart by, so each of its requests still counts as the turn's, as before.
- The kernel's spend cap, still unused until the cutover, counts a request that has no answer (its claim lost before the answer was written, or its turn cut) at its hold plus its bound, the worst it can have cost, and the run's cost then reads unknown with the known part beside it. Before, such a request counted at its hold alone, so a request that missed the cache could pass the cap unseen. `runner.request` keeps the bound the host gave beside the hold; a host that gives none is unchanged.
- The kernel's spend cap, still unused until the cutover, prices a request the host sends beside the harness's own (a learned workflow's node) as a cache miss: the session's previous request never stands for it. A request carrying the wrap-up's note that fits only without the note is sent without it (`withoutNote`), and one that fits neither way is refused in the words for its client's own body. The note never refuses what fits.
- The kernel's spend cap, still unused until the cutover, refuses to admit a step id again while its last end mark is unwritten, so a retried settle can't book the new step at the old step's figure. It reads a host hook's spend or hold that isn't a finite figure of 0 or more as unknown and refuses the request, and never counts it as $0 or as room. It won't price a request in flight at 0 output when it has no hold, no output limit and no ceiling.
- The kernel's spend cap, still unused until the cutover, prices a model with tiers as its provider bills it: a request whose whole input (fresh and cached) passes a tier's threshold is held, and booked where the cap prices it, at that tier's rates, as pi-ai's calculateCost prices it on the catalog's own table. Before, it held such a request at the base rates, half the bill for gpt-6-sol past 272,000 input tokens, so a run could pass its cap by up to 2x. `ModelPrice` takes the catalog's `tiers` as given.
- The kernel gains its spend cap, unused until the cutover and not exported from the package: one rule decides every paid step for every harness (a model request, a priced tool, a decision), the same pricing, clamp, refusal words, wrap-up note, park and raise, with marks that let a reopened run read what it spent. No code path uses it yet.
- The kernel has one registry of host tools, still unused until the cutover: read, write, edit, bash and the five background tools, each with main's name, words, schema and replay, in main's order. It also holds their limits, the tool gate's shell family, and the run's hands port. bash is bounded to the hands' ceiling. The background tools run on the computer's processes, eight at once, each started, counted and given its id in one step, and reach only processes they started; with no computer they are refused in words. An executor answers a failure in words apart from its output, so a timed-out bash keeps what it printed, and only an abort throws. The host gives read, write, edit and bash's own run, and a registry missing one of them is refused when it is built. With no computer, bash runs in the run's folder and is asked first.

- A message the person stopped before the harness began it is no longer lost. - A model request under a spend cap is booked by one rule on every harness: the kernel's `bookRequest`, from how the

  - **A whole answer** books its own cost, or its hold when that cost cannot be read. On pi, that used to make what the run
    had spent unknown.
  - **An error status before any event**, or a request refused at connect, books nothing.
  - **A failure once the request left, a gateway's 504 or 524, or an answer after an attempt that was lost** books the
    hold.
  - **A stop** books what streamed: its content, and the part of a hidden reasoning budget that did not stream.

The model proxy books a stopped response with both (`stoppedHiddenTokens`, `stoppedReasoningBytes`), and the runner counts all it sent plus the part of the budget its reasoning did not cover.
  - **What streamed is the content, not the wire.** On `claude-agent` and `codex` a stop counted the response's bytes as sent, the provider's framing included: about 11.7 bytes a character of text on the Responses API and 24 on the Messages API.   - An effect is its intent, then at most one outcome, each durable before what follows: a completed or failed effect is answered from its records and never runs again.
