## 0.1.0-beta.32 (2026-11-08)

- The code taken from vercel-labs/durable-harness is now AgentRun's own: the port froze, and the pristine upstream copies, the named patches, the import tables, `scripts/port-durable-harness.mjs` and `npm run verify:port` are gone. `vendor/durable-harness/UPSTREAM.json` still records where each copy came from, and each copy keeps its header and NOTICE its attribution. With it go the kernel's paths that never run:
  - `AgentAdapter.version` and `AdapterCapabilities.fork` (no adapter forks; a node that asks for `context: "fork"` is refused as before).
  - `DriveContext.config`, and `requires`/`needs` on a host tool and an effect's options; `kernel/types.ts` is no longer pinned to upstream's types.
  - The Codex harness's `codex.spend` ledger and its dollar caps (`sandbox({ budget })`, `GatewayLedger`, the gateway handler's `budget`, `ledger` and `onCap`), which never fired, and its table of removed options.
  - `Box`, `BoxSpec`, `BoxedChild`, `Isolation` and `boxSlot` (`@parcha/agentrun-kernel/host`), which nothing implemented or used.
  - The model proxy's parts only tests used (`inputTokensMaxOf`, `matchRoute`, `parseStrict`, `reportedCostOf`) move to `@parcha/agentrun-kernel/testing`; `providerIdsOf` and `MCP_ROUTE_VERSIONS` leave the host API.
  - The box egress proxy (`startEgressProxy`, `parseAllow`, the address table) moves into agentrun-serve, its one user.

  Fixed: a run on Claude Code or Codex now closes its harness session when its process lets the run go, as the adapter's `close()` contract asks; before, serve never called it. On today's adapters an idle session's `close()` stops no process of its own (each drive already ends its CLI or app-server when its turn ends), so this keeps the contract for an adapter whose session holds one. For it, pi-durable-disk's `DoorHook` has a required `close()`: the door's stop calls it once, busy or idle (on a drain after the abort, on a fence alongside the kill, within the abort's bound). A hook with nothing of its own to stop resolves at once. `DoorHook` also has a required `harness` id: a `close()` that throws, rejects or overruns its bound is logged with it ("door close failed" / "door close timed out") through `serveRun`'s new optional `log`, which the run CLI passes its log line to. A harness session that lands after the door's close (a stop while it was still opening) is closed too, once.
- Each adapter states what its harness is, and serve reads that instead of the harness's name. `@parcha/agentrun-harness-claude/facts` and `@parcha/agentrun-harness-codex/facts` export `facts` (the kernel's `AdapterFacts`): the API its proxy speaks (`wire`), whether it takes a message mid-turn, the memory one run reserves, its thinking levels, its own web search (`native` or `live`), whether its model is its own, how it names a model, its install line and pins, the schemas its MCP client drops, whether it binds the session's MCP servers, an MCP tool alias, and its proxy policy. Serve keeps one table from a harness id to its entry and one `providerFor(wire, env, model)`: opencode and codex take one route because both speak the Responses API, and the gateway base rule is written once, so pi's runs take it too. Nothing else changes for a run, a capability or a refusal's words.
  Upgrading: an AGENT_MODEL_BASE_URL that is plain http to a non-loopback host, names a user, or has a query, fragment or dot segment is now refused on pi, as on Codex and OpenCode (a backslash or whitespace too); the refusal names the setting, and the gateway's key is never sent there. `startServe`'s `fauxHarness` option is gone; a test passes `harnessTable`, a module of harness table entries (`entries(builtins)`), in its place. `AGENTRUN_SERVE_FAUX_HARNESS` is no longer read; `AGENTRUN_HARNESS_TABLE` is set from `harnessTable` alone and dropped from the server's own environment.
- Agents on codex call a saved MCP server's tools: grant `mcp:<server>/<tool>` in `definition.tools`, as on pi and claude-agent, and `features.mcp_client.harnesses` now lists codex. The harness writes each granted server in Codex's `mcp_servers` itself, at the session's model proxy (`/mcp/<server>`, behind the session key), with only the granted tools enabled and approve mode, so Codex never holds the credential. The proxy records each call in the session before it sends it, by Codex's own call id, so a call a crash cut off is answered interrupted and never sent again. A server that does not start fails the turn (`required`). The Codex proxy policy admits the granted tools in the `mcp__<server>` namespace Codex 0.164 sends them in, and the timeline reads `<server> · <tool>`. The kernel's model proxy mounts `/mcp/<server>` itself, once for every harness with an MCP client of its own, from the session's MCP and the client fact its adapter declares (`capabilities().mcpClient`, the `_meta` key of a call's id: `claudecode/toolUseId` on Claude Code, `callId` on Codex); `ModelProxyOptions.mcp` takes `{ session, client }` in place of a handler.
- Codex installs itself on first use, as Claude Code does, through one table of the harnesses that install on first use (`src/harness-install.ts`). The first run on codex, or the first agent saved on it, installs the version AgentRun pins (`@openai/codex@0.164.0`, with this platform's binary package) from npm into `<data>/harnesses/codex`; Claude Code's install moves to `<data>/harnesses/claude-agent`: an install an earlier build left at the top of `<data>/harnesses` (its package.json, lock and node_modules, read-only) is removed before the first install, with one log line, and Claude Code installs again; a `harnesses` directory that holds anything else is left as it is. Each is pinned by a lock the server ships (`harnesses/codex/`, every package by sha512) and installs the same way: `npm ci --ignore-scripts --include=optional` into a fresh directory, checked there (for Codex, that its platform package and binary landed, whatever the person's npm config omits), renamed into place and made read-only; a server that stops mid-install stops its npm. A codex run waits for the install and shows `Installing Codex (first use)…` while it does; until it is installed, `GET /v2/capabilities` lists codex with `installs: "on_first_use"`. Codex runs only the binary in that tree, never a copy beside the server; when npm fails, the run's error names the command that installs it by hand. Codex's npx hint (`-p @openai/codex@0.164.0`) is gone. The server image no longer carries a Codex CLI: its build removes `@openai/codex`, its platform packages and its bin link, and `docker/image-check.sh` refuses an image that holds any of them. The hint that restarts AgentRun with OpenCode keeps how it was started: npx's `-y`, `--port` and `--no-open`. `node scripts/harness-locks.mjs` (formerly `claude-lock.mjs`) makes both locks again. `@parcha/agentrun-harness-codex` takes the binary a host installed (`binary: { path, packageVersion }`, checked against the pins) and exports `codexTarget()`.
  Upgrading: Codex installs itself on first use, and the server image no longer carries a Codex CLI. Claude Code installs again on its first run, under `<data>/harnesses/claude-agent`; an earlier install at the top of `<data>/harnesses` is removed.
- The last data serve kept by a harness's name moves to the adapters' facts: a CLI's own tools and the table tool each one is (`AdapterFacts.nativeTools`, stated by claude-agent and codex), the harnesses each model key runs (from their wires' vendors; OpenRouter's key runs every one) and OpenRouter's default model for each wire's vendor. Nothing changes for a run, a capability or a refusal's words.
- A run near its spend cap is told once to finish: when what is left is under three times its typical request (the median of the run's own model's priced requests after the first), the model's next request carries "About $X left of this run's budget: finish now with your answer.", and the Timeline shows it as the server's row. On pi it goes into that request's context; on claude-agent, codex and opencode the model proxy adds it to the request's body after everything the CLI sent, so the cached prefix is unchanged. No message is queued, so nothing runs after the model's answer. Once per cap, across restarts; a raise re-arms it.
- With the built-ins off, a code-mode model (luna, sol) is no longer offered Codex's own `apply_patch`. Code mode listed it as a nested tool of `exec` with no environment to run it, so every call failed with "No usable execution environment is available". The harness now hands Codex its own bundled model catalog with `apply_patch_tool_type` set to null (`model_catalog_json`). `model_catalog_json` is now reserved: an app's `config` may not set it. With `builtins: true`, `apply_patch` stays. If the binary gives no catalog, the session runs on Codex's own and says so: the sandbox note the model gets with its first message reads "Codex's own apply_patch stays listed: …" with the reason.

  A host tool's images now reach a Codex model as images. The tool's answer to Codex carries each one as an `inputImage` item (a data: URL) after its text, where before only the text went.
- On Codex, a call that returned images and completed just before the session stopped, before Codex recorded its answer, is now repaired as its text plus a line saying how many images it returned, which are not shown again. Before, the model got the images' base64 as JSON text.
- Every deny the model reads now says plainly that the call never left: "It was not run: nothing was sent and nothing was charged." It covers a tool set to deny, an ask refused because no one can approve, the owner's deny of a parked call, and a person's declining message. After a deny, a model no longer tells the person it can't confirm whether a charge was made.

  An approved call that ran before a crash keeps its saved result when its tool is set to deny before the run reopens: the model gets that result, never "nothing was charged", and it is booked once. A call cut after it started but before its outcome is denied with no claim either way ("It had started before the deny, and whether it took effect is not known.").

  The same holds for a replay-safe host tool on claude-agent and codex (web_fetch, web_search) that the kernel runs again after a crash cut its first attempt: if it is now denied, or refused for want of an approver, the words say it had started and whether it took effect is not known, never that nothing was charged. If it now asks and PARKS, the request keeps that it is a replay in the run's store (`replayed` on the approval request), so the owner's Deny or a declining message says the same, after a restart too. Host tools now hear the kernel's attempt (`HostTool.call`'s `attempt`). On pi, which reruns a cut replay-safe call with the same call id and no sign of a rerun, the gate keeps its own mark of each replay-safe call it let through that can bill (web_fetch, web_search: an `agentrun.gate_passed` entry, written before the tool runs), and reads its marks before the run resumes, on an agentic run and a workflow's model node alike, so a rerun of one is treated the same way.
- On codex and claude-agent, a tool call (a remote MCP server's included) has its Timeline row while it runs, from the moment the session records its intent, and a call a crash cut off gets its result row at the next open from the session's record of it: "interrupted ... it may or may not have taken effect" for one that is not safe to repeat. Before, a running call had no row, and a cut call never got one.
  - On codex, a code-mode script's call the host parked for a person's approval (an MCP tool's or a host tool's) is never told to the model as completed: the cut script's output says it "was waiting for a person's approval and did not run". The host marks such an answer `parked` (`HostTool` and `McpCallResult`), which the MCP door never sends the harness's client.
- A learned workflow's model nodes, its `llm` call nodes and a call node's native search, on claude-agent, codex and opencode, are requests on the run's one route: the session's own model proxy, under a side key the proxy mints for the host (`ModelProxy.sideKey`, `AdapterSession.port`). They get the harness's own body rules, provider, key, price and booking, labelled `learned_workflow` on the session's records (`runner.request.host`), under the run's one cap, as a side call: the spend cap's wrap-up never counts it toward a typical request, and it never takes the wrap-up's note. They reach an operator's gateway at ANTHROPIC_BASE_URL or AGENT_MODEL_BASE_URL as the harness's requests do, and never go around it, so a run there is offered its learned workflows (the learning pin's `workflows_off` is gone). A side request is never the turn's answer request: a content-filter stop on it does not halt the turn.
  Upgrading: Finish or cancel capped runs that used learned workflows before upgrading: their earlier learned-workflow spend is not counted against the cap after it. A pin written before this keeps the workflows it left out, and its `workflows_off` is no longer read.

## 0.1.0-beta.30 (2026-11-05)

- On codex, a content-filter stop whose final Responses event is longer than the model proxy keeps of it now ends the turn
  through a gateway that sends each event as its data alone (LiteLLM sends no `event:` lines). Before, only a stream that
  named its events was read, and Codex asked for the refused answer again until its turn limit. The policy reads the
  event's type from its data, whatever the JSON's spacing.
- A Codex run stopped just after its message was sent to Codex no longer loses the message. Codex answers `turn/start` before it writes the message to its rollout: on the real app-server, killed at the answer or 20 ms after it, the rollout held no user message; 100 ms after, it did. A stop in that window kills Codex with the message sent and never recorded, and the next Codex, resumed from the session's rollout, never has it. The stop's settle now reads Codex's rollout as the session keeps it, the rollout the next Codex is resumed from, and carries a placed message it lacks into the next one, as claude-agent's settle reads its CLI's transcript. The `turn/start` send mark is gone (the kernel's `markSent` and `sentMarks` with it); a stopped drive still starts no turn.
- A run whose model provider stops the answer on its content filter now ends `failed` with `error.code` `moderated` and
  says so in plain words: "The model provider stopped this answer (its content filter). Rephrase the request, or try
  another model." Before, it ended `run_failed` with the provider's jargon ("Response incomplete: content_filter"). The
  Timeline's error row keeps the harness's words for the stop (pi-ai's on pi, the kernel's on claude-agent and codex). On pi the run reads pi-ai's words for the stop on each API. On
  claude-agent and codex the session's model proxy reads the provider's stop (Anthropic's `refusal`, an OpenAI answer
  `incomplete` for `content_filter`) and the harness ends the turn at once: the CLI no longer asks for the refused answer
  again, turn after turn. Only the turn's own answer request ends it: a side call the CLI makes beside the turn (one
  without the session's tools) that the provider stops is logged and left to the CLI. The refused request is booked at
  the usage its end reports. The kernel exports `CONTENT_FILTERED`, the text such a turn ends with; a provider policy may
  say a stop through `filtered` and a side call through `answers`, and the model proxy tells its machine through
  `onFiltered`.
- A request you stop under a cap counts the reasoning it never streamed. A model whose reasoning streams only as a summary (the Responses API's reasoning, Claude 4-class thinking) is billed for far more than the summary's bytes. A stop after about 10,000 hidden reasoning tokens on a gpt-5-class model with a 20 KB context cost about $0.106 and counted $0.038, so deliberate stops could pass a cap. A stopped request that reasons now also counts the part of its reasoning budget that did not stream: input + streamed + 1,024 + max(0, reasoning budget - reasoning streamed), never more than its hold. Real usage still replaces the figure when it comes.
  - **On pi:** a reasoning model's stopped request counts its thinking level's budget (on Anthropic's API, the `budget_tokens` it was sent with, for a model whose thinking takes one). A Claude model that thinks adaptively (every current one on Anthropic's API) is sent no budget, and its thinking is bounded only by its output limit, so it counts that limit less 1,024 tokens: in practice its hold. A stop after a 300-byte thinking summary on Sonnet 5.5 with a 20 KB context under a $1 cap counted $0.142 at medium and $0.224 at high, against about $0.45 for 40,000 adaptive thinking tokens. The request's output limit is now the one actually sent: the cap had taken a thinking budget out of it that pi-ai never sends (8,192 tokens at medium), so the request was held at more than it was sent with. With no level, on an API whose model reasons at its own default, it counts its whole output limit. With thinking off on Anthropic's API, on a model whose thinking can be off, nothing more.
  - **Adaptive thinking counts up to the hold.** On every current Claude model, on pi and on `claude-agent`, the provider is given no thinking budget, so a stopped request counts up to the hold the cap took for it. Under a cap with little left beside that hold, the request after the stop can be refused.
  - **On `codex`:** the effort's budget (minimal 1,024, low 2,048, medium 8,192, high 16,384), none at effort `none`, and the output limit when the body names no effort.
  - **On `opencode`:** the same as `codex` (the same Responses API): what a stop counts as streamed is the content its deltas carried, not the wire, plus the unstreamed part of its effort's budget. On the walk through OpenCode's proxy (a request at $100 a million output tokens under a $0.50 cap, stopped after 1,146 characters of answer text after the stream's echo of the request) the stop booked 106,831 bytes, its whole $0.50 hold, and refused "Go on."; it now counts $0.217, and "Go on." goes.
  - **On `claude-agent`:** the thinking budget, or `max_tokens` when thinking is adaptive, for every request that thinks; none with thinking off. Thinking that streamed is subtracted, so a stop after a budget's worth of visible thinking counts nothing on top.
  - **Kernel:** a provider policy may read a request's hidden reasoning from its body (`reasoningHidden`). It may also read the reasoning in each streamed event (`reasoningBytesOf`). The model proxy books a stopped response with both (`stoppedHiddenTokens`, `stoppedReasoningBytes`), and the runner counts all it sent plus the part of the budget its reasoning did not cover.
  - **What streamed is the content, not the wire.** On `claude-agent` and `codex` a stop counted the response's bytes as sent, the provider's framing included: about 11.7 bytes a character of text on the Responses API and 24 on the Messages API. A codex request at $100 a million output under a $0.50 cap, stopped after 1,146 characters, booked its whole hold and refused "Go on.". It now counts each text, reasoning and tool-argument delta's UTF-8 bytes, as pi counts its streamed blocks: $0.217, and the next request goes. A provider policy reads them (`contentBytesOf`).
  - **A stop before the provider's first header** on `claude-agent` and `codex` now counts as a stop with nothing streamed (its input and 1,024 tokens, as on pi), not its whole hold. A response the provider answered with an error status still counts at its hold.
- A message the person stopped the instant it was sent is no longer lost on claude-agent, and the same window is closed on Codex and OpenCode. Asked "Reply with exactly this code and nothing else: CARRY-CLAUDE-7", stopped within its first second, then told "Go on.", a claude-agent run answered "There's nothing earlier in this conversation for me to continue from": Claude takes a message within its first second, so the stop landed after the harness placed it and before the CLI was handed it, and nothing carried it. Now a stop's settle carries a placed message its CLI never took into the next one, as it carries one stopped before it was placed. On claude-agent that is a message the CLI's own transcript, as the session keeps it, does not hold: that transcript is the history a resumed CLI is given, so a carried message is never sent twice. On Codex it is a message Codex's own rollout, as the session keeps it, does not hold. OpenCode marks a message just before it sends it (`prompt_async`), and a marked message is never carried: a crash between the mark and the send loses it rather than sending it twice. After a stop, no new turn is started.
  - **A recovered message is not carried again.** After a crash between a message's placement and its CLI's record, the recovery message carries its words. It now records which messages it carries, before it goes (a kernel effect by its id on claude-agent, its `PROMPT_STREAM` record on OpenCode). Once the CLI holds the recovery message, a stop's settle and a later recovery both count those messages sent, so nothing is sent twice, even after a second crash. Codex's recovery already did this through its client id.
  - **A follow-up's own prompt** (the host's, named to the settle) is withdrawn and never carried into the person's next message, as the follow-up says: a host prompt that never ran is not sent. A person's message waiting beside it is left as it is.

## 0.1.0-beta.29 (2026-11-04)

- **The Codex adapter takes the host's skills, and its sessions no longer see Codex's bundled ones**
  - `codexAdapter({ skills: [{ name, files }] })`: Codex lists each skill to the model by its name and description, and the model reads its `SKILL.md` and its other files with `read_skill_file`, the shared read-only host tool (Codex has no shell here). The skills are written into each session's `CODEX_HOME` at the start of every drive, where Codex lists a user's skills in a turn with its built-ins off; it lists none from a working directory's `.agents/skills` there. A host tool named `read_skill_file` is refused when the adapter has skills.
  - Codex's bundled skills (imagegen, openai-docs, skill-creator, skill-installer) are off in every Codex session, with skills or without (`[skills.bundled] enabled = false`). Before, Codex installed them at every start and listed them to the model, so a session was shown skills its host never gave it.
  - The skills are checked when the adapter is made, and a bad one throws before the binary is looked for. The check, `skillProblems`, and the skill's shape, `HostSkill`, are now in `@parcha/agentrun-kernel` beside `readSkillFileTool`. The Claude adapter's `skillProblems` and `ClaudeAgentSkill` are that check and shape, re-exported, so nothing changes for its users; the Codex adapter exports the same `skillProblems`.
  - The local Codex machine takes a seed of files for one of its private directories (`seed: { dir, files }`, each file's text by its relative path), written at acquire and again after every wipe. A path that is absolute, empty, climbs or starts with a dot, or a directory not the machine's own, is refused when the machine is made.
- The Codex adapter says what Codex 0.164.0 does to a tool's schema, so no difference is silent. Codex sanitizes the schema its model is given: it strips bounds, patterns, formats, titles, defaults and a few annotations, and it drops or retypes a few shapes (a tuple `items`, `prefixItems`, `patternProperties`, `if`/`then`/`else`, `not`, a non-scalar or untyped non-string `enum`/`const`, `contains`, `dependentRequired`, `propertyNames`, a boolean `items`, constraints inside `allOf`). Checking a session now refuses each of those shapes by tool, JSON pointer and keyword, before anything is paid. For the stripped keywords, the tool's description lists them in plain words under one fixed heading, sorted by pointer, so the model still reads them; the host and the DSL keep checking against the original schema. The measurement is recorded for the public schema corpus and replayed offline.
- A Codex session can turn on Codex's own web search, live: `codexAdapter({ webSearch: "live" })` sets `web_search = "live"` in Codex's config, and the session's model proxy admits exactly the hosted `web_search` tool the pinned binary then sends (and a `tool_choice` naming it) and refuses any other web search tool; every other hosted tool is dropped or refused as before. Each search a response ran (its `tool_usage.web_search.num_requests`) is added to the response's price at OpenAI's $10 per 1,000 calls, so it counts in the session's cost and the host's budget; a model with no known search price, or a response that does not say how many searches it ran, is booked at an unknown cost. A request that offers web search has no input bound (a search's content is billed as input), so a cap that holds each request's worst case treats its input as unknown. Off by default, and off is unchanged. `CodexWebSearch` is the option's type.
- The harness packages are published from this release under their final names: `@parcha/agentrun-adapters` is `@parcha/agentrun-kernel`, `@parcha/agentrun-claude-agent` is `@parcha/agentrun-harness-claude`, `@parcha/agentrun-codex` is `@parcha/agentrun-harness-codex`. Their subpaths, directories, harness ids and `AGENTRUN_*` environment variables do not change.
  - Messages these packages raise start with `agentrun-kernel:`, `agentrun-harness-claude:`, `agentrun-harness-codex:`.
- New package `@parcha/agentrun-harness-codex`, held (not on npm yet): Codex as an AgentRun harness. `codexAdapter(options)` is an `AgentAdapter`, so `createHarnessRunner(codexAdapter(...), { store, tools })` runs a DSL `agent` node on Codex 0.164.0's app-server.
  - Codex's built-in tools are off. A classic model is offered exactly the host's tools and `submit`; a code-mode model is offered code mode's `exec` and `wait`, which reach the host's tools by their own names. A test runs the pinned binary against a scripted model that calls every built-in and checks that nothing runs, writes or spawns.
  - Codex's model traffic goes through a per-session proxy on the loopback interface that holds the provider key, forwards only `POST /v1/responses`, fixes the model, stores nothing at the provider, drops Codex's own web search and every tool that is not the session's (refusing any other provider-hosted tool), and asks the runner before every paid request.
  - The adapter checks the Codex binary it will run against the pins when it is made: the platform package's version, the binary's sha256 and the version it reports. A mismatch or a missing binary is a typed error. A relative `CODEX_BIN` is resolved from the host's working directory, and that absolute path is the one checked and run.
  - Codex runs in the session's own directories with an empty working directory and an allowlisted environment.
  - Sessions are durable in the store the host lends: a session a process died inside resumes from its records, and a `never` tool's cut-off call is reported, never repeated, and a call delivered twice runs its tool once.
- A spend cap below one request's worst case at its model's output ceiling no longer refuses the run before it starts. Each request is limited to the output tokens what is left of the cap can buy, thinking included, and held at that, so the cap stays exact. A request is refused only when what is left cannot buy its least: 1,024 tokens for its answer, plus its thinking's least when it thinks. A $0.50 cap on Claude Sonnet now runs; before, any cap under about $1.30 could never send a request.
  - A refusal says, in plain words, what the run spent of its cap, what its next request needs and the cap that would run it ("Not sent: ... Raise the cap to at least $0.48 to run it."), on the run's error and its timeline row, after the code `spend_cap_reached (out of budget): `, which pi-ai's retry takes as final. A request the cap refused counts as no model request in the run's usage, on every harness; a run whose only request was refused says "no model request sent". A reply the limit cut short says so on the run's timeline.
  - The model proxy asks the host with a request's own output limit and its least (`outputTokensAsked`, `outputTokensLeast`), and writes the admitted limit (the ticket's `outputTokensMax`) into its body through a policy's new `limitOutput`; it never sends a request unlimited that was admitted with a limit, nor a body longer than the one its input was measured on. The runner's `beforeRequest` may answer `outputTokensMax` beside `holdUsd`, and holds each request in flight at the limit it was admitted with; a limit that is no whole number of tokens above 0 refuses the request, never sends it unlimited.
- A turn that a halt ended with a reason now ends `failed`, naming it, never `interrupted` with the reason dropped: a harness's spend cap, its transcript mirror, a refused spawn. Only the session's own stop (its interrupt or its close, told apart by identity with the kernel's `SessionHalt`) and its host's stop end a turn `interrupted`. `abortedOutcome` decides it, and both adapters use it. This changes how spend-cap and mirror halts end a turn: a host that read `interrupted` for them now reads `failed` with the reason.
- A model that runs its tools in code mode, such as gpt-6-sol, now runs on the Codex adapter; it was refused before any request. The adapter no longer reads the binary's model catalog or refuses a code-mode model when a session is checked, and the proxy passes Codex's `exec` and `wait` (and drops the sub-agent and user-input tools listed beside them, and refuses a code-mode request that allows parallel tool calls). A host tool the script calls arrives as a nested call under an id of Codex's own, which no line of the session's log carries, so a `never` tool called that way was declined for good; it now runs once, as soon as the `exec` it runs under is in the log.
- After a crash, a host tool's call that was cut off is told to Codex by the replay policy the run's log recorded when it started, as the recovery note of the same turn tells it. Before, the output Codex got for a `safe` call said it may have taken effect, while the note said it was safe to repeat: the drive that opens after a crash marks a safe call for a retry, which the output's own rule did not count as interrupted.
- A Codex session no longer tells the model its files are read-only. Codex sent a `<permissions instructions>` developer message ("`sandbox_mode` is `read-only`: The sandbox only permits reading files") about its own sandbox, which binds only its built-in tools, and those are off. The host's tools write. A model that believed the message refused to write at all and ended its turn with no tool call. The adapter now sets `include_permissions_instructions = false`. Codex's sandbox itself stays read-only.
  - A model Codex's catalog marks multi-agent V2 (luna, sol) is no longer told it can spawn sub-agents. `multi_agent = false` turns off only V1, so Codex still built V2's collaboration tools, which the model proxy dropped, and sent `<multi_agent_role>` and `<multi_agent_mode>` messages describing them. The config now sets `[agents] enabled = false`, which turns off both versions.
  - `CODEX_INSTALL` is exported: the pinned install line (`npm install --save-exact @openai/codex@<version>`) that `CodexNotInstalled` names, so a host can print it without copying its format.
- Codex dies with the process that started it. The session machine starts Codex with a watch on its parent (the host's `parentWatched`, inside the host's confinement), so a host that is SIGKILLed and runs no close leaves no Codex behind, on a box with or without `setpriv`. A confinement prefix must exec Codex in place, as `setpriv` does: a wrapper that forks and stays as the parent defeats the watch.
- A call that Codex's rollout holds with no output now gets one from the log whenever a thread resumes, before any turn is sent, and not only under a recovery note. A turn that ended without answering a call (one interrupted mid-call, or settled instead of resumed) left it unanswered, and the next turn's history, with a call left open, was refused by the provider. A cut-off code-mode `exec` is answered first, as a custom tool output built from its nested calls. Every other call gets the generic output, of the kind the call asks for: a custom tool call such as Codex's own `apply_patch` gets a custom tool call output, and a host tool that happens to be named `exec` is answered as the function call it is. A `never` call the ended turn completed is answered as recorded only when a recovery note resumes that turn; a new turn that calls it again runs it. A `wait` of code mode that was waiting on a cell when the session stopped is told so, and that the cell's script was cut off, not that it never started.
- `codexAdapter` refuses a `webSearch` other than `"live"` with a `TypeError` that names the package as its other errors do, `agentrun-harness-codex: webSearch is "live" or absent`; it began `agentrun-codex:`, the package's name before the rename.
- Checking a harness's binary against its pins no longer reads the whole binary into memory, and runs once per binary in a process. `verifyCodexBinary` (the codex binary, 294 MiB) and `verifyClaudeAgentCli` (claude-agent's CLI, 231 MiB) each read the file whole to hash it, and agentrun-serve checked each again for every model it resolved: twice per harness in its start's probe, then once per save and once per run check, and a run's own process once more when it made its adapter. One start probe peaked at 395 MiB of memory, 675 MiB with a default model, past a 512 MiB container's limit. The hash now reads 1 MiB at a time, and a check that passed is kept for the process while the binary stays the same file (its path, device, inode, size, and modification and change times, with the pins); touched or replaced, it is checked again, and a failed check is never kept. The kernel's `@parcha/agentrun-kernel/host` exports both parts, `sha256OfFile` and `checkedOnce`.
- A claude-agent or codex run works in the run's workspace, the directory its file tools write to. Before, the CLI's working directory was an empty one beside it (`runs/<id>/harness/work`): Claude told its model that path, so a file written at its absolute path was refused as "outside the workspace", and the answer quoted the server's data directory. In QA this happened in 3 of 4 Claude runs that wrote a file.
  - `SessionIO.cwd`: a host may name the session's working directory, its workspace. The Claude and Codex adapters run their CLI there, and keep their own state in the session's private directory as before. git stops at the workspace's parent. serve passes the run's `work/`.
  - A file tool's refusal, an error such as ENOENT, and a write's or edit's result on claude-agent and codex name paths in the workspace relative to it (`notes/a.md`, `../escape.md: outside the workspace`), never by the server's data directory. A read's result is the file's own text and is not changed.
- A host tool's result reaches the model whole on claude-agent and codex. The Claude Agent CLI saved an MCP tool's result past 50,000 characters (a long `web_fetch` page, a `monid` answer, a 50 KB `read`) to a file under its own config directory and told the model to read it, which the run's confinement refuses, so the model could not read the page; Codex kept only the two ends of a result past its truncation policy (10,000 tokens for the models its catalog holds, about 12,000 characters for another). `@parcha/agentrun-kernel` states the bound once, `HOST_RESULT_MAX_CHARS` (120,000 characters, over every host tool's largest result); the Claude Agent adapter lists each host tool with it as `anthropic/maxResultSizeChars` and sets `MAX_MCP_OUTPUT_TOKENS` to it, and the Codex adapter sets `tool_output_token_limit` to it as Codex counts it (four bytes of UTF-8 a token: 90,000).
  `web_fetch` (and `fetch_page`) reads a page a part at a time: `offset` and `max_chars` (20,000 by default, at least 200, at most 50,000; a smaller one or an offset below 0 is refused before anything is fetched, saying so; a workflow's call node reads 50,000 by default) name the part, the Page gives `chars`, its length, and a part that is not the whole page has `truncated` while more follows, `next_offset` where it begins and `original_chars` where the whole length is known; an agent reads a line after the JSON saying which characters these are and the offset that reads on. A page whose HTML pi-browser cut at 1,000,000 characters before reading it gives `html_chars`, its whole length, on every part and no `original_chars`, and the line after its last part says `The page was cut at 1,000,000 characters of HTML before reading; the rest wasn't read.`; `converted: "text"` says its text is plain text, its conversion to markdown having run out of time. The text was cut at 60,000 characters with no way to read the rest. A page's links come with the part at offset 0, at most 200 in 20,000 characters, and a URL longer than 4,096 characters is refused before anything is sent.
  `web_search` leaves out its least relevant results when its answer would pass 100,000 characters, and `omitted` counts them.
- A host tool's result reaches a harness at most `HOST_RESULT_MAX_CHARS` (120,000) characters long. The kernel's tool bridge, which every host tool's result passes on its way to Claude Agent or Codex, keeps a longer one's start, cut where a character ends, ends it with a line saying where it was cut (`[cut at N of M characters]`), and flags the call's `tool_end` `truncated: true`; the call's record keeps the whole result. On a Codex resume, a call the rollout left unanswered is answered from that record with the same cut. A skill file read with `read_skill_file`, a delegate's answer and a rejection listing every schema error reached the harness whole, however long (a 1 MiB skill file, a 6 MB answer).
- The model proxy now tells the host, before a paid request is sent, the most input tokens it can be billed for. A spend cap could only count a request's cost once it was billed, so a single request whose input alone was over what was left of the cap was still sent and paid. `beforeRequest` now carries `inputTokensMax`: the UTF-8 bytes of the body exactly as it is sent, plus the input the provider adds that the body does not carry. A byte-level BPE token covers at least one byte, so this never undercounts the body, however dense its text. Each `inFlight` entry carries its own `inputTokensMax` until that request answers, so a cap can hold every open request at its own bound. When the provider's addition cannot be read, `inputTokensMax` is undefined, never 0, and a cap treats that input as unknown.
  - What a provider adds is in one place, `providerInputOverhead(api, shape)` from `@parcha/agentrun-kernel/host`. `api` is pi's API kind, and `shape` is whether the request has tools, its tool_choice and its image count. Each figure is the largest the provider documents for any current model:
    - `anthropic-messages`: the tool-use system prompt the Messages API adds to a body with tools, 675 tokens for tool_choice auto or none and 804 for any or tool, plus 4,784 tokens for each image, its high-resolution tier's maximum.
    - `openai-responses`, and the Azure and Codex Responses kinds: no prompt of their own, and 73,800 tokens for each image. That is 30,000 patches, the most an image may have, times 2.46, the largest model multiplier.
    - `openai-completions`, which OpenAI-compatible gateways speak too: nothing for its per-message formatting, since the body's bytes already bound it; 804 tokens when the request has tools, whatever its tool_choice, the largest Anthropic tool-use prompt, since a gateway may route to an Anthropic model; and 73,800 tokens for each image.
    - Every other API kind, among them pi's `mistral-conversations`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex` and `pi-messages`, and a faux `faux:<id>`: nothing for text, an assumed 2,048 tokens when the request has tools, and 73,800 tokens for each image. The tool allowance for these kinds is assumed, not documented; it is documented only for `anthropic-messages`, the OpenAI Responses kinds and `openai-completions`. `providerInputOverhead` never returns undefined: only a body that cannot be measured is unmeasured.
  - Images are billed by their area, not their bytes, so a small compressed image of large dimensions is counted at its maximum. A Codex body with a file input (a PDF, billed by its pages) is left unmeasured.
  - A provider policy says what its provider adds with `serverInputOverhead(body)`. The Claude and Codex policies read their body's shape and use the figures above.
  - The faux adapter in `@parcha/agentrun-kernel/testing` measures its prompt's UTF-8 bytes for each request, as a real adapter's proxy measures its body.
  - `inputTokensMaxOf(policy, body, sent)` is exported from `@parcha/agentrun-kernel/host`.
  - The proxy serializes the body once before admission and sends exactly what it measured. A body that cannot be serialized is refused before the runner is asked, so it is never booked.
- A Claude or Codex turn stopped while the session was still recording the person's message stays stopped. Before, the stop found no turn running, so the session read idle, and the stopped message stayed pending and was sent with the next message. Now a turn that ends on its session's stop leaves the session reading `open_turn` while that message is pending, so serve's stop settles it, and it is never sent.
- A Claude or Codex turn the person stopped stays stopped when the run's process is replaced. Before, the next process found the stopped turn still open in the session and resumed it: it ran its tools and paid for its model requests again, and its answer came before the person's follow-up. Now serve's open reads the run's stop record and settles that turn, ended `interrupted`, with nothing sent, and the follow-up is a turn of its own. A turn a crash or a drain cut is resumed as before.
  - A stop that lands before the harness took the person's message withdraws that message too, so it is never sent later: not with the follow-up in the same process, and not by a process that replaces it.
  - `AdapterSession` has `settleOpenTurn()`: it records the open turn as ended, interrupted, withdraws the input the turn never placed, and sends nothing. The Claude Agent, Codex and faux adapters implement it. A harness that runs as a child process does both with `settleTurn(drive)` from `@parcha/agentrun-kernel/process`. An adapter written outside this repository without it keeps the old behaviour: its stopped turn is resumed.
  - After `interrupt()`, the Claude Agent and Codex sessions read `open_turn` while the stopped turn is still open in their records. serve's stop settles it there; a runner's pause leaves it for the next process to resume.
  - When the earlier process died before it wrote the stopped turn's end, the next one writes it, `interrupted`, before the follow-up's turn starts.
