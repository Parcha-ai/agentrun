## 0.1.0-beta.29 (2026-11-04)

- **A checkpoint is never unpacked on the host: a box's links stay data, made again only inside the box a restore goes to**
  - `pullCheckpoint` unpacked the box's archive into `localVault`'s directory with the host's general-purpose `tar -x -p`, so a box could make the host create symbolic links, hard links, named pipes and setuid files in the vault. Now the box sends only the bytes of the files the pull asks for, end to end; the vault keeps each file's content once, as a plain file of its own named by its SHA-256 and checked against it. Directories, symbolic links, hard links (`ManifestEntry.link`), named pipes (`kind: "fifo"`, which a checkpoint no longer refuses) and modes, setuid included, are the record's manifest and nothing else on the host.
  - A listing with a path that is absolute, has a `.` or `..` segment, or goes through a link, or a file without a SHA-256, is refused before a byte moves (`failed`), and a record like that is never restored.
  - A restore writes a tar stream from the record and the contents, and the new box's own `tar` makes the tree, links included. The tree is listed and hashed there against the record, hard links and pipes too.
  - `CheckpointVault` gains `holds`, `keep` and `content`, and `VaultError` the code `refused`. `Checkpoint.filesRoot` and `PendingCheckpoint.filesRoot` are gone: read a checkpoint's files through `content(session, entry.sha256)`. A vault of your own adds the three methods.
  - A generation an earlier version kept as an unpacked tree is `refused`, named in the restore's `no_checkpoint` message: it is never read, unpacked or restored. A pull after it takes the whole workspace again, and `prune` removes it with the generations it ages out.
- `@parcha/pi-transport/sync` moves a run's files between the host and a box that shares no disk with it, on top of `extractTar`. `seedDir` copies a host directory into a box path (a host link is never followed, modes are capped at 0755, `readOnly` paths go without a write bit) and returns a `mark`: the box's listing with the SHA-256 of each file sent. `pullDir` brings back what changed since the mark: the box lists the directory and a path comes back when it is new or listed differently, never by comparing the box's clock with the host's, with `exclude` and `mirrorDeletes` (off by default); every member goes through `extractTar`, and two names of one inode both arrive as files. `seedAgentHome` and `pullAgentHome` keep an agent home's `learning/` host-owned (seeded read-only, never pulled back, never removed), and a home pull never overwrites or removes a host file another run changed since the seed: it replaces the host's copy only while that copy is still the bytes the mark's SHA-256 records, and counts the rest as `host_changed`.
  A box's listing is read up to `maxListingBytes` (default `MAX_LISTING_BYTES`, 64 MiB), on every path that lists a box, checkpoints included: past it the box's program is stopped and the call is `too_large`, so a box cannot make the host hold an unbounded listing.
  An `exclude` pattern that starts with `/` is now anchored at the root (`/learning` is the top-level `learning` only); before, such a pattern matched nothing.
- A bwrap box's arguments are built in one place, every variable input is checked, and a probe says whether a Linux host can run such a box and, when it can't, why. A bwrap box runs each command of a box under bubblewrap, with a host directory as its workspace. The module is internal (`src/box/bwrap-args.ts`, not exported): the provider that uses it comes in a later release.
  - `bwrapArgs` builds the whole `bwrap` argv of one command. It makes new user, pid, network, IPC, UTS and cgroup namespaces, with no `-try` form, and passes `--disable-userns`, `--cap-drop ALL`, `--die-with-parent`, `--new-session` and a hostname of the box's own. A private `/proc`, `/dev` and `/tmp` are mounted before any bind. The system is read-only: `/usr`, the `/bin`, `/sbin` and `/lib*` beside it or linked into it, and a named part of `/etc`. The box gets its own `/etc/passwd` and `/etc/group` (its user and `nobody`) and `/etc/hosts` on fixed descriptors. The workspace is bound read-write at the box's working directory, the root is remounted read-only, and `--clearenv` leaves only the spec's environment. `/run`, `/var` and the host's `/tmp` are never bound.
  - The workspace must be its own real path, with no link in it. These are refused by name: a relative path, a `..` segment, a path not in normal form, `/` and the shared roots (`/home`, `/tmp`, `/var`, `/srv` and others), anything in the system, `/etc`, `/proc`, `/sys`, `/dev`, `/run`, `/boot` or `/root`, the server's home, and a hidden path the caller names, or what holds one.
  - A home or a hidden path that lies inside a bound system directory, as named or through its links, is masked in the box after that bind by an empty tmpfs of mode 555, remounted read-only on its own, since the root's remount doesn't reach it. A part of `/etc` inside one is left out. One that is or holds a system root is refused, since masking it would leave the box without its system.
  - The network is `none`, with a loopback of the box's own. `open` would share the host's network namespace and its loopback services, so it is `unsupported`, and so is an allowlist.
  - `probeBwrap` reads and runs bwrap and changes nothing on the host. It runs one box built as an exec's, running `true`, and matches what bwrap says against the known denials. It answers missing, setuid, older than 0.8.0, root without `CAP_SETFCAP`, a user namespace denied (naming AppArmor's restriction of unprivileged user namespaces, or the sysctl that denies them, and leaving the fix to the administrator), a run killed at its time bound, or available with its version.
- A Docker box binds paths of this machine that the spec names in `BoxSpec.mounts` (`{ source, target, readOnly? }`), read-only where asked, with `--mount type=bind`, never `-v`. A source this machine does not have is refused with `not_found` before Docker is asked. Paths go to Docker as given, so pass canonical ones. Every provider refuses a malformed list as `invalid`: a path that is not absolute and in normal form, a `..` segment, a comma, quote or control character, a target of `/`, a target named twice, or more than 8 mounts. Every provider but Docker refuses any mount as `unsupported` before it makes anything. `BoxProvider.mounts` is `true` only on a provider that binds them, so a caller can ask before it chooses one; the box receipts ledger keeps it on the providers it wraps.
- Jev places a step with only an OpenRouter key. `jevClassifier(process.env)` picks the placer's classifier as serve's decisions do: TypeSafe's own API (`typesafe`, `jev-latest`) when `TYPESAFE_API_KEY` is set, else Jev through OpenRouter's System One (`openrouter`, `~typesafe/jev-latest`) when `OPENROUTER_API_KEY` is. Pass it to `jevPlacer` with pi-ai's `typesafeProvider()` and `openrouterProvider()` in the host's `Models`. Through OpenRouter a decision's `costUsd` is known, from pi-ai's price for the model.
- `@parcha/pi-transport/sync` unpacks a tar archive a box made, on the host, with the package's own reader (`extractTar`, or `openExtractor` fed a chunk at a time) instead of `tar`. It writes regular files and directories only: a symbolic or hard link, a device, a pipe or any other member is skipped, counted by reason and never created, and a link's skip carries its `target` so a caller can keep it as data. A name is refused when it is absolute, holds `.`, `..`, an empty segment or a NUL, or passes 255 bytes a segment or 4095 a path; `admit` limits what may be written. Every directory is opened from a held handle with `O_NOFOLLOW`, so nothing lands outside the destination and no link already there is followed; each file is written under a temporary name and renamed into place; modes are capped at 0644/0755 with no setuid, setgid, group or world write. The extraction stops cleanly past `maxBytes` of archive, headers and names included (default `MAX_PULL_BYTES`, 1 GiB), or `maxEntries` members (default `MAX_PULL_ENTRIES`, 100,000), keeping every file written before the stop whole. `removeEntries` removes paths under a directory by the same walk, unlinking a link itself and a directory only when empty.
- An agent whose place is `{"mode": "sandbox", "box": "docker"}` runs its `read`, `write`, `edit` and `bash` in a Docker container, on pi, claude-agent and codex alike, while its loop, its log, its model calls and every key stay on the server. The container is made on the run's first such call and labelled with the run's id. It binds the run's `work/` alone at `/run/agentrun/run/work` (a mount source through a link is refused), has no network, gets `LANG` and `HOME` and nothing of the server's environment, and runs as the server's user. It is found again by its label after a crash, the commands the dead process left killed first, and destroyed when the run ends, when it is archived, and by the next start once its run has ended. `bash` takes pi's arguments, with a 300 s default timeout and its output's tail. `read`, `write` and `edit` take a path in the box's work directory only, and their errors name the box's paths, never the server's. This carries the coding-tool source that was proposed on its own (no shell on this machine). `bash` is refused on a runner place, and so is a sandbox place on a workflow, and `browser` in a sandbox place. What the server files in a run's `work/` (monid's long answers, the browser's evidence) is written through held directory handles and never follows a link a box's command planted there. On a host without `/proc/self/fd` (macOS), where a directory is reached by its path, the server files none of these in a sandbox run's `work/`: monid's long answers there say they could not be saved, and the browser's evidence is not filed. A file tool's absolute path under the run's own work directory on this machine names the same file in the box. `AGENTRUN_DOCKER_IMAGE` names the image (default `debian:bookworm-slim`). The console leaves `bash` unticked on a new agent and offers it only on an agent whose place is a sandbox. In pi-transport, `dockerBoxes({ user })` runs a box's programs as that uid:gid, and `endLeftCommands(box)`, from `@parcha/pi-transport/hands`, kills the command groups a gone host left in a box, leaving a tombstone for one not written down yet.
- An agent whose place is `{"mode": "sandbox", "box": "daytona"}` runs its `read`, `write`, `edit` and `bash` in a Daytona sandbox, on pi, claude-agent and codex alike, as a Docker place does. The server holds Daytona's key (`DAYTONA_API_KEY`, with `AGENTRUN_BOXES=daytona`) and gives it to nothing else: it makes the run's sandbox on the run's first such call, with its network blocked (`networkBlockAll`; a sandbox Daytona does not report blocked is deleted and the call fails), the fixed environment and the run's labels, and the run's process reaches that sandbox only through the server's box relay on loopback, which takes a run's call only with that run's own door token, adds the key to the calls a run's tools make of their own sandbox (a read of it, and its toolbox's programs and files), refuses every other call, and never follows a redirect (nor does pi-transport's Daytona client): a redirect would carry the key. Each run's door now takes a token of its own, `runs/<id>/door-token`, made at its first launch, and a run's end-of-run notes that hold it are refused like any other secret. A sandbox cannot bind the run's `work/`, so the server copies `work/` into it at `/run/agentrun/run/work` when it makes it, copies what changed back at each turn's end and once more before the run's end is recorded (with pi-transport's safe extractor: nothing outside `work/`, no link, a file the server changed meanwhile kept), and destroys it only once that last copy is whole: a copy that fails is tried again before the end is recorded, and one that stops for good (an archive the server cannot read, a limit it cannot pass) keeps the sandbox, said in the log, its auto-delete turned off and set to stop after 15 idle minutes (its disk kept, its compute stopped), woken and copied back by the next start. A run's sandbox that Daytona stopped, paused or archived (or is stopping, pausing or archiving) is started again, an archived one restored, when the server needs it, never replaced. A read of the run's files waits for a copy its turn's end began, and a start pulls a run it finds waiting. What the server files in `work/` meanwhile (monid's long answers) is copied into the sandbox too, and an edit the sandbox makes to such a file comes back. A start pulls, then destroys, the sandbox of a run that ended while its sandbox was left. In pi-transport, a Daytona box takes `network: "none"` (`networkBlockAll`, and `facts().network` is `none` only when Daytona reports it), a workspace the sandbox's user may not create is made with `sudo -n`, and a paused sandbox counts as not running (a host starts it again).
- A process left over from an earlier launch of a name now does nothing once the name is launched again. The launcher's supervisor, watchdog and program runner took their generation from the spec they read when they started, so a supervisor that the earlier launch's watchdog started just as the name was launched again took the new generation as its own and acted in the new launch's directory: it could start a program that had exited there a second time. Each of these processes is now given the generation of the process that started it and keeps it; when the spec holds another one, it exits and writes nothing. The watchdog also checks its generation before it registers.
- `launchStop` no longer waits out a 15-second lock that a killed watchdog's last command took after the stop removed it. The stop ended the supervisor's and the watchdog's shells alone, and a command the watchdog was running, the `mkdir` of its output's trim lock, lived on: when it ran after the stop removed the lock, it took the lock with no live holder, and the stop's own trim waited until the lock broke (16 s on a loaded runner). With `setsid`, the stop now kills each one's process group, which holds what it started, and goes on once the groups are empty; without it, the stop stops each shell, kills its children and then it, and goes on once they are gone. Either wait ends after 2 s at most; a process the stop could not end in that time is named in the launch's log (`[launcher] could not end <pid> (<name>); removed the trim lock anyway`), never passed over. Clearing a launch directory ends them the same way.
- On a box without `setsid`, `launchStop` now ends the program. There, the program's runner leads no process group, so the stop's group signals reached nothing: the program kept running while the stop reported `stopped`. The drain's SIGTERM now goes to every process under the runner, and the kill stops the runner and each process under it before killing them all. On every box, a stop that cannot confirm the program is gone within 2 s of its kill now fails with `the program did not end: <what is left> still there after its kill`, writes no `stopped` state, and leaves the stop for a later one to take over. Without `setsid`, the processes the stop kills are written to `stop.killed` first, each with its start, so a stop that takes over finds them once the runner is gone, and never touches a process that has since taken one of their ids.
- **A store a box made is opened on the host only as a read-only copy of its main file, and never written: no trigger, view or schema of its own, no extension**
  - `verifyStore` opened a checkpoint's store, a file the box made, with SQLite's default settings, and `replayCommits` opened it to write through pi-durable, so a trigger in it ran on the host's commits. Now both read such a file one way only, following SQLite's guidance for a database file another security domain could have written: a regular file of at most `DEFAULT_MAX_STORE_BYTES` (1 GiB, or `{ maxBytes }`) has its main file copied, without following a link, into a directory the host makes (no journal or write-ahead log of the box's is ever beside what SQLite opens), and the copy is opened `immutable` and read-only, with no extension loading, `trusted_schema` off, `cell_size_check` on and `mmap_size` 0.
  - The schema must be the one pi-durable makes, object for object, before the quick check runs: a trigger, a view, a virtual table or a table of the file's own is refused with the new `StoreErrorCode` `refused`, as is one that is not a regular file. Two stores that verified before are refused now: a store of another pi-durable schema version, and a store over 1 GiB.
  - `replayCommits` never opens the file to write: the rows of pi-durable's tables are read into a store pi-durable makes on the host, which takes the file's place, and the commits go into that one. A file it refuses is `failed` with nothing applied, and a restore then uses the checkpoint as it is. `verifyStore` and `replayCommits` take an optional `{ maxBytes }`.
- A run's Docker box drops every capability, and a Docker daemon on another machine never binds this machine's `work/`.
  - `dockerBoxes({ dropCapabilities: true })` runs each box with `--cap-drop ALL` and `--security-opt no-new-privileges`. Serve's run boxes always use it. Without it, a server run as uid 0 made boxes that were root with Docker's default capabilities, so `bash` could `mknod` a device node in `work/` (`c 10 130`, the watchdog) for the file tools on the host to open. With it, `attach` ends a box made without it (an older version's, its run resumed) instead of taking it, so a fresh hardened box replaces it. The option is off by default in pi-transport, because a launcher that drops from root to another user needs Docker's default set.
  - `dockerBoxes`' `mounts` is now false when `DOCKER_HOST`, or the docker context (`DOCKER_CONTEXT`, else the config's `currentContext`), names a daemon on another machine (tcp://, ssh://, or a context whose record names no unix socket). With `DOCKER_HOST` and `DOCKER_CONTEXT` both set, both must be this machine, and each create checks again, so a `docker context use` after the provider was made refuses the next spec with mounts. A spec with mounts is then refused as `unsupported`, naming the setting and how to undo it. In serve, a run's box on such a daemon is not bound, so `read`, `write` and `edit` go through the box, never this machine's `work/`.
- **`moveWorkspace` no longer refuses a correct copy of a file whose time is just short of the next second**
  - The target check compares a file's whole seconds, the part a tar header keeps. It read them as a number, so a source time in the last ~120 ns of a second rounded up to the next second, and a copy that was right failed with `mismatch` ("has another modification time"). It now reads the seconds from the time's text. The message names both times.
- pi-transport's box and hands tests drop the cases another test already runs on the same path, the tests of test helpers, and two waits or checks that could not fail for the reason they name. Gone, with what still proves each:
  - Box cases the conformance suite runs on the same registration: the local label refusal (the conformance label case), and the receipt of a box with no price (`box-receipts.test.ts`).
  - A local watchdog case, folded into the expiry case, which now also ends a program that cleared its environment.
  - In the hosted sandbox provider's tests, a case for odd probe output, folded into the facts case, and an env case whose behaviour the fake itself supplied (the sandbox-env case and the conformance suite on that registration remain).
  - The tests of the hosted sandbox provider's live suites' label helper, and of `waitNotRunning`'s positive path and bound; that helper's negative controls stay, and every leak guard calls it.
  - Two benchmarks with no assertion in live files no job runs.

  Repaired: Daytona's environment check plants Daytona's own variables and checks that no request or box carries them, and that a provider given no URL sends every request to the built-in one, in place of a source grep. The hands pool's receipts are counted per case against the boxes it made, so a ledger that receipts one box of several fails. The release-during-command case waits for the command to run, not 500 ms.
- Install and `npx` commands in the READMEs and docs name `@latest` instead of `@beta`. Releases publish under npm's `latest` tag, and `beta` was not moved with them: it still pointed at 0.1.0-beta.21 while `latest` was 0.1.0-beta.28, and `@parcha/pi-durable-agent`, `@parcha/pi-git-remote` and `@parcha/pi-agent-learn` had no `beta` tag at all, so their install lines failed. The harness demo's hint for a missing `@parcha/pi-transport` names `@latest` too. `@parcha/agentrun-harness` is not on npm yet (its `latest` is a placeholder), so its README says it is held and installs it from a packed tarball. The README's Render option gives measured memory: a Starter's 512 MB runs about 3 pi agents at once, and Claude Code or Codex runs want a 2 GB instance. The stranger check reads the install line as `@latest`, installs `@latest` with `--registry`, and walks the keyless examples against the registry's `latest`. The release guide drops the step that moved `beta` after a release; `beta` is kept only for older links, with the one-time command to bring it up to a release.

## 0.1.0-beta.28 (2026-10-28)

- The launcher has its own subpath, `@parcha/pi-transport/launch` (`./home` still exports the same names), and a launched program no longer inherits the box runtime's environment. Its environment is PATH, HOME, LANG (`C.UTF-8`), `PI_TRANSPORT_INCARNATION` (the incarnation, from 1) and the spec's `env`; a program that read a variable of the box's own lists it in the new `inheritEnv` (default `false`). Who breaks: a caller of `launch` whose program relied on a variable set on the box (`BoxSpec.env`, or the provider's runtime). What to do: name each such variable in `inheritEnv`.
  - `env` refuses a key-shaped name (a `_`-separated segment KEY, TOKEN, SECRET, PASSWORD, PASSWD, CREDENTIAL or CREDENTIALS) by name, never its value, and PATH, HOME, LANG and every name the launcher sets: `env` rests in a file of the box and never holds a secret. `env` and `inheritEnv` also refuse every variable the C library itself strips in secure mode (glibc's `UNSECURE_ENVVARS`, such as `GCONV_PATH`, `GLIBC_TUNABLES` and `LOCPATH`, and musl's `MUSL_LOCPATH`; `TMPDIR` excepted) beside `LD_*` (`env` is exported before a root launcher drops to `user`), the launcher clears them at the exec that starts its shell, and it reads only `/proc` (no `PI_TRANSPORT_PROC`).
  - A launch has a handle, `Launch` (`{ v: 1, name }`, JSON with no secret), on its state as `state.launch`; `launchState(box, launch, ctx)` and `launchStop(box, launch, options, ctx)` take it, beside `launchStatus` and `stopLaunch` by name. The state also reports `incarnation` and `restarts`.
  - `Box.launcher` (optional, new on the `Box` interface): a box that keeps a program alive natively (a test's fake box) answers the three calls itself; they read it on every call. A provider leaves it undefined.
  - A launch's `stdin` (disk's mount token) is replayed to every incarnation, and its `secrets` reach every incarnation on one fd (`PI_TRANSPORT_SECRETS_FD`), both on ONE path: the launch frame on the stdin of the exec that starts the launcher, held only in the launcher's memory, never in a file of the box, an environment, an argv or the state. Only a box with `secretsVia: "fd"` takes them (new optional `BoxFacts.secretsVia`, absent meaning no channel: `unsupported`); `local` and `docker` report `fd`.
  - `user`: who the program runs as. A root launcher drops to it (`setpriv` or `runuser`); a launcher that is not root runs the program only as itself. A launch with `stdin` or `secrets` whose program is not root needs the box's ptrace scope at 1 or more, measured in the box.
  - `toolsUser`: with a program run as root, the user it runs everything it does not trust as. A launch with `stdin` or `secrets` runs as root only with one. The launcher verifies it in the box (it exists, is not root and has not the root group, has no sudo rule, and can run no setuid or setgid root file and no file with capabilities), the program gets `PI_TRANSPORT_TOOLS_USER` and `PI_TRANSPORT_TOOLS_UID`, and the state reports it. Each getcap line is read to its file whatever its form (several capability groups, `path = caps`, a path with spaces), and a line that names no file is `unsupported`. The check takes at most 60 s, and a start's call to the box (a revive's too) is given that and its usual 30 s on top, so the check ends inside the call. What the launcher cannot measure is the host's guarantee (README).
  - A stop is one stop's: a second stop at the same time waits for the first and never kills before its `beforeStop` hook ends, a stop whose first one died takes it over, and a `launch` of the name during a stop waits for it. The phase is `stopping` meanwhile. Every stop returns the state of the incarnation it stopped, as the launcher recorded it before it released the name, never a launch of the name that started after it, and a stop that reaches the box only after such a launch took the directory leaves that launch alone (when the host and the launch's launcher.sh are both of this version: a host that passes no generation, or a launch an older launcher.sh runs, keeps the old behaviour, where a late stop can still act on a later launch of the name).
  - `launchSpecError(name, spec)`: the spec's own check, pure (no box, no I/O): the same `invalid` error `launch` gives, for a host that asks before it makes a box to launch in. `launch` asks it first.
  - The launcher's spool (`.pi-transport-launch` in the box's `TMPDIR`) and each launch directory must be the launcher's uid's alone: a directory, never a symbolic link, owned by that uid, with no group- or other-write bit; every directory above the spool, up to `/`, must be root's or that uid's, never a symbolic link, with no group- or other-write bit unless it has the sticky bit (`TMPDIR` is read as the directory it names). Every call checks them before it uses them, and the launcher checks them again before each process it starts from them and before a stop's hook. A local box makes its own `home`, `tmp` and `pids` directories mode 700. A failed check is `unsafe`, and nothing runs from the directory. The box also needs `ls`.
  - New `LaunchErrorCode`s: `unsupported` (a spec the box cannot honour), `refused` (a box setting that would expose what a launch holds) and `unsafe` (a spool or launch directory another user could change).
- A box can be asked for a network, ports and FUSE, and its facts say what it has: `BoxSpec.network` (`"open"`, `"none"` or `{ allow: [...] }` of domains, wildcard domains and IPv4 CIDRs), `BoxSpec.ports` (each `https` by default, or `tcp`) and `BoxSpec.capabilities` (`["fuse"]`). A provider that cannot give one refuses the spec with `unsupported`; a malformed value is `invalid`.
  - `BoxFacts` gains six optional fields, `network`, `ports`, `diskGb`, `startedAt`, `fuse` and `ptraceScope`, so a custom provider needs no change. An absent field never grants anything: `fuse` absent is `false`, `network` and `ports` absent are unknown (a caller that must be sure of `none` or of no exposed port refuses), `ptraceScope`, `diskGb` and `startedAt` absent are unknown. `readFacts(facts)` reads them that way.
  - `Box.endpoint(port, context)` (optional) returns where an exposed port is reached: an `https` URL, or a `tcp` host and port, never a provider's id.
  - `modalBoxes` implements all of it: `network` and `ports` map to Modal's network and tunnel parameters; `capabilities: ["fuse"]` starts a `vm` and checks, as root in the box, that `/dev/fuse` is a character device that root can open (the mount is root's), ending a box that fails the check; `diskGb`, `ptraceScope` and `fuse` are what the box reports. `dockerBoxes` takes `network: "none"`. `localBoxes`, `daytonaBoxes` and the Archil exec box refuse anything but `open`.
  - The box conformance suite checks the facts that are present.
  - `modalBoxes.attach` of a live sandbox always returns the handle and never ends the box: the facts are read again (a failed read is retried three times); a read that answers gives them as measured (a box with no usable FUSE reads `fuse: false`, and the caller ends it through the handle); if every try errs, the handle keeps the hardware the create measured, kept in a tag, and every security fact (the Yama setting, the network, the ports) is left out as unknown; a box whose tag holds nothing measured (made before the tag) gets an `unknown` attach error instead, and keeps running. A failed workspace setup on attach is an attach error too (never an ok handle on a box that may have no workspace).
- `fakeBoxes()` in `@parcha/pi-transport/testing`: a fake box provider for testing a host against the `Box` contract with no machine, key or network. It records every call (argv, env names, stdin bytes, files, spec, typed result) and `leaks(marker)` finds a value in anything recorded. A test scripts outcomes by rule (a typed failure, a delay, a hang, a lost end of an empty stdin, a dropped or truncated stream, a scripted exit, a box that ends mid-call, a create that fails but leaves its box findable by `list`) on a `fakeClock()` that moves only when told. Programs are functions a test registers; a box's files are in memory. Each fake box fills `Box.launcher`, so the launcher's own `launch`, `launchState` and `launchStop` run over it with a scriptable state, the restart policy, the stdin replayed to every incarnation, and the stdin and secrets recorded on the launch call only. The `modalLike()` and `daytonaLike()` presets are included; the `startedAt` and `ptraceScope` facts they report are extra until the box contract carries them.
- A Modal box reports `secretsVia: "fd"`, so a launch can carry a stdin and secrets to it: the launch frame rides the stdin of the exec that starts the launcher, and no value goes in an argv, the `env` or `secrets` parameters, a tag or a fact. The provider is trusted with the box; whether it keeps an exec's stdin is undocumented, and no claim is made about it.
  - Behaviour change: a `close()` of a Modal program's input that fails while the program still runs is now returned by `wait()` (an `unknown` error naming the input), where it was ignored; a close that fails on a program that already exited is still ignored. A second `close()` of the same input (a launch closes it after the frame, and `finish` closes it again) is no failure: the input is closed once, tracked by the adapter itself.
- A Modal box's `facts().gpu` is the GPU it was served, not the one asked for: the model `nvidia-smi` names in the box (a bare `H100` may be served an H200), one name for identical cards and every model, joined by ` + `, for a mixed box. A box that asked for a GPU and reports none fails the create and is ended. On attach the read runs again and the box is always handed back: a model named is the fact, none named reads `gpu: null` (the caller ends it through the handle), and when every try errs the handle keeps the model measured at create, kept in the box's tag, or the attach is an error for a box whose tag has none. The meaning of a published fact changes (it was the request): a caller that compared `facts().gpu` with its spec now compares with the model's name. Docker still repeats the request, and its documentation says it is not measured.
- The launcher's check of a tools user (`toolsUser`) walks its mounts by filesystem type and no longer fails on a pseudo filesystem. It walked every mount without `nosuid`, so `/proc`, where a process ends mid-walk, made `find` exit non-zero and the check refuse the launch (seen on a VM whose `/proc` has no `nosuid`). The kernel's pseudo filesystems (`proc`, `sysfs`, `cgroup`, `cgroup2`, `devpts`, `mqueue`, `securityfs`, `debugfs`, `tracefs`, `bpf`, `pstore`, `configfs`, `fusectl`, `binfmt_misc`, `efivarfs`) are skipped, and every other type, an unknown one, `tmpfs` and `devtmpfs` included, is still walked, so a setuid root file on any of them is still refused. The walk ignores an entry that vanishes mid-walk only where `find` takes `-ignore_readdir_race`, found by running it; a `find` without it keeps the strict walk and a vanished entry stays `unsupported`, as does every other `find` error.

It needs `sh`, `setsid`, `sed`, `cut`, `awk`, `wc`, `tail`, `date` and `sleep`, and runs on Debian, Alpine and a VM whose init never reaps.

  gate holds a running session still for a move with nothing cut, or opens again and names what held it. An app is
  `(ctx) => options` without `env` and `models`, so one module runs on the host and in a box.

  host passes in.

  in the host.
- A workspace or file copy no longer reports a stall while a side is still starting. The stall limit ("no byte moved")
  was running during each side's setup (the parts directory, the program's start), so a box that took longer than the
  limit to answer one call cut a healthy copy with `timeout` after 0 bytes; the hold is now taken before the first call
  and kept until the side is up. The default limit is 60 s, so only a smaller `stallMs` on a slow box was exposed.
- Accept pi 1.3: the `@earendil-works/pi-durable` and `@earendil-works/chord` peer ranges now end below 1.4, with the floors unchanged (1.0.4, and 1.1.0 for `@parcha/pi-browser`). pi 1.3.0 pins its own packages to exact versions, so an install is all 1.2 or all 1.3; CI runs every package's whole suite on a 1.3.0 family as well as on 1.2.0.

A durable node's `submit` then spends none of its submissions. Before 1.3 the tool ran with `{}`, so `submit` answered with the schema's violations and counted one submission.

  costs no second request (`connectHome`'s `server`: one `serveModels` server for every link to a runner). An order

  steps, the take of a numbered lease the one point of no return; a host that starts again finishes the move from
  the lease, which keeps the move's id and the seal; the store keeps the workspace it last ran in. A home holds its
  store alone: a second runner at the same place is `busy`, and `recoverHome` stops a runner still running there first
  (`stopRunner`). `boxRunner` starts a runner in a box over its own `exec`. A session can move back to a place it left.
  Recovering a home sealed at the lease's epoch first takes the next epoch for that place, so it moves the epoch; when a

  ranges are unchanged.
- The tests of "a phase that moves no byte is not a stall" no longer race on a loaded machine: once a slowed setup call ends, tar has the stall limit to move a first byte, and 25 or 400 ms is less than the spawn of a real process can take on a busy runner (a failure of the form "no byte moved for 25 ms, after 0 bytes" on other pull requests). The limit is now one second and the slowed phase is three times that, so the claim is tested with no scheduling noise. Tests only.
- `boxEnv`'s abort and timeout no longer leave a command running when the call that kills it fails. The kill call's result used to be dropped, so a kill exec that failed fast or timed out on a loaded provider API left the command's process group running in the box after `exec` had answered `aborted` or `timeout`, and nothing ended it later. The kill now reads back that no live process of the group is left (a zombie is not counted: `kill -0` succeeds on one, and in a container whose first process does not reap, a killed group would have stayed "alive" for ever), and the call is sent again at 1, 2 and 4 seconds when it fails, times out or finds the group alive, within 10 seconds of wall time, a call in flight included. A stop whose kill call worked answers as fast as before; one that needed a retry answers later, by at most 10 seconds.
