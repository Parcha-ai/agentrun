# Changelog

## [Unreleased]

- New held package `@parcha/agentrun-serve`: the Agentrun v2 API (`agentrun.v2/0`, the contract the hosted API serves) on
  your own machine. `agentrun-serve` serves `http://127.0.0.1:7340/v2` over agent homes of `@parcha/pi-durable-agent` in a
  data directory (default `~/.local/share/agentrun/agents`, `--data`), with a bearer token it writes there at mode 0600 and
  prints at start with `AGENTRUN_BASE_URL`. It binds loopback only, refuses a `Host` that is not a loopback name, and sends
  no CORS headers. It serves capabilities, agents (create, list, read), runs (start, list, read, the timeline as JSON pages
  with the change-number cursor and as server-sent events, messages that steer, answer or follow up, stop, cancel), a
  run's files under `work/`, and usage as an estimate. Each run is a child process of `pi-durable-disk run`, read through
  its door while it is live and from its released store after; a run that answered is carried back to its home and is
  finished. A run's tools are the ones its definition names, of `read`, `write`, `edit` and `ask_person`, which ends the
  turn until a message answers it. With an `output_schema`, a run's output is its final answer parsed as a JSON object,
  and an answer that is not one ends it `failed` (`output_invalid`). `--faux MODULE` answers every model request from a module, with no key and no network; without it the model is
  an OpenAI Responses endpoint named in `AGENT_MODEL_BASE_URL` and `AGENT_MODEL`. Home export and import, definition
  updates, uploads, quotes and kill answer `501 unsupported_here`, and capabilities say so.
- A run that a restarted server adopted now ends final after it answers. The server read the run's store as soon as the run said it was released, while the run's process could still hold the store's exclusive lock until it exited; that read failed with `database is locked`, was not retried, and left the run `completed` but never final until the next start. The server now reads an adopted run's store once its process has exited (it reads anyway, and says so, if the process lives on 30 s after it released the run), retries a store that another connection holds within the same bounded retries as a busy agent home, and writes each wait and a run it could not settle or recover to stderr.
- `packages/serve`: the recovery tests' stand-in run writes `run.json` whole, through a temporary file and a rename, as a run does. A plain rewrite let the server's 500 ms read land on a half-written record, read it as no record, and settle the adopted run early, which failed "an adopted run that released is read only once its process has exited" about once in a loaded full run.
- A half-written JSON file can no longer crash agentrun-serve. Reading a run's `run.json` or a `serve.json` caught a failed read but not a parse error, so a half-written file threw out of the adoption timer as an unhandled rejection, which ends a Node process by default. A file that is not whole JSON now reads as no file. An adopted run whose record cannot be read while its process lives is read again at every tick and stays supervised; the server says so once it has been unreadable for 5 s. The server writes its own `serve.json` files whole, through a temporary file and a rename.
- `agentrun-serve` serves one agent store of `@parcha/pi-durable-agent` instead of an agent home per agent: the data directory holds `store.sqlite` and `runs/<id>/`, and beta.24 agent homes in it are not read. An agent is a row with revisions written once; a definition with `instructions` makes an agentic revision and one with `workflow` (an agentrun-dsl workflow, checked before anything is written) a workflow revision, and an agentic one may name its `model` as `provider/model-id` and its `thinking` level (never off; a run's `effort` outranks it, and `AGENT_THINKING` is the host's default). `PUT /v2/agents/{id}/definition` now commits a new revision whose parent is the current one and makes it current (without `skills`, the current revision's skill files carry over; `If-Match` guards it), `GET /v2/agents/{id}/revisions` lists them, `POST /v2/agents/{id}/current` makes one current again, and `GET /v2/runs` lists every agent's runs, newest first, by agent, revision and status. A run pins the current revision or the one `POST .../runs` names, and the store's row records it; the Agent's ETag is its current revision. A definition's `input_schema`, `output_schema` and `max_cost_usd` have no place in a revision and are refused by name (per-run `max_cost_usd` stays). Capabilities list the `tools` an agentic revision may name and what a workflow's model nodes get (`workflows`).
  A workflow revision's run starts its workflow with `startWorkflowRevision` of `@parcha/pi-durable-agent/workflow` in the run's process, each model node on the host's model of its tier (`AGENT_MODEL_FAST` and `AGENT_MODEL_STRONG`, each falling back to `AGENT_MODEL`, listed in capabilities' `models`), and the server carries it back with `workflowCarry` once the process has exited, as it carries back every run; its output is the run's `result.output`, its rows come when it ends, and it takes no messages; one that escalated is `failed` with `error.code` `escalated` and its summary. A workflow that needs a tool call, a judge or code is not runnable here (`409`), and an input its workflow does not take is `422`. A model comes from `--faux`, from the `AGENT_MODEL_BASE_URL` gateway (every model id through one endpoint), or else from pi-ai's providers with their keys from the environment; `AGENT_MODEL` is the default for a revision that names none, and a model that cannot be reached here is `409 agent_not_runnable`. When the server starts, a run whose process went before the run ended is opened again on its directory and resumes from its store, where it was marked failed.
- `agentrun-serve` runs in one container: `--listen ADDR` listens on another address than 127.0.0.1 (there every `Host` name is served and the token is the only lock), and `AGENTRUN_TOKEN` gives the token in place of `DIR/.token`'s and is never printed. The repository has `packages/serve/docker/Dockerfile` (the server and the open packages it runs, everything it keeps under `/data`), a compose example that publishes the port on loopback only, and `render.yaml`, a Render blueprint with a persistent disk and a generated token. The image's build context is an allowlist (`.dockerignore`): a `.env`, `.env.*` or `.npmrc` never enters it, wherever it is in the checkout.
- `agentrun-serve` serves a page at `/`, AgentRun Server, for the person who holds its token: the agent store's page from `@parcha/pi-durable-agent` (agents, revisions with the prompt diff and the workflow graph, runs, a run's timeline) plus every run across agents, forms that create an agent, commit a revision, make a revision current and start a run through `/v2`, and a live run followed until it is final, with an answer box while it waits on `ask_person`. The server prints one more line, `Open` and the page's address with `?token=` and its token; opening it sets an `HttpOnly`, `SameSite=Strict` cookie that stands in for the Bearer header (a write only from the page's own origin with a JSON body).
  `@parcha/pi-durable-agent/serve` exports what another server needs to serve the store's page: `storeApi(store)`, the read-only JSON behind its `/api/*` paths, and `STORE_PAGE_FILES`, its files. The page takes a script loaded before `page.js` that sets `window.agentStoreHost`; `pi-durable-agent serve` loads none. A cost under a cent now shows two significant digits ($0.00014, not $0.000), and a recorded 0 shows as $0.
- `PUT /v2/agents/{id}/definition` with `If-Match` is compared inside the store's commit, so of two edits that read the same revision exactly one lands and the other answers `412`, where both could land, the second on top of the first. A run's process loads only the model tiers its revision uses, so a workflow of fast nodes runs with `AGENT_MODEL_FAST` and no `AGENT_MODEL`. A run's process no longer gets the server's token: `AGENTRUN_TOKEN`, `AGENTRUN_API_KEY` and any variable holding the token are left out of its environment, and model keys and the `AGENT_MODEL` variables still reach it.
- The README's Safety section says what holds a run in: its file tools reach its own `work/`, plus reads of its own `tmp/` and writes in a temporary directory made for a tool, and nothing else (pi-durable-disk's confinement in the run's process, since the run and the server share a user), and no path offers a shell, so `bash` stays off. A new suite of real runs probes it: reads of the server's and the door's tokens, `store.sqlite`, another run's `work/` and `tmp/`, `/proc` and a link planted in `work/`, writes and an edit outside `work/` (its own `tmp/` included), and `bash` called by an agent and by a workflow's model node are each refused, with nothing changed on disk, while the same run still reads and writes inside `work/` and reads its own `tmp/`.
- Through a gateway (`AGENT_MODEL_BASE_URL`), a revision that names its model as `provider/model-id` is now sent to the gateway whole (`openai/gpt-4o`), as a gateway like OpenRouter names its models `vendor/model`; it was sent as `model-id` alone. Who breaks: a gateway that expects the id without its provider. What to do: set `AGENT_MODEL_GATEWAY_IDS=bare` to keep the old behaviour. Unchanged: `AGENT_MODEL`, `AGENT_MODEL_FAST` and `AGENT_MODEL_STRONG` are sent as they are set, and the price is still the named provider's catalog entry for the model, else the highest.
- Archive an agent or a run: `POST /v2/agents/{id}/archive` and `POST /v2/runs/{id}/archive` (and `.../unarchive`), this server's own routes outside the `/v2` contract, listed in `capabilities.features.archive`. An archived agent and its runs, or one archived run, are hidden from `GET /agents`, `GET /runs` and `GET /agents/{id}/runs` (`?archived=true` lists only those), and kept: every read by id still answers, with `archived_at`, and `/usage` still counts them. A new run of an archived agent is `409 agent_not_runnable`; a run already going keeps going. Nothing is deleted, and `DELETE` stays `405`. The page has Archive and Unarchive on an agent's page and a run's page, and Show archived on the agents and on All runs.
- `AGENTRUN_PUBLIC_URL` sets the address the printed `Open` link and `AGENTRUN_BASE_URL` name, so a container published on another port, or behind a proxy, prints a link that works; a value that is not an http(s) URL stops the server at start. The compose example's `AGENTRUN_PORT` publishes another port and sets that URL. `render.yaml` and the compose example take `OPENROUTER_API_KEY` (pi-ai's OpenRouter provider, `AGENT_MODEL=openrouter/<model>`) and a gateway's `AGENT_MODEL_BASE_URL` and `AGENT_MODEL_API_KEY`. The root README opens with AgentRun as an open platform to manage your agents (the platform, AgentRun Server and the building blocks), then the two ways to host it: `docker run` with the public image, or Render's Starter with a disk.
- `GET /v2/openapi.json` serves this API as an OpenAPI 3.1 document, with no credential, as capabilities are, and capabilities link it (`links.openapi`). It is the `agentrun.v2/0` contract, vendored unchanged in `src/openapi/agentrun-v2.openapi.json` with its source (repository, pull request and commit) in `info.x-agentrun-source`. The server marks its own routes outside the contract (`GET /runs`, `GET /agents/{id}/revisions`, `POST /agents/{id}/current`, and the document itself) `x-agentrun-serve: true`, and the six operations it answers `501` (home export and import, kill, the two upload routes and quotes) `x-agentrun-serve-unsupported` with the reason. A test holds the document to the server's route table, both ways.
- On pi-durable 1.2 and later, the model's record of an `ask_person` call was empty: the tool returned its text under `content`, which 1.2 renamed to `output`. It now returns both, so every pi-durable serve takes (1.1 to 1.3) reads it. The released image ships pi-durable 1.1.0 and was not affected; builds from source on 1.2 or 1.3 were.
- AgentRun Server caps its concurrent runs, says whether it can work, and settles runs a full disk left behind.

  - The most runs at once (each with a live process) is `--max-runs N` or `AGENTRUN_MAX_RUNS`, by default `max(1, floor((memory − 128 MiB) / 72 MiB))` from the container's memory limit or the machine's (5 on a 512 MB instance, which ran out of memory at about 6 before). Over it, `POST /v2/agents/{id}/runs` is `429 rate_limited` with `retry-after`, and nothing starts. `capabilities.limits.max_concurrent_runs` reports it.
  - `GET /v2/health`, with no credential, is `200` when the agent store opens for a read and the data directory's disk has 64 MiB free (`AGENTRUN_MIN_FREE_MB`), else `503` naming the check that failed, and no path, size or version. Compose's healthcheck and `render.yaml`'s `healthCheckPath` use it; before, the health check was `/v2/capabilities`, which stayed `200` on a full disk.
  - A run whose end the agent store cannot write (a full disk) still ends: a cancel makes it `cancelled`, priced from its rows, where before it stayed `queued` or `working` and cancel could not settle it. The server writes the end again every 30 s until it lands.
  - A message to a run whose process was killed opens it again at once, where before it was `503` for up to the 90 s lease: a heartbeat of a process that is gone is no longer trusted.
  - A free-disk reading that fails is `disk: "cannot_check"` (`503`), never room. A data directory serves one AgentRun Server at a time; two on a shared disk are not supported.
- Through a gateway (`AGENT_MODEL_BASE_URL`) with no `AGENT_MODEL_PRICE`, a model id pi-ai's catalog knows now takes the catalog's list price, so its runs' costs are estimated instead of reading $0. A revision's `provider/model-id` takes that provider's entry when it is paid; a bare id (`AGENT_MODEL` and the tier variables), a provider the catalog does not list for it, or one it lists at $0 takes the highest price any provider lists: one entry's whole price, the most input plus output, never a $0 entry over a paid one, so a named provider's $0 never switches off `max_cost_usd`. A price you set still wins, and an id the catalog does not know is still priced at $0. A behavior change: a run's `max_cost_usd` now applies to these gateway models and stops the run with `spend_cap_reached` once its estimate passes the cap; at $0 it never fired.
- A run whose process fails as it starts is no longer started again while its end is being written. The first message's delivery could start a second process in that window, so the run read `failed` while that process still held its place under `--max-runs`, and the next start was refused (429). Nothing starts a run's process now while a settle of that run is in progress.

  A run whose first message was still on its way when the server stopped no longer has its end written after the stop, into a store the stop had closed. The next start recovers the run and writes its end then. A run's first message also waits out a process that is slow to come up, up to the ready time (45 s), whatever deadline a later request to the run has.
- AgentRun Server is easier to run: a stop ends within the platform's grace, the token link takes any token, and stdout says what happened.

  - `--drain-timeout D` sets how long a busy run may finish its turn when the server stops (default 30s), and the image's command sets 6s, so a busy stop ends in about 7.5 s, inside Docker's default 10 s grace, so a busy `docker stop` no longer ends in SIGKILL (exit 137). Compose sets `stop_grace_period: 15s`. Render waits 30 s and does not let a service with a disk change it, which `render.yaml` now says. A turn cut off resumes at the next start.
  - The page's `/?token=` link signs in with a token holding `+`, `/` or `=` whether it is URL-encoded or not (a `+` sent raw arrives as a space), and the printed link encodes the token. Before, Render's generated tokens often had a `+`, and the documented link answered 401.
  - stdout gets one logfmt line per request (method, path without its query, status, ms), per run start and end (run, agent, status, cost) and per refused credential (route and reason, never the token or any part of it). `AGENTRUN_LOG=quiet` leaves out the request lines. A run whose process failed at its start says why in words, not as the process log's raw JSON.
  - `DIR/.token`'s token is printed only by the start that made it; a later start prints `AGENTRUN_API_KEY=<in DIR/.token>` and `?token=<in DIR/.token>`. `startServe` returns `tokenMade`, takes `log`, and `banner` is exported.
- AgentRun Server refuses to start on a data directory that holds agent homes from 0.1.0-beta.26 or earlier (`<data>/<agent>/agent.sqlite`), naming each one, instead of starting with none of their agents or runs showing. That includes a volume already started on 0.1.0-beta.27 that still holds one, an agent named `runs`, and a symlinked home. The serve README's "Upgrading from 0.1.0-beta.26" says what to do: keep the earlier version on that directory, or start this one on a new directory, or with the old homes moved out.
- `POST /v2/agents` and `PUT /v2/agents/{id}/definition` now check a definition for what keeps it from running here, with the checks a run makes before it starts. A definition that can never run here is `422 input_invalid` by field and nothing is saved: a tool this host does not bind (`definition.tools[i]`, `bash` among them), a model pi-ai does not know (`definition.model`), empty instructions (`definition.instructions`), or a workflow that needs a tool call, a judge, code or a node tool other than `read`, `write` and `edit` (`definition.workflow`). Before, these saved (`201`/`200`) and every run was `409`. A definition this host cannot run yet but could (no key for the model's provider, no default model, no model for a workflow tier) still saves, and the answer lists what is missing in `warnings`; the page shows them. Runs of such a revision, or of one saved before these checks, are still `409 agent_not_runnable`.
- `max_cost_usd` is now a cap, checked before each model request in the run's own process: when what the run has spent plus the request's worst case (its input tokens at the model's input price, its max output tokens at the output price) would pass the cap, the request is not sent and the run ends `failed` with `spend_cap_reached`. Before, it was checked only after each response, so one request could cost any amount over the cap. Spent so far is read back from the run's store when its process starts, so it survives a restart. The server's check after each response stays as a backstop, and a run the cap stopped now keeps the answer it paid for in `result.final_answer` instead of `result: null`.

  A cancelled run, and any run that made no model request, now costs $0 instead of `null`, and `/v2/usage` adds a run whose cost is unknown as $0, so one such run no longer makes every total and line `null`. The README says what `limits.max_cost_usd: null` means: no ceiling on the cap a run may name.

  A response of unknown price (one with no cost in its usage) leaves its run's `cost.usd` `null`, never $0, and `/v2/usage` counts such runs in `unpriced_runs`, in its total and in each line, beside the dollars of the runs whose cost is known.
