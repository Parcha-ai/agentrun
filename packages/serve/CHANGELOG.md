# Changelog

## [Unreleased]

## 0.1.0-beta.29 (2026-11-04)

- New held package `@parcha/agentrun-serve`: the Agentrun v2 API (`agentrun.v2/0`, the contract the hosted API serves) on
  your own machine. `agentrun-serve` serves `http://127.0.0.1:7340/v2` over agent homes of `@parcha/pi-durable-agent` in a
  data directory (default `~/.local/share/agentrun/agents`, `--data`), with a bearer token it writes there at mode 0600 and
  prints at start with `AGENTRUN_BASE_URL`. It binds loopback only, refuses a `Host` that is not a loopback name, and sends
  no CORS headers. It serves capabilities, agents (create, list, read), runs (start, list, read, the timeline as JSON pages
  with the change-number cursor and as server-sent events, messages that steer, answer or follow up, stop, cancel), a
  run's files under `work/`, and usage as an estimate. Each run is a child process of `pi-durable-disk run`, read through
  its door while it is live and from its released store after; a run that answered is carried back to its home and is
  finished. A run's tools are the ones its definition names, of `read`, `write`, `edit` and `ask_person`, which ends the
  turn until a message answers it. With an `output_schema`, a run's output is its final answer parsed as a JSON object,
  and an answer that is not one ends it `failed` (`output_invalid`). `--faux MODULE` answers every model request from a module, with no key and no network; without it the model is
  an OpenAI Responses endpoint named in `AGENT_MODEL_BASE_URL` and `AGENT_MODEL`. Home export and import, definition
  updates, uploads, quotes and kill answer `501 unsupported_here`, and capabilities say so.
- A run that a restarted server adopted now ends final after it answers. The server read the run's store as soon as the run said it was released, while the run's process could still hold the store's exclusive lock until it exited; that read failed with `database is locked`, was not retried, and left the run `completed` but never final until the next start. The server now reads an adopted run's store once its process has exited (it reads anyway, and says so, if the process lives on 30 s after it released the run), retries a store that another connection holds within the same bounded retries as a busy agent home, and writes each wait and a run it could not settle or recover to stderr.
- `packages/serve`: the recovery tests' stand-in run writes `run.json` whole, through a temporary file and a rename, as a run does. A plain rewrite let the server's 500 ms read land on a half-written record, read it as no record, and settle the adopted run early, which failed "an adopted run that released is read only once its process has exited" about once in a loaded full run.
- A half-written JSON file can no longer crash agentrun-serve. Reading a run's `run.json` or a `serve.json` caught a failed read but not a parse error, so a half-written file threw out of the adoption timer as an unhandled rejection, which ends a Node process by default. A file that is not whole JSON now reads as no file. An adopted run whose record cannot be read while its process lives is read again at every tick and stays supervised; the server says so once it has been unreadable for 5 s. The server writes its own `serve.json` files whole, through a temporary file and a rename.
- `agentrun-serve` serves one agent store of `@parcha/pi-durable-agent` instead of an agent home per agent: the data directory holds `store.sqlite` and `runs/<id>/`, and beta.24 agent homes in it are not read. An agent is a row with revisions written once; a definition with `instructions` makes an agentic revision and one with `workflow` (an agentrun-dsl workflow, checked before anything is written) a workflow revision, and an agentic one may name its `model` as `provider/model-id` and its `thinking` level (never off; a run's `effort` outranks it, and `AGENT_THINKING` is the host's default). `PUT /v2/agents/{id}/definition` now commits a new revision whose parent is the current one and makes it current (without `skills`, the current revision's skill files carry over; `If-Match` guards it), `GET /v2/agents/{id}/revisions` lists them, `POST /v2/agents/{id}/current` makes one current again, and `GET /v2/runs` lists every agent's runs, newest first, by agent, revision and status. A run pins the current revision or the one `POST .../runs` names, and the store's row records it; the Agent's ETag is its current revision. A definition's `input_schema`, `output_schema` and `max_cost_usd` have no place in a revision and are refused by name (per-run `max_cost_usd` stays). Capabilities list the `tools` an agentic revision may name and what a workflow's model nodes get (`workflows`).
  A workflow revision's run starts its workflow with `startWorkflowRevision` of `@parcha/pi-durable-agent/workflow` in the run's process, each model node on the host's model of its tier (`AGENT_MODEL_FAST` and `AGENT_MODEL_STRONG`, each falling back to `AGENT_MODEL`, listed in capabilities' `models`), and the server carries it back with `workflowCarry` once the process has exited, as it carries back every run; its output is the run's `result.output`, its rows come when it ends, and it takes no messages; one that escalated is `failed` with `error.code` `escalated` and its summary. A workflow that needs a tool call, a judge or code is not runnable here (`409`), and an input its workflow does not take is `422`. A model comes from `--faux`, from the `AGENT_MODEL_BASE_URL` gateway (every model id through one endpoint), or else from pi-ai's providers with their keys from the environment; `AGENT_MODEL` is the default for a revision that names none, and a model that cannot be reached here is `409 agent_not_runnable`. When the server starts, a run whose process went before the run ended is opened again on its directory and resumes from its store, where it was marked failed.
- `agentrun-serve` runs in one container: `--listen ADDR` listens on another address than 127.0.0.1 (there every `Host` name is served and the token is the only lock), and `AGENTRUN_TOKEN` gives the token in place of `DIR/.token`'s and is never printed. The repository has `packages/serve/docker/Dockerfile` (the server and the open packages it runs, everything it keeps under `/data`), a compose example that publishes the port on loopback only, and `render.yaml`, a Render blueprint with a persistent disk and a generated token. The image's build context is an allowlist (`.dockerignore`): a `.env`, `.env.*` or `.npmrc` never enters it, wherever it is in the checkout.
- `agentrun-serve` serves a page at `/`, AgentRun Server, for the person who holds its token: the agent store's page from `@parcha/pi-durable-agent` (agents, revisions with the prompt diff and the workflow graph, runs, a run's timeline) plus every run across agents, forms that create an agent, commit a revision, make a revision current and start a run through `/v2`, and a live run followed until it is final, with an answer box while it waits on `ask_person`. The server prints one more line, `Open` and the page's address with `?token=` and its token; opening it sets an `HttpOnly`, `SameSite=Strict` cookie that stands in for the Bearer header (a write only from the page's own origin with a JSON body).
  `@parcha/pi-durable-agent/serve` exports what another server needs to serve the store's page: `storeApi(store)`, the read-only JSON behind its `/api/*` paths, and `STORE_PAGE_FILES`, its files. The page takes a script loaded before `page.js` that sets `window.agentStoreHost`; `pi-durable-agent serve` loads none. A cost under a cent now shows two significant digits ($0.00014, not $0.000), and a recorded 0 shows as $0.
- `PUT /v2/agents/{id}/definition` with `If-Match` is compared inside the store's commit, so of two edits that read the same revision exactly one lands and the other answers `412`, where both could land, the second on top of the first. A run's process loads only the model tiers its revision uses, so a workflow of fast nodes runs with `AGENT_MODEL_FAST` and no `AGENT_MODEL`. A run's process no longer gets the server's token: `AGENTRUN_TOKEN`, `AGENTRUN_API_KEY` and any variable holding the token are left out of its environment, and model keys and the `AGENT_MODEL` variables still reach it.
- The README's Safety section says what holds a run in: its file tools reach its own `work/`, plus reads of its own `tmp/` and writes in a temporary directory made for a tool, and nothing else (pi-durable-disk's confinement in the run's process, since the run and the server share a user), and no path offers a shell, so `bash` stays off. A new suite of real runs probes it: reads of the server's and the door's tokens, `store.sqlite`, another run's `work/` and `tmp/`, `/proc` and a link planted in `work/`, writes and an edit outside `work/` (its own `tmp/` included), and `bash` called by an agent and by a workflow's model node are each refused, with nothing changed on disk, while the same run still reads and writes inside `work/` and reads its own `tmp/`.
- Through a gateway (`AGENT_MODEL_BASE_URL`), a revision that names its model as `provider/model-id` is now sent to the gateway whole (`openai/gpt-4o`), as a gateway like OpenRouter names its models `vendor/model`; it was sent as `model-id` alone. Who breaks: a gateway that expects the id without its provider. What to do: set `AGENT_MODEL_GATEWAY_IDS=bare` to keep the old behaviour. Unchanged: `AGENT_MODEL`, `AGENT_MODEL_FAST` and `AGENT_MODEL_STRONG` are sent as they are set, and the price is still the named provider's catalog entry for the model, else the highest.
- Archive an agent or a run: `POST /v2/agents/{id}/archive` and `POST /v2/runs/{id}/archive` (and `.../unarchive`), this server's own routes outside the `/v2` contract, listed in `capabilities.features.archive`. An archived agent and its runs, or one archived run, are hidden from `GET /agents`, `GET /runs` and `GET /agents/{id}/runs` (`?archived=true` lists only those), and kept: every read by id still answers, with `archived_at`, and `/usage` still counts them. A new run of an archived agent is `409 agent_not_runnable`; a run already going keeps going. Nothing is deleted, and `DELETE` stays `405`. The page has Archive and Unarchive on an agent's page and a run's page, and Show archived on the agents and on All runs.
- `AGENTRUN_PUBLIC_URL` sets the address the printed `Open` link and `AGENTRUN_BASE_URL` name, so a container published on another port, or behind a proxy, prints a link that works; a value that is not an http(s) URL stops the server at start. The compose example's `AGENTRUN_PORT` publishes another port and sets that URL. `render.yaml` and the compose example take `OPENROUTER_API_KEY` (pi-ai's OpenRouter provider, `AGENT_MODEL=openrouter/<model>`) and a gateway's `AGENT_MODEL_BASE_URL` and `AGENT_MODEL_API_KEY`. The root README opens with AgentRun as an open platform to manage your agents (the platform, AgentRun Server and the building blocks), then the two ways to host it: `docker run` with the public image, or Render's Starter with a disk.
- `GET /v2/openapi.json` serves this API as an OpenAPI 3.1 document, with no credential, as capabilities are, and capabilities link it (`links.openapi`). It is the `agentrun.v2/0` contract, vendored unchanged in `src/openapi/agentrun-v2.openapi.json` with its source (repository, pull request and commit) in `info.x-agentrun-source`. The server marks its own routes outside the contract (`GET /runs`, `GET /agents/{id}/revisions`, `POST /agents/{id}/current`, and the document itself) `x-agentrun-serve: true`, and the six operations it answers `501` (home export and import, kill, the two upload routes and quotes) `x-agentrun-serve-unsupported` with the reason. A test holds the document to the server's route table, both ways.
- **The page is yours: one owner and a password, on by default**
  - AgentRun Server is for one person, who signs in to the page with a password. This is on unless `AGENTRUN_ACCOUNTS=0`. With no `AGENTRUN_PUBLIC_URL` (as `docker run` gives it; on Render, its `RENDER_EXTERNAL_URL` stands in), the first visit sets the password, 12 characters or more, and signs in. With it, setup takes the code the server prints, or the token as the Bearer. A second setup is a 403. `startServe` takes this as `accounts` and `openSetup` (both off by default for a library caller).
  - The password is kept as a scrypt hash (N 2^15, r 8, p 1, with a 16-byte salt and its parameters) in `DIR/owner.json` (0600). A session is a cookie signed with HMAC-SHA256 under the key in `DIR/.session-secret` (0600). It holds when it was made, when it ends (30 days, checked from the signed payload) and the session epoch. The cookie is HttpOnly, SameSite=Strict and Path=/, `__Host-agentrun-session` with Secure on https. No run's tool reaches either file.
  - `POST /v2/setup`, `POST /v2/auth/sign-in`, `POST /v2/auth/sign-out` and `GET /v2/auth/session` take writes only from the page's own origin with a JSON body. Sign-in tries are limited to 10 per address in 15 minutes, keyed on the connection's peer, never on a header. **Sign out everywhere** ends every session on every browser.
  - `agentrun-serve reset-password --data DIR`, run where the data directory is, clears the password and ends every session; the next visit sets a new one. It is never an HTTP route.
  - The token keeps working for scripts and the CLI. With accounts on, a `?token=` page link sets no cookie and the start's `Open` line holds no token: the page is the owner's session alone, so **Sign out everywhere** leaves no browser in. The sign-in limit keeps up to 10,000 addresses; past that a new one gets a 429 and an address already limited stays limited.
  - Every route but capabilities, the contract and health takes the owner's session or the token. The contract's answers do not change.
- On pi-durable 1.2 and later, the model's record of an `ask_person` call was empty: the tool returned its text under `content`, which 1.2 renamed to `output`. It now returns both, so every pi-durable serve takes (1.1 to 1.3) reads it. The released image ships pi-durable 1.1.0 and was not affected; builds from source on 1.2 or 1.3 were.
- AgentRun Server caps its concurrent runs, says whether it can work, and settles runs a full disk left behind.

  - The most runs at once (each with a live process) is `--max-runs N` or `AGENTRUN_MAX_RUNS`, by default `max(1, floor((memory − 128 MiB) / 72 MiB))` from the container's memory limit or the machine's (5 on a 512 MB instance, which ran out of memory at about 6 before). Over it, `POST /v2/agents/{id}/runs` is `429 rate_limited` with `retry-after`, and nothing starts. `capabilities.limits.max_concurrent_runs` reports it.
  - `GET /v2/health`, with no credential, is `200` when the agent store opens for a read and the data directory's disk has 64 MiB free (`AGENTRUN_MIN_FREE_MB`), else `503` naming the check that failed, and no path, size or version. Compose's healthcheck and `render.yaml`'s `healthCheckPath` use it; before, the health check was `/v2/capabilities`, which stayed `200` on a full disk.
  - A run whose end the agent store cannot write (a full disk) still ends: a cancel makes it `cancelled`, priced from its rows, where before it stayed `queued` or `working` and cancel could not settle it. The server writes the end again every 30 s until it lands.
  - A message to a run whose process was killed opens it again at once, where before it was `503` for up to the 90 s lease: a heartbeat of a process that is gone is no longer trusted.
  - A free-disk reading that fails is `disk: "cannot_check"` (`503`), never room. A data directory serves one AgentRun Server at a time; two on a shared disk are not supported.
- Through a gateway (`AGENT_MODEL_BASE_URL`) with no `AGENT_MODEL_PRICE`, a model id pi-ai's catalog knows now takes the catalog's list price, so its runs' costs are estimated instead of reading $0. A revision's `provider/model-id` takes that provider's entry when it is paid; a bare id (`AGENT_MODEL` and the tier variables), a provider the catalog does not list for it, or one it lists at $0 takes the highest price any provider lists: one entry's whole price, the most input plus output, never a $0 entry over a paid one, so a named provider's $0 never switches off `max_cost_usd`. A price you set still wins, and an id the catalog does not know is still priced at $0. A behavior change: a run's `max_cost_usd` now applies to these gateway models and stops the run with `spend_cap_reached` once its estimate passes the cap; at $0 it never fired.
- **A run that ended is never started again, so its place is free once it reads failed**
  - A run's first message waits for the run's process to come up. When that process failed at its start, the settle that ended the run could finish while the wait read the run's `run.json`, and the wait then started the process again: a second process for a finished run, holding its place, so the next start under `--max-runs` could be a 429 `rate_limited`.
  - The wait now checks whether the run ended after each read, and a run that ended or is finishing is never launched.
- A run whose process fails as it starts is no longer started again while its end is being written. The first message's delivery could start a second process in that window, so the run read `failed` while that process still held its place under `--max-runs`, and the next start was refused (429). Nothing starts a run's process now while a settle of that run is in progress.

  A run whose first message was still on its way when the server stopped no longer has its end written after the stop, into a store the stop had closed. The next start recovers the run and writes its end then. A run's first message also waits out a process that is slow to come up, up to the ready time (45 s), whatever deadline a later request to the run has.
- AgentRun Server is easier to run: a stop ends within the platform's grace, the token link takes any token, and stdout says what happened.

  - `--drain-timeout D` sets how long a busy run may finish its turn when the server stops (default 30s), and the image's command sets 6s, so a busy stop ends in about 7.5 s, inside Docker's default 10 s grace, so a busy `docker stop` no longer ends in SIGKILL (exit 137). Compose sets `stop_grace_period: 15s`. Render waits 30 s and does not let a service with a disk change it, which `render.yaml` now says. A turn cut off resumes at the next start.
  - The page's `/?token=` link signs in with a token holding `+`, `/` or `=` whether it is URL-encoded or not (a `+` sent raw arrives as a space), and the printed link encodes the token. Before, Render's generated tokens often had a `+`, and the documented link answered 401.
  - stdout gets one logfmt line per request (method, path without its query, status, ms), per run start and end (run, agent, status, cost) and per refused credential (route and reason, never the token or any part of it). `AGENTRUN_LOG=quiet` leaves out the request lines. A run whose process failed at its start says why in words, not as the process log's raw JSON.
  - `DIR/.token`'s token is printed only by the start that made it; a later start prints `AGENTRUN_API_KEY=<in DIR/.token>` and `?token=<in DIR/.token>`. `startServe` returns `tokenMade`, takes `log`, and `banner` is exported.
- AgentRun Server refuses to start on a data directory that holds agent homes from 0.1.0-beta.26 or earlier (`<data>/<agent>/agent.sqlite`), naming each one, instead of starting with none of their agents or runs showing. That includes a volume already started on 0.1.0-beta.27 that still holds one, an agent named `runs`, and a symlinked home. The serve README's "Upgrading from 0.1.0-beta.26" says what to do: keep the earlier version on that directory, or start this one on a new directory, or with the old homes moved out.
- `POST /v2/agents` and `PUT /v2/agents/{id}/definition` now check a definition for what keeps it from running here, with the checks a run makes before it starts. A definition that can never run here is `422 input_invalid` by field and nothing is saved: a tool this host does not bind (`definition.tools[i]`, `bash` among them), a model pi-ai does not know (`definition.model`), empty instructions (`definition.instructions`), or a workflow that needs a tool call, a judge, code or a node tool other than `read`, `write` and `edit` (`definition.workflow`). Before, these saved (`201`/`200`) and every run was `409`. A definition this host cannot run yet but could (no key for the model's provider, no default model, no model for a workflow tier) still saves, and the answer lists what is missing in `warnings`; the page shows them. Runs of such a revision, or of one saved before these checks, are still `409 agent_not_runnable`.
- `max_cost_usd` is now a cap, checked before each model request in the run's own process: when what the run has spent plus the request's worst case (its input tokens at the model's input price, its max output tokens at the output price) would pass the cap, the request is not sent and the run ends `failed` with `spend_cap_reached`. Before, it was checked only after each response, so one request could cost any amount over the cap. Spent so far is read back from the run's store when its process starts, so it survives a restart. The server's check after each response stays as a backstop, and a run the cap stopped now keeps the answer it paid for in `result.final_answer` instead of `result: null`.

  A cancelled run, and any run that made no model request, now costs $0 instead of `null`, and `/v2/usage` adds a run whose cost is unknown as $0, so one such run no longer makes every total and line `null`. The README says what `limits.max_cost_usd: null` means: no ceiling on the cap a run may name.

  A response of unknown price (one with no cost in its usage) leaves its run's `cost.usd` `null`, never $0, and `/v2/usage` counts such runs in `unpriced_runs`, in its total and in each line, beside the dollars of the runs whose cost is known.
- A run's spend cap now counts every request's input on every harness, with one bound: a token per UTF-8 byte of what is sent, plus what the provider adds server-side. That bound is at the dearer of the model's input and cache-write prices, plus the request's output ceiling. What the provider adds is documented for Anthropic and OpenAI (their tool-use prompt and per-image maximum). For every other API kind it is assumed: 2,048 tokens for a request with tools, and the largest per-image maximum for each image. So the bound never undercounts as documented for Anthropic and OpenAI, and as an assumed bound elsewhere.
  - codex and claude-agent: before, the cap priced only the output ceiling, so a request with a large input could pass a cap it should not. Each request still in flight now holds its own input bound too, so requests sent side by side cannot pass the cap together. A request whose input could not be measured is refused under a cap.
  - pi: the input was pi's estimate, about 3.5 characters a token. It is now the byte bound, which is stricter, so **a capped pi run can now be refused a request it used to be allowed**, most of all for dense text such as non-Latin scripts and emoji.
  - A model serve has no price for, a gateway model the catalog does not list and no price is set for, is refused under a cap. Before, it read $0 and never reached one. A model the catalog lists at $0 is a known $0 and passes, and with no cap nothing is refused.
  - No API kind is refused for being one: a capped run on Gemini, Bedrock, Mistral or a Chat Completions gateway is priced as above.
- Uploads work on the first try. `upload.url` in the answer to `POST /v2/files` is now a path from the server's root, `/v2/files/{file_id}`, where it was `/files/{file_id}` relative to `/v2`: a client that appended it to the `/v2` base (`$AGENTRUN_BASE_URL$url`) now sends it to the server's address instead (`${AGENTRUN_BASE_URL%/v2}$url`), or resolves it against the base as a URL; a doubled `/v2` answers a `404` that says so. The route itself, `PUT /v2/files/{file_id}`, is unchanged.
  - A file is sent in one call: `POST /v2/files?path=<its path>` with its bytes as the body (`curl --data-binary @plan.md`), any type but a multipart form, answered `201` with the file `ready`, its length the body's and its hash its own. `content_type` and `sha256` may go in the query too, and `Idempotency-Key` replays the first file for the same bytes. The contract's two-step JSON reservation and `PUT` are kept.
  - `GET /v2/files` lists the server's uploads, newest first, `GET /v2/files/{file_id}` reads one's record, and `DELETE /v2/files/{file_id}` removes it; a run that copied a deleted file keeps its copy.
  - The page's session may send a file in one call with any content type, still only with the page's own `Origin`: `POST /v2/files` is marked to take bytes, beside `PUT /v2/files/{file_id}`.
- `npx @parcha/agentrun` installs the server it was released with: `@parcha/agentrun-serve` is its one dependency, at the release's exact version, so npx installs the two together and nothing is fetched at run time (no `@latest`). The command passes its arguments through, with its store (`--data ~/.agentrun` unless `--data` names another), and the server's CLI picks what it used to: with no `--port`, `agentrun-serve` takes the first free port from 7340, found by listening, so a port another process takes at the same moment is passed over (`--port N` is still exact and fails at once when taken, `0` any); `--open` opens the console's page in the browser once the server listens (never the banner's sign-in link, so the token stays out of the opener's arguments and the browser's history), except in CI or on Linux with no display (the command passes it unless `--no-open`). The CLI sets no model: with no `AGENT_MODEL`, the server's default is the first provider key it has, set where it starts or saved in the console's Settings → Model keys, so a key saved later moves the default with no restart. The release publishes the command after the server, and `release-preflight` refuses a command whose server pin is not the release version, so every release bumps the command too. `@parcha/agentrun` is 0.3.3.
- `boxSlot` (`@parcha/agentrun-kernel/host`) runs one session's harness boxes one at a time, whatever the isolation: how a box starts and how it is reaped are its arguments, in the shapes of the kernel's new `Box` (`host/box.ts`: `BoxSpec`, `BoxRecord`, `BoxRecorder`, `BoxedChild`, `Reaped`, `BoxError`).
  - `start` is synchronous. It is refused with `BoxError` `box_busy` while the session's last box is live, being reaped, or was not counted empty. The box's start writes its record before the spawn (`ahead`) and before its first process is let go (`started`).
  - The box is reaped as soon as its process exits or is never let go. Only the reap's own count frees the slot. The box's exit status and output are never read, since anything in the box can forge them. A box left with processes, or one nothing could count, rejects with `box_not_empty` and keeps the session from starting another. `adopt` reaps the record a session's last box left before anything starts.
  - serve's `writeDurableSync` and `writeDurable` sync the new file and its directory before they return. `boxRecorder` writes a run's `box.json` with them, and refuses a record that names no writer, since such a record could never be cleared safely.
  - A box that exits while its `started` record is still being written is reaped once that write lands, by the record it wrote. A box that has ended records nothing more, so a late write never replaces the next box's record.
  - The durable writes write every byte or fail. A short write (a disk nearly full) is never synced and renamed as a whole record; the recorder refuses it with `box_record_failed` and leaves no part behind.
- A `claude-agent` run loads the revision's skills through the Claude Agent CLI's Skill tool instead of reading them all in its system prompt. The model is shown each skill as `agentrun:<name>`, loads its `SKILL.md` when it needs it, and reads the skill's other files with `read_skill_file`; the system prompt carries the instructions alone. A skill the adapter does not take (a name that is not lowercase letters, digits and dashes, a `SKILL.md` without front matter giving its `name` and a `description`, a file path that is not plain or is deeper than five segments) stays inlined in the system prompt as before, and so do all of them when together they hold more than 1 MiB. The check is the adapter's own `skillProblems`, so a run is never refused for a skill serve took. `pi` and `codex` runs still inline every skill.
- An agent's page in the console runs the agent and shows its analytics. A run bar under the header takes an agentic agent's first message, or a workflow agent's input as JSON (prefilled with its example, else its fields empty), and an effort from the server's `features.efforts` ("default" sends none). - The server's secrets are out of every process's environment. `agentrun-serve`, the bin and the image's entrypoint, is now a small launcher. It hands the server each secret it names over a pipe and starts it with `env -u` for each, so none is in the server's `/proc/<pid>/environ` or command line. The secrets are the API token, `AGENT_MODEL_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `BROWSERBASE_API_KEY` and `OPENROUTER_API_KEY`. Before it starts any other process, the launcher moves each secret out of its environment into its own memory. The server reads the pipe first thing and closes it, and hands each run's process the run secrets over a pipe of its own, never its environment, which the run's process reads in a preload before anything else loads. In the image, PID 1 is still tini, started by the launcher. Capabilities' `secrets` says how secrets are held and the limit: in memory, they rely on the kernel refusing a process of the same user to attach (Yama `ptrace_scope` 1 or more). Operators still set the same variables. Started as `node dist/cli.js`, the server reads them from its environment, as before. The bin needs a POSIX `sh` with a builtin `printf`: Linux or macOS, not Windows.
- A data root serves one server at a time, and the server now enforces it instead of the README only saying so. A server takes `<data>/server.lock` (mode 0600) and holds it until it closes. It takes the lock after the checks that only read and refuse, such as agent homes from 0.1.0-beta.26, so a start they refuse still creates nothing. It takes it before anything that writes. A second server on the same root, in another process or in the same one, is refused before it opens a store, adopts a run or binds a port. The CLI exits 1 with one line: `agentrun-serve: another server holds this data root (<data>/server.lock): stop it, or start this one with another --data`. A crashed server's lock is released by the kernel, so the next start reuses the file. `takeServerLock(dataRoot)` and `ServerLockHeldError` are exported.
- **`/v2/stats` counts an escalated run as completed and needing review, never as failed**

Now `runs.failed` counts failed runs alone, and `runs.needs_review` counts the escalated ones. Each analytics group (totals, by harness and effort, by day, by source) counts an escalated run in `completed`, with `needs_review` beside it, under the agent and date filters too. The new fields are marked `stats/3`.

- A stopped run stays stopped until the person sends another message, whatever happens to the messages it shows. The stop is kept as a place in the run's store (`stopped_at` in the run's `serve.json`: the stopped message's id, or place 0 when the stop came before any message), and the run reads stopped while no message shown is newer. Before, it was a count of the messages shown, which a compaction changes. Now a run stopped and then compacted stays stopped, even when the compaction summarized the stopped message itself. A run that was sent a new message and then compacted back to the stop's count no longer reads as stopped. A stopped run whose compaction summarized every message it showed reads `input_required`, not `queued`. A run with no rows shown yet still reads `queued`. A stop the run refuses leaves nothing saved. A run stopped by an older server (`stopped_after`, a count) reads as before.
- A stop works on a run that is working but still reads `queued`. A message sent to a run shows in its timeline only once the run's process reports it, so right after a start, on a loaded machine, a run well into its turn could still read `queued` (state `working`), and `POST /v2/runs/{id}/stop` answered `stopped: false`. The stop now waits, up to a request's deadline, until the run's timeline shows every message sent to it, then stops the turn as it stops any working run: `stopped: true`, and the run reads `input_required`. It waits for the timeline first so that what the stop records as the person's last message is the one the turn was answering, and the stop holds once that message shows. A run that ends, is cancelled or loses its process while the stop waits answers `stopped: false`, as before.
- A stopped run stays `input_required` and `idle` across a server restart. It used to read `working` and `idle`, and when its process was gone the next server opened it again as if it still had work to do. The server now keeps the stop in the run's `serve.json`, as the count of messages the person had sent when it was stopped, so the next message ends the stop with nothing to delete.
  A server that stopped between saving a stop and its abort reaching the run left the turn working while the run read stopped; the next server now finishes that stop, aborting the adopted turn once.
- **serve no longer stalls while another process holds the agent store**
  - Every read and write of the agent store waits for a busy store without blocking the server, so other requests are still answered meanwhile. Before, one write could hold up every request for up to 5 s.
  - A request waits up to about 2 s for the store, then answers `409 home_busy` with `retry_after_ms`. A run's end keeps trying until it is written.
  - Creating an agent while the store was busy answered `409 agent_exists`, and a read answered `500 internal`. Both now wait, then answer `home_busy` if the store stays busy.
  - An edit that waits for the store is checked against the revision current when it commits, so two edits held up together cannot both write: the second gets `422` at `definition.version`, or, being the same edit, the revision the first made.
  - A workflow run that ends while the store is held waits for it as long as a run's end does, and one still held after that is settled again every 30 s, not left until the next start.

- serve's test helper `follow()` returns as soon as the run's timeline reaches the status it waits for. For a status that is not an end (`working`, `input_required`), it used to ask for one more page to confirm the status, and that long poll only answers early on a change, so each such follow waited out its whole 2 s. A page already carries the run's status and every row up to it, so the first page with nothing more to come is enough. Ends still wait for the final page. About 25 follows across the run, capacity, cap, recovery, stop, box and webhook tests are each about 2 s faster. Two tests that leaned on the extra 2 s now wait on state: the webhook test of a run adopted while it waits reads the outbox until every notice is sent, instead of sleeping 500 ms before counting ids, and the test of a reply that resolves only after its stop also checks the rows the next server reads after a restart, where the turn's process has ended, so a kept reply cannot be missed.
- When the recovery test for a stop saved before its abort reached the run fails because the follow-up never completes, its failure message now carries the run's timeline, so a one-off failure in CI can be told apart from a run that never ended.
- serve's run and lifecycle tests drop 11 tests that rebuilt a setup another test already runs, and move their checks into that test. timeline-append.test.mjs is gone: stop-compacted.test.mjs's six-message compacted run now checks that its timeline holds every message in order, plus each answer. A run whose process served and then died with its server is opened again exactly once by the next one, now checked in recovery.test.mjs's relaunch test, which replaces the same test in launch-loss.test.mjs. A released run carried back by the next server is now checked in the locked-run-store test. A torn run record is checked in the adopted-run test. A model failure's `run_failed`, message and null result are checked in the run-schema test. A follow-up after a restart is checked in the restart test of `runs.test.mjs`. The `?archived` filters and `/usage` of an archived run are checked in the first archive test. Serve's cancel mark being the one the run's guard reads is checked in the cancel-before-attach test. A reopen giving its place back to a new start is checked in the two-follow-ups test. Nothing written after close is checked in the slow-start restart test. Tests that slept so a request would reach the server first now wait for the server's own record of it: they send the request under an `Idempotency-Key` and wait until a probe under the same key reads `idempotency_mismatch`. That covers the start and the follow-ups that wait for a place, a follow-up that waits for a run's end to be written, and the follow-up and start whose run or agent is archived while they wait. The archived follow-up is now checked for 409 `not_continuable`, where before it only had to be anything but 202. The cancel-before-attach test waits for the cancel mark instead of 1.8 s of sleeps. The test of a record unreadable for over 5 s waits for the server's warning, not a fixed 6.5 s. The follow-up test no longer says "or cancelled" in its name, because `runs.test.mjs`'s cancel test checks that.
- serve's tests that start a server in a process of their own wait for the line it prints once it listens, or for its exit, never for a fixed time. The launcher tests in `secret-custody.test.mjs` and `tool-keys.test.mjs`, and the start waits in `run-metrics`, `harness-run`, `launch-loss`, `operability`, `decision-key` and `server-lock`, each polled their child's output against a clock of 10 to 120 s, so a start slowed by a loaded machine failed them as "the server did not start" though it was starting. They now share one wait in `support.mjs` that resolves on that whole line and fails at once, with what the child printed, when it exits or cannot be spawned. A 120 s backstop is left only for a child that neither prints the line nor exits.
- Three serve test areas run faster and check the same things. Eleven of the work/ read checks in `workspace-reads.test.mjs` call the workspace module straight on a scratch work/ directory, laid out as a run's, with the server's own canary file beside it. They used to start a server and finish a run first, about 7 s each on a loaded machine; now they take milliseconds. The tests that go through the file view over HTTP still use a server, and every assertion stays. The mid-map pause test in `dwf.test.mjs` uses a 300 ms fake decision instead of 1.5 s; a pause that let calls through still fails it. The retried start sweep in `box-sweep.test.mjs` uses one server and no earlier run. The start's own sweep and the first run's sweep both fail, and the next run's sweep succeeds. Locally, under load, this saves about 90 s of test time on `workspace-reads`, 9 s on the pause test and 6 s on the sweep retry.
- The two server-lock tests now spawn a process only where the test is about one. The second server, which must be refused, is still the bin in its own process: it exits 1 with its one line and leaves the data root as it was. The first and third servers run in the test's process. The crash case kills a process that only took the lock, checks that a start is refused while that process lives, then checks that the next start succeeds. Locally, under load, the two tests take about 5 s less.
- **The webhook test for a redelivery in flight no longer races the server's 15 s fetch timeout on a loaded machine**
  - The test held a redelivery unanswered while it made 50 more test sends, each writing the outbox to disk twice. On a loaded machine those sends could outlast the 15 s a try waits for an answer, so the held redelivery failed as "no answer in 15 s" and the test with it.
  - It now fills the attempt log first, then holds the redelivery while a single send pushes the message's first attempt out of the log. It checks the same things, and that the outbox on disk still keeps the message while its redelivery waits.
- The webhook test whose server dies under a waiting run starts that server in a process of its own, and now waits for it with the shared `printed` wait in `support.mjs`: it resolves on the server's whole `AGENTRUN_API_KEY=` line and fails at once, with what the child printed, if it exits. Before, it polled the child's output against a 20 s clock, so a start slowed by a loaded machine failed the test as "waited for the server's banner" though the server was still starting.
- Install and `npx` commands in the READMEs and docs name `@latest` instead of `@beta`. Releases publish under npm's `latest` tag, and `beta` was not moved with them: it still pointed at 0.1.0-beta.21 while `latest` was 0.1.0-beta.28, and `@parcha/pi-durable-agent`, `@parcha/pi-git-remote` and `@parcha/pi-agent-learn` had no `beta` tag at all, so their install lines failed. The harness demo's hint for a missing `@parcha/pi-transport` names `@latest` too. `@parcha/agentrun-harness` is not on npm yet (its `latest` is a placeholder), so its README says it is held and installs it from a packed tarball. The README's Render option gives measured memory: a Starter's 512 MB runs about 3 pi agents at once, and Claude Code or Codex runs want a 2 GB instance. The stranger check reads the install line as `@latest`, installs `@latest` with `--registry`, and walks the keyless examples against the registry's `latest`. The release guide drops the step that moved `beta` after a release; `beta` is kept only for older links, with the one-time command to bring it up to a release.
- A server built without its console says, at `/`, that the repository's `npm ci && npm run build` builds it, as the README now does. The README's Webhooks section says a receiver may be on your own machine or network: loopback and private-network addresses are allowed.
- The README's "Spend cap" section no longer says a capped `claude-agent` or `codex` run cut mid-request refuses its next request: those runs also continue after a cut, at the worst case the cap held, as pi runs do.
- The serve README has a sandbox in 60 seconds near its top: pull the box's image, start the server with `AGENTRUN_BOXES=docker`, make an agent whose place is a Docker box with `bash`, `write` and `read`, run it, watch its timeline, and read the file it wrote from `GET /v2/runs/{id}/files`, with a no-key variant on a three-line faux model. The root README points to it.
  - The sandbox text is one section: the place, the boxes, a run in a Docker box, the box's image and the published image, where it was spread over about 490 lines.
  - `AGENTRUN_DOCKER_IMAGE` has its own part: the default `debian:bookworm-slim` has no python or git, and a box has no network, so it says how to pick or build an image that has them.
  - It says plainly that the published image cannot host boxes yet (no docker command, no daemon), and why mounting the host's Docker socket into it is no way around that.
  - The tools table lists `bash`, and the places that still said a run has no shell (the tools, a run's life, safety) say it runs only in a box.
