## 0.1.0-beta.57 (2026-11-24)

**Breaking:**

- The harness's Claude login (`ClaudeAgentLogin`) no longer has the `shared` flag 0.1.0-beta.56 gave it. Every status check now runs the CLI on a copy of the account file, as a check on a login marked `shared` did, so the flag has nothing left to choose. A host that set it drops it. TypeScript flags `shared` in a login written as an object literal as an unknown property; from JavaScript it is ignored. <!-- changes/claude-login-no-shared.md -->
- `startClaudeLogin` no longer takes a `home` option. A host that calls it with `{ home }` sets that home on the login as `userHome` instead (`startClaudeLogin(cli, { ...login, userHome: home })`); the status check and a run on macOS read the same field, so one home serves all three. TypeScript flags a `home` option as an unknown property; from JavaScript it is ignored, and the sign-in runs in the login's own `home`, else the OS's home. <!-- changes/claude-login-start-home.md -->
- `claudeLoginStatus` no longer takes a `home` option. A host that calls it with `{ home }` sets that home on the login as `userHome` instead (`claudeLoginStatus(cli, { ...login, userHome: home })`); the sign-in and a run on macOS read the same field, so one home serves all three. TypeScript flags a `home` option as an unknown property; from JavaScript it is ignored, and the check runs in the login's own `home`, else the OS's home. <!-- changes/claude-login-status-home.md -->

**Changes:**

- `web_search`'s default, `auto`, is now agentrun's own search on every harness: Parallel where the server holds a Parallel key, else keyless Firecrawl with keyless Exa behind it. Before, `auto` on codex was Codex's own live search, and on pi with a direct `anthropic/*` or `openai/*` model it was one request to that provider's hosted search. Both now go through agentrun's `web_search` instead. This changes what a codex or pi search costs and returns: Parallel's fee per search on the server's key, or keyless Firecrawl at no charge, in place of the provider's per-search fee, and those providers' results in place of Codex's or the model provider's. <!-- changes/web-search-auto-ours.md -->
  `native` stays a provider you can pick, for an agent (`definition.tool_settings`) or the server (`PUT /settings/tools`). Picked, it still turns on Claude's WebSearch, Codex's live search or pi's hosted search, and it is unavailable where it was before (behind a gateway, on OpenRouter, under a spend cap). To keep the old behaviour on codex or pi, pick `native`. claude-agent's `auto` is unchanged.
  The openapi document's `web_search` provider list is unchanged (`native` stays in it). Only `auto`'s description and capabilities' `resolves` and `why` change: on codex and pi, `resolves` reads `parallel` or `firecrawl-keyless` where it read `native`. A run that started before the upgrade keeps the plane it launched with, `native` included, for its life.
  A claude-agent session now also names the claude CLI's WebFetch in its `disallowedTools` (`CLAUDE_AGENT_ALSO_OFF`), as it names WebSearch. WebFetch was already off three ways: the session's tools list is empty, the PreToolUse hook denies it, and the CLI's sandbox network is deny-all. Naming it keeps the host's `web_fetch` the session's only fetch even if one of those changes.
- A claude-agent run on a clock the host set (the adapter's `now`; in serve, a template eval case's `now:`) is now told that clock's day by the Claude CLI too. The CLI dates the session from the machine's clock in its own lines ("Today's date is 2026-11-24.", and "Today's date is now ..." on a later day), and has no setting for it. On a case clock set to another day, the model was told both days and went by the CLI's, so every date a grader checked against the case clock failed. The session's model proxy now rewrites those two lines to the clock's day in the run's zone (`zone`), in the CLI's own `system` message only, where the CLI puts them. The person's prompt, the model's replies, tool results and the app's system prompt are never rewritten, so a date someone wrote, quoted or read reaches the model as it was. A run with no `now`, which is every production run, is unchanged. <!-- changes/claude-agent-case-clock-date.md -->
  A session on a person's Claude login has no model proxy, so there the CLI's lines keep the machine's date. Run clocked cases on the provider route (an API key or gateway).
- Settings → Model keys' login on this machine: fixes to the claude CLI's sign-in and to its status check. <!-- changes/claude-sign-in-followups.md -->
  - The line shown for "this machine's" login on the CLI's default folder starts a CLI whose path holds `=` (a data folder such as `/data/a=b`): it still clears the CLI's folder variables with 0.1.0-beta.56's `env -u CLAUDE_CONFIG_DIR -u CLAUDE_SECURESTORAGE_CONFIG_DIR ...`, and such a path goes to `sh -c 'exec "$0" auth login'` as its `$0`. Before, env read that path as one more variable, and the CLI never started. The line runs alike pasted into sh, bash, zsh, fish or tcsh; env skips a `claude` alias or function of the person's shell.
  - `PUT /v2/settings/claude-login` that moves the login to the other `place` ends a sign-in the server started that still waits, and answers once its CLI is gone; before, that CLI kept waiting to sign in at the old place. A `PUT` at the same place leaves it waiting. A move or a turn-off that lands while a sign-in is starting now waits for that start and then ends it, or comes first, and the sign-in starts on what it saved; before, the sign-in could start after it with the old setting, at the old place or for a login that was off.
  - "This machine's" login honours `CLAUDE_SECURESTORAGE_CONFIG_DIR` in the server's environment, as the person's own claude CLI with that variable does: the status check, the sign-in, the shown line and a run keep the tokens in that folder (on macOS the Keychain item named from it). Set and empty, it means `~/.claude` and, on macOS, the Keychain item with no suffix, which the CLI gets as an empty value there. A relative value is not taken. The view says it as `machine.credentials`, and the console names it under the folder. Before, the server ignored it and read the tokens from the config folder, so a person whose CLI sets it read signed out. The harness's login takes `secure` and `unsuffixed` for it, and `claudeSignInEnv` and `claudeLoginCommand` take the platform, as `claudeLoginEnv` does. A run with the CLI's own sandbox on denies its commands reading that folder too, as it does the login's own folders; on macOS an empty value names a Keychain item, and adds nothing.
  - The sign-in's CLI dies with the server that started it: `startClaudeLogin` starts it under the kernel's parent watch (`parentWatched`: the parent-death signal through `setpriv` on Linux, else the watching shim), as a session's CLI is. Before, a server killed outright (SIGKILL, the OOM killer) left `auth login` running with no limit, holding the browser's callback port. A CLI path that is no program still reads as never started, in the spawn's words. `startClaudeLogin` takes `watch` to choose the watch. A sign-in stopped or ended at its limit under the shim ends only once its CLI is gone, though the CLI ignores SIGTERM: the shim kills it 2 s after passing the TERM on, before the server's own kill 5 s after it, which reaches the shim alone.
  - The login's setting names the machine it was turned on for by an id the server makes once in its data folder (`machine-id`, 0600) and reads back on every later start, in place of the hostname. Before, a laptop's hostname changed with its network, so a login turned on at home read "turned on for another machine" elsewhere, and its runs asked for a key. Two data folders are two machines.
  - Settings → Model keys: Turn on says why it is grey while "Only I run agents on this server" is not ticked, beside it and as its description for a screen reader.
  - The Playground's "No model yet" bar is gone for an agent on Claude Agent (`claude-agent`) while the login is on and reads signed in, since Claude Agent runs on it. Before, it offered ChatGPT or a key as if no model were there. An agent on another harness keeps the bar. The bar reads the revision picked in the Playground, which the run will use, and the agent's current one when none is picked; a picked revision whose definition the console does not hold keeps it. The bar stays for a run in a sandbox box, by the revision's own place or the server's default one, since only a run on the runner uses the login. It stays too for a revision that names a model the login does not serve: only Anthropic's own models (or none) run on it, and an OpenRouter model, Anthropic's included, still needs `OPENROUTER_API_KEY`. The console reads the login once, again on leaving Settings (where a sign-in finishes) and after a run starts, never on each move between pages, since each read runs `claude auth status` on the server.
  - The status check copies the account file only when it is a regular file of at most 32 MiB, read without holding up the server: it opens the file without waiting (`O_NONBLOCK`) and checks what it opened before reading. Before, a FIFO in its place stopped the whole server until something wrote to it, and a device such as `/dev/zero` or a huge file was read whole into memory. A FIFO, a device, a folder or a bigger file is copied as nothing, as a file that doesn't parse is. A link is still followed, since dotfile managers often link `~/.claude.json`.
  - Every status check runs the CLI on a copy of the account file in a folder of its own, AgentRun's own login folder included, never on the file itself, so a check never has the CLI rewrite the login's `.claude.json`. In 0.1.0-beta.56 the check on AgentRun's own folder, and on any harness login not marked `shared`, read the login's folder as its config dir, as that release's entry says; none does now. The harness login's `shared` flag is gone (see its breaking entry).
  - A server sweeps the status checks' folders (`agentrun-claude-status-*` in the temporary folder) as it starts, when the Claude login is allowed on it: the ones this user owns whose check has ended: each check writes in its folder when it ends at the latest (its limit, whatever the caller gave, and 2 s), and the sweep takes the folder more than 15 s after that; a folder with no such end, or one that lies before its file was written (empty, a partial write, a negative), is taken once changed more than twice the status check's limit ago. `claudeLoginStatus` throws a `RangeError` for a `timeoutMs` that is no whole number of ms from 1 to 2^31 - 1, before it starts the CLI. A check that was killed mid-way (SIGKILL runs no clean-up) left its folder, with a copy of the account file in it, until the machine cleared its temporary folder. The harness exports `sweepClaudeStatusFolders`.
  - The status check ends at its limit whatever the CLI does: it asks the CLI to go (SIGTERM), kills it (SIGKILL) 1 s later, and waits at most 1 s more for the CLI's output, then reads as timed out. Before, it sent one SIGTERM and waited for the output's pipe to close, so a CLI that ignored the TERM, or a process it started that held its output open, kept the check, and the run's claim behind it, waiting for ever.
  - The person's home is read once, where the server makes the login (the server's `HOME` when it is an absolute path, else the OS's home), and the status check, the sign-in and a run on macOS all take it from the login's new `userHome`. Before, the sign-in took the server's `HOME` while the status check and a run took the OS's home, so a server started with another `HOME` signed in at one home and checked another. `claudeLoginStatus` and `startClaudeLogin` no longer take the `home` option 0.1.0-beta.56 gave them (see their breaking entries).
  - A Claude-plan run no longer fails because the login's status check was slow. On a loaded machine the claude CLI could take longer than the check's 15 s, and the run was refused as "could not say whether its login is signed in" though the login was fine. Now a check that gives no answer (the CLI outlasts it, or answers nothing that reads as a status) is asked once more; if that one gives no answer either, the run goes on when the same login read signed in within the last 10 minutes on this server (at a run's check or in Settings), and is refused as before otherwise, in words that say why (a check that timed out says so, and after how long). Any other failure of the check, such as no CLI at its path, refuses the run at once in its own words, as before. A signed-out answer still refuses the run at once, and is never asked again. The harness's `claudeLoginStatus` throws `ClaudeLoginTimedOut` (`code: "timed_out"`) when the CLI outlasts its limit, and `ClaudeLoginNoStatus` (`code: "no_status"`) when it answers in time with no status.
  - On macOS, a run on the login runs in the person's home, so the claude CLI writes its cache and logs under their `~/Library/Caches/claude-cli-nodejs`, where they stay after the run. Removing that folder is safe.

## 0.1.0-beta.56 (2026-11-24)

- Settings → Model keys' "Open the CLI's sign-in here" signs the claude CLI in at the login's own folder, so the login reads signed in afterwards. The sign-in ran with a temporary config dir, where `auth login` wrote the account it signed in (`.claude.json`); that folder was removed when the sign-in ended, and the login's folder stayed without it, so AgentRun kept saying "not signed in" while running the shown command by hand worked. The sign-in, the shown command and the status check now take their variables from one function (`claudeSignInEnv`), and the status check reads the login's folder as its config dir. <!-- changes/claude-sign-in-folder.md -->

The console shows "Waiting for the browser…" from it, after a reload too. A sign-in no browser answers within 10 minutes is ended and says so, with the button to start it again; before, it ended silently and the browser's page then failed to reach it. A second press, turning the mode off, or stopping the server ends a sign-in that still waits; the stop waits for its CLI to exit, so no CLI keeps the browser's callback port from the next server.
  - The view names the folder it asks about (`folder`), and this machine's own login folder for the claude CLI (`machine`). That folder follows the CLI's rule: `CLAUDE_CONFIG_DIR` when the server's environment sets it to an absolute path, else `~/.claude`. Before, AgentRun set both dirs to `~/.claude`, which reads `~/.claude/.claude.json` (where the person's CLI keeps no account) and, on macOS, a Keychain item named from that folder rather than the person's own (the one with no suffix), so it read signed out there while the person's CLI was signed in. The harness's `claudeLoginEnv` takes the platform (this host's by default), and its login takes `home` for this place. A login in a `CLAUDE_CONFIG_DIR` folder keeps both dirs set to it, which is where the person's CLI with that variable keeps its login.
  - The status check on "this machine's" login (either folder) never runs the claude CLI on the person's own account file. The CLI rewrites `.claude.json` on every start whose config version is not its own (and the first time adds `settings.json`, a backup and a lock beside it), so asking it in place rewrote the person's file on every view, every 2 seconds while a sign-in waited, and at every run's start. Each check now copies the file (opened only to read) into a folder of its own, gives the CLI that folder as its config dir and the tokens as a run reads them, and removes the folder however the check ends. The copy leaves out the fields that hold secrets (`primaryApiKey`, the API key an older CLI signed in with; `env`; every `mcpServers`), and a file that doesn't parse as a JSON object is not copied; a run's config dir has none of them either, so a login whose only key is that `primaryApiKey` reads signed out, as a run on it would be. The harness's login takes `shared` for this place, and `claudeLoginStatus` takes the platform.
  - On macOS a login read signed out in AgentRun, and its runs failed in about 2 seconds with "signed out", while `claude auth status` in a terminal said signed in. The CLI reads its tokens there from the login keychain, which is under the person's home, and the status check ran AgentRun's own folder and a `CLAUDE_CONFIG_DIR` folder in a temporary home, and a run in the session's. The status check now runs in the person's home (the server's `HOME`) on every place and platform, keeping each place's credentials dir, which names the Keychain item ahead of the config dir; a run on the login on macOS gets that home too, its config and other dirs still the session's. `claudeLoginStatus` takes `home`, as `startClaudeLogin` does.
  - The harness's `startClaudeLogin` returns the sign-in (`ended`, which says how it ended, and `stop()`) in place of nothing, and starts the CLI in the person's home rather than a temporary one when no home is given.

## 0.1.0-beta.39 (2026-11-16)

- A capped Claude Agent run on a Claude model reached through a gateway (Sonnet 5.5 through OpenRouter) no longer stops at its second step with most of its cap left. The provider's count is asked for only at Anthropic, and no local tokenizer counts Claude, so each request was bounded by its bytes: about four times its tokens. An inbox agent's second request read as about 32,000 tokens, so at a $0.10 cap the step after one that cost $0.01-0.02 "needs at least $0.10" and the run paused, where a real step costs about $0.03. The model proxy now keeps each model's last request whose answer reported its whole input, and bounds a later request that carries it unchanged by that billed input plus the bytes of the messages it adds, when that is lower. That request must match the earlier one in everything that bills input apart from the added messages (system, tools, thinking, effort, model); a moved cache marker (a `cache_control` key on a tool, a system or message content block, or a block of a tool result's content) does not count as a change, and a `cache_control` key anywhere else is compared as text. The wrap-up note is asked for on that bound. A first request, a request that changes its tools or prompt, one that adds a document, or one that offers the hosted search keeps its byte bound, and a step that does not fit is still refused.

  pi on a Claude model takes the same bound, through the same policy. Through a gateway, the smallest cap that takes a pi desktop run on Sonnet through its four screenshots to its answer goes from $0.12 to $0.09, the same as straight to Anthropic: the run needs $0.082, where it needed $0.110 on its bytes. Its first request keeps its byte bound ($0.052).
- A capped run on a model whose tokenizer is o200k_base, reached over Messages without Anthropic's count (pi on GPT-6.1 Sol through OpenRouter, sent through serve's translation), bounds each request's input by a local count with its stated margin, as a Responses request to a gateway already does. Before, its bytes were the bound: after a few long pages the body passed 272,000 bytes, every rate was priced at Sol's long-context tier, and a $1.50 run stopped at $0.10-0.27 because the cap refused to send a step it could pay for. A Claude model, a body with a document, or one that offers the hosted search keeps the provider count or the byte bound.
  When a run's cap is below what its model needs for one more step and an answer, the wrap-up's words now say so with both amounts, and the effort the model's request asked for when it named one ("This run's cap of $0.25 is below what gpt-6.1-sol at medium effort needs for one more step and an answer, about $0.32."), so a run that stopped its tools at its first call shows the cap was the cause. The rule that decides when a run wraps up has not changed.
  Saving an agent with a cap below that figure (POST /agents, an edit of its definition, or a package install with a per-run budget) now saves with a warning on `definition.max_cost_usd` ("This agent's cap of $0.25 is below what gpt-6.1-sol at medium effort needs for one more step and an answer, about $0.32: a run will wrap up at its first tool call."). It is never refused. The figure is priced on the first request the agent's harness sends: the harness's own input before the agent's prompt (Codex about 12,200 tokens, from billing; Claude Agent, OpenCode and pi measured on their pinned builds, each stated beside its pin), the agent's prompt where the model's tokenizer is o200k_base, and the least output at the agent's effort, its thinking included: a pi agent on a Claude model that thinks with a budget is priced with Claude's 1,024-token thinking minimum, as its first request asks for it.
- A claude-agent session with skills now tells its model that the Skill tool is its own and when to load a skill. The tools note said the app's `mcp__hands__` tools were the model's only ones, so a model that read it had no reason to call Skill, and template agents often skipped their SKILL.md. Measured on two watch templates (Claude Sonnet 5.5, 6 runs each): skill loads went from 2 of 6 and 0 of 6 to 6 of 6 and 4 of 6.
- A run's environment line now tells the date in the run's time zone, by weekday, day, month and year, and names the zone (`Today is Sunday 15 November 2026 (America/Los_Angeles).`), where it told the UTC date, a day ahead of the person's in an evening west of UTC. A run a schedule trigger started takes that trigger's zone; every other run takes the server's zone (`TZ`), and a zone the server does not know reads as UTC. The line carries no hour, so it changes once a day and the prompt cache holds within the day. A template eval's clock line to its graders says its date the same way.
- OpenRouter runs book what OpenRouter charged; routers need no cap or a read-back cost; a provider's error inside a stream is booked by what it reported.
  - A request on an OpenRouter model is booked at the cost OpenRouter states in the answer's usage (with your own provider key, its fee plus the provider's charge). The price table's figure is kept beside it (`tableUsd`). A cap still holds each request at list price before it leaves. A stated cost that is missing, not a number, or above that hold is not used: the table's figure is booked instead.
  - OpenRouter's routers (`openrouter/auto`, `openrouter/free` and the others) have no price here, because the model they pick is not known in advance. A run with a spend cap is refused before it starts. A run without one is booked at the cost OpenRouter reports, else unknown, never $0.
  - A provider's error inside a successful (200) stream (Anthropic's `overloaded_error`, `api_error` or `rate_limit_error`, OpenRouter's mid-stream errors, a Responses `response.failed`) is booked by one rule. If the stream reported tokens before the error, they are booked at list price, or at the cost OpenRouter stated, and the run's cost stays known: before, such a request was booked at the cap's hold and made the run's cost unknown. If it reported no tokens, it is booked as refused at $0, and the run's record keeps the provider's message (`refusal`, or `providerError` beside a booked figure). That holds only while the model generated nothing: once the stream shows the model began its output (a content block, a Responses output item, hidden reasoning included, or a text-tools model's reply the runner had not sent yet), an error with no usage is booked at an unknown cost, never $0.
  - Kernel: `startModelProxy` books a cost stated in the answer's usage when its origin is OpenRouter's or serve's translation route's (`statesUsageCost`, `ROUTE_ORIGIN`), on every harness: claude-agent, codex and opencode runs on OpenRouter book what OpenRouter charged too. `Ended` gains `tableUsd` on an answer, `{ end: "answered", label: "error", reason }` and `{ end: "nothing", label: "refused", reason }`. `bookRequest` books the table's figure (rule `answered:over_hold`) when a reported figure is above the hold. The claude-agent policy's usage reads a stream that ends in an `error` event as whole. Routers and in-stream errors are handled on those harnesses too.
- On Claude Agent, a tool call that ran beside a call waiting for approval keeps its result. Before, when one answer from the model made two MCP calls, a read that runs on its own and a write that asks, and the run paused on the write, the read's result was lost once the run went on. The model was told the read was interrupted, so it ran the read again.
  - The read had finished and its result was in the run's journal, but the Claude Agent CLI had not written it to its own transcript before the pause let it go. On the resume, every call left without a result in that transcript whose end the journal holds now gets that recorded result before the CLI starts again. Nothing runs twice and nothing is asked again.
  - A call the pause or a crash cut off before it ended is answered as interrupted, as before. A call the pause held before it started still runs once it is approved.
  - The same rule covers every CLI harness that resumes from its own transcript (Codex, OpenCode). Codex already kept the result in its own transcript.

## 0.1.0-beta.38 (2026-11-14)

- A run's MCP tools are host tools on every harness: each call passes the run's one tool gate before anything is sent, and the runner calls the server with the credential, books the call and records it, as it does any host tool. opencode now runs MCP tools (`features.mcp_client.harnesses` lists it, and an opencode agent granted `mcp:<server>/<tool>` saves and runs). claude-agent offers a granted tool as `mcp__hands__mcp__<server>__<tool>` and codex as `mcp_<server>__<tool>` (Codex refuses a dynamic tool named `mcp__*`); the Timeline, tool settings and approvals still name it `mcp:<server>/<tool>`. On a code-mode Codex model, a script's tool call held for a person's approval runs once on their allow, under its own call id, and the script's cut-off `exec` reads its result (or, when the `exec` had yielded, the model's `wait` on its cell); before, the resume told the model the call may have run, and the call the model made again asked again, so the allow never reached a call.

  Who breaks: a run parked on an MCP call at the MCP door before this version does not resume its call: cancel it and start it again. The kernel's tool bridge, which every host tool's result passes on its way to Claude Agent or Codex, keeps a longer one's start, cut where a character ends, ends it with a line saying where it was cut (`[cut at N of M characters]`), and flags the call's `tool_end` `truncated: true`; the call's record keeps the whole result. On a Codex resume, a call the rollout left unanswered is answered from that record with the same cut. A skill file read with `read_skill_file`, a delegate's answer and a rejection listing every schema error reached the harness whole, however long (a 1 MiB skill file, a 6 MB answer).
- The model proxy now tells the host, before a paid request is sent, the most input tokens it can be billed for. A spend cap could only count a request's cost once it was billed, so a single request whose input alone was over what was left of the cap was still sent and paid. `beforeRequest` now carries `inputTokensMax`: the UTF-8 bytes of the body exactly as it is sent, plus the input the provider adds that the body does not carry. A byte-level BPE token covers at least one byte, so this never undercounts the body, however dense its text. Each `inFlight` entry carries its own `inputTokensMax` until that request answers, so a cap can hold every open request at its own bound. When the provider's addition cannot be read, `inputTokensMax` is undefined, never 0, and a cap treats that input as unknown.
  - What a provider adds is in one place, `providerInputOverhead(api, shape)` from `@parcha/agentrun-kernel/host`. `api` is pi's API kind, and `shape` is whether the request has tools, its tool_choice and its image count. Each figure is the largest the provider documents for any current model:
    - `anthropic-messages`: the tool-use system prompt the Messages API adds to a body with tools, 675 tokens for tool_choice auto or none and 804 for any or tool, plus 4,784 tokens for each image, its high-resolution tier's maximum.
    - `openai-responses`, and the Azure and Codex Responses kinds: no prompt of their own, and 73,800 tokens for each image. That is 30,000 patches, the most an image may have, times 2.46, the largest model multiplier.
    - `openai-completions`, which OpenAI-compatible gateways speak too: nothing for its per-message formatting, since the body's bytes already bound it; 804 tokens when the request has tools, whatever its tool_choice, the largest Anthropic tool-use prompt, since a gateway may route to an Anthropic model; and 73,800 tokens for each image.
    - Every other API kind, among them pi's `mistral-conversations`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex` and `pi-messages`, and a faux `faux:<id>`: nothing for text, an assumed 2,048 tokens when the request has tools, and 73,800 tokens for each image. The tool allowance for these kinds is assumed, not documented; it is documented only for `anthropic-messages`, the OpenAI Responses kinds and `openai-completions`. `providerInputOverhead` never returns undefined: only a body that cannot be measured is unmeasured.
  - Images are billed by their area, not their bytes, so a small compressed image of large dimensions is counted at its maximum. A Codex body with a file input (a PDF, billed by its pages) is left unmeasured.
  - A provider policy says what its provider adds with `serverInputOverhead(body)`. The Claude and Codex policies read their body's shape and use the figures above.
  - The faux adapter in `@parcha/agentrun-kernel/testing` measures its prompt's UTF-8 bytes for each request, as a real adapter's proxy measures its body.
  - `inputTokensMaxOf(policy, body, sent)` is exported from `@parcha/agentrun-kernel/host`.
  - The proxy serializes the body once before admission and sends exactly what it measured. A body that cannot be serialized is refused before the runner is asked, so it is never booked.
- A Claude or Codex turn stopped while the session was still recording the person's message stays stopped. Before, the stop found no turn running, so the session read idle, and the stopped message stayed pending and was sent with the next message. Now a turn that ends on its session's stop leaves the session reading `open_turn` while that message is pending, so serve's stop settles it, and it is never sent.
- A Claude or Codex turn the person stopped stays stopped when the run's process is replaced. Before, the next process found the stopped turn still open in the session and resumed it: it ran its tools and paid for its model requests again, and its answer came before the person's follow-up. Now serve's open reads the run's stop record and settles that turn, ended `interrupted`, with nothing sent, and the follow-up is a turn of its own. A turn a crash or a drain cut is resumed as before.
  - A stop that lands before the harness took the person's message withdraws that message too, so it is never sent later: not with the follow-up in the same process, and not by a process that replaces it.
  - `AdapterSession` has `settleOpenTurn()`: it records the open turn as ended, interrupted, withdraws the input the turn never placed, and sends nothing. The Claude Agent, Codex and faux adapters implement it. A harness that runs as a child process does both with `settleTurn(drive)` from `@parcha/agentrun-kernel/process`. An adapter written outside this repository without it keeps the old behaviour: its stopped turn is resumed.
  - After `interrupt()`, the Claude Agent and Codex sessions read `open_turn` while the stopped turn is still open in their records. serve's stop settles it there; a runner's pause leaves it for the next process to resume.
  - When the earlier process died before it wrote the stopped turn's end, the next one writes it, `interrupted`, before the follow-up's turn starts.
