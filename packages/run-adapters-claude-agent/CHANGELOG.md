## 0.1.0-beta.31 (2026-11-06)

- Agents call a saved MCP server's tools on pi and claude-agent: grant `mcp:<server>/<tool>` in `definition.tools`. A save checks the name against the server's saved tools (`422` naming them). A run's first launch pins the granted tools as saved and the server's URL; its credential reaches only runs that grant one of its tools, over the run's secrets pipe. pi binds each tool in the run's process; claude-agent's own MCP client calls it at the session's model proxy (`/mcp/<server>`, behind the session key), so the CLI never holds the credential. A call follows no redirect, a crash-cut call is answered interrupted and never sent again, a moved server is sent nothing, and the timeline reads `<server> · <tool>`. `features.mcp_client.harnesses` lists the harnesses that run them. Every call passes the run's tool gate and its spend cap.

## 0.1.0-beta.30 (2026-11-05)

- A run whose model provider stops the answer on its content filter now ends `failed` with `error.code` `moderated` and
  says so in plain words: "The model provider stopped this answer (its content filter). Rephrase the request, or try
  another model." Before, it ended `run_failed` with the provider's jargon ("Response incomplete: content_filter"). The
  Timeline's error row keeps the harness's words for the stop (pi-ai's on pi, the kernel's on claude-agent and codex). On pi the run reads pi-ai's words for the stop on each API. On
  claude-agent and codex the session's model proxy reads the provider's stop (Anthropic's `refusal`, an OpenAI answer
  `incomplete` for `content_filter`) and the harness ends the turn at once: the CLI no longer asks for the refused answer
  again, turn after turn. Only the turn's own answer request ends it: a side call the CLI makes beside the turn (one
  without the session's tools) that the provider stops is logged and left to the CLI. The refused request is booked at
  the usage its end reports. The kernel exports `CONTENT_FILTERED`, the text such a turn ends with; a provider policy may
  say a stop through `filtered` and a side call through `answers`, and the model proxy tells its machine through
  `onFiltered`.
- A request you stop under a cap counts the reasoning it never streamed. A model whose reasoning streams only as a summary (the Responses API's reasoning, Claude 4-class thinking) is billed for far more than the summary's bytes. A stop after about 10,000 hidden reasoning tokens on a gpt-5-class model with a 20 KB context cost about $0.106 and counted $0.038, so deliberate stops could pass a cap. A stopped request that reasons now also counts the part of its reasoning budget that did not stream: input + streamed + 1,024 + max(0, reasoning budget - reasoning streamed), never more than its hold. Real usage still replaces the figure when it comes.
  - **On pi:** a reasoning model's stopped request counts its thinking level's budget (on Anthropic's API, the `budget_tokens` it was sent with, for a model whose thinking takes one). A Claude model that thinks adaptively (every current one on Anthropic's API) is sent no budget, and its thinking is bounded only by its output limit, so it counts that limit less 1,024 tokens: in practice its hold. A stop after a 300-byte thinking summary on Sonnet 5.5 with a 20 KB context under a $1 cap counted $0.142 at medium and $0.224 at high, against about $0.45 for 40,000 adaptive thinking tokens. The request's output limit is now the one actually sent: the cap had taken a thinking budget out of it that pi-ai never sends (8,192 tokens at medium), so the request was held at more than it was sent with. With no level, on an API whose model reasons at its own default, it counts its whole output limit. With thinking off on Anthropic's API, on a model whose thinking can be off, nothing more.
  - **Adaptive thinking counts up to the hold.** On every current Claude model, on pi and on `claude-agent`, the provider is given no thinking budget, so a stopped request counts up to the hold the cap took for it. Under a cap with little left beside that hold, the request after the stop can be refused.
  - **On `codex`:** the effort's budget (minimal 1,024, low 2,048, medium 8,192, high 16,384), none at effort `none`, and the output limit when the body names no effort.
  - **On `opencode`:** the same as `codex` (the same Responses API): what a stop counts as streamed is the content its deltas carried, not the wire, plus the unstreamed part of its effort's budget. On the walk through OpenCode's proxy (a request at $100 a million output tokens under a $0.50 cap, stopped after 1,146 characters of answer text after the stream's echo of the request) the stop booked 106,831 bytes, its whole $0.50 hold, and refused "Go on."; it now counts $0.217, and "Go on." goes.
  - **On `claude-agent`:** the thinking budget, or `max_tokens` when thinking is adaptive, for every request that thinks; none with thinking off. Thinking that streamed is subtracted, so a stop after a budget's worth of visible thinking counts nothing on top.
  - **Kernel:** a provider policy may read a request's hidden reasoning from its body (`reasoningHidden`). It may also read the reasoning in each streamed event (`reasoningBytesOf`). The model proxy books a stopped response with both (`stoppedHiddenTokens`, `stoppedReasoningBytes`), and the runner counts all it sent plus the part of the budget its reasoning did not cover.
  - **What streamed is the content, not the wire.** On `claude-agent` and `codex` a stop counted the response's bytes as sent, the provider's framing included: about 11.7 bytes a character of text on the Responses API and 24 on the Messages API. A codex request at $100 a million output under a $0.50 cap, stopped after 1,146 characters, booked its whole hold and refused "Go on.". It now counts each text, reasoning and tool-argument delta's UTF-8 bytes, as pi counts its streamed blocks: $0.217, and the next request goes. A provider policy reads them (`contentBytesOf`).
  - **A stop before the provider's first header** on `claude-agent` and `codex` now counts as a stop with nothing streamed (its input and 1,024 tokens, as on pi), not its whole hold. A response the provider answered with an error status still counts at its hold.
- A message the person stopped the instant it was sent is no longer lost on claude-agent, and the same window is closed on Codex and OpenCode. Asked "Reply with exactly this code and nothing else: CARRY-CLAUDE-7", stopped within its first second, then told "Go on.", a claude-agent run answered "There's nothing earlier in this conversation for me to continue from": Claude takes a message within its first second, so the stop landed after the harness placed it and before the CLI was handed it, and nothing carried it. Now a stop's settle carries a placed message its CLI never took into the next one, as it carries one stopped before it was placed. On claude-agent that is a message the CLI's own transcript, as the session keeps it, does not hold: that transcript is the history a resumed CLI is given, so a carried message is never sent twice. On Codex it is a message Codex's own rollout, as the session keeps it, does not hold. OpenCode marks a message just before it sends it (`prompt_async`), and a marked message is never carried: a crash between the mark and the send loses it rather than sending it twice. After a stop, no new turn is started.
  - **A recovered message is not carried again.** After a crash between a message's placement and its CLI's record, the recovery message carries its words. It now records which messages it carries, before it goes (a kernel effect by its id on claude-agent, its `PROMPT_STREAM` record on OpenCode). Once the CLI holds the recovery message, a stop's settle and a later recovery both count those messages sent, so nothing is sent twice, even after a second crash. Codex's recovery already did this through its client id.
  - **A follow-up's own prompt** (the host's, named to the settle) is withdrawn and never carried into the person's next message, as the follow-up says: a host prompt that never ran is not sent. A person's message waiting beside it is left as it is.

## 0.1.0-beta.29 (2026-11-04)

- `ClaudeAgentNotInstalled` says, in one line, what is missing and how to install it: the message keeps its prefix ("Claude Agent SDK not installed"), names the SDK, its platform package with the CLI, or the MCP library it brings as a peer, and ends with `; install it with: npm install --save-exact @anthropic-ai/claude-agent-sdk@0.3.286`, which is also on the error as `install` (and exported as `CLAUDE_AGENT_SDK_INSTALL`). A `cliPath` that holds nothing keeps its own message, with no install line. A host that matched the whole message exactly now matches its prefix.
- A host's gateway headers reach the provider on every model request a Claude Agent session makes: `claudeAgentAdapter({ provider: { ..., headers: { "x-litellm-tags": "job:...,purpose:...,run:..." } } })`, the same LiteLLM spend-tag header a pi lead's model requests carry, so a gateway attributes the Claude lead's spend to its job. The session's model proxy (`startModelProxy({ headers })` in `@parcha/agentrun-kernel/host`) adds them to every forwarded request, paid and free, after the client's own headers (so the CLI can neither set nor override them) and before the credential's. They are checked when the adapter is made (`hostHeaderProblems`): a token name that is not the proxy's own (`authorization`, `x-api-key`, `host`, `content-*`, `anthropic-*`, ...), and a one-line value of at most 1024 characters. A host sends a gateway's headers only to that gateway.
- A call the CLI turns down itself (a tool the session doesn't have, a built-in that is off) reaches the host as a failed call by its name, with the model's input, and the adapter logs it once with the CLI's reason. The host hears it only once the CLI's answer is in the session's store, as a tool's `tool_end` waits for its outcome. An answer that does not reach the store within `barrierMs` leaves the call unshown, and the adapter logs `a refused call is not shown`. A call the session's tool server ran is never taken for one the CLI turned down, whatever its error text, so it is heard once.
- A host's skills reach the Claude Agent model: `claudeAgentAdapter({ skills: [{ name, files }] })`. Each session writes them as a local plugin in its own private directory and starts the CLI with that plugin and those skills alone (as `agentrun:<name>`), still with no settings sources, so the CLI's bundled skills and any skill in a home directory are neither listed nor loadable. With skills the model is offered the Skill tool, which the session's tool proxy now lets through; without them it is not. A loaded skill survives a crash: it is part of the history the session store restores. The skills are checked when the adapter is made (`skillProblems`): plain names, a `SKILL.md` whose front matter names the skill and describes it, plain relative paths, 1 MiB in all. With skills the model also gets `read_skill_file` (`readSkillFileTool`, from `@parcha/agentrun-kernel`, for any harness): a read-only, replay-safe host tool that reads one of a skill's own listed files, exactly. A path that climbs (`..`) or is absolute is refused before any filesystem call, an unlisted path or another skill's file is refused by name, and no link is followed anywhere in the path (checked part by part, opened without following one, and checked again after the open).
- `claudeAgentAdapter({ webSearch: true })` turns on Claude's own WebSearch, and nothing else of the CLI's: the model may call it, the PreToolUse hook lets it through with its intent recorded before it runs (safe to repeat after a crash), and the system prompt's note names it. The CLI runs each search as a request of its own through the session's model proxy, which then admits Anthropic's web search server tool exactly as the pinned CLI sends it (`web_search_20250305`, at most 8 searches, the domains the model named); every other hosted tool, a later web search version, and every server tool's block stay refused. Each search the provider reports (`usage.server_tool_use.web_search_requests`, read from a stream's last `message_delta` or a whole body) is booked at $10 per 1,000 searches (`CLAUDE_WEB_SEARCH_USD`) on top of the host's `price`, into the session's cost and so its spend cap. A request with the web search tool reports no input bound (`inputTokensMax` undefined): the provider bills the pages it reads as input. In `@parcha/agentrun-kernel`, `ProviderPolicy.serverInputOverhead` may now return `undefined`, a policy's word that a body has no input bound: the model proxy leaves `inputTokensMax` undefined (never 0) and, unlike a throw or a non-count, reports no failure. WebFetch stays off. Default off: a session without the option runs as before.

Their subpaths, directories, harness ids and `AGENTRUN_*` environment variables do not change.

A host may pass the SDK module and the CLI's path (`sdk`, `sdkVersion`, `cliPath`).
  - The CLI's built-in tools are off: the host's tools are its only tools, each call recorded before it runs, and a `PreToolUse` hook denies every other call and every error path. A test runs the pinned CLI against a scripted model that tries its built-ins, the web, sub-agents, scheduled jobs and another MCP server: nothing runs, writes or fetches.
  - The CLI's model traffic goes through the session's loopback proxy (`@parcha/agentrun-kernel/host`) with an Anthropic policy: the pinned CLI's routes only, the session's model, no provider-hosted tool or anything the provider would fetch, the session's tools only, a known `anthropic-beta` set, and the runner asked before every paid request. A refusal names no request content.
  - The CLI runs in the session's own directories with an empty working directory and an allowlisted environment; no provider key, sign-in or operator settings reach it.
  - A host can start the CLI under its own confinement with `confine` (a `setpriv --no-new-privs` prefix, say): it may only add in front of the pinned binary and its arguments, and never touches the environment; anything else is refused when the CLI starts. Every child of a session gets `GIT_CEILING_DIRECTORIES` set to the session's directory, so the CLI's own git never looks for a repository above it.
  - A request on the session's small model is asked about and priced as the small model (the Anthropic policy names the model of the body it checked).
  - Every drive of a session writes through one serialized writer, so a drive opened after an interrupt reads only once the halted drive's last writes are in: a `never` tool that finished as the interrupt landed is folded completed, never taken for abandoned. An interrupt waits for a host tool's call in flight rather than abandon it, so a host tool must honour its signal or carry its own deadline.

  - The Claude Agent adapter sends them to the model inline in the tool's result. It checks each image first, a type Anthropic's API takes (`image/jpeg`, `image/png`, `image/gif`, `image/webp`), base64, at most `maxImageBytes` (default 5 MB, `CLAUDE_AGENT_MAX_IMAGE_BYTES`; at most 10 MB), and makes an image it can't send the call's error, by the tool's name and the image (`toolImageProblems`).
  - The session's model proxy lets an image through only inline inside a tool's result, and leaves out the note the CLI adds beside it naming the file it kept in its own session directory.
  - A session resumed in a new directory still sends the image, from the store.
- `toolSchemaProblems(tool, schema)` lists what a harness adapter refuses in a host tool's input schema before a session starts, the same on every harness, each as `<tool>: <JSON pointer>: <why>`: a root that is not `{ "type": "object" }`, a schema that is not JSON or not valid JSON Schema 2020-12 (a `$schema` must name 2020-12, 2019-09, draft-07, -06 or -04), and a remote `$ref` (a local one into `$defs` is followed). An adapter's `check()` calls it first and then adds its own harness's measured refusals.
  - The Claude Agent adapter's `check()` uses it, and also refuses a root with `anyOf`, `allOf` or `oneOf`, which the pinned CLI drops without a word, the tool missing from the session. Put the alternatives under a property. `open` refuses a session whose tools have any of these, naming each.
- A call's `tool_end` reaches the host only once its outcome is in the session's records, with the text recorded as `result`, and `createHarnessRunner(...).stop({ drainMs })` pauses every node a runner is running: no new turn, tool call or paid request starts, and the calls in flight run on until their outcomes are recorded, for at most `drainMs`, before the node fails `aborted`. Run again with the same step, the node resumes from its records, and a call that finished during the pause is never run or paid for again.
  - Before, the Claude Agent adapter sent `tool_end` as the tool returned, before its outcome was written, and an interrupt cut off a call in flight, so a `safe` call ran again when its session resumed.
  - `AdapterSession.interrupt` takes `{ drainMs }`. An adapter that cannot drain stops at once, as before. The Claude Agent adapter drains, and refuses a new turn while it does.
  - A failed call's `tool_end` carries its recorded text too.
- A spend cap below one request's worst case at its model's output ceiling no longer refuses the run before it starts. Each request is limited to the output tokens what is left of the cap can buy, thinking included, and held at that, so the cap stays exact. A request is refused only when what is left cannot buy its least: 1,024 tokens for its answer, plus its thinking's least when it thinks. A $0.50 cap on Claude Sonnet now runs; before, any cap under about $1.30 could never send a request.
  - A refusal says, in plain words, what the run spent of its cap, what its next request needs and the cap that would run it ("Not sent: ... Raise the cap to at least $0.48 to run it."), on the run's error and its timeline row, after the code `spend_cap_reached (out of budget): `, which pi-ai's retry takes as final. A request the cap refused counts as no model request in the run's usage, on every harness; a run whose only request was refused says "no model request sent". A reply the limit cut short says so on the run's timeline.
  - The model proxy asks the host with a request's own output limit and its least (`outputTokensAsked`, `outputTokensLeast`), and writes the admitted limit (the ticket's `outputTokensMax`) into its body through a policy's new `limitOutput`; it never sends a request unlimited that was admitted with a limit, nor a body longer than the one its input was measured on. The runner's `beforeRequest` may answer `outputTokensMax` beside `holdUsd`, and holds each request in flight at the limit it was admitted with; a limit that is no whole number of tokens above 0 refuses the request, never sends it unlimited.
- `web_search` and `web_fetch` work on pi, `claude-agent` and `codex` with only a model key. Each resolves in one order: the provider the user picked (the agent's own `definition.tool_settings` over the server's `PUT /v2/settings/tools`), then the native tool, then the kernel's keyless fallback. `web_search` is `auto` by default, native where there is one: Claude's own WebSearch (its adapter is opened with it, and no `web_search` host tool is offered), and on pi one request to the run's own model provider with its hosted search (Anthropic's `web_search_20250305` at 5 searches, OpenAI's Responses `web_search`), read from the provider's events and booked as one of the run's requests, its tokens plus $0.01 a search. On codex it is Codex's own search, each search booked at $0.01, except behind a gateway or under a spend cap, where it is keyless Exa; on claude-agent under a spend cap it is keyless Exa too, since Claude's own search has per-use fees a cap cannot reserve yet; a pi model behind a gateway or on another provider likewise searches Exa's public MCP endpoint with no key (`exa-keyless`, at most 8 results; a 429 at its free limit, or a 403 for a connection that is not direct IPv4, answers `{error}`, never retried). Every provider answers one shape, `{provider, query, results: [{url, title, snippet, published?}], text?}`, snippets cut at 3,000 characters, and the model's copy ends with a line asking it to cite the URLs it relies on; Parallel's search answers it too. `web_fetch` is the kernel's guarded fetch by default, and a page whose text it cuts at 60,000 characters says `truncated: true` with `original_chars` ; Parallel (search and extract) runs only where it is picked, and only then is its key handed to the run; a picked Parallel that gives no page leaves the direct fetch's page saying why (`parallel`), never a silent fallback. A pick of Parallel without `PARALLEL_API_KEY` resolves `unavailable`, and a run naming the tool is refused (`409`). Settings are `{web_search?: {provider: auto|native|exa-keyless|parallel|off}, web_fetch?: {provider: kernel|parallel}}` (`off` turns `web_search` off: nothing is searched, and a run naming it is refused, `409`), kept in the data directory (`tool-settings.json`, 0600); a `permission` is refused (`422 not_yet`) until the tool gate, and `capabilities.features.tool_permissions` is false. `GET /v2/capabilities` gives the two tools a `resolves` per harness, with the providers offered, the server's (`provider`) and the default (`default_provider`): capabilities is the one tool catalog (an unavailable tool says why, `reason`: a provider pick's own words such as `web_search is turned off in settings`, or `Needs` and the variables it is missing), and `GET /v2/agents/{id}` projects it onto the agent as `tools` (each granted tool in the same order; for one with a choice the provider in force, `provider_from`, `default_provider` and `resolved` on its harness and model). Under a run's cap pi's own search request is bounded at its context plus 125,000 input tokens and its most fee (Claude's and Codex's own searches do not run under a cap), its booked cost stops the next request, and a run whose booked spend passes its cap shows one timeline row saying by how much. In `@parcha/pi-durable-agent` a revision keeps `toolSettings`, and the timeline counts any request marked with a string `request` label as a side request, as it did a compaction's summary, and a `web_search` that answers `{error}`, or a `web_fetch` page followed by its line for the model that is `ok: false`, reads as a failed call, in its row and in the run's tool counts. With no key and no native search, web_search falls back to Exa's public keyless MCP endpoint, a third-party service with its own unpublished rate limits (a 429 past them) and terms (https://exa.ai/terms), reached over direct IPv4: set `web_search` to `native` (native only) server-wide or in an agent's `tool_settings` to turn it off, or pick `parallel` with `PARALLEL_API_KEY` to search with a key. `auto`, the default, is native where there is one, else keyless Exa. Upgrading: a server holding `PARALLEL_API_KEY` used to read every `web_fetch` page through Parallel's extract on its own; now it is the guarded direct fetch unless Parallel is picked, so set `PUT /v2/settings/tools {"web_fetch": {"provider": "parallel"}}` to keep that. A run keeps the tools its first launch resolved for its life, and a workflow's model and call nodes' tools resolve whether or not its revision lists them. `claudeAgentAdapter` takes `webSearchAllowance`: with its web search on, a search request is bounded at its body plus that many input tokens, instead of having no bound. `fetch_page` leaves the tool table: it is a legacy name for `web_fetch`, so a revision or call node naming it still saves and runs `web_fetch` under that name, resolved as `web_fetch` is.
- A turn that a halt ended with a reason now ends `failed`, naming it, never `interrupted` with the reason dropped: a harness's spend cap, its transcript mirror, a refused spawn. Only the session's own stop (its interrupt or its close, told apart by identity with the kernel's `SessionHalt`) and its host's stop end a turn `interrupted`. `abortedOutcome` decides it, and both adapters use it. This changes how spend-cap and mirror halts end a turn: a host that read `interrupted` for them now reads `failed` with the reason.
- After a crash mid-turn, the claude-agent harness's recovery note no longer reaches the user's answer. The note (which tool calls completed, which may have half-run) was sent as a user message, and the model sometimes answered it back ("No tool calls had run, so nothing needed undoing, and ..."). It now rides in the resuming drive's system prompt. The user's turn holds only the user's own words: the interrupted turn's prompts the transcript lost, and messages sent since. With none, it is a bare "Continue.". A resumed session sends the system prompt recorded at its start, whatever a later launch passes (`systemPrompt.snapshot`, Agent SDK 0.3.286), so the resuming drive alone renders its own (`snapshot: false`). That drive records nothing, so the next drive sends the original prompt again. The note names each tool call of the cut-off turn by its name, id and status, and nothing it read: no input, output or error text. Those can hold what a file or a web page said, and the system prompt would give that the harness's authority. They are not put in the user's turn either, quoted or not, so a recovered turn sees the calls' statuses and is told to check the actual state before relying on them.
- A claude-agent run whose key the provider refuses now fails at the provider's first 401, in seconds, with the plain key words (for example "OpenRouter refused OPENROUTER_API_KEY (401: User not found): …"). Before, it read Working for about three minutes while the Claude CLI retried the 401 a dozen times. The session's model proxy reads the 401's words from at most 4 KB of its body, for at most 2 s, decoded and with no control character, and ends the turn as the spend cap does. A body with no string message gives no detail, so the run's error carries just the refused-key words. Codex already failed at its first 401.
- Checking a harness's binary against its pins no longer reads the whole binary into memory, and runs once per binary in a process. `verifyCodexBinary` (the codex binary, 294 MiB) and `verifyClaudeAgentCli` (claude-agent's CLI, 231 MiB) each read the file whole to hash it, and agentrun-serve checked each again for every model it resolved: twice per harness in its start's probe, then once per save and once per run check, and a run's own process once more when it made its adapter. One start probe peaked at 395 MiB of memory, 675 MiB with a default model, past a 512 MiB container's limit. The hash now reads 1 MiB at a time, and a check that passed is kept for the process while the binary stays the same file (its path, device, inode, size, and modification and change times, with the pins); touched or replaced, it is checked again, and a failed check is never kept. The kernel's `@parcha/agentrun-kernel/host` exports both parts, `sha256OfFile` and `checkedOnce`.
- A harness's own process dies with the process that started it. The Claude Agent CLI runs detached, in its own process group, and does not exit when its stdin closes, so a host that was SIGKILLed (and ran no close) left its CLI running, reparented, one more per crash. `@parcha/agentrun-kernel/host` now has `parentWatched(child)`: on Linux with util-linux setpriv the child starts under `setpriv --pdeathsig KILL --` (the kernel kills it the moment its parent dies), elsewhere under a small node shim that kills it when it is reparented. The Claude Agent machine launches every child with it, inside the host's confinement (`launchCommand`: the confine prefix, then the watch, then the pinned binary), so the death signal is set after any switch of user the prefix makes. The watch adds nothing to the child's environment.
- A claude-agent or codex run works in the run's workspace, the directory its file tools write to. Before, the CLI's working directory was an empty one beside it (`runs/<id>/harness/work`): Claude told its model that path, so a file written at its absolute path was refused as "outside the workspace", and the answer quoted the server's data directory. In QA this happened in 3 of 4 Claude runs that wrote a file.
  - `SessionIO.cwd`: a host may name the session's working directory, its workspace. The Claude and Codex adapters run their CLI there, and keep their own state in the session's private directory as before. git stops at the workspace's parent. serve passes the run's `work/`.
  - A file tool's refusal, an error such as ENOENT, and a write's or edit's result on claude-agent and codex name paths in the workspace relative to it (`notes/a.md`, `../escape.md: outside the workspace`), never by the server's data directory. A read's result is the file's own text and is not changed.
- A host tool's result reaches the model whole on claude-agent and codex. The Claude Agent CLI saved an MCP tool's result past 50,000 characters (a long `web_fetch` page, a `monid` answer, a 50 KB `read`) to a file under its own config directory and told the model to read it, which the run's confinement refuses, so the model could not read the page; Codex kept only the two ends of a result past its truncation policy (10,000 tokens for the models its catalog holds, about 12,000 characters for another). `@parcha/agentrun-kernel` states the bound once, `HOST_RESULT_MAX_CHARS` (120,000 characters, over every host tool's largest result); the Claude Agent adapter lists each host tool with it as `anthropic/maxResultSizeChars` and sets `MAX_MCP_OUTPUT_TOKENS` to it, and the Codex adapter sets `tool_output_token_limit` to it as Codex counts it (four bytes of UTF-8 a token: 90,000).
  `web_fetch` (and `fetch_page`) reads a page a part at a time: `offset` and `max_chars` (20,000 by default, at least 200, at most 50,000; a smaller one or an offset below 0 is refused before anything is fetched, saying so; a workflow's call node reads 50,000 by default) name the part, the Page gives `chars`, its length, and a part that is not the whole page has `truncated` while more follows, `next_offset` where it begins and `original_chars` where the whole length is known; an agent reads a line after the JSON saying which characters these are and the offset that reads on. A page whose HTML pi-browser cut at 1,000,000 characters before reading it gives `html_chars`, its whole length, on every part and no `original_chars`, and the line after its last part says `The page was cut at 1,000,000 characters of HTML before reading; the rest wasn't read.`; `converted: "text"` says its text is plain text, its conversion to markdown having run out of time. The text was cut at 60,000 characters with no way to read the rest. A page's links come with the part at offset 0, at most 200 in 20,000 characters, and a URL longer than 4,096 characters is refused before anything is sent.
  `web_search` leaves out its least relevant results when its answer would pass 100,000 characters, and `omitted` counts them.
- A host tool's result reaches a harness at most `HOST_RESULT_MAX_CHARS` (120,000) characters long. The kernel's tool bridge, which every host tool's result passes on its way to Claude Agent or Codex, keeps a longer one's start, cut where a character ends, ends it with a line saying where it was cut (`[cut at N of M characters]`), and flags the call's `tool_end` `truncated: true`; the call's record keeps the whole result. On a Codex resume, a call the rollout left unanswered is answered from that record with the same cut. A skill file read with `read_skill_file`, a delegate's answer and a rejection listing every schema error reached the harness whole, however long (a 1 MiB skill file, a 6 MB answer).
- The model proxy now tells the host, before a paid request is sent, the most input tokens it can be billed for. A spend cap could only count a request's cost once it was billed, so a single request whose input alone was over what was left of the cap was still sent and paid. `beforeRequest` now carries `inputTokensMax`: the UTF-8 bytes of the body exactly as it is sent, plus the input the provider adds that the body does not carry. A byte-level BPE token covers at least one byte, so this never undercounts the body, however dense its text. Each `inFlight` entry carries its own `inputTokensMax` until that request answers, so a cap can hold every open request at its own bound. When the provider's addition cannot be read, `inputTokensMax` is undefined, never 0, and a cap treats that input as unknown.
  - What a provider adds is in one place, `providerInputOverhead(api, shape)` from `@parcha/agentrun-kernel/host`. `api` is pi's API kind, and `shape` is whether the request has tools, its tool_choice and its image count. Each figure is the largest the provider documents for any current model:
    - `anthropic-messages`: the tool-use system prompt the Messages API adds to a body with tools, 675 tokens for tool_choice auto or none and 804 for any or tool, plus 4,784 tokens for each image, its high-resolution tier's maximum.
    - `openai-responses`, and the Azure and Codex Responses kinds: no prompt of their own, and 73,800 tokens for each image. That is 30,000 patches, the most an image may have, times 2.46, the largest model multiplier.
    - `openai-completions`, which OpenAI-compatible gateways speak too: nothing for its per-message formatting, since the body's bytes already bound it; 804 tokens when the request has tools, whatever its tool_choice, the largest Anthropic tool-use prompt, since a gateway may route to an Anthropic model; and 73,800 tokens for each image.
    - Every other API kind, among them pi's `mistral-conversations`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex` and `pi-messages`, and a faux `faux:<id>`: nothing for text, an assumed 2,048 tokens when the request has tools, and 73,800 tokens for each image. The tool allowance for these kinds is assumed, not documented; it is documented only for `anthropic-messages`, the OpenAI Responses kinds and `openai-completions`. `providerInputOverhead` never returns undefined: only a body that cannot be measured is unmeasured.
  - Images are billed by their area, not their bytes, so a small compressed image of large dimensions is counted at its maximum. A Codex body with a file input (a PDF, billed by its pages) is left unmeasured.
  - A provider policy says what its provider adds with `serverInputOverhead(body)`. The Claude and Codex policies read their body's shape and use the figures above.
  - The faux adapter in `@parcha/agentrun-kernel/testing` measures its prompt's UTF-8 bytes for each request, as a real adapter's proxy measures its body.
  - `inputTokensMaxOf(policy, body, sent)` is exported from `@parcha/agentrun-kernel/host`.
  - The proxy serializes the body once before admission and sends exactly what it measured. A body that cannot be serialized is refused before the runner is asked, so it is never booked.
- A Claude or Codex turn stopped while the session was still recording the person's message stays stopped. Before, the stop found no turn running, so the session read idle, and the stopped message stayed pending and was sent with the next message. Now a turn that ends on its session's stop leaves the session reading `open_turn` while that message is pending, so serve's stop settles it, and it is never sent.
- A Claude or Codex turn the person stopped stays stopped when the run's process is replaced. Before, the next process found the stopped turn still open in the session and resumed it: it ran its tools and paid for its model requests again, and its answer came before the person's follow-up. Now serve's open reads the run's stop record and settles that turn, ended `interrupted`, with nothing sent, and the follow-up is a turn of its own. A turn a crash or a drain cut is resumed as before.
  - A stop that lands before the harness took the person's message withdraws that message too, so it is never sent later: not with the follow-up in the same process, and not by a process that replaces it.
  - `AdapterSession` has `settleOpenTurn()`: it records the open turn as ended, interrupted, withdraws the input the turn never placed, and sends nothing. The Claude Agent, Codex and faux adapters implement it. A harness that runs as a child process does both with `settleTurn(drive)` from `@parcha/agentrun-kernel/process`. An adapter written outside this repository without it keeps the old behaviour: its stopped turn is resumed.
  - After `interrupt()`, the Claude Agent and Codex sessions read `open_turn` while the stopped turn is still open in their records. serve's stop settles it there; a runner's pause leaves it for the next process to resume.
  - When the earlier process died before it wrote the stopped turn's end, the next one writes it, `interrupted`, before the follow-up's turn starts.
