# Changelog

## [Unreleased]

## 0.1.0-beta.47 (2026-11-19)

**Breaking:**

- The package no longer records a binary's first-seen digest itself: `fileDigestRecord`, `verifyFirstSeen`, the `DigestRecord` type and `ACP_CODES.binaryDrift` (`ACP_BINARY_DRIFT`) are gone. A binary no pin names has its first digest recorded by AgentRun's installer alone (`agentrun harness install`), and a later binary that differs is refused there and at `harness-check` with `HARNESS_BINARY_MISMATCH`. Code that called `verifyFirstSeen` pins the binary's sha256 and calls `verifyPinnedBinary`, or installs it through `agentrun harness install --recipe`. <!-- changes/acp-one-first-seen-pin.md -->

**Changes:**

- New package `@parcha/agentrun-harness-acp` (private for now): any Agent Client Protocol agent as a harness adapter, from a recipe that says how to start it over stdio, what it declares (`session/load`, MCP over HTTP or stdio), where it keeps its sessions and who bills its model. Built on the official `@agentclientprotocol/sdk` 2.7.0.
  - The agent runs in a private HOME with an environment allowlist (PATH, LANG, TZ and the recipe's own variables), in a process group of its own. Its session store is mirrored into the session's records, credential files left out, so another runner's agent loads it back.
  - The host's tools reach it as one loopback MCP server, over HTTP when it is declared and advertised, else stdio. Each call runs once through the kernel's tool bridge, under the agent's own tool call id.
  - A permission request for one of the agent's own tools (a shell, an edit) goes through the host's gate (allow, deny or park), is journaled, and survives a runner swap. The adapter answers `allow_once` or `reject_once` and never an `always` option. It never trusts the status ACP reports for a tool.
  - initialize is checked against the recipe: a capability the recipe declares and the agent does not advertise refuses the session with `ACP_CAPABILITY_MISMATCH`.
  - A plan-billed agent (its vendor bills the owner's plan, so no request reaches the host) is bounded by the adapter itself: the run stops at the recipe's `maxTurns` (`ACP_TURN_LIMIT`) or `maxToolCalls` (`ACP_TOOL_CALL_LIMIT`).
  - A crash mid-turn resumes with `session/load` when the agent has it, else on a new agent session that is given the conversation so far. Either way the agent reads the kernel's recovery note, and a call it started is never run again.
- Goose 1.59.2 runs as an AgentRun harness on the ACP adapter: `gooseAdapter({ binary, model, provider, price })` checks the binary's sha256 against its pin, starts `goose acp` from the shipped recipe (`recipes/goose.json`, loaded by `recipeFile` and `gooseRecipe`), and points each Goose process at a model proxy of its own (`gooseProxy`) on the session's booking, so the run's cap and books hold as they do for Claude Code. <!-- changes/acp-goose-harness.md -->
  - The recipe turns every bundled Goose extension off, blocks Goose's model catalog download with a dead egress proxy, mirrors its sessions so another runner's Goose loads them, and leaves the model our MCP tools (`agentrun__<name>`) and Goose's `load_skill`.
  - Goose's proxy forwards only `POST /v1/messages`, with the API's version and the one `anthropic-beta` value the pinned Goose sends (`GOOSE_BETAS`), never Goose's `agent-session-id`. It answers `GET /v1/models` itself with the run's model, and refuses any other model, tool, hosted tool or beta before the provider is asked.
  - `GOOSE_PIN` records the release as the ACP registry listed it, with where and when it was read. `verifyPinnedBinary` refuses a binary whose sha256 differs (`ACP_BINARY_MISMATCH`), reading it and never running it. `gooseAdapter` checks it when the adapter is made and again before every Goose process starts (the adapter's new `beforeStart` option), so a binary replaced in between never runs unchecked. `verifyFirstSeen` records the first verified digest of an agent the registry lists without one, and refuses later drift (`ACP_BINARY_DRIFT`).
  - The adapter's `proxy` option is now called with the session's booking, its tools' names and a halt of its drive (`AcpProxySession`).
  - The kernel's model proxy can answer a local route with a fixed JSON body (`ProxyRoute.localJson`), only to the session's key or a side key.
- Goose is a harness in serve's table (`goose`), run by `gooseAdapter` on the host's Anthropic Messages provider, the same origin and key claude-agent's proxy takes, priced and capped by the same hooks. Its owner installs it with `agentrun harness install goose` (`agentrun-serve install-harness goose`), never a run: nothing on a run's path downloads anything. <!-- changes/goose-install-and-harness-row.md -->
  - The install downloads the pinned archive for this platform (`GOOSE_PIN`) with node's fetch, checks its sha256 before unpacking, unpacks it with the system `tar -xjf` (a fixed argument list, no shell) into a fresh folder beside `<data>/harnesses/goose`, checks the binary's sha256, then renames the folder into place and makes it read-only. A crash part way leaves the old folder or none, and the next install sweeps what it left. Every failure is named (`HARNESS_PLATFORM_UNSUPPORTED`, `HARNESS_DOWNLOAD_FAILED`, `HARNESS_ARCHIVE_MISMATCH`, `HARNESS_UNPACK_FAILED`, `HARNESS_BINARY_MISMATCH`, `HARNESS_INSTALL_BUSY`) with the command to try again. Run again with the pinned binary in place, it downloads nothing. No provider key reaches it.
  - Capabilities list Goose (label, its promises `resume: load`, `tool_gate: permission`, `billing: proxy`) only once the pinned binary is installed and verified, read at AgentRun's start: restart AgentRun after installing it. Before then an agent on goose saves with a warning, and its run is refused (`agent_not_runnable`), each naming `HARNESS_NOT_INSTALLED` and the install command.
  - `@parcha/agentrun-harness-acp` exports Goose's facts (`gooseFacts`), its install command (`GOOSE_INSTALL`) and its code (`GOOSE_NOT_INSTALLED`). The package is held from npm for now, so a serve installed from npm has no goose row until it ships.
- Cursor runs as a harness (`cursor`), over ACP, on its owner's own Cursor API key: install its pinned release with `agentrun harness install cursor` (or `agentrun-serve install-harness cursor`), set `CURSOR_API_KEY` where AgentRun starts, and restart. Each run is billed to your Cursor plan, under Cursor's terms, with no spend cap of AgentRun's: it stops after 20 turns or 100 tool calls (`AGENTRUN_CURSOR_MAX_TURNS`, `AGENTRUN_CURSOR_MAX_TOOL_CALLS`), and capabilities show its card (`harnesses[].card`). <!-- changes/cursor-harness.md -->
  - Cursor makes no file edits: every Write is denied in its CLI config until Cursor asks before an edit, as it asks before a shell command or a tool. Its own shell commands, and any other call of its own, are asked first, of a person who can approve them, and refused where no one can (they run on AgentRun's host, never on the run's computer, so bash's setting is not theirs); AgentRun's tools over MCP go through the agent's tool settings.
  - `CURSOR_API_KEY` is handed to Cursor's runs alone, read by name at each start. The credential Cursor derives from it (`auth.json`, which would hold its tokens and the key itself) is never written: its path is a folder Cursor cannot write a file at, and Cursor runs on the key in its environment, so a killed run or server leaves no credential on disk. Cursor's warning that it could not save one is left out of a failed run's words (a recipe's `quiet`). Its whole private HOME is deleted when its process ends.
  - A model is `cursor/<model-id>` (`cursor/gpt-5.4-nano`; `cursor/default` for Cursor's own default), checked against the models Cursor lists for the key (`ACP_MODEL_UNLISTED`). A key whose Cursor team administrator turned headless CLI use off is refused as `CURSOR_HEADLESS_DISABLED`.
  - The release is pinned by its archive's sha256, its launcher's, and a digest of every file it unpacks to; a drift in any of them refuses the run (`ACP_BINARY_MISMATCH`). The archive installer takes tar.gz as well as tar.bz2 (`ARCHIVE_FORMATS`), and so does a harness recipe's loader. A recipe may not take any id the server's harness table already has, `cursor` and `goose` included.
  - Cursor's release is pinned for linux-x86_64 alone. On any other host, a Mac included, Cursor is refused `ACP_BINARY_UNPINNED` before any install is looked at. `cursorRelease(platform)` gives the release pinned for a platform, or none.
  - A new Cursor pin needs a key walk on it first. The walk runs a turn, a hard kill mid-turn and the close on the real binary. At each point it counts the files of the session folder that hold the key or a JWT-shaped token, and it never prints them. CI refuses a pin that the walk's record does not name, so a release that starts saving its key somewhere else fails before it ships.
- Bring your own harness, door 1: a recipe. A JSON file names an ACP agent's registry release (the archive's URL and sha256, the binary inside it), its model billing (through AgentRun's model proxy, or the owner's plan with turn and tool-call limits), its literal env, files and session folders in the private HOME, and what it declares. `agentrun harness install --recipe FILE` installs the release, and `agentrun harness-check --recipe FILE --model PROVIDER/MODEL` runs it for real: the agent's own tools off, its environment an allowlist, the cap or plan limits, the pinned binary at every start, no side request (stage 2); a SIGKILL then resume, a denied call, one of AgentRun's tools over MCP, a second runner (stage 3). It writes a JSON report and prints the three facts a harness row carries: `resume`, `tool_gate`, `billing`. See [docs/harness-recipe.md](https://github.com/Parcha-ai/agentrun/blob/v0.1.0-beta.47/docs/harness-recipe.md) and [HARNESS-SCORECARD.md](https://github.com/Parcha-ai/agentrun/blob/main/HARNESS-SCORECARD.md), which rates 25 agents. <!-- changes/harness-recipe-door-one.md -->

  The loader refuses a recipe that breaks one of five rules by its code: a key that is not the harness's own (`RECIPE_KEY_NOT_OWN`), a binary not pinned to a registry archive (`RECIPE_BINARY_UNPINNED`), a file or folder outside the private HOME (`RECIPE_PATH_OUTSIDE`), an install step of its own (`RECIPE_INSTALLS_ITSELF`), an environment beyond the allowlist (`RECIPE_ENV_NOT_ALLOWLIST`). A release whose registry entry lists no binary digest is pinned to the first one its owner's install records; a later binary that differs is refused, at an install and a check alike (`HARNESS_BINARY_MISMATCH`). A recipe's keys reach the agent the way a run's do, read by name at its start: `harness-check` on a host without one is refused before the agent starts (`ACP_KEY_MISSING`). The ACP adapter logs each permission the agent asks for (`acp: the agent asked permission`).
- `@parcha/agentrun-harness-acp`, the adapter that runs an Agent Client Protocol agent as a harness (Goose's among them), is no longer held: the next release publishes it, after the kernel and before the server. `@parcha/agentrun-serve` now depends on it, so a server installed from npm has the Goose row: its owner installs Goose's pinned binary with `agentrun-serve install-harness goose --data <dir>`, restarts the server, and Goose is offered. The package's archive holds `dist`, Goose's recipe (`recipes/goose.json`), the README, LICENSE and NOTICE; `scripts/verify-packages.mjs` imports its root and `./facts` in the clean consumer and reads the recipe from the installed package. <!-- changes/unhold-harness-acp.md -->
- The ACP adapter ties `agentrun: <tool>`, the tool's underscores as spaces (Goose 1.59.2's title), to our tool, so the host's gate is asked once per call, at the MCP call, not twice. <!-- changes/acp-goose-tool-title.md -->
