# Changelog

## [Unreleased]

- New package `@parcha/agentrun-harness-acp` (private for now): any Agent Client Protocol agent as a harness adapter, from a recipe that says how to start it over stdio, what it declares (`session/load`, MCP over HTTP or stdio), where it keeps its sessions and who bills its model. Built on the official `@agentclientprotocol/sdk` 2.7.0.
  - The agent runs in a private HOME with an environment allowlist (PATH, LANG, TZ and the recipe's own variables), in a process group of its own. Its session store is mirrored into the session's records, credential files left out, so another runner's agent loads it back.
  - The host's tools reach it as one loopback MCP server, over HTTP when it is declared and advertised, else stdio. Each call runs once through the kernel's tool bridge, under the agent's own tool call id.
  - A permission request for one of the agent's own tools (a shell, an edit) goes through the host's gate (allow, deny or park), is journaled, and survives a runner swap. The adapter answers `allow_once` or `reject_once` and never an `always` option. It never trusts the status ACP reports for a tool.
  - initialize is checked against the recipe: a capability the recipe declares and the agent does not advertise refuses the session with `ACP_CAPABILITY_MISMATCH`.
  - A plan-billed agent (its vendor bills the owner's plan, so no request reaches the host) is bounded by the adapter itself: the run stops at the recipe's `maxTurns` (`ACP_TURN_LIMIT`) or `maxToolCalls` (`ACP_TOOL_CALL_LIMIT`).
  - A crash mid-turn resumes with `session/load` when the agent has it, else on a new agent session that is given the conversation so far. Either way the agent reads the kernel's recovery note, and a call it started is never run again.
- Goose 1.59.2 runs as an AgentRun harness on the ACP adapter: `gooseAdapter({ binary, model, provider, price })` checks the binary's sha256 against its pin, starts `goose acp` from the shipped recipe (`recipes/goose.json`, loaded by `recipeFile` and `gooseRecipe`), and points each Goose process at a model proxy of its own (`gooseProxy`) on the session's booking, so the run's cap and books hold as they do for Claude Code. <!-- changes/acp-goose-harness.md -->
  - The recipe turns every bundled Goose extension off, blocks Goose's model catalog download with a dead egress proxy, mirrors its sessions so another runner's Goose loads them, and leaves the model our MCP tools (`agentrun__<name>`) and Goose's `load_skill`.
  - Goose's proxy forwards only `POST /v1/messages`, with the API's version and the one `anthropic-beta` value the pinned Goose sends (`GOOSE_BETAS`), never Goose's `agent-session-id`. It answers `GET /v1/models` itself with the run's model, and refuses any other model, tool, hosted tool or beta before the provider is asked.
  - `GOOSE_PIN` records the release as the ACP registry listed it, with where and when it was read. `verifyPinnedBinary` refuses a binary whose sha256 differs (`ACP_BINARY_MISMATCH`), reading it and never running it. `gooseAdapter` checks it when the adapter is made and again before every Goose process starts (the adapter's new `beforeStart` option), so a binary replaced in between never runs unchecked. `verifyFirstSeen` records the first verified digest of an agent the registry lists without one, and refuses later drift (`ACP_BINARY_DRIFT`).
  - The adapter's `proxy` option is now called with the session's booking, its tools' names and a halt of its drive (`AcpProxySession`).
  - The kernel's model proxy can answer a local route with a fixed JSON body (`ProxyRoute.localJson`), only to the session's key or a side key.
