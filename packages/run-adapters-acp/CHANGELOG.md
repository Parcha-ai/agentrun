## [Unreleased]

## 0.1.0-beta.59 (2026-11-25)

**Breaking:**

- Ollama models run only on a harness that forwards the route, an output schema beside tools on Ollama is refused, and an ACP agent's permission requests for AgentRun's tools are no longer answered from their titles. What to change on upgrade: <!-- changes/b51-breaking.md -->
  - A harness module on Messages or Responses that should keep running Ollama models must forward its model requests with the `fetch` its launch hands it (`ModuleLaunch.fetch`, given to `startModelProxy`'s `fetch`) and set `forwardsRoute: true` in its facts. Without the fact it is offered no Ollama model, and a run of it that names one is refused before it starts, in words that name these two steps.
  - A claude-agent node with an output schema on an Ollama model now stops with a 400 `invalid_request_error`, since the claude-agent harness sends its tools on every turn and Ollama can't hold an answer to a format and also call tools. Drop the schema, or run the node on a model with a key.
  - A recipe for an agent that asks permission before every tool call needs an `allowFile` in a form its agent reads, or the title tie (`quirks.permissionTie: "title"`). Without either, every request for an AgentRun tool goes to the host's gate as the agent's own call, and its runs stop there.
  - An agent's `tool_call` title no longer names the AgentRun tool it calls. A recipe without `announces` (the new field where its agent's `tool_call` names the tool) has every call matched to its MCP call by its arguments alone, a call with no arguments included. A call announced with no input at all is matched to an MCP call that nothing else matches, the oldest first, until the agent reports it ended, so two such calls in flight can trade ids. Declare `announces` to tie each call to its own.
  - Goose's offer promises `tool_gate: "config"` (was `"permission"`): its calls of AgentRun's tools are held by its permission file and the host's gate at the MCP call.
  - `agentrun harness-check` fails `mcp_tool` for an agent that asks permission for `check_echo` on a recipe with neither field. A recipe whose check passed before can fail its next one.
  - `examples/harness-recipe/antigravity.json` declares `announces` and the title tie (`quirks.permissionTie: "title"`), since agy asks permission for every MCP call: its requests for the AgentRun calls it announced are answered allow once, and the host's gate decides at the MCP call. A copy of the recipe made before this release has neither and needs both, or its runs stop at the gate.
  - The exported test helper `fakeAgentRecipe` (`@parcha/agentrun-harness-acp/testing`) now gives its recipe an `allowFile` (style "goose", the default) or the title tie (style "cursor"), and each style's `announces`, as each shipped recipe does. The fake's style "cursor" now announces its MCP calls late, as Cursor 2026.11.13 does (`announce: "early"` for the old shape). A suite that relied on the fake asking for AgentRun's tools and being answered from the title gets neither by default.

**Changes:**

- Goose 1.59.2 no longer asks permission for a call of one of AgentRun's tools, and the ACP adapter no longer reads Goose's titles. Before, it tied `agentrun: <tool>` (with or without Goose's summary, `agentrun: write · proof.txt`) to our tool and answered `allow_once`, and a title in a form it did not read reached the tool gate as Goose's own call and stopped the run at input_required. <!-- changes/acp-announces.md -->
  - A recipe's new `allowFile` (`{ path, form }`) is written into the private HOME at each start from the tools that start lists. Goose's recipe declares its permission file, `.config/goose/permission.yaml` in the form `goose-permission`, every tool allowed as `agentrun__<tool>` and nothing else, so the gate asks once, at the MCP call.
  - The adapter answers a permission request `allow_once` without the gate only where the recipe declares `quirks.permissionTie: "title"`: Cursor's recipe, since its allowlist asks for every MCP call, and the Antigravity example's, since agy asks for every one too. Every other request goes to the host's gate, journaled, whatever its title says.
  - A recipe's new `announces` field says where the agent's `tool_call` names the tool it calls: Goose 1.59.2's `_meta.goose.toolCall.toolName` (`agentrun__<tool>`), Cursor's late update's `rawInput` (`providerIdentifier`, `toolName`, `args`), agy's `name` (`mcp_agentrun_<tool>`, its `prefix`). Its `extras` names fields an agent writes beside the arguments that the MCP call never carries (agy's `toolSummary`), left out before the two are matched. A path that starts at the `tool_call`'s `title`, `toolCallId`, `kind`, `status`, `rawOutput`, `content`, `locations` or `sessionUpdate` is refused (the agent's text or a tool's output), and a recipe with the title tie and no `announces` is refused. A call is matched to its MCP call by that tool and its arguments, never by a title. A call it names as another tool (Goose's own `load_skill` with the same arguments) never takes our call's id, so the resume memo keys our call under its own id.
  - A title naming our tool on a call of the agent's own (a read titled `agentrun__write`) no longer marks it ours, so Cursor's tie never answers its request; the host's gate does.
  - The host gate's question about an agent's permission request carries the request's `toolCallId` in its `args`. `agentrun harness-check` matches a permission request to `check_echo` by that `toolCallId` or by the check's nonce as its input's `text`, never by its title. Its `mcp_tool` row counts every request (`permissionAsks`) and those for `check_echo` (`ourAsks`); a request for the agent's own call fails no stage. A recipe file passes `allowFile`, `announces` and `quirks` through.
  - `AGENTRUN_LOG=debug` makes serve write into a run's log one line per call an ACP agent announces, on a recipe that declares `announces`: `acp: the agent announced a call`, with the call's `toolCallId`, its `kind`, the tool name the recipe's field holds when it names an AgentRun tool (at most 200 characters; `native` for any other call, since a recipe's field may sit inside the call's input) and the AgentRun tool it named, never the call's input. A call announced with no name (Cursor's) gets the line again when a later update names it. Unset or `quiet`, no such line is written.
- The Antigravity example recipe names agy's calls of AgentRun's tools by the field agy writes them in, `name` (`mcp_agentrun_<tool>`): `announces` with `prefix: "mcp_agentrun_"`, and `extras: ["toolSummary"]`, so the summary agy adds to the arguments it reports is left out when the call is matched to its MCP call. agy asks permission for every MCP call, so the recipe declares the title tie: a request titled `Run mcp_agentrun_<tool>`, the whole text, for a call `announces` named as that same tool, is answered allow once, with the host's gate asked at the MCP call itself, as for Cursor. The Antigravity example recipe now passes `harness-check` (agy 1.5.14): it declares MCP over stdio, since agy advertises no MCP over HTTP, and names `.gemini/antigravity-cli/conversations` as its state, so a resume after a kill and another runner both load the conversation. <!-- changes/antigravity-recipe-check.md -->
- A model the runner's route translates onto a harness's wire (this machine's Ollama models on Anthropic's Messages and OpenAI's Responses) is offered only to a harness whose proxy forwards with the route's `fetch`, and the Messages translation no longer drops what it can't run. Before, any harness on the wire was offered those models, including a module that sends its requests to the network, where nothing answers. <!-- changes/b51-route-hints.md -->
  - `AdapterFacts` gains `forwardsRoute`. claude-agent, Goose, codex and opencode set it, and so does every recipe that builds on Goose's facts. A harness without it is offered none of the route's models, takes none as its default, and its words say to add a key ("No model yet for <harness>: add an OpenRouter or Anthropic key"). A run that names one is refused before it starts.
  - An output schema (`output_config.format` of type `json_schema`) on a Messages request with no tools now reaches Ollama as its `format`. Before, it was dropped and the answer came back unconstrained. Beside tools it is refused with a 400 `invalid_request_error` that says to drop the output schema or use a model route that takes tools with a format, because Ollama holds the whole answer to the format and leaves the model no way to call a tool.
  - The Messages translation answers `POST /v1/messages` and `POST /v1/messages/count_tokens` alone. Any other method or path is a 404 `not_found_error` in Anthropic's error shape, and nothing reaches Ollama.
  - `agentrun harness-check` on a model the route translates (`--model ollama/<tag>`) now reaches it. Its recorder wraps the route's own fetch, so the recipe's agent gets the same route a server's run gets and the check still sees every request. Before, every request went to the route's placeholder origin and `mcp_tool` failed.

## 0.1.0-beta.57 (2026-11-24)

- A Goose 1.59.2 call of one of AgentRun's tools whose title carries Goose's summary of its arguments (`agentrun: write · proof.txt`) is now tied to that tool. Before, it reached the tool gate as Goose's own call (`acp_other`) and waited for an approval, so a write the agent was allowed to make stopped the run at input_required. The title alone still ties nothing: the call needs the tool_call Goose announced for it, and a kind with effects of its own (a shell, an edit) is never ours. <!-- changes/acp-goose-title-summary.md -->
- A harness recipe's install is checked by one rule, its tree, in harness-check, harness sign-in, a server's harness entry and each start. The tree digest covers every file, the binary among them, so an install no longer writes a separate first-seen binary record: it records its first tree alone, and a recipe's own binarySha256 is still checked at install. An install with no tree record is refused with the line that installs it again, and an install folder holding any link that leads out of it, as the filesystem resolves it (a chain of links included), or that leads to nothing (the tree digest holds a link by its target's name, not the bytes behind it: the executable behind a linked folder, or code beside it) is refused at the install, before anything is put in place, and at every check; an old install that holds one is not taken as already installed, so installing it again says why. The check note keeps the recipe, the tree and the platform. A recipe's keyMethod is checked by the ACP package's AUTH_METHOD, the adapter's own definition. <!-- changes/recipe-install-tree.md -->

## 0.1.0-beta.53 (2026-11-22)

- A harness recipe now covers an outside agent's release as its vendor ships it (Google's agy CLI among them), and the owner's own sign-in, made by the agent itself: <!-- changes/recipes-outside-harness.md -->
  - `.zip` releases install, unpacked in Node with no `unzip` on the host. An entry that leaves the folder (`..`, an absolute path, a backslash), a symbolic link, a device, an encrypted entry or a duplicate refuses the whole archive before anything lands.
  - An archive is pinned by one digest, its `sha256` or, where the vendor's manifest lists that, its `sha512` (Google's agy CLI manifests). `release.registry` is optional, for a release that is the vendor's own rather than the ACP registry's.
  - Every file the archive unpacks to is pinned, not the binary alone: the tree's sha256 is recorded at the first install (or given as the release's `treeSha256`), and a check or a sign-in refuses a sidecar that changed since.
  - A release may give its own `args` per platform, over the recipe's.
  - `model.id` picks a plan-billed agent's model among those its `session/new` lists (`session/set_model`); one it does not list is refused before a prompt.
  - A key may be handed under the name the agent reads: `keys: [{ "name": "ANTIGRAVITY_GEMINI_API_KEY", "env": "GEMINI_API_KEY" }]`. It is read by its saved name, so the server's own `GEMINI_API_KEY` never reaches the agent. `keyMethod` is the method the agent's ACP `authenticate` signs in with on it (`gemini-api-key`).
  - One list in the kernel, `launchEnv` (`LAUNCH_ENV`, `LAUNCH_ENV_PREFIXES`), names the variables that change what a process loads or runs before its own code: `PATH`, `LD_*`, `DYLD_*`, `NODE_OPTIONS`, `NODE_PATH`, `PYTHON*`, `BASH_*`, `ENV`, `GIT_*` and a few shells' and interpreters' start-up variables. A key is never handed under one of them, nor a recipe's `env` or `model.env` named one. The recipe loader and the ACP adapter both refuse them.
  - A key's saved and handed names follow the kernel's `KEY_NAME` (capitals, digits and `_`, at most 64) in the recipe loader as in the ACP adapter, so `harness-check` no longer refuses a lowercase key name the loader took. Other variable names keep `ENV_NAME`.
  - `signIn: { "args": [...], "homeArg": FLAG }` names the agent's own sign-in, as T3 Code runs agy: `agentrun harness sign-in --recipe FILE` starts the installed, unmodified agent on your terminal with its arguments, `args` (`--login`) and `homeArg` naming its own folder (`--gemini-dir DIR`). The agent prints the address, reads the code you paste and keeps its sign-in in that folder; exit 0 is signed in (`HARNESS_SIGN_IN_FAILED` otherwise).
  - harness-check runs on the recipe's keys alone, never the sign-in, so a plan-billed recipe names a key beside any `signIn`. A run on the sign-in hands the agent `homeArg` and its folder, no key, nothing it prints kept.
  - AgentRun never reads, refreshes or sends the sign-in's token, and has no usage reader: it never opens the folder, and a test keeps every credential file and Google account or quota endpoint out of the harness sources.
  - The ACP adapter's `stderr: "none"` (`AcpRecipe`) keeps nothing an agent prints, for a run on a sign-in: a failure says its exit status and AgentRun's own code, and an error the agent answers says its JSON-RPC code alone.
- An ACP run (Cursor, Goose, or a harness recipe) no longer stalls after many turns. Before, the adapter copied the agent's whole session store into the run's records at every turn, so the records grew with the square of the turn count. After about 20 Cursor turns they no longer fit the 32 MiB channel to the run's process: an approval answered 204, and the run then waited for good. Now the mirror stores each file as 64 KiB pieces, each written once per session, so a store that grows by appending costs only its new bytes. It never copies SQLite's `-shm` file, and holds at most 8 MiB per session. Past that, the run's timeline says "The agent's session state passed 8 MiB, so a resume starts it fresh with the conversation so far." and the mirror stops. A run whose records no longer cross to its process now fails at once, naming the size and the limit, and the approval that woke it is answered that the run failed. Adapters get a `notice` event, which serve shows as a step on the run's timeline. A session store mirrored before this version is not restored: such a run resumes fresh with the conversation so far. <!-- changes/acp-state-mirror-bounded.md -->

## 0.1.0-beta.52 (2026-11-21)

- An ACP agent's failure words no longer keep a piece of a recipe key when the agent is still writing that key at the end of its stderr tail, or when two keys overlap: every place a key or its start appears is found in the text as written, then all of them are cut at once. <!-- changes/acp-key-cut-tail-end.md -->

## 0.1.0-beta.51 (2026-11-21)

- An ACP agent's own tool call (Cursor's shell) that parked on a person no longer loops once answered: the resume takes the answer before the agent starts, and the recovery note says what the person decided. Before, restarted Cursor asked for a different command, the answer was never taken, and the run restarted every few seconds until the plan's turn limit. An agent that keeps asking the person about other commands instead of the one they allowed ends its turn with `ACP_REASK_LIMIT`. <!-- changes/acp-parked-permission-settled.md -->
- An ACP agent (Cursor) that skipped a command the person allowed no longer has its turn cut after three more commands its tool setting allows: only commands that wait for the person count toward `REASK_LIMIT`. An allow-once is now used once: if a later agent process in the same turn asks for the same command again, the person is asked again instead of the old allow running it a second time. <!-- changes/acp-reask-parks-only.md -->

## 0.1.0-beta.48 (2026-11-20)

- A harness module builds its harness the way the built-in harnesses are built: `entries(builtins, kit)` now gets a kit with `kit.adapterEntry(facts, adapter)` and `kit.acpEntry({ facts, recipe, proxy })`, so the harness is offered its wire's vendor's models, named on that vendor's and OpenRouter's key rows, and gated and named by its own facts. [HARNESS.md](../../HARNESS.md) is the guide, and `examples/harness-module` is a whole module (Goose under an id of its own). <!-- changes/harness-modules-kit.md -->
  - The built-in harnesses read the same facts as before, with or without a module loaded.
  - An adapter harness that loads skills itself gives `kit.adapterEntry` a `skillCheck`: the run's skills it accepts are taken out of the prompt and handed to its adapter as `launch.skills`.
  - `kit.acpEntry`'s offer promises resume `"restart"` unless given `resume: "load"`, which its recipe must declare (`declares.load`); otherwise its first launch is refused (`HARNESS_RESUME_UNDECLARED`).
  - `missing(env)`, on either builder, says what no model key fixes (a binary, say). It is asked before the key, so the harness's offer says it and names no key. An error it or the adapter throws with a `code` refuses the harness with its facts' install fix for that code, as the built-in Goose's are.
  - `@parcha/agentrun-serve/conformance` adds `suiteHostTools`, and `@parcha/agentrun-harness-acp/testing` exports the fake ACP agent (`FAKE_ACP_AGENT`, `fakeAgentRecipe`), so a module's author runs the conformance suite with no binary, model or key. The run spec a subject hands `createAdapterLoop` names its harness's `facts`.
- An ACP agent's failure words cut the recipe's keys before they are shortened, so a cut that lands inside a key (the last 300 characters, or the start of the stderr tail the adapter keeps) leaves no piece of it. <!-- changes/acp-cut-keys-before-tail.md -->

## 0.1.0-beta.47 (2026-11-19)

**Breaking:**

- The package no longer records a binary's first-seen digest itself: `fileDigestRecord`, `verifyFirstSeen`, the `DigestRecord` type and `ACP_CODES.binaryDrift` (`ACP_BINARY_DRIFT`) are gone. A binary no pin names has its first digest recorded by AgentRun's installer alone (`agentrun harness install`), and a later binary that differs is refused there and at `harness-check` with `HARNESS_BINARY_MISMATCH`. Code that called `verifyFirstSeen` pins the binary's sha256 and calls `verifyPinnedBinary`, or installs it through `agentrun harness install --recipe`. <!-- changes/acp-one-first-seen-pin.md -->

**Changes:**

- New package `@parcha/agentrun-harness-acp` (private for now): any Agent Client Protocol agent as a harness adapter, from a recipe that says how to start it over stdio, what it declares (`session/load`, MCP over HTTP or stdio), where it keeps its sessions and who bills its model. Built on the official `@agentclientprotocol/sdk` 2.7.0.
  - The agent runs in a private HOME with an environment allowlist (PATH, LANG, TZ and the recipe's own variables), in a process group of its own. Its session store is mirrored into the session's records, credential files left out, so another runner's agent loads it back.
  - The host's tools reach it as one loopback MCP server, over HTTP when it is declared and advertised, else stdio. Each call runs once through the kernel's tool bridge, under the agent's own tool call id.
  - A permission request for one of the agent's own tools (a shell, an edit) goes through the host's gate (allow, deny or park), is journaled, and survives a runner swap. The adapter answers `allow_once` or `reject_once` and never an `always` option. It never trusts the status ACP reports for a tool.
  - initialize is checked against the recipe: a capability the recipe declares and the agent does not advertise refuses the session with `ACP_CAPABILITY_MISMATCH`.
  - A plan-billed agent (its vendor bills the owner's plan, so no request reaches the host) is bounded by the adapter itself: the run stops at the recipe's `maxTurns` (`ACP_TURN_LIMIT`) or `maxToolCalls` (`ACP_TOOL_CALL_LIMIT`).
  - A crash mid-turn resumes with `session/load` when the agent has it, else on a new agent session that is given the conversation so far. Either way the agent reads the kernel's recovery note, and a call it started is never run again.
- Goose 1.59.2 runs as an AgentRun harness on the ACP adapter: `gooseAdapter({ binary, model, provider, price })` checks the binary's sha256 against its pin, starts `goose acp` from the shipped recipe (`recipes/goose.json`, loaded by `recipeFile` and `gooseRecipe`), and points each Goose process at a model proxy of its own (`gooseProxy`) on the session's booking, so the run's cap and books hold as they do for Claude Code. <!-- changes/acp-goose-harness.md -->
  - The recipe turns every bundled Goose extension off, blocks Goose's model catalog download with a dead egress proxy, mirrors its sessions so another runner's Goose loads them, and leaves the model our MCP tools (`agentrun__<name>`) and Goose's `load_skill`.
  - Goose's proxy forwards only `POST /v1/messages`, with the API's version and the one `anthropic-beta` value the pinned Goose sends (`GOOSE_BETAS`), never Goose's `agent-session-id`. It answers `GET /v1/models` itself with the run's model, and refuses any other model, tool, hosted tool or beta before the provider is asked.
  - `GOOSE_PIN` records the release as the ACP registry listed it, with where and when it was read. `verifyPinnedBinary` refuses a binary whose sha256 differs (`ACP_BINARY_MISMATCH`), reading it and never running it. `gooseAdapter` checks it when the adapter is made and again before every Goose process starts (the adapter's new `beforeStart` option), so a binary replaced in between never runs unchecked. `verifyFirstSeen` records the first verified digest of an agent the registry lists without one, and refuses later drift (`ACP_BINARY_DRIFT`).
  - The adapter's `proxy` option is now called with the session's booking, its tools' names and a halt of its drive (`AcpProxySession`).
  - The kernel's model proxy can answer a local route with a fixed JSON body (`ProxyRoute.localJson`), only to the session's key or a side key.
- Goose is a harness in serve's table (`goose`), run by `gooseAdapter` on the host's Anthropic Messages provider, the same origin and key claude-agent's proxy takes, priced and capped by the same hooks. Its owner installs it with `agentrun harness install goose` (`agentrun-serve install-harness goose`), never a run: nothing on a run's path downloads anything. <!-- changes/goose-install-and-harness-row.md -->
  - The install downloads the pinned archive for this platform (`GOOSE_PIN`) with node's fetch, checks its sha256 before unpacking, unpacks it with the system `tar -xjf` (a fixed argument list, no shell) into a fresh folder beside `<data>/harnesses/goose`, checks the binary's sha256, then renames the folder into place and makes it read-only. A crash part way leaves the old folder or none, and the next install sweeps what it left. Every failure is named (`HARNESS_PLATFORM_UNSUPPORTED`, `HARNESS_DOWNLOAD_FAILED`, `HARNESS_ARCHIVE_MISMATCH`, `HARNESS_UNPACK_FAILED`, `HARNESS_BINARY_MISMATCH`, `HARNESS_INSTALL_BUSY`) with the command to try again. Run again with the pinned binary in place, it downloads nothing. No provider key reaches it.
  - Capabilities list Goose (label, its promises `resume: load`, `tool_gate: permission`, `billing: proxy`) only once the pinned binary is installed and verified, read at AgentRun's start: restart AgentRun after installing it. Before then an agent on goose saves with a warning, and its run is refused (`agent_not_runnable`), each naming `HARNESS_NOT_INSTALLED` and the install command.
  - `@parcha/agentrun-harness-acp` exports Goose's facts (`gooseFacts`), its install command (`GOOSE_INSTALL`) and its code (`GOOSE_NOT_INSTALLED`). The package is held from npm for now, so a serve installed from npm has no goose row until it ships.
- Cursor runs as a harness (`cursor`), over ACP, on its owner's own Cursor API key: install its pinned release with `agentrun harness install cursor` (or `agentrun-serve install-harness cursor`), set `CURSOR_API_KEY` where AgentRun starts, and restart. Each run is billed to your Cursor plan, under Cursor's terms, with no spend cap of AgentRun's: it stops after 20 turns or 100 tool calls (`AGENTRUN_CURSOR_MAX_TURNS`, `AGENTRUN_CURSOR_MAX_TOOL_CALLS`), and capabilities show its card (`harnesses[].card`). <!-- changes/cursor-harness.md -->
  - Cursor makes no file edits: every Write is denied in its CLI config until Cursor asks before an edit, as it asks before a shell command or a tool. Its own shell commands, and any other call of its own, are asked first, of a person who can approve them, and refused where no one can (they run on AgentRun's host, never on the run's computer, so bash's setting is not theirs); AgentRun's tools over MCP go through the agent's tool settings.
  - `CURSOR_API_KEY` is handed to Cursor's runs alone, read by name at each start. The credential Cursor derives from it (`auth.json`, which would hold its tokens and the key itself) is never written: its path is a folder Cursor cannot write a file at, and Cursor runs on the key in its environment, so a killed run or server leaves no credential on disk. Cursor's warning that it could not save one is left out of a failed run's words (a recipe's `quiet`). Its whole private HOME is deleted when its process ends.
  - A model is `cursor/<model-id>` (`cursor/gpt-5.4-nano`; `cursor/default` for Cursor's own default), checked against the models Cursor lists for the key (`ACP_MODEL_UNLISTED`). A key whose Cursor team administrator turned headless CLI use off is refused as `CURSOR_HEADLESS_DISABLED`.
  - The release is pinned by its archive's sha256, its launcher's, and a digest of every file it unpacks to; a drift in any of them refuses the run (`ACP_BINARY_MISMATCH`). The archive installer takes tar.gz as well as tar.bz2 (`ARCHIVE_FORMATS`), and so does a harness recipe's loader. A recipe may not take any id the server's harness table already has, `cursor` and `goose` included.
  - Cursor's release is pinned for linux-x86_64 alone. On any other host, a Mac included, Cursor is refused `ACP_BINARY_UNPINNED` before any install is looked at. `cursorRelease(platform)` gives the release pinned for a platform, or none.
  - A new Cursor pin needs a key walk on it first. The walk runs a turn, a hard kill mid-turn and the close on the real binary. At each point it counts the files of the session folder that hold the key or a JWT-shaped token, and it never prints them. CI refuses a pin that the walk's record does not name, so a release that starts saving its key somewhere else fails before it ships.
- Bring your own harness, door 1: a recipe. A JSON file names an ACP agent's registry release (the archive's URL and sha256, the binary inside it), its model billing (through AgentRun's model proxy, or the owner's plan with turn and tool-call limits), its literal env, files and session folders in the private HOME, and what it declares. `agentrun harness install --recipe FILE` installs the release, and `agentrun harness-check --recipe FILE --model PROVIDER/MODEL` runs it for real: the agent's own tools off, its environment an allowlist, the cap or plan limits, the pinned binary at every start, no side request (stage 2); a SIGKILL then resume, a denied call, one of AgentRun's tools over MCP, a second runner (stage 3). It writes a JSON report and prints the three facts a harness row carries: `resume`, `tool_gate`, `billing`. See [docs/harness-recipe.md](https://github.com/Parcha-ai/agentrun/blob/v0.1.0-beta.47/docs/harness-recipe.md) and [HARNESS-SCORECARD.md](https://github.com/Parcha-ai/agentrun/blob/main/HARNESS-SCORECARD.md), which rates 25 agents. <!-- changes/harness-recipe-door-one.md -->

  The loader refuses a recipe that breaks one of five rules by its code: a key that is not the harness's own (`RECIPE_KEY_NOT_OWN`), a binary not pinned to a registry archive (`RECIPE_BINARY_UNPINNED`), a file or folder outside the private HOME (`RECIPE_PATH_OUTSIDE`), an install step of its own (`RECIPE_INSTALLS_ITSELF`), an environment beyond the allowlist (`RECIPE_ENV_NOT_ALLOWLIST`). A release whose registry entry lists no binary digest is pinned to the first one its owner's install records; a later binary that differs is refused, at an install and a check alike (`HARNESS_BINARY_MISMATCH`). A recipe's keys reach the agent the way a run's do, read by name at its start: `harness-check` on a host without one is refused before the agent starts (`ACP_KEY_MISSING`). The ACP adapter logs each permission the agent asks for (`acp: the agent asked permission`).
