## 0.1.0-beta.33 (2026-11-10)

- A run parked at its spend cap no longer shows a "Model request failed: 400 {…agentrun_proxy…}" row in its Timeline. The model proxy refused that request before it was sent, and the park's row already says what happened. That refused request also no longer counts as a model request in the run's usage line.

  The cap's refusal now carries its code through to the proxy as a field: the runner's `Refusal.code`, then `HarnessRunError.refusal`. The proxy writes `code: "spend_cap_reached"` in its refusal body. The Timeline matches on that code and `type: "agentrun_proxy"`, never on the words. Every other model failure, a provider's 400 included, keeps its row.
- A tool call refused before it ran now reads as refused in the run's Timeline, never as a call that ran and failed. This covers a tool set to deny on the server or the agent, and a call a person denied. The row reads "Refused: write deny.md: Permission denied: write is set to deny on this server…" instead of "Wrote deny.md failed: …". Every tool reads that way, named by what it would have acted on: a path, a command, a page, or the tool's name alone.

  pi's adapter marks a refused call's result in its `details` with the new `CALL_REFUSED` key (from `@parcha/pi-durable-agent/timeline`). The model never reads that field, and the Timeline matches on it, never on the refusal's words. A call that ran and errored still reads "<label> failed: <error>".

## 0.1.0-beta.32 (2026-11-10)

- Everything the agents make is now on the disk, apart from the data directory's own files. Each agent has one folder, `<data>/disk/agents/<agent>/` (its id in lower case, a dash, and 16 hex digits of its SHA-256). That folder holds the agent's learning folder (`learning/`) and its runs (`runs/<run>/`, each with `store/run.sqlite` and `work/`). store.sqlite and the server's files stay at the top of the data directory, as the control plane, and only the server opens them. A run's row in store.sqlite now holds its claim: `claim_epoch` and `claim_holder`. Each launch of the run's process bumps the epoch, with that process as the holder, and hands the process its epoch. Once the process is gone, the server takes the run back: it bumps the epoch, names itself the holder, and checkpoints the run's database. A run's database (pi-durable-disk's exclusive profile) is WAL, under an exclusive lock, with `wal_autocheckpoint = 0` and synchronous FULL. The run's process ends with its WAL in place: its store's close keeps the connection open (`keepWal`), and the process ends by process.exit, which never checkpoints. A test pins this node:sqlite behaviour, and its inverse: a close does checkpoint. The server reads a run's database with a fresh read-only, lock-free open (`vfs=unix-none`, EXCLUSIVE) per read. It opens the WAL only once the WAL holds a commit that SQLite's recovery would take: a frame with the header's salts, a valid chained checksum and a nonzero commit size. Until then it reads the database file alone, as an immutable file. A lock-free reader of a WAL whose first transaction is still being written recovers no frame, and its close removes that WAL, which loses the writer's rows. agentrun-pi exports that check as `walHasCommit`, and both readers use it. It never shows a read whose last entry is behind one it read before. It never opens the database for writing while a process holds the run. A data directory an earlier version wrote (runs under `<data>/runs/`, or a store of store version 1) is refused at start, in words, and nothing is migrated. pi-durable-agent's store is now store version 2. It names a run's folder by its row's agent (`runDir`, `runStorePath`), and adds `claimRun` and `runClaim`. A store of version 1 is refused. serve gains the local disk adapter: `mount`, `sync`, `unmount` and `revoke` for one machine, where a runner works in the folder itself and a revoke is the server's take-back of the claim. agentrun-pi's durable readers take `unlocked` (a fresh `vfs=unix-none` read, as the server's), which serve's reads of a run's decisions use. A run's folder is never made through a symbolic link: a link on the way to it refuses the run's start, and refuses an import that finishes a run its last import left without a transcript (pi-durable-agent `runFolders`).
- A workflow run's graph, once the run has ended, and the server's reads at the run's end (`workflowCarry` and `readWorkflowRun` of its outcome) now read the run's database lock-free, as every other server read does. They make no -wal or -shm file beside it, never wait on a lock, and never remove a WAL that holds commits. `GET /runs/{run_id}/graph` drops its `stale` field. The view it marked (the last whole view, or the live view, shown while the run's store was busy) can no longer happen, since a lock-free read never meets a busy store. The console no longer reads the field. pi-durable-agent's `readWorkflowRun(run, { unlocked })` and `workflowCarry(run, outcome, { unlocked })` take the unlocked read. agentrun-pi exports `withDurableFile`.
- The pi family is 1.5.0 exactly (pi-durable, pi-ai, pi-coding-agent, chord), with one typebox (1.3.27); the older-pi CI legs are gone. A pi 1.5 run store is SQLite schema 2, which pi 1.3.0 or earlier cannot open again, so there is no rollback past this release. Tool results are under `output` only. A browser charge serve fails to count makes the run's spend unknown, and a capped run then refuses its next paid call until the spend is known again. The door's `GET /events` and a recording's live lines read through an adapter on pi 1.5's `observeCommits` (pi-durable-disk `./internals` `watchEvents`, with no compatibility promise) until they move to `conversation.watch`. A failed run store's close releases this process's live browser sessions again; a normal close keeps them for the next run. A claude-agent, codex or opencode run opens on pi 1.5, and an image it reads through pi's read tool is read. particle-1's cap hold keeps Particle's list price over pi-ai's promotional catalog price; a request is still booked at OpenRouter's billed total. The agent store reader reads pi-durable schema 2.
- A run's row in store.sqlite is now the whole lock on the run. Its `claim_epoch` changes only by compare-and-set. pi-durable-agent's `claimRun(runId, holder, from)` bumps the epoch only while the row still holds `from`; otherwise it is refused as `stale` and writes nothing. The new `setRunHolder(runId, epoch, holder)` names the holder under that epoch only. A holder is a name of at most 1,024 characters. serve's run process no longer writes `run.json` or `owner.lock`. It has no heartbeat and no lease watchdog. Its row names it instead: its pid, that process's start time, this boot and, once it serves, its door. The process prints the door on stdout, and the server writes it into the row. The process never opens store.sqlite. Its status (`sleeping`, `paused`, `done`, `failed`, with its detail) goes into its own run.sqlite, in pi-durable-disk's `RUN_STATUS_TABLE`. A take-back or a launch reads the row and kills any holder that still lives before it bumps the epoch. So no process of a lower epoch runs, or commits to the run's store, after the bump. A run whose holder is gone is taken over by its row. A stale run.json beside it, naming a live process, changes nothing. Before, that made the server adopt a process that was not the run's. pi-durable-disk's `openDurableRun` takes `epoch`, and `pi-durable-disk run` takes `--epoch N`. Both are for a run whose host holds its claim: no owner lock, no run.json, no heartbeat, no seal check. The run's record lives in its store, and the previous incarnation's record there is `previous`. The internals entry adds `RUN_STATUS_TABLE` and `processTable`.

  Upgrading: stop the server and let its runs' processes exit before you start this version. A run process an earlier version started is not adopted, because the run's row names no holder for it. Any run.json and owner.lock files left in run folders are ignored.
- **`fetch_page` is gone: grant `web_fetch` instead.** web_fetch's old name no longer saves, runs, maps to a permission or gets a Timeline label: a revision naming it is refused like any tool this server does not bind (`422 not_an_option` at its `tools[i]`), a workflow whose model or call node names it at `definition.workflow`, and the gate maps it to no settings key. Upgrading: an agent saved before this that still grants `fetch_page` is refused at its next run (`409 agent_not_runnable`, `details.unbound`) until it is saved again with `web_fetch`. `@parcha/pi-durable-agent` registers its fetch label and outcome for `web_fetch` alone.

## 0.1.0-beta.31 (2026-11-06)

- A browser charge now shows on the browser call's own row, not on a "Tool cost" row of its own. Before, every browser call added a row like "Tool cost: browserbase charged $0.0002 for browser", and the session's release added another, all for fractions of a cent that Usage already counts.
  - **The call's row carries it.** The browser call's `tool_use` row has `usage: {"usd": 0.0017, "requests": 0}`: every charge booked under that call, summed. Once one of them has no price, it reads `{"usd": null, "requests": 0, "so_far_usd": ..., "unpriced": ...}`. A browser charge makes no row of its own.
  - **A release lands on the last call.** The release's charge is booked under the session's last call, so it lands on that call's row. A charge that names no call (a session a reopened process released) goes to the last call charged for its session, else to its conversation's latest browser call.
  - **Live, it is an update.** A charge booked after the answer is served on `/v2` as a change of that row, with the same `id` and the new `usage`. The live reducer re-emits the row.
  - **Totals do not change.** The run's cost, its usage row ("... and 3 paid tool calls") and `/usage` count each charge once, as before. On a live run, `/usage` reads `browser_time` from these rows; for an ended run it reads the store, as before.
  - **Other tools' charges are unchanged.** monid's and Parallel's web_search keep their own "Tool cost" row.
  - **pi-durable-agent** exports `BROWSER_CHARGE` and `chargedTool(row)`. `chargedTool` names the tool whose charge a row carries. The text view shows a call's charge on its line ("Read the page "Example" · $0.0017").

A capture keeps only the origins it names, a restore returns only the origins asked for that were captured (a host-only cookie counts for its own host only, a domain cookie for the hosts under it too), a provider context comes back only to a restore that names every origin it was captured for (its own `origins`, when the browser host records them, are kept and given back as they came), a persistent cookie keeps its expiry, and a session cookie comes back for at most 24 hours (`maxSessionCookieAgeMs` may only lower it). A capture is dated by its state's `capturedAt` (a time still to come counts as now), and one older than the session already kept is ignored. With `runId`, a capture is refused while another live run holds the session's save lease.
  - `agent.vault` is on `SECRET_KINDS`: never exported, packed or seeded into a run. A pack's manifest names the saved sessions in `vault` and carries no value and no key file. `handedOut()` lists what restore returned, for a redactor.
- `@parcha/pi-durable-agent` is no longer held: its manifest drops `"private": true`, so a release publishes it to npm, at the workspace version, after `@parcha/pi-transport`. Its README's install lines pin the pi packages to 1.3.0 (pi 1.4 is not supported yet; a later release widens the range). Its quickstart runs in an empty directory after one `npm install` of the package and the pi packages it runs with: CI runs it that way from the packed package (`scripts/stranger/pi-durable-agent.json`), and also runs the README's install line as written, with the packed package in place of `@beta`.
- The session vault no longer keeps a provider context for more origins than its capture allows. A context's own `origins` that go beyond the capture's are refused (`AgentHomeError` `invalid`, naming the fault and no origin or context id) and nothing is written, since an opaque context cannot be cut down and would keep those origins' sign-ins. A restore gives a provider context back only to a request that names every origin it was captured for and every origin it records; any other gets `null`.
