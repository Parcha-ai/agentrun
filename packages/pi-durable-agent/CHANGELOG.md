# Changelog

## [Unreleased]

## 0.1.0-beta.29 (2026-11-03)

- **`openStore` and `openStoreReader` take `busyTimeoutMs`**
  - `openStore(dir, { busyTimeoutMs })` and `openStoreReader(dir, { busyTimeoutMs })` set how long a call waits synchronously for another connection to let go of the store before it throws SQLite's busy error. The default stays 5000; 0 throws at once, for a host that waits without blocking.
  - `createAgent` on a busy store throws SQLite's busy error. Before, it said the agent already exists.
- The agent store records a session another harness ran on this machine (Claude Code, Codex or pi) as a run that has already ended. `store.importRun({ agent, revision, state, startedAt, endedAt, costUsd?, summary?, source, session })` writes the run at the source's own times plus a `run_imports` row naming its source and session, in one transaction, and makes the run's directory and store directory 0700 whatever the umask, and `runs/` too when the import makes it. A time that does not exist (`2026-02-30`) is refused, never rolled to another date. The same source and session imports once. The reads carry `importedFrom`. An imported run is read-only: `reopenRun` and `carryBack` refuse it, and a trigger in `store.sqlite` refuses any change to its row, so a version that does not know imports cannot change one either. The table comes without a new store version.
- The agent store keeps a run's metrics: its tokens, model requests, models and tool calls, beside its row. `runMetricsOf(records)` from `@parcha/pi-durable-agent/timeline` makes them from the entries of all of a run's conversations, counting requests as the usage row does; an aborted response's partial usage, a cost written with no usage, a request cut before its answer and a response that reports no input at all (the zeros a transcript import writes) are counted in `unmetered`, never summed as 0 tokens. `carryBack(runId, { ..., metrics })` and `importRun({ ..., metrics })` write them, with what only the host knows (`activeMs`, `effort`, `model`, `costUsdEst`, `costBasis`), in the transaction that writes the run's row; a run opened again and ended again has them replaced. `store.runMetrics(runId)` reads them back. The new `run_metrics` and `run_tool_metrics` tables come without a new store version: an earlier version still opens the store and reads every run.
- An agent definition can name its place: `{mode: "runner"}`, which has no shell, or `{mode: "sandbox", box}` with `bwrap`, `docker`, `modal` or `daytona`, where the agent's file and shell tools run in the box while its loop, its log and every key stay on the server; any other shape is `422 input_invalid` on `definition.place`. The revision keeps the place it names, an explicit runner included, and a definition that names none keeps none, so existing revisions keep their ids and answers show no place for them. An edit that names no place keeps the agent's. `GET /v2/capabilities` lists `places` (the modes, the default `runner`, and each box with whether this server has it); no box is set up on any server yet, so a sandbox place saves with a warning and its runs are `409 agent_not_runnable` with `details.box`.
- A workflow run's timeline shows its decisions. Each decision its `judge`, `pick`, `sift`, `route`, `ask` and `verify` nodes recorded is a row of kind `decision` once the run has ended:
  - its summary names the node and the provider that answered, then each answer with the probability of what it said (`coi (jev): is_coi yes 0.92`), or for a route the branch it took (`route: review`, with `unsure` or `refused` when that is why);
  - its text lists the sources the provider cited (title, then URL) and the questions it refused;
  - its `usage` carries its own cost, and the run's usage row adds it in once: one unknown cost makes the total unknown, never a lower figure.
  `TimelineKind` gains `"decision"`.
- **A definition names its harness: pi, claude-agent or codex**
  - `definition.harness` is `pi` (the default, and what a definition that names none gets), `claude-agent` or `codex`; any other is `422 input_invalid` on the field. Every answer names it. An edit that names no harness keeps the agent's (as it keeps its skill files), and the page sends back the harness it read. The default is never stored, so a revision written before this field and one that names pi are the same revision.
  - `GET /v2/capabilities` lists `harnesses`: each with `available` and, when not, its `reason`. A definition naming a harness this server does not run yet saves with a warning on `definition.harness`, and its runs are `409 agent_not_runnable` with `details.harness`, never run on pi instead. This server runs pi today.
  - `GET /v2/openapi.json` marks every property this server adds to the contract's objects `x-agentrun-serve` with the addition that made it (`harness/1`, and `model/1` and `serve/1` for what it added before), and lists them in `info.x-agentrun-serve.fields`. Without them, the contract is as vendored.
  - The agent store (`@parcha/pi-durable-agent`) keeps an optional `harness` id in a revision's body, so in its id.
- An agent whose definition says `learning: true` starts every run from what it has learned, on pi, claude-agent and codex alike. Learning is off unless the agent says so, and the server's `--learning off` (or `AGENTRUN_SERVE_LEARNING=off`) turns it off for every run; capabilities report the switch as `features.learning`.
  - The agent's learning folder, `learning/` in its home (`DATA/homes/<key>/learning/`, the key as the home's), is in Claude Code's auto-memory format: `MEMORY.md`, one line per active note (`- [name](file.md) — description`), and one `<slug>.md` per note with `name`, `description`, `type` (`user`, `feedback`, `project`, `reference`) and optionally `status: superseded | retired` with `superseded_by`. It is plain git with `main` checked out, made by the agent's first run that learns with an empty `MEMORY.md`, and the server is its only writer, with hooks, fsmonitor, lazy fetches and system and global config off.
  - Each run pins `main`'s commit in `runs/<id>/learning.json`, kept through a resume or a follow-up. The first 200 lines of that commit's `MEMORY.md` go into the run's instructions under `# Learned`, and `MEMORY.md` and the active notes are copied into the run's `work/.learning/`.
  - A learning fault never blocks a run: a folder that cannot be made or read starts the run with nothing learned. The run's `learning` reads `{state: "seeded"}`, `{state: "dropped", reason: "seed_failed"}`, or `null` for a run that does not learn; run lists carry `{state, reason}`. A server that goes down while it copies the notes into a run has saved the run's input first, so the next one relaunches the run with its first message and nothing learned; a copy it finds there unsaved goes, and the run's learning reads `seed_failed`.
  - `@parcha/pi-durable-agent`: an agentic revision keeps `learning` when its input sets it, so a definition that leaves it out keeps its revision id.
- A monid key saved through the settings API puts monid's catalog in an agent's hands on every harness, with no restart, only in the runs that name a monid tool, and monid's charges in the run's cost and under its spend cap.

  - A tool key saved through `PUT /v2/settings/tool-keys/{id}` is read by name like a secret the launcher hands over, the launcher's value winning for a name it holds. Each run gets the saved keys at its launch, over the same pipe as the launcher's secrets (a workflow run's `PARALLEL_API_KEY` on its decision descriptor), and never in any process's environment; no run gets the seal key. A value that does not open is treated as not set: it never crashes the server, and nothing unsealed stands in for it. A `PUT` or `DELETE` needs no restart: capabilities, the harnesses' offers, a save's checks and a run's checks see the change at once. A run already running keeps what it was handed, and the next launch takes what is saved then. Capabilities give each tool's key as `tools[].key`, a `GET /settings/tool-keys` id (`browserbase` for `browser`). `BROWSERBASE_PROJECT_ID` joins the launcher's list of secrets, as every field a tool key holds does. `agentrun-serve import` reads the launcher's secrets by name and opens the saved keys in its data directory, and cuts both out of what it writes. Before this, the launcher's secrets were not cut, because the import read them from an environment they had already been moved out of.
  - A run's process gets a tool key's fields (`MONID_API_KEY`, `BROWSERBASE_API_KEY` and `BROWSERBASE_PROJECT_ID`) over its secrets pipe only when its revision names a tool the key unlocks, as `GET /v2/settings/tool-keys` lists them: an agentic revision's `tools`, or the tools a workflow's model and call nodes name. Until now every run's process held every tool key the server held, whatever its tools. The tools are read from the revision the run is pinned to, at every launch: a relaunch, and a run opened again after a server restart, get the same keys as its first launch. The model keys still reach every run, and the decision keys go as before. A `typesafe` key (`TYPESAFE_API_KEY`) is saved the same way and unlocks Jev's decisions (`decisions.jev`). Each key row has a kind: only a `tool` row's fields are scoped this way, and a key of any other kind reaches every run.
  - `monid.discover`, `monid.inspect` and `monid.run` run on claude-agent and codex too, as host tools in the run's process: the same calls and answers as on pi, on the key the run's process gets over its pipe, a long answer filed under the run's `work/evidence/monid/`. The harness calls and journals each under its wire name (`monid_discover`, `monid_inspect`, `monid_run`), as pi does, and the run's timeline shows it so. A `monid.run` call a crash cut off is answered interrupted, never sent again; `discover` and `inspect` may run again. Capabilities and the monid key's row list every harness for the three, and a claude-agent or codex revision naming one saves with no warning that it runs on pi only.
  - What a `monid.run` charged is the run's spend, on every harness. It is booked once in the run's own records as a tool cost (`agentrun.tool_cost`, `TOOL_COST` from `@parcha/pi-durable-agent/timeline`: `{tool: "monid.run", charged_by: "monid", usd}`), which the timeline adds to the run's cost and shows on a `phase` row of its own (`Tool cost: monid charged $0.0030 for monid.run`); the usage row counts it apart from the model requests. A run that may have charged and reports no cost books an unknown charge, never $0: the run's cost reads `null`, and under a cap every later request is refused. Each run is marked before it is sent (`agentrun.tool_started`, `TOOL_STARTED`), held at the price an earlier `monid.inspect` in the run quoted, else at a $1 allowance; its charge settles the mark, and a mark a crash left unsettled leaves the run's cost unknown, as a cut model request does, while the cap counts it at its held figure, never $0. `GET /v2/usage` grouped by meter shows the charges as their own meter, `tools` (capabilities' `usage.meters`). Under a `max_cost_usd`, each `monid.run` is held as a model request is: unless the run's spend plus what the run is held at (the quote, else the $1 allowance) fits the cap, or when the spend is unknown, the call is refused with a `spend_cap_reached` error the model reads, naming its price and the cap (and that an inspect gives a quote when the allowance was used), and monid is not called. Runs go one at a time under a cap; on claude-agent and codex the check also holds each model request still in flight at its worst case. `discover` and `inspect` cost nothing and are never refused.
- **A workflow run on AgentRun Server is drawn live, pauses and resumes, and a workflow is checked before it is saved**
  - `GET /v2/runs/{id}/graph`: the run's workflow and graph, each node's state (map items labelled from the run's input, with the branch each route took for them; a route's branch), the decisions with their receipts (state seen, images, evidence, cost basis, error), the calls with their input and output, and totals. While the run goes it reads a live view the run's process writes (`live.json`), so a poll never waits on the run's store or answers `home_busy`.
  - `POST /v2/runs/{id}/pause` and `/resume`: what is in flight finishes, and nothing new starts until the resume; a paused run stays paused across a restart. Run status gains `paused` (marked `pause/1`), `GET /runs?status=paused` lists them, and `GET /stats` counts a paused run as active.
  - `POST /v2/workflows/validate { workflow, tools? }` answers `{ ok, issues: [{ path, code, message }], warnings }` and writes nothing. A refused save's `422` lists every issue as a field (`definition.workflow/<path>`) with its `code`.
  - A workflow run's title is its agent's name and a few words of its input, never its JSON. A run's `llm` calls count in its cost.
  - pi-durable-agent: `workflowIssues(workflow, tools?)` lists every issue a save would refuse; `checkWorkflowBody`'s refusal carries them, each with its message.
  - dsl: the recovery driver's `pinJson()` gives its frame as it stands, for a host's live view.
- An escalated workflow run reads as waiting for a person, not as failed. Its `status` is `completed` (state `idle`), with `error` and `result.output` null, and a new nullable `review` on the run and on the runs list: `{kind, node, reason, at}`. `kind` is the escalation's kind as its escalate node names it, `node` is the label of the node it escalated at, `reason` is the escalation's summary, and `at` is when it ended. Every other run's `review` is null. The field is this server's own on the `/v2` document (`Run.review`, `RunSummary.review`, marked `x-agentrun-serve: review/1`). A run ended before this kept no review: it reads its row's summary as the reason, with kind and node null. A workflow run still takes no messages (501 `unsupported_here`). `readWorkflowRun` gains `escalation: {kind, label, summary}`.
- `web_search` and `web_fetch` work on pi, `claude-agent` and `codex` with only a model key. Each resolves in one order: the provider the user picked (the agent's own `definition.tool_settings` over the server's `PUT /v2/settings/tools`), then the native tool, then the kernel's keyless fallback. `web_search` is `auto` by default, native where there is one: Claude's own WebSearch (its adapter is opened with it, and no `web_search` host tool is offered), and on pi one request to the run's own model provider with its hosted search (Anthropic's `web_search_20250305` at 5 searches, OpenAI's Responses `web_search`), read from the provider's events and booked as one of the run's requests, its tokens plus $0.01 a search. On codex it is Codex's own search, each search booked at $0.01, except behind a gateway or under a spend cap, where it is keyless Exa; on claude-agent under a spend cap it is keyless Exa too, since Claude's own search has per-use fees a cap cannot reserve yet; a pi model behind a gateway or on another provider likewise searches Exa's public MCP endpoint with no key (`exa-keyless`, at most 8 results; a 429 at its free limit, or a 403 for a connection that is not direct IPv4, answers `{error}`, never retried). Every provider answers one shape, `{provider, query, results: [{url, title, snippet, published?}], text?}`, snippets cut at 3,000 characters, and the model's copy ends with a line asking it to cite the URLs it relies on; Parallel's search answers it too. `web_fetch` is the kernel's guarded fetch by default, and a page whose text it cuts at 60,000 characters says `truncated: true` with `original_chars` ; Parallel (search and extract) runs only where it is picked, and only then is its key handed to the run; a picked Parallel that gives no page leaves the direct fetch's page saying why (`parallel`), never a silent fallback. A pick of Parallel without `PARALLEL_API_KEY` resolves `unavailable`, and a run naming the tool is refused (`409`). Settings are `{web_search?: {provider: auto|native|exa-keyless|parallel|off}, web_fetch?: {provider: kernel|parallel}}` (`off` turns `web_search` off: nothing is searched, and a run naming it is refused, `409`), kept in the data directory (`tool-settings.json`, 0600); a `permission` is refused (`422 not_yet`) until the tool gate, and `capabilities.features.tool_permissions` is false. `GET /v2/capabilities` gives the two tools a `resolves` per harness, with the providers offered, the server's (`provider`) and the default (`default_provider`): capabilities is the one tool catalog (an unavailable tool says why, `reason`: a provider pick's own words such as `web_search is turned off in settings`, or `Needs` and the variables it is missing), and `GET /v2/agents/{id}` projects it onto the agent as `tools` (each granted tool in the same order; for one with a choice the provider in force, `provider_from`, `default_provider` and `resolved` on its harness and model). Under a run's cap pi's own search request is bounded at its context plus 125,000 input tokens and its most fee (Claude's and Codex's own searches do not run under a cap), its booked cost stops the next request, and a run whose booked spend passes its cap shows one timeline row saying by how much. In `@parcha/pi-durable-agent` a revision keeps `toolSettings`, and the timeline counts any request marked with a string `request` label as a side request, as it did a compaction's summary, and a `web_search` that answers `{error}`, or a `web_fetch` page followed by its line for the model that is `ok: false`, reads as a failed call, in its row and in the run's tool counts. With no key and no native search, web_search falls back to Exa's public keyless MCP endpoint, a third-party service with its own unpublished rate limits (a 429 past them) and terms (https://exa.ai/terms), reached over direct IPv4: set `web_search` to `native` (native only) server-wide or in an agent's `tool_settings` to turn it off, or pick `parallel` with `PARALLEL_API_KEY` to search with a key. `auto`, the default, is native where there is one, else keyless Exa. Upgrading: a server holding `PARALLEL_API_KEY` used to read every `web_fetch` page through Parallel's extract on its own; now it is the guarded direct fetch unless Parallel is picked, so set `PUT /v2/settings/tools {"web_fetch": {"provider": "parallel"}}` to keep that. A run keeps the tools its first launch resolved for its life, and a workflow's model and call nodes' tools resolve whether or not its revision lists them. `claudeAgentAdapter` takes `webSearchAllowance`: with its web search on, a search request is bounded at its body plus that many input tokens, instead of having no bound. `fetch_page` leaves the tool table: it is a legacy name for `web_fetch`, so a revision or call node naming it still saves and runs `web_fetch` under that name, resolved as `web_fetch` is.
- `GET /v2/stats` answers a dashboard's first page in one request: how many agents there are, the runs in all and how many are active, need input, failed or have a status this server cannot tell, each agent's run count, the total cost, and what is archived. It is this server's own route, outside the contract, marked `x-agentrun-serve: "stats/1"` in `/v2/openapi.json` with a closed schema. A running run is counted in exactly one of `active`, `needs_input` and `status_unknown`; one this server does not hold is `status_unknown`. The total cost sums only the runs that ended with a known cost and is null when none did, never $0. `unknown_runs` counts the rest. Archived agents and runs are left out of every number and counted on their own. Every number comes from SQL aggregates over `store.sqlite`, and no run's files are opened.
  The agent store gains `stats()`, which answers those counts and sums, and an index on `runs` (`runs_by_state`) added without a new store version. An earlier version still opens the file.
- `GET /v2/stats` answers `analytics`: the runs' tokens, requests, time and tool calls summed from the metrics the agent store keeps, over the runs not archived that the new optional `from`, `to` (RFC 3339 date-times) and `agent` query parameters pick (400 when one is malformed). It gives `totals` with coverage (`runs` beside `runs_with_metrics`, so a run with no metrics never reads as 0 tokens), `time`, `by_harness_effort`, `by_day` (UTC), `by_source` (`live` or the source an imported run came from) and the top 20 `tools`. Every other field of the answer is unchanged and stays the whole store's. The store reads it with `store.analytics({ from?, to?, agent? })`, SQL over `store.sqlite` alone in one snapshot; a store without the metrics tables answers with none. The served document marks the addition `stats/2`.
- A tool's key is saved by name through the settings API and kept only as ciphertext, opened only by the server on its host. `GET /v2/settings/tool-keys` lists the keys (`parallel`, `monid`, `browserbase`), what each unlocks and each field's `set` and `source`, never a value; `PUT /v2/settings/tool-keys/{id}` with `{values: {NAME: "..."}}` seals each value with AES-256-GCM, bound to its field's name, into `DIR/tool-keys.json` (0600), and `DELETE` forgets it. The seal key is `AGENTRUN_SEAL_KEY`, which the launcher takes from the environment or keeps in `agentrun/seal.key` under `$XDG_CONFIG_HOME` (or `~/.config`), made the first time, outside the data directory; a run's process never gets it. With none, nothing is saved (`409 no_sealing_key`) and `capabilities.features.tool_keys.at_rest` is `unavailable`. A field the server is started with is `409 key_set_by_server`. A stored value that does not open (no seal key, another one, a damaged file) never stops the server: GET marks it `stored_unreadable` and `reenter` says why, and the log says so once, naming the file. `MONID_API_KEY` joins the launcher's secrets. pi-durable-agent exports the vault's `seal` and `unseal`, unchanged, for a host's own secrets.
  In a container, pass `AGENTRUN_SEAL_KEY` or mount a directory at `XDG_CONFIG_HOME`: the container's own `~/.config` goes with it, and a new one's fresh seal key does not open the keys the volume holds.
- A cancel means cancel: once a run is cancelled, its process sends no model request, however the cancel and the process's start interleave. serve marks the cancel in the run's directory before it reaches for the run's process, and the run's process refuses, before it is sent or counted, any request it would make after that mark. A cancelled run sends no compaction summary either, and a request it refused is not counted as one: the timeline skips pi's error entry for it (`REQUEST_REFUSED`). A request is checked against the cancel twice: once before its start is marked, and again after, right before it leaves. A cancel that lands while the mark is being written still stops the request, and its start is then withdrawn (`REQUEST_ENDED` with `unsent: true`), so the run's cost counts only what was sent.
- A run's cost includes pi's compaction summaries. A summary is a paid model request that pi books only in its own usage document, never as an entry the run's timeline sums, so a run that compacted under-counted its cost and its requests, and /usage with it. serve now marks a summary's request like a generation's (`request: "compaction"`) and writes its cost (`REQUEST_COST`, `agentrun.request_cost`), which the timeline counts and sums; one aborted before its answer, or open when the run settles, makes the cost unknown. A run that compacts also completes again: serve counted the messages still to arrive from the number of user rows the run showed, and a woken run's compacted conversation shows fewer, which read as messages still waiting, so the run stayed working; they are now counted by id.
- **A run's cost reads unknown once a model request was cut, never $0**
  - The timeline's cost row counts a request cut before its end (a stopped turn, a killed process) as unknown, so the run's sum reads "unknown" from then on. Before, the cut request added its stream's reported usage: $0 on the OpenAI Responses API, which reports usage only at the end, and only the input and first output token on Anthropic's Messages API. Either way the provider charged more than the sum showed.
  - serve's run cost takes the timeline's usage row as it is. A run opened again by a follow-up whose rows say unknown no longer shows the cost the agent store kept from its earlier end.
  - A request cut before it streamed any content leaves no assistant entry in the store, so it is not counted at all; that is unchanged here.
- A workflow's decision requests (its judge, pick, sift, route, ask and verify nodes on Jev or Parallel) count in its run metrics, so `/v2/stats` and Mission Control no longer undercount a workflow's tokens. `runMetricsWithDecisions(records, decisions)` takes the run's decision receipts beside its entries (`runMetricsOf(records)` keeps its one parameter, so `.map(runMetricsOf)` is safe): each is a request, by `provider/model`, with its `usage` (`input_tokens`, `output_tokens`) in the token sums; a receipt with no usage, or a cancelled one, is counted in `unmetered`, never as 0 tokens. serve passes a workflow run's receipts at its end.
- A pi run whose model ends its turn with a stop that holds only an empty text block (and perhaps an empty thinking block), with no tool call, now completes. Before, the timeline showed no row for it, so the run read `working` and `idle` until it was cancelled and its timeline never turned final. The timeline now shows a `final_answer` row with empty text for that answer, and the run completes with `result.final_answer` `""`. A message with no text block at all, such as a request the Claude or Codex bridge writes without content, still shows no row.
- `runMetricsOf` never returns metrics the agent store refuses, whatever tool and model names a run's entries hold. A model can make up a tool name of any length, and as many as it likes: a run's end with those metrics was refused (`invalid`), and so was an import. A name longer than 256 characters is now cut to its first 255 and "…", so the same name is always the same key, and a lone surrogate reads as U+FFFD. A run keeps its 100 busiest tools and 100 busiest models; the rest are summed under `…other tools` and `…other models`, and a tool result with no name counts under `…unnamed tool` (it was `tool`). No entry's name is one of those three: a name that starts with "…" gets another. `METRIC_NAMES` from `@parcha/pi-durable-agent/timeline` holds the limits and the three names.
- A pi run's model request is counted when it leaves, not when its answer starts. serve marks each generation request on the run's root before sending it (`agentrun.request_started`), and again if its stream ends aborted (`agentrun.request_ended`, with the provider's `responseId` when it named one before the cut). The timeline (`REQUEST_STARTED`, `REQUEST_ENDED` from `@parcha/pi-durable-agent/timeline`) counts every marked request: one with no `pi.assistant` entry (cut before its first content, by a stop, a cancel or a crash), other than the latest still in flight while the run works, makes the run's cost unknown (once the run is settled, a last request with no entry was cut by the process that ended), with every request counted, never the sum of the others. A run's rows are as before otherwise: no usage row appears for a request still in flight, and one with no marks reads as it did. A request the cap refuses is never sent and never marked; pi's compaction is not marked. A model stream that throws while it is read ends the request as an error instead of leaving the turn waiting.
- A claude-agent or codex run that a stop or a crash cut off mid-tool, and that the next process resumed, completes once it answers. The cut call's "interrupted" row used to be made at the end of the timeline, after the answer, when the next process's turn ended, and the server reads a run's last row to know it answered: the run stayed Working until another restart. The row now sits right after its call, in the live timeline and in the stored one.
- **A completed run takes a follow-up, as the contract says**
  - `POST /runs/{id}/messages` to a completed agentic run is a `follow_up`: the run opens again on its own store and session, under its spend cap, answers, and completes again. It used to be `409 not_continuable`. It is the same run, before and after a server restart.
  - A follow-up sent while the run's end is still being written (its process closing, or its carry back waiting on a busy store) waits for it, up to a request's deadline, then continues the run; past the deadline it is `503 unavailable`, to try again.
  - Opening it takes a place under `--max-runs`: with none free the message is `429 rate_limited`, and the run stays completed.
  - A failed or cancelled run, an archived run and a run of an archived agent stay `409 not_continuable`: archiving closes a run.
  - The agent store has `reopenRun`, which opens a completed run again (running, no end); its cost and summary stay until the next `carryBack`.
- On codex and claude-agent, a request's cost is written with its answer even when it is booked after the harness has the answer: the harness's proxy answers before it books the response. A turn's end now waits up to 2 s for those costs. A cost that comes after the wait leaves the answer written with its cost pending (`REQUEST_COST_PENDING`): the run's cost reads unknown until it comes in, as a `REQUEST_COST_LATE` the timeline adds to the cost without counting another request. So the run's spend, its spend cap and `/usage` count it once, and one paid request is one request. If the process goes before it can, the next open writes it from the session's booking, and never writes the request twice. Through a gateway (`AGENT_MODEL_BASE_URL`), codex now sends the model id as the gateway was configured with it, provider-qualified or not, and no longer strips `openai/` from it. On pi, a run's spend cap now also counts its compaction summaries' cost, read back from its store when its process starts, which it did not count before: a run near its cap can be refused a request it used to be allowed.

- Prompt variants in the agent home: a new kind, `agent.prompts`, keyed by id, holds one `base`, one `generic`, any number of `overlay`s and at most one `question` (`{ role, label, text, when?, criteria? }`). An overlay's `when` is its selection rule, `{ question, option, threshold }`: the question's id, the option the variant needs and its least probability. The question's text is a Jev choice question, and its `criteria` describe options by name; every question also has the option `other`. `setPrompts(home, variants, { ifRevision?, access? })` replaces the set in one commit under the home's lock and refuses one that is not exactly one base and one generic, with unique ids that are one URL segment, labels of at most 200 characters, texts of at most 64 KiB, thresholds from 0 to 1, and rules that name the set's question and an option no other overlay needs (`AgentHomeError` `invalid`; `stale` for a moved `ifRevision`). An equal set writes nothing. `readAgentHome` returns `prompts`.
  - `choosePrompt(prompts, input, { judge, lookup?, signal? })` picks the variant a run starts with. The judge, a Jev runner or any function of its shape (the package imports no Jev), answers the question about the input; the overlay whose option meets its threshold is chosen, the highest probability winning. When none is, an optional lookup runs once and the judge answers again with what it found. Otherwise the generic. It returns `{ variant, instructions, passes, lookup, reason }`: the base's text and the variant's, each pass with its model, cost and latency, whether a lookup ran and what it read (never its text), and why. A judge or lookup failure gives the generic, never an error. An answer whose choice is not one of the offered options, that gives a probability for another option, or whose probability or confidence is not a number from 0 to 1 is a judge failure; the probabilities' sum is Jev's to check. An error's message is cut to 500 characters, so `reason` always fits the 2,000 characters `startRun` takes.
  - `startRun` and `prepareRun` take `prompt: { id, reason }`, the variant the host chose, and record it on the run's `agent.runs` entry; an id that is not one of the agent's variants is refused. Prompts are on `EXPORTABLE_KINDS` and travel in a pack; `importPack` with `replace` takes the pack's set, removing every variant the pack does not have (the whole set when it carries none). `readPack` refuses a pack whose prompts are a set `setPrompts` would refuse (the `format` check), so `importPack` never writes one; a pack with no prompts is still taken.
- A session vault in the agent home: `sessionVault(home, { hostKey, maxSessionCookieAgeMs?, runId?, access?, now? })` keeps a signed-in browser session for the agent's next run as ciphertext only, behind the `SessionVaultPort` a browser host calls (`capture` at release, `restore` at create, `forget`). A session is a local Chrome's cookies and localStorage, or a Browserbase or Kernel context id.
  - Each session is AES-256-GCM in a new secret kind, `agent.vault`, under its own item key, bound to its agent, session and kind; it also holds the session's origins and capture time, and a restore refuses a row whose clear origins or `capturedAt` differ from them, so a changed row can neither stretch the session-cookie cap nor cut a provider context down. The item keys are wrapped by the home's vault key and that by the host's key (`HostKey`, `{ id, wrap, unwrap }`; `localHostKey(id, bytes)` for a key held in the process), in `vault.keys` beside `agent.sqlite`, owner-only, outside the store so that a key can be destroyed. The first capture binds the vault to the host key; any other is refused with a new `AgentHomeError` code, `key`.
  - `forget` destroys a session's item key, so its earlier revisions can never be read; a capture destroys the key before it; `forgetAll` destroys every key. A capture keeps only the origins it names, a restore returns only the origins asked for that were captured (a host-only cookie counts for its own host only, a domain cookie for the hosts under it too), a provider context comes back only to a restore that names every origin it was captured for (its own `origins`, when the browser host records them, are kept and given back as they came), a persistent cookie keeps its expiry, and a session cookie comes back for at most 24 hours (`maxSessionCookieAgeMs` may only lower it). A capture is dated by its state's `capturedAt` (a time still to come counts as now), and one older than the session already kept is ignored. With `runId`, a capture is refused while another live run holds the session's save lease.
  - `agent.vault` is on `SECRET_KINDS`: never exported, packed or seeded into a run. A pack's manifest names the saved sessions in `vault` and carries no value and no key file. `handedOut()` lists what restore returned, for a redactor.
- `@parcha/pi-durable-agent` is no longer held: its manifest drops `"private": true`, so a release publishes it to npm, at the workspace version, after `@parcha/pi-transport`. Its README's install lines pin the pi packages to 1.3.0 (pi 1.4 is not supported yet; a later release widens the range). Its quickstart runs in an empty directory after one `npm install` of the package and the pi packages it runs with: CI runs it that way from the packed package (`scripts/stranger/pi-durable-agent.json`), and also runs the README's install line as written, with the packed package in place of `@beta`.
- The session vault no longer keeps a provider context for more origins than its capture allows. A context's own `origins` that go beyond the capture's are refused (`AgentHomeError` `invalid`, naming the fault and no origin or context id) and nothing is written, since an opaque context cannot be cut down and would keep those origins' sign-ins. A restore gives a provider context back only to a request that names every origin it was captured for and every origin it records; any other gets `null`.
